# 資安測試：滲透測試、動態弱點掃描、AI 輔助自我檢測與修補時限

> 第六十三輪，回應 Issue #142（上線前與定期滲透測試、CI 動態弱點掃描及修補時限，含 AI 輔助自我檢測評估）。
> 給誰看：資訊室、OASIS（AI推動辦公室）、要和資安廠商談範圍的同事。
> 狀態：**示意稿**。時限與頻率須由資訊室依本署資通安全責任等級與現行規範確認；本文件不取代正式的資安管理文件。
> 相關：[deploy.md](deploy.md) §9（權限與安全）、§10（安全標頭）、§10.4（security.txt）、§32（DAST 操作）、[a11y.md](a11y.md)、[ci-cd-overview.md](ci-cd-overview.md)、[careers-privacy.md](careers-privacy.md)、[attack-surface.md](attack-surface.md)（對外暴露面清單，另一分支撰寫中）。

## 1. 威脅背景

近期 ARTEX 類事件顯示，攻擊者已能用 AI 代理人自動化滲透測試：自動偵察、串接已知弱點、依回應調整手法，速度與規模遠超人工。防守方不需要恐慌，但需要**同等程度的自動化**：把能機器判定的檢查放進 CI、排程重跑，並讓人力集中在機器看不出來的邏輯與設定問題。這份文件整理本站現在已有的自動檢查、上線前該做的人工滲透測試、CI 裡新增的動態掃描，以及發現弱點之後誰在多久內要處理。

## 2. 原型已有的自動檢查

| 檢查 | 擋什麼 | 在哪裡看 |
| --- | --- | --- |
| 個資掃描（`npm run pii`） | 身分證、居留證、手機、個人信箱、名單姓名進入 Git | [careers-privacy.md](careers-privacy.md)；ci-cd-overview 關卡表 |
| schema／治理閘門（`npm run check`） | 內容欄位、跨檔參照、治理規則 | ci-cd-overview 關卡表 |
| CSP hash | 內嵌指令碼只允許建置時算出的 hash，注入的指令碼不執行 | [deploy.md](deploy.md) §10.1 |
| JS 預算 | 單頁 JS 上限，避免意外引入大量第三方碼 | ci-cd-overview 關卡表（效能預算） |
| 連結檢查 | 壞連結、被移走的附件、指向非預期網域的連結 | ci-cd-overview 關卡表 |
| axe 無障礙 | WCAG 2.2 AA | [a11y.md](a11y.md) |
| 第三方 action 釘 SHA | 供應鏈：action 被換成惡意版本 | [deploy.md](deploy.md) §9；`tests/round23-security.test.mjs` |
| 分支規則集 | 誰能直接推 main、合併要幾個核准 | [deploy.md](deploy.md) §9 |

這些檢查都是「我們知道要防什麼」的防線；它們**不能取代**由外部人員用攻擊者的角度找出我們沒想到的問題，這就是下一節。

## 3. 上線前與定期滲透測試

**範圍（請資訊室與廠商書面確認資產清單）**

- 靜態站與 CDN／主機設定（標頭、TLS、快取、重新導向、舊網址 301）。
- 表單與個資接收系統（電子報、職缺、陳情等；契約見 [deploy.md](deploy.md) §11、§13）。
- 寫入閘道與後台（驗證、角色、稽核紀錄、送審流程）。
- Git 平台與 CI runner（GitHub Enterprise Server 或 GitLab；分支保護、服務帳號、runner 隔離、密鑰存放）。
- 雲端設定（Azure 等；身分、網路、儲存體存取）。

哪些項目實際在範圍內，取決於尚未決定的事項 #129、#130、#132 的結論；本文件不替它們決定，結論出來後回頭更新範圍清單。

**頻率**

- **上線前**：由具資格的第三方執行一次。
- **上線後**：依本署等級之附表頻率（常見為弱點掃描每年兩次、滲透測試每年一次），請資訊室核對現行附表。
- **重大改版後**：架構或驗證方式變更、新增個資處理功能、換 Git 平台或主機時，另行加測。

**交付物**：滲透測試報告（含重現步驟與嚴重度）、修補後的複測結果；缺陷進入第 6 節的流程。

**負責**：資訊室主辦與簽約。OASIS 提供架構文件與對外暴露面清單（[attack-surface.md](attack-surface.md)），並在修補 PR 上審查。

## 4. CI 動態弱點掃描（DAST）

**做什麼**：`.github/workflows/dast.yml`（「DAST (OWASP ZAP baseline, weekly)」）建置整站（`BASE_PATH=''`，讓本機伺服器在根路徑提供）、啟動 `scripts/serve.mjs`（關閉寫入閘道）、以 OWASP ZAP 的 baseline 模式對 `http://localhost:4173/` 做被動掃描，並把報告放進 job summary 與名為 `dast-report` 的 artifact（`report.html`、`report.json`、`report.md`，保留 30 天）。

**怎麼手動跑**：GitHub → Actions → DAST (OWASP ZAP baseline, weekly) → Run workflow，可改爬站分鐘數（預設 5）。排程是每週一 03:00（台灣時間）。

**怎麼讀報告**

- ZAP 對每條規則給 `PASS`、`WARN-NEW`／`WARN-INPROGRESS`、`FAIL-NEW`。baseline 模式只做被動檢查（不送攻擊負載），所以結果多半是標頭、Cookie、資訊洩漏類。
- **預期會看到的 WARN**：GitHub Pages 無法自訂回應標頭，所以 CSP、HSTS、`X-Content-Type-Options` 等相關規則會出現警告。這些標頭在 `dist/headers/` 裡備好，供正式主機使用（[deploy.md](deploy.md) §10.3）；掃描對象是本機伺服器，同樣不一定帶這些標頭，須對照 `dist/headers/` 判讀。
- 掃描對象是**靜態站加模擬後端**。關於模擬後端的發現，要拿真實接收系統的契約（[deploy.md](deploy.md) §11、§13）對照，判斷是否適用於正式環境。

**為什麼是每週加手動，而不是每個 PR**：需要 docker、要爬站、耗時；原型階段的規則還沒有調校，每個 PR 都跑只會製造雜訊。先看一段時間的基準線，再決定要不要放進 PR 階段。

**發現怎麼處理（分流表）**

| 結果 | 做法 |
| --- | --- |
| 真實問題 | 依第 6 節開 `security` issue、修補、重掃確認 |
| 接受風險 | 寫下理由、責任人、複查日期，記在 issue 並關閉 |
| 不適用（模擬後端、GitHub Pages 限制） | 註明對應的契約或文件章節，必要時在 ZAP 規則檔裡標記忽略 |

**未涵蓋**：需要登入的寫入閘道與後台（掃描器沒有帳號）、Azure 等雲端設定、內網與 CI runner。這些由第 3 節的人工滲透測試負責。

**本輪的限制（誠實說明）**：開發沙盒沒有 docker 也沒有對外網路，這個工作流程**在本輪沒有實際跑過 ZAP**；第一次真正的執行是在 GitHub 上的排程或手動執行。第一次跑完請有人讀報告、把預期的 WARN 整理成基準線。

## 5. AI 輔助滲透測試評估

**可接受的條件（全部要有）**

1. 書面授權，明列被測資產。
2. 隔離的測試環境（staging 複本，使用模擬個資，不連正式資料與正式密鑰）。
3. 與廠商的合約，包含資料處理（送給模型的內容、保存期限、是否用於訓練）與完整紀錄。
4. 明確的時間窗與緊急停止（kill switch）。
5. 發現進入同一套分流與修補流程（第 6 節）。

**絕對不可以**：對正式環境執行、對未經授權的資產執行、使用真實個資。

**一個觀察**：本站的原始碼是公開的，攻擊者（包含 AI 代理人）本來就能讀。所以安全不能建立在「程式碼沒人看過」上：密鑰只放環境變數、不進 Git；個資不進 Git（[careers-privacy.md](careers-privacy.md)，`npm run pii` 把關）。這也讓 AI 輔助測試的風險較可控：它能看到的，和攻擊者本來能看到的差不多。

**建議**：允許作為人工滲透測試**之後的追加一輪**，不是取代。AI 擅長廣度與重複；業務邏輯、權限設計、組織流程的問題仍需要人。

## 6. 弱點修補時限

**示意，待資訊室依本署規範確認。** 時限從「確認弱點成立」起算。

| 嚴重度 | 判定 | 緩解 | 修補 |
| --- | --- | --- | --- |
| 嚴重 | 已被利用，或造成個資外洩 | 48 小時內 | 7 日內 |
| 高 | 可被遠端利用、影響完整性或機密性 | 7 日內 | 7 日內 |
| 中 | 需特定條件才能利用 | — | 30 日內 |
| 低 | 影響有限、縱深防禦類 | — | 90 日內 |

**與通報管道的串接**：研究者依 [deploy.md](deploy.md) §10.4 的 `security.txt` 通報 → 資訊室分流、定嚴重度 → 在 GitHub／GitLab 開標籤為 `security` 的 issue（**真實弱點用私有追蹤，不在公開 issue 寫攻擊細節**）→ 修補 PR 走標準車道（OASIS 審）→ 複測 → 關閉並回覆通報者。公眾版的通報說明在 `/policy/security/`。

## 7. 教訓

防守方需要和攻擊方同等的自動化，但自動化只有在「每個發現都有負責人與期限」時才有價值。沒有人讀的掃描報告只會帶來虛假的安全感。所以：先用不擋合併的方式跑，建立基準線、清掉雜訊；等基準線乾淨了，再把其中穩定的規則升級成閘門。
