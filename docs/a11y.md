# 無障礙基準與自我評量

> 第二十四輪新增。給資訊室、前台維護同事與稽核人員：本站以什麼標準為目標、WCAG 2.2 比 2.1 多了什麼、現在做到哪、CI 怎麼把關。
> 原則：**機器能判定的由 CI 擋，機器判不了的明說「待人工稽核」**，不假裝全部合格。

## 1. 目標標準

- 數位發展部「網站無障礙規範」2026-05-29 修正、**2026-11-30 施行**，新增 WCAG 2.2 的成功準則。本站目標：**新版網站無障礙規範 AA 等級（對應 WCAG 2.2 AA）**。
- 依據：[WCAG 2.2](https://www.w3.org/TR/WCAG22/)；規範法源：[全國法規資料庫（K0060095）](https://law.moj.gov.tw/LawClass/LawAll.aspx?pcode=K0060095)。
- 為什麼不停在 2.1：2.2 的新增項目多半是行動裝置與認知、動作障礙者的實際痛點（點不到、被遮住、重複輸入），而且 2026-11-30 後是法定基準；現在補的成本最低。決策記錄見 [architecture-decisions.md](architecture-decisions.md) 第 16 節。

## 3. 自我評量（第二十四輪時點）

「符合」＝已由自動檢測或程式碼結構確認；「待人工稽核」＝需要人用鍵盤、螢幕閱讀器或真機確認，目前**沒有**證據；「不適用」＝站上沒有該功能。

| 準則 | 現況 | 依據／說明 |
| --- | --- | --- |
| 2.4.11 焦點不被遮蔽（最低） | 待人工稽核 | 手機有固定底部 tab 列（`.c-tabbar`）；未做逐頁鍵盤走查，尚無 `scroll-padding` 保證。axe 判不出 |
| 2.5.7 拖曳動作 | 符合（不適用為主） | 站上沒有必須拖曳的功能；後台附件區的拖放上傳另有「選擇檔案」按鈕替代 |
| 2.5.8 目標尺寸（最低） | 部分符合 | 輪播圓點、/data/ 端點連結已補到 24px（本輪）；其餘按鈕多為 36–44px。內文中夾雜的行內連結屬規範例外；自訂 HTML 內容仍須人工檢查 |
| 3.2.6 一致的求助 | 符合（程式碼）／待人工確認 | 頂端工具列（無障礙、網站導覽、防疫專線 1922）與頁尾聯絡區在每頁同一版面元件輸出，位置一致 |
| 3.3.7 避免重複輸入 | 待人工稽核 | 站上表單多為單頁（智慧查詢、聯絡信箱預覽）；人才招募模擬報名跨步驟，需確認 |
| 3.3.8 無障礙的驗證 | 不適用（原型） | 原型後台為示範登入（模擬帳號）；正式環境走機關 SSO＋MFA，設計見 [admin-auth.md](admin-auth.md)，上線前須依本準則複查 |
| WCAG 2.1 既有 AA 項目（對比、鍵盤、標題、地標、語言、1.4.10 重排等） | 自動檢測可判定的部分符合 | 見第 5 節；螢幕閱讀器朗讀品質、圖片 alt 的內容是否「有意義」仍待人工稽核 |

**axe 的限制：** 自動工具大約只能抓到三成到五成的問題。通過 `npm run a11y` ≠ 符合規範；它是「不退步」的底線，不是稽核報告。

### 4.1 第四十輪（#83）修掉的殘留項

線上 axe（25 路徑 × 桌機／手機）剩下兩類 moderate：`/ask/?q=登革熱` 的 heading-order、`/admin/` 與 `/admin/publish/` 的 region。這一輪的處理：

| 發現 | 位置 | 修法與理由 |
| --- | --- | --- |
| heading-order：`/ask/?q=登革熱` | `src/client/answer/render.js` 的 `situationCards()`（疫情卡） | 實際跳級的是**疫情卡的標題 `<h3>`**：它由 JS 在答案區塊**之前**產生，前面只有 sr-only 的 `<h1>`，所以是 h1→h3。改成 `<h2>`（卡片本身是帶 `aria-label` 的獨立區塊，與下方「回答」同層）；`answer.css` 的 `.c-answer-sit h3` 規則同步改 h2，並補上標題內連結的樣式（原本靠 `.c-sit-card h3 a`）。來源清單（h3）、「接下來可以」（h3）、「你可能也想知道」（h3）都接在答案 h2 之後，本來就合法。**限制**：這些 h3 如果在沒有 h2 的答案（例如只有 actions 沒有句子的情況）出現仍會跳級；目前沒有這種答案，若新增要同步處理。 |
| region：`/admin/`、`/admin/publish/`、`/admin/review/` | `src/templates/admin/_layout.mjs` 的 `.adm-demo` | 原本是地標之外的 `<div role="note">`（`role="note"` 不是地標）。改成 `<aside class="adm-demo" aria-label="示範說明">`，成為 complementary 地標；位置與外觀不變（仍在導覽列與 `<main>` 之間）。沒有放進 `<header>`，是因為它在 DOM 順序上位於 `<nav>` 之後，放進 header 會改變閱讀順序。`<nav class="adm-nav">`、`<footer class="adm-foot">`、`<main>` 本來就是原生地標元素。 |
| target-size（serious）：`/ask/?q=登革熱` 的來源卡 | `answer.css` `.c-source-card__body .c-deflist dd a` | 新增掃描 `/ask/?q=` 之後才露出來的：來源卡 `<dd>` 裡獨立成行的連結高約 20px、與下一行只隔 6px，不符 WCAG 2.5.8 的 24px。加 `display:inline-block; min-height:24px; line-height:24px`。**以前沒被發現是因為掃描清單裡沒有載入答案後的 `/ask/` 畫面**（空的 `/ask/` 沒有來源卡）。 |

前後數字（本機 `BASE_PATH='' PAGEFIND=off` 建置、`npm run a11y`，掃 22 頁 × 2 視窗；全文搜尋「有結果」那一頁需要 Pagefind 索引，沒有索引時列為略過）：region 6 筆（3 頁 × 2 視窗）→ 0；serious（target-size）1 筆 → 0；heading-order 本機 axe 沒有重現（線上有），但標題結構傾印 h1→h3 → h1→h2，依 axe 的規則這就是會被標的位置。

## 5. 怎麼跑自動檢測

```bash
BASE_PATH='' node scripts/build.mjs     # 先建置（腳本本身不建置；沒有 dist/ 會直接報錯）
npm run a11y                            # 對 dist/ 跑 axe-core
```

- 範圍：（第四十輪起含 `/ask/?q=登革熱`，載入答案後才掃，`#answer[aria-busy=false]`）首頁、疾病頁、疾病列表、疫苗、旅遊、新聞、Q&A、智慧查詢、疫情、資料、專業版、後台首頁、後台上架、/en/、/vi/、核心教材文件頁（第二十八輪，長文件版面＋學習目標）（dist 內沒有的會略過並列出）；每頁在桌機 1280px 與手機 320px 各掃一次。
- 規則集：`wcag2a, wcag2aa, wcag21aa, wcag22aa, best-practice`。
- 結果：**serious／critical → exit 1**（擋合併）；moderate／minor 只列警告，**但會輸出數量與規則別次數**（報告開頭、終端機最後一行 `[a11y] 阻擋 N、警告 M：region×…`，以及 `A11Y_JSON=檔名` 的機器可讀摘要）；CI 的 PR 留言「無障礙檢測」列會顯示「另有 N 項 moderate／minor 警告，不擋合併」，不會因為不擋就悄悄累積；手機 320px 出現橫向捲動也算失敗（1.4.10）。另輸出 Markdown 摘要（`A11Y_REPORT=檔名` 可另存；在 GitHub Actions 自動寫進 job summary）。
- 瀏覽器：`CHROME_BIN` 環境變數優先；其次 `PLAYWRIGHT_BROWSERS_PATH`（預設 `/opt/pw-browsers`）內的 chromium；都沒有就用 Playwright 內建（`npx playwright install chromium`）。
- 用其他目錄：`DIST_DIR=/tmp/x npm run a11y`。建置時若有 `BASE_PATH`，執行檢測時要設同樣的 `BASE_PATH`。
- CI：`.github/workflows/content-pr.yml` 以 `BASE_PATH=''` 另建一份到暫存目錄後執行；結果列在 PR 留言表格「無障礙檢測（axe）」，並列入「能不能合併」的條件。

## 6. 手機語言選單（#33）

- 桌機（>720px）維持頂端橫排語言列（`nav.langs.langs--inline`）。
- 手機（≤720px）橫排改成單一按鈕 `<details class="langmenu"><summary>🌐 語言／Language</summary>…`，展開後七種語言各用自己的語言標示（`lang`／`hreflang` 屬性齊全），不需 JS；≤959px 的「選單」面板底部也有同一組語言。
- 為什麼用 `<details>`：原生支援鍵盤與螢幕閱讀器（朗讀「已展開／已收合」），不必另寫 JS 與 `aria-expanded`。
- **暫不做、列為建議**：依瀏覽器 `Accept-Language` 自動提示切換語言。理由：原型不是每頁都有七語（只有 reviewed 的才有），自動提示可能把人導到沒有該頁的語言；要做應先確認各語言涵蓋率與是否記住使用者選擇（需 cookie 告知），所以延後。

## 8. 主選單子選單（第四十七輪）

三個有面板的主選單項目（傳染病、疫苗、出國與入境）旁有 `<details class="c-nav__dd" data-nav-dd><summary class="c-nav__more">`，展開 `.c-nav__panel`。設計理由見 [navigation.md](navigation.md) 第 5 節；注意現行 cdc.gov.tw 選單結構是推斷，非直接確認。

**無障礙名稱從哪來：** summary 的可見內容只有 chevron 圖示（`aria-hidden="true"`），名稱來自裡面的 `.sr-only` 文字「展開「疫苗」的子選單」（i18n `nav.more`，七語）。**不在 summary 上用 `aria-label`**，因為各讀屏軟體對 summary 的 `aria-label` 支援不一致，用可見文字節點最穩。summary 也不加 `role` 或 `aria-expanded`：`<details>` 原生就暴露「已展開／已收合」。面板是 `role="group"` 加 `aria-label`（`nav.panel.label`），內部小標用 `<p>`，不用標題，避免頁首出現會讓標題階層跳級的標題。

| WCAG | 對應 | 做法 |
| --- | --- | --- |
| 1.4.13 hover 或焦點出現的內容 | 不適用，但說明 | 面板由點擊開啟，不由 hover 或焦點觸發，所以「可關閉、可停留、不消失」三條件不適用；CSS 禁止任何 `:hover` 開面板的規則（測試掃 base.css）。這也是不用 hover 的理由之一：hover 式 mega menu 最常在這條失分 |
| 2.1.1 鍵盤 | 通過 | summary 原生可 Tab 聚焦、Enter／Space 開合；面板內都是一般連結，Tab 依序可達 |
| 2.1.2 沒有鍵盤陷阱 | 通過 | 面板不是 modal，不鎖焦點；Tab 離開面板，`focusout` 就收合（只在焦點確定移到面板外時才關，點面板內純文字由點外面的判斷處理，不會誤收）；Esc 關閉並把焦點回到 summary |
| 2.4.3 焦點順序 | 通過 | 面板的 DOM 緊接在對應的主選單連結與 summary 之後，Tab 順序＝視覺順序；桌機面板絕對定位但 DOM 順序不變；手機手風琴本來就在文件流中 |
| 4.1.2 名稱、角色、值 | 通過 | 角色與展開狀態來自 `<details>/<summary>` 原生語意，名稱來自 `.sr-only` 文字，不自訂 ARIA，避免與原生語意衝突 |
| 2.5.8 目標尺寸（最小） | 通過 | summary 桌機 36×44、手機 48×48（絕對定位在該列右側，連結右側留 56px padding 不被蓋住）；面板連結桌機 min-height 40px、手機 44px |

驗證：`tests/round47-nav-panels.test.mjs` 檢查 summary 結構（`.sr-only`、無 `aria-label`／`aria-expanded`／`role`）、面板內無標題、ui.js 含 Esc 與 `focusout` 處理，並用 Playwright 在 1280px 與 390px 實測開合、Esc 焦點、點外面關閉、面板不被裁切，以及在 1280px 開傳染病面板後用 axe 掃描整個首頁無 serious／critical。尚未用 NVDA／VoiceOver 實測，列入第 7 節的人工走查。

## 9. 人工走查腳本與標章申請準備（第四十八輪，Issue #104）

給資訊室與承辦同仁。第 7 節列的「尚未處理」有三項只有人能做：螢幕閱讀器實測（NVDA＋Chrome、VoiceOver＋iOS Safari）、2.4.11 焦點不被遮蔽、3.3.7 重複輸入。這一節是可以照著做的腳本、要填的表，以及申請無障礙標章要準備的證據。**為什麼要人工做：** axe 這類工具只能檢查標記「有沒有」，不能判斷「讀起來順不順」。同一段正確的 HTML，螢幕閱讀器可能朗讀成毫無意義的一串；標章的檢測單位與評審也只認人工檢測紀錄，不認 CI 綠燈。

### 9.2 走查腳本

**環境（兩組都要，結果分開記）：** Windows＋NVDA（最新穩定版）＋Chrome；iPhone＋VoiceOver＋Safari。網站用正式預覽網址，不用本機。每頁先用滑鼠不碰、全程只用鍵盤（桌機）或滑動手勢（手機）。NVDA 開「語音檢視器」（NVDA 選單 → 工具 → 語音檢視器），可以把朗讀內容直接複製進結果表。

- D. 沒有任何焦點被固定在頁面上的元素蓋住（2.4.11）。

### 9.4 申請無障礙標章要準備什麼

標章的受理單位、費用與時程以主管機關當期公告為準，申請前先向數發部（或其委託的檢測機構）確認；以下是我們這邊該備齊的證據，不是申請表本身。

1. **範圍清單：** 申請標章的網址範圍（首頁、各列表與詳細頁範本、表單、後台是否納入）。原型是範本產生的，可以用「範本 × 代表頁」說明，不必逐頁。
2. **自動檢測紀錄：** 每次發版的 `npm run a11y` 輸出（`A11Y_REPORT=檔名` 可存 Markdown、`A11Y_JSON=檔名` 存摘要）；本節 9.1 是範例。
3. **人工檢測紀錄：** 9.2 填好的結果表、錄音或截圖、測試者姓名與輔具版本、日期。至少兩組輔具（NVDA＋Chrome、VoiceOver＋iOS Safari），並保留不通過項目的修前修後紀錄。
4. **2.2 新增準則逐項聲明：** 2.4.11、2.4.13、2.5.7、2.5.8、3.2.6、3.3.7、3.3.8 各一行，寫通過／不適用並附理由（可直接引用第 2、3、8 節）。
5. **無障礙聲明頁：** 網站上要有聲明（符合等級、已知限制、回報管道與回覆時限）；已知限制要寫實話，例如七語翻譯是否都有 `lang`。
6. **回報與修正流程：** 使用者回報無障礙問題的窗口、回覆期限、誰負責修（可引用 `docs/guide-public.md` 的無障礙段落）。
7. **維持機制：** CI 的 axe 閘門（嚴重／阻擋即不得合併）、每次改版型要重做的人工項目（選單、表單、`/ask/`）。
8. **第三方內容清單：** 嵌入的影片、地圖、外部表單；各自的無障礙聲明或替代管道。

**誰做什麼：** 資訊室準備 1、2、5、7；承辦同仁依 9.2 執行並填表（3、4）；法規或主管確認 5、6 的文字。建議順序：先做 9.2 的 NVDA 與 VoiceOver 各一輪，修完再做第二輪，再申請。
