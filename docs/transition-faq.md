## 0. 先看這張表

| 問題 | 一句話結論 |
| --- | --- |
| (1) 小改現行官網做得到嗎 | **AI 問答外掛做得到，資料治理做不到。** 治理的核心是「缺欄位就上不了線、一份內容算出所有產出」，這要改的是內容存放與發布的方式，不是加一個外掛。建議：**內容層與治理新建，版型可以慢慢換**。 |

| (5) 時間、切換、錢 | **時程估算**：切換前 12–18 個月，之後舊站唯讀 12 個月；內容移轉與七語翻譯是最大變數。同網域、逐頁 301、分專區切，不是某天整站換掉。**經費另案評估**，不在公開文件中。 |
| (6) LINE 疾管家會不會跟著換 | **會，而且不用另建知識庫。** 疾管家改呼叫署內一支小服務，這支服務跑網站同一套智慧問答引擎、讀同一份索引，所以答案、出處、拒答規則與評估集全部共用。不建議讓廠商拿網頁自建向量庫、讓模型自由回答。細節在 [line-chatbot.md](line-chatbot.md)。 |

## 1. 假如要導入 AI 和資料治理，現行官網小改行不行？

### 1.1 結論

**AI 問答可以外掛在舊站上；資料治理不能。** 原型的三件核心事情（[ARCHITECTURE.md](../ARCHITECTURE.md) §0）：治理是內容裡的必填欄位、人填一次機器算其餘、AI 只轉述不創作。前兩件都要求「內容是結構化資料、發布有閘門」，而現行官網（推論）的內容是 CMS 資料庫裡的 HTML 內文、按上架立即生效，兩者在「內容怎麼存、怎麼發布」這一層就不同。這一層不換，治理只能靠人記、靠公文提醒，和現在一樣。

但「架構新建」不等於「版型大改」，兩件事可以分開（這也是第 2 題同事擔心的點）。可以新建內容層與發布流程，前台一開始沿用接近現行官網的視覺，之後再換。

### 1.2 現行官網（推論）長什麼樣

以下是從公開可見的現象推論，請資訊室校正：

| 看到的現象 | 推論 | 對導入的影響 |
| --- | --- | --- |
| 網址如 `/Disease/SubIndex/{22 字元加密 ID}`、`/Bulletin/Detail/{ID}?typeid=9`、`/File/Get/{ID}`，路徑不分大小寫 | ASP.NET MVC 加 CMS，內容存在關聯式資料庫，以加密主鍵當網址 | 網址不可讀、不穩定；每一筆舊網址都要人工對照才能轉址（[migration-playbook.md](migration-playbook.md) §1） |
| 疾病頁的「致病原、傳染方式、預防方法」等是同一頁的子頁籤 | 內文是一大塊 HTML，不是一欄一欄的結構化資料 | AI 與 API 拿不到「這一段是症狀、那一段是預防」；跨頁一致性無法自動檢查 |
| 頁面上看不到權責單位、最後審閱日、依據哪份正本；指引 PDF 新版上傳，舊版網址不見或仍可開 | CMS 沒有治理欄位，也沒有版本鏈 | 民眾與 AI 分不出現行版與舊版，這正是規劃文件要解的問題 |
| robots.txt 禁爬 `/File/`、`/Uploads/` | 附件被整批擋掉 | 搜尋引擎與 AI 讀不到指引正本，也看不到之後設的轉址 |
| RSS 只有 4 個頻道，guid 為時間戳 | 訂閱與機讀出口有限 | 無法「訂閱某疾病」或「訂閱某文件的改版」 |
| 所有單位介紹在同一頁（[admin-auth.md](admin-auth.md) 第 115 行） | 機關型內容沒有獨立網址 | 無法被直接連結、搜尋、引用 |

### 1.3 「小改」能做到與做不到的

| 想要的能力 | 小改現行官網 | 為什麼 |
| --- | --- | --- |
| 網站上放一個 AI 問答框 | **做得到**：爬現行官網建索引，另掛一個問答服務 | 問答服務不需要改 CMS。但它讀到的是沒有權責、沒有版本、沒有結構的 HTML，答案能附「哪一頁」，附不了「哪一版、誰負責、是否現行」；舊版 PDF 和現行版對它一樣可信 |
| 每筆內容必填權責單位、審閱日、依據正本 | **部分**：多數 CMS 可加自訂欄位 | 欄位加得上，**閘門加不上**：舊後台是「按上架即生效」，欄位空著一樣能上線；審閱到期、逾期、衍生內容待辦都要另寫排程程式去查資料庫 |
| 一份內容同時產生網頁、API、機讀版、AI 索引、治理儀表板，且永不矛盾 | **做不到** | 這些產出要從同一份結構化資料算出來。從 HTML 內文反推結構，每種型別都要寫解析規則，而且承辦人一改版面就壞 |
| 文件版本鏈（舊版自動標失效、noindex、轉到現行版、異動對照） | **做不到**（除非 CMS 本身有文件版本功能並允許客製） | 現行做法是「新版 PDF 覆蓋或新增附件」，系統不知道兩個檔是同一份文件的兩個版本 |
| 可讀、穩定的網址（`/diseases/dengue/`） | **做不到小改** | 網址由 CMS 路由決定；改網址規則等於改 CMS，而且舊網址仍然要做一次完整的 301 對照，工沒有少 |
| 每次改動有人核准、有紀錄、能一鍵回復 | **部分** | 看 CMS 有沒有工作流與版本功能；通常只有「最後修改人／時間」 |
| 發布分車道（新聞稿自動、疾病頁要人審、緊急 10 分鐘） | **做不到** | 需要 CI 當審核者（[publishing-lanes.md](publishing-lanes.md)），CMS 沒有這個概念 |

### 1.4 為什麼「新建內容層」反而比「改舊 CMS」便宜

1. **改舊 CMS 要改廠商的產品**。客製欄位、工作流、版本功能、API 匯出，每一項都是對封閉系統的客製，依賴原廠商，而且每次升版都可能壞。原型的內容層是 JSON 加 JSON Schema 加 Node 腳本，三個 npm 相依，任何會寫程式的人都接得起來（[git-as-cms.md](git-as-cms.md) §2「廠商綁定」列）。
2. **治理算得出來，是因為內容本來就是結構化的**。原型 300 筆內容在建置時算出 2,605 頁、API、機讀版、KPI 與季報，是「算」出來的，不是人維護的。舊 CMS 要做到同樣的事，每一項都是一支新程式。
3. **舊網址轉址的工是一樣的**。無論小改或新建，只要想要可讀網址，99 種疾病與所有欄目的舊網址都要逐筆對照。這份工不會因為「小改」而省下來，所以不應該成為選小改的理由。
4. **真正省工的地方在人**：承辦人填表的步數不變（6 步，[publishing-lanes.md](publishing-lanes.md) §11），但以後不用記得「哪份文件該審了」「新聞稿寫的是舊版建議」，機器會擋、會提醒。

### 1.5 建議的路

**內容層與治理新建，前台漸進，舊站轉成唯讀再退場。** 這就是規劃文件三階段的第一階段「打底」（[roadmap-mapping.md](roadmap-mapping.md)）：先把內容搬進結構化、有治理欄位的正本，就算前台還沒換，也立刻有過期預警、舊版標示、API 與機讀版。AI 問答放在第二階段，等白名單內容與評估集到位再開。

## 2. 另外做一個新站、舊站留著，這樣不行嗎？會發生什麼問題？

### 2.1 結論

**並行可以，條件是舊站「唯讀、有期限、逐頁轉址」。** 這正是 [migration-playbook.md](migration-playbook.md) §5 的做法：切換後舊站唯讀保留 12 個月，已搬的頁面由伺服器 301 到新頁，沒搬的頁面才由舊站提供。**不可以的是兩個都在更新的「雙活」**，問題列在 2.2。

同事怕的「變化太大」，有兩個比較便宜的解法，不必靠雙活：
- **版型漸進**：新站第一版的視覺可以接近現行官網（同色系、同主選單順序），先換骨架不換皮；民眾看到的差別是「多了一句話提問和疫情狀態、頁面多了權責與審閱日」。版型是模板檔，之後任何時候可以改。
- **分專區切**：先切一個專區（原型用結核病示範），民眾進到該專區才看到新版；其他專區照舊。每個專區切換都走同一套 checklist（§5.4）。

### 2.2 雙活會發生什麼

| 問題 | 具體會怎樣 | 為什麼嚴重 |
| --- | --- | --- |
| **兩份正本** | 同一份指引、同一則疫苗建議在兩站各有一版；承辦人改了一邊忘了另一邊 | 民眾、1922、媒體、AI 各看到不同數字。原型第三十三輪做的「跨單位說法不一致」偵測只能看新站，看不到舊站 |
| **兩套網址** | 衛教單張、LINE 疾管家、公文、維基百科、衛生局網站，各自連到不同站 | 將來要退場時，外部連結還是要全部處理一次；拖得越久，指向舊站的連結越多 |
| **搜尋引擎判重複內容** | 兩站都可索引時，搜尋引擎自行選一個當「標準版」，常常選到舊站（因為累積的連結多） | 新站的搜尋排名長期起不來；關掉舊站時流量才一次掉下來，而且是在最沒準備的時候 |
| **AI 與 AI 搜尋引用到舊的** | 外部的 AI 搜尋（規劃文件附錄 H）會繼續引用舊站網址與舊版內容 | 規劃文件的目標是「讓 AI 引用官方正本」；兩站並行時沒有「正本」可言 |
| **兩倍上架工** | 新聞稿、通函、疫情發布每次要上兩次，或要寫同步程式 | 同步程式把舊站 HTML 餵進新站等於把治理欄位空著，又回到第 1 題的問題；反過來新站推回舊站則是在維護一條只為退場而存在的管線 |
| **兩倍資安與無障礙責任** | 兩個站都要巡檢、修補、過無障礙 AA 標章、設安全標頭 | 舊 CMS 的攻擊面（登入頁、檔案上傳、資料庫）正是新架構想拿掉的 |
| **民眾不知道該信哪個** | 兩個「疾管署官網」，網域又相同或相近 | 公信力問題，不是技術問題 |
| **退場日無限延後** | 沒有期限的並行，實務上就是永遠並行 | 所有上面的成本變成常態成本 |

### 2.3 什麼樣的「兩站」是健康的

| 情境 | 可以嗎 | 條件 |
| --- | --- | --- |
| 試點期：新站只開給同事與少數試用者看 | 可以 | 子網域或內網、`noindex`、頂端橫幅標「試行」；原型現在就是這樣（`SITE_MODE` 預設原型模式，[deploy.md](deploy.md) §9） |
| 切換後：舊站唯讀 12 個月 | 可以，而且必要 | 舊站關閉編輯；已搬頁面 301；未搬頁面頁首告示「本站已搬家」；到期下線，301 永久保留（[migration-playbook.md](migration-playbook.md) §5） |
| 分專區切換，過渡期一部分專區在新站 | 可以 | 同網域，由前端伺服器依路徑決定送到新站或舊站；每個已切專區的舊網址 301 |
| 兩站都在更新、都可索引、沒有期限 | **不可以** | 2.2 的全部問題 |

## 3. 怎麼知道幫忙營運建置的廠商有沒有能力照這個原型的架構做？

### 3.1 結論

**用原型當考題，不要用簡報當依據。** 原型是公開、可執行、有 357 項治理測試與 195 題評估集的 repo。能不能照這個架構做，一天之內就能驗出來。評選分三層：實作測驗、問答、合約條件。

### 3.2 實作測驗（三題，可以在評選前要求廠商先做，或列為第一個月的交付）

| 題目 | 做法 | 看什麼 | 參考文件 |
| --- | --- | --- | --- |
| **第一題：跑起來** | `git clone`、`npm ci`、`npm run build`、`npm test`、`npm run eval`，並以 `BASE_PATH=''` 建一版在他們自己的 nginx 或 IIS 上開起來 | 全部綠燈；能說出建置失敗時錯在哪一筆內容的哪個欄位；能說出為什麼是靜態站 | [deploy.md](deploy.md) §1、§7 |
| **第二題：加一種內容型別** | 照手冊新增一個型別（例如「衛教講座」），含 schema、模板、索引、治理欄位、機讀版、一條評估題，開 PR 讓 CI 檢查 | PR 一次通過或能自己修到通過；新型別自動有權責、審閱日、逾期待辦；沒有在模板裡偷算治理（規則只能在治理引擎一處） | [deploy.md](deploy.md) §3、[ARCHITECTURE.md](../ARCHITECTURE.md) §7 程式約定 |
| **第三題：把一個專區的舊網址轉過去** | 給一份真實舊網址清單（例如某疾病專區 30 筆），要求產出移轉清單、建置出 `redirects/nginx.map` 或 IIS rewriteMap，在測試機驗證每一筆一跳到位、無鏈式、含 query 的識別型網址正確 | 懂 301／302／410 的差別；知道 `{id}` 佔位不能進伺服器檔；知道 robots 要先放行 | [migration-playbook.md](migration-playbook.md) §2、§3、§8 |

加分題：寫一條新的治理規則（例如「文件生效日早於依據正本者開待辦」）並附單元測試；或把 404 log 跑過 `scripts/analyze-404-log.mjs` 並解讀報表。

### 3.3 問答（聽他們怎麼回答，不是聽答對沒）

| 問題 | 好的回答會提到 | 警訊 |
| --- | --- | --- |
| 「為什麼這個原型不用傳統 CMS？你會建議改用你們的 CMS 嗎？」 | Git 當正本、CI 當閘門、靜態輸出、開放格式；若建議換，會說明如何保留 JSON 正本與 CI 閘門 | 建議整個換成他們的產品，內容進他們的資料庫 |
| 「AI 問答怎麼保證不說沒根據的話？」 | 抽取式優先、每句有出處、LLM 只改寫並後檢、評估集當閘門、拒答與 1922 轉介 | 「接上某家大模型就好」、沒有引用、沒有評估 |
| 「舊網址怎麼處理？」 | 逐筆 301、不轉首頁、410、robots、Search Console、保留 12 個月 | 「全部轉首頁」或「做個搜尋頁就好」 |
| 「承辦人會不會要學 Git？」 | 不會；寫入閘道代為開分支與合併請求，同事只看到儲存／送審／核准 | 「每個人開一個 GitLab 帳號」 |
| 「個資怎麼放？」 | 個資不進 Git；表單 POST 到署內系統；甄選結果只公布報名編號 | 把報名資料存進網站資料庫 |
| 「無障礙怎麼做到 AA？」 | 語意標記、鍵盤、對比、axe 進 CI、人工稽核與標章 | 「上線後再買檢測」 |
| 「流量尖峰（疫情記者會）怎麼辦？」 | 靜態檔加 CDN，沒有資料庫可以掛 | 談擴充資料庫與應用伺服器 |

### 3.4 合約與驗收怎麼寫

1. **repo 歸機關**：原始碼、內容、schema、CI 設定放在署內 GitLab，廠商以帳號進來工作；合約結束不需要「資料移轉」。
2. **驗收寫成可以機器檢查的條件**：`npm test` 與 `npm run eval` 全綠；評估集版本題全對；無障礙 CI 無 critical；舊網址轉址命中率 T+7 ≥ 95%、T+30 ≥ 99%；404 率 T+30 ≤ 1%（KPI 表在 [migration-playbook.md](migration-playbook.md) §7.4，目標值由委員會核定）。
3. **文件更新是交付物**：每一輪變更要更新 `docs/`，寫「為什麼這樣做比較好」，讓資訊室與下一家廠商看得懂（本專案的慣例）。
4. **不得引入未經同意的常駐服務與外部雲端依賴**：新增資料庫、第三方 SaaS、外部 LLM 直連都要列為變更申請。
5. **交接演練**：合約期中與期末各一次，由資訊室在乾淨機器上照 `docs/` 重建整站與閘道。
6. **人員**：至少一位能寫 Node 與 CI YAML、一位懂公部門無障礙與資安標頭、一位做過網站移轉與 SEO 的人；要求在實作測驗時到場的就是會做案子的人。

### 3.5 為什麼這樣選比看簡報好

簡報和公司規模不能回答「會不會做這種架構」。這個架構的門檻不高（Node、Git、CI、靜態主機），但觀念很具體（正本只有一份、閘門在建置、AI 不創作、舊網址逐筆轉）。三道實作題能在一天內分出「照著手冊做得出來」與「想把它改回自己熟悉的 CMS」兩種廠商。

## 4. 用 200 字很快說明新原型和既有疾管署網站的差別

### 4.1 給主管與同事（199 字）

現在的官網是「一頁一頁上架」：內容存在系統資料庫，網址是加密編號，誰負責、何時審過、依據哪份正本，頁面和 AI 都看不到。新原型把內容和資料只存一份，每筆都必須填權責單位、審閱日、依據正本，缺一項就上不了線；網頁、API、機讀版、智慧問答都由這一份自動產生，不會互相矛盾。智慧問答只摘錄官方原文並附出處，不自己編答案。對民眾是一句話提問、先看疫情狀態；對同事是填表照舊，審核、提醒與紀錄由系統自動完成。

### 4.2 給民眾（180 字）

新官網先回答你的問題，再讓你逛。首頁第一眼是「現在疫情怎樣」和一個問題框，問「兩歲前要打哪些疫苗」會直接看到官方原文的答案和出處，不是一串搜尋結果。每一頁都寫著負責單位、最後審閱日和依據的指引版本，舊版文件會自動標示「已失效」並帶你到現行版。網址變成看得懂的字（例如 /diseases/dengue/），七種語言，支援螢幕閱讀器。舊網址不會壞，會自動帶到新頁。

## 5. 預計要花多少時間？新舊網站怎麼切換？（經費另案評估）

> **這一節的時程全部是估算。** 沒有現行官網的頁數與附件量、各組可投入的人力可以對照；以下用「假設加區間」的方式寫，請把它當成採購規劃的起點。最後以採購程序為準。經費不在這份公開文件裡，見第 8 節。

### 5.1 假設

| 項目 | 假設值 | 若實際不同會怎樣 |
| --- | --- | --- |
| 舊站規模 | 疾病 99 種、欄目約 20 個、可索引頁面數千、附件（PDF）數千 | 頁數與附件量直接決定移轉人力；請資訊室從 CMS 匯出一張「頁面與附件清單」後重估 |
| 內容移轉方式 | 用原型的批次轉換工具（已做 12 批示範）自動產草稿，信心低者人工檢視；久遠內容封存不轉 | 若決定「全部人工重寫」，移轉成本至少翻倍 |
| 多語 | 一級內容七語，其餘以中英為主，機器翻譯加人工審核 | 七語全量人工翻譯是最大的單一變數，可獨立採購、分年做 |
| 登入 | 試點用 Google Workspace，正式依資安政策選 Workspace 或 Keycloak | Keycloak 多養一套要建置與維運的服務 |
| 主機 | 靜態檔在機關主機或政府雲加 CDN；寫入閘道與 GitLab 在內網 | 不需要資料庫授權與應用伺服器 |
| LLM | 只做答案改寫與離線評估，經署內後端代理 | 用量小；若改成生成式對話，用量與資安審查都要重估 |
| 自建或外包 | 工程外包、內容與審核在署內 | 內容搬遷若外包，時程可控；在署內做則是各組的隱性人力 |

### 5.2 時程（切換前 12–18 個月，切換後舊站唯讀 12 個月）

| 階段 | 期間（估） | 做什麼 | 出口條件 |
| --- | --- | --- | --- |
| **0. 準備** | 2–3 個月 | 採購；資訊室回答 [deploy.md](deploy.md) §14.8 的問題（AD／Workspace、GitLab、主機位置）；從舊 CMS 匯出頁面與附件清單；委員會核定治理欄位與 KPI 目標 | 合約簽訂；清單在手；欄位定案 |
| **1. 打底與試點** | 4–6 個月 | 署內 GitLab、CI、寫入閘道、登入上線；兩個單位（公關室加一個業務組）真的用後台上架兩個月（[publishing-lanes.md](publishing-lanes.md) §10）；一個專區（建議麻疹或登革熱）完整搬遷並在測試機驗 301 | 試點 KPI 達標；一個專區的舊網址 100% 有去處 |
| **2. 全量移轉與重建** | 6–9 個月 | 批次匯入全部欄目與 99 種疾病；各組 Steward 逐筆確認；七語一級內容；無障礙 AA 人工稽核與標章；安全標頭與滲透測試；AI 問答白名單與評估集擴到 500 題 | `pending` 清零、`verified` 100%、`{id}` 佔位為 0；評估集全對；無障礙與資安通過 |
| **3. 切換** | 1 個月（T-30 到 T+30） | 依 [migration-playbook.md](migration-playbook.md) §6 的 checklist：robots 放行、基準記錄、內容凍結、三種轉址檔測試、T-0 部署、通知、每日 404 報表 | T+30 檢討：404 率 ≤ 1%、轉址命中率 ≥ 99% |
| **4. 舊站唯讀** | 12 個月 | 舊 CMS 唯讀；每週 404 報表補對照；T+12 個月下線舊站本體，301 永久保留 | `pending` 為 0；301 條數未減少 |

階段 1 與 2 可以部分重疊（試點專區搬完就開始下一批），所以總時程寫 12–18 個月。縮短的方法是先切高流量專區（疾病、疫苗、新聞）而把低流量欄目留在舊站唯讀期處理，不是壓縮測試與確認。

### 5.3 費用：經費另案評估

**本文件不列金額。** 原型放在公開的 GitHub 儲存庫，經費估算由署內另案以內部文件評估，見第 8 節。這裡只列評估時應分開看的項目與變數，讓估算的人不漏項：

| 項目 | 一次性或每年 | 主要變數 |
| --- | --- | --- |
| 工程：內容層、治理引擎、前台、後台、寫入閘道、CI、轉址、無障礙、資安 | 一次性 | 原型已有可執行的基礎，工程主要是補正式環境（登入、閘道上線、預覽存取控制、表單端點）、視覺定稿、使用者測試與修正 |
| 內容移轉：匯出、批次轉換、人工檢視、Steward 確認、舊網址對照 | 一次性 | 最大變數：頁數、附件數、信心低者人工檢視的比例；若各組自己做，這筆變成署內人力 |
| 多語：一級內容七語翻譯與審核 | 一次性加每年 | 可分年、可獨立採購；中英先行 |
| 主機與 CDN、GitLab 主機、閘道主機 | 一次性加每年 | 靜態站不需要資料庫與應用伺服器；CDN 依流量 |
| LLM 用量（改寫與離線評估，經後端代理） | 每年 | 抽取式為主，LLM 只對開啟的使用者改寫；若做評估判官會多一些 |
| 無障礙標章、滲透測試、資安檢測 | 一次性加每年 | 公部門既有採購項目 |
| 維運與功能演進（廠商） | 每年 | 建置後第二年起；比傳統 CMS 少掉資料庫與應用伺服器的修補 |

評估時請記得：
- **不含署內人力**：各組 Steward 逐筆確認、審核、提供評估題，是現在就該做的治理工作，但會集中在移轉期。
- **省下來的要一起算**：現行 CMS 的授權、維運、資料庫與主機費在舊站下線後停止；請資訊室提供現行年費當對照。
- **不要為了省錢砍的兩項**：舊網址逐筆對照（砍了就是 404 與搜尋流量歸零）、評估集與無障礙稽核（砍了就是上線後才發現）。

### 5.4 新舊網站怎麼切換

一句話：**同一個網域、逐頁 301、分專區切、舊站唯讀 12 個月、301 永久保留。** 完整版在 [migration-playbook.md](migration-playbook.md)，這裡只講同事會問的幾件事。

1. **網址不換網域。** 民眾還是進 `www.cdc.gov.tw`；由前端伺服器依路徑決定送到新站或舊站。這樣不需要用搜尋引擎的「變更地址」工具，書籤與連結也不會因為換網域全部失效。
2. **一頁一頁有去處，沒有第四種。** 每個舊網址只能是：301 到新頁、410 已刻意移除、或暫時由唯讀舊站提供。不轉首頁，不留 404。
3. **先切一個專區。** 試點專區搬完、301 在測試機驗過、404 報表能每週跑，再複製到下一批。這樣每一步的風險都只有一個專區大。
4. **切換日前 30 天**：舊站 robots 放行附件路徑（否則搜尋引擎看不到轉址）、記錄搜尋流量基準、舊站頁首預告。**前 7 天**：舊站內容凍結，新內容只寫新站；轉址檔在測試機批次驗證。**當天**：部署新站、啟用轉址、提交 sitemap、抽驗 20 個舊網址、舊站轉唯讀、通知 1922、LINE 疾管家、衛生局與媒體。
5. **切換後**：每日看 404 前 50 名（前兩週），之後每週；搜尋流量 3–12 週內回復是正常的，T+4 週低於基準一半才啟動排查。
6. **回復計畫**：舊站主機在唯讀期內不回收；任何一條 301 都能撤掉切回舊站。所以切換不是「不能回頭」的動作。
7. **12 個月後**：舊站本體下線，新頁上的「本頁取代舊網站 N 個頁面」自動隱藏，**301 規則永久保留**（成本極低，外部連結永遠不會壞）。

### 5.5 為什麼這樣切比「某天整站換掉」好

- 整站一次換，等於 99 種疾病與所有欄目的對照在同一天全部要對，錯了一起錯，而且 301 會被瀏覽器永久快取，修不回來。
- 分專區切，每一次切換的 KPI（404 率、命中率）都可以在下一次切之前看到，流程在第二個專區就會比第一個順。
- 唯讀期給了「還沒搬完」一個合法的位置，承辦人不必為了趕切換日草率決定封存或刪除。

## 6. LINE 疾管家會不會跟著換？

### 6.1 結論

**會，而且是新網站最自然的延伸，不必另外建一份知識庫。** 新網站建置時已經同時產出機讀版頁面、`/v1/*.json` 開放資料、給 AI 的 `llms.txt`，以及智慧問答用的答案索引（每段有句子、出處網址、權責單位、審閱日）。疾管家要做的是**呼叫署內一支小服務**，這支服務載入和網站相同的問答引擎與索引；疾管家的 webhook 把民眾的問題丟給它，拿回「幾句官方原文加出處加審閱日加網址」再轉成 LINE 訊息。網站怎麼答，疾管家就怎麼答；相關度門檻、拒答與 1922 轉介、評估集全部共用。完整評估、三種接法的比較、要先問承辦與廠商的問題，見 [line-chatbot.md](line-chatbot.md)。

### 6.2 為什麼不讓廠商自己做

| 做法 | 問題 |
| --- | --- |
| 廠商爬網頁、自建向量庫、讓模型自由回答 | 失去版本鏈、逾期標示、「疫情態勢人工發布不得推論」這些治理訊號；兩邊答案會不一致；多一份要同步、要稽核的知識庫 |
| 疾管家只放連結（切換日本來就要做） | 零風險，但機器人仍然只會給連結，不會回答；舊網址寫死在選單裡的要用 `/v1/legacy-map.json` 全部換掉 |
| 呼叫網站同一套引擎（建議） | 零第二份知識庫；要用語言模型改寫時接在同一條管線後面的署內代理（[ask-search-llm.md](ask-search-llm.md) §7），不是前面 |

### 6.3 對第 3 題與第 5 題的影響

- 評選廠商時可以加一道問答：「疾管家怎麼接新網站？」好的回答會說「呼叫同一套引擎與索引」，警訊是「我們幫你建一個知識庫」。
- 這支小服務的工程與主機屬於第 5.3 節的「工程」與「主機」項目，經費隨該案另案評估；疾管家本身的 LINE 平台費與原廠商合約另計。

## 8. 為什麼經費不寫在這裡（2026-10-15）

這份文件原本的第 5.3 節有一張「一次性與每年費用」的估算表，2026-10-15 移除，改為「經費另案評估」。原因：

1. **這個儲存庫是公開的。** 原型放在 GitHub public，GitHub Pages 的展示站也從這裡重建；任何寫進 `docs/` 的數字，廠商、媒體與其他機關都看得到。
2. **沒有依據的數字會被當成依據。** 那張表是在沒有現行維運合約金額、頁數與附件量的情況下用假設推出來的區間，但公開後會被當成「署方預期的預算」，影響廠商報價與採購評選的公平性。
3. **採購敏感資訊屬於內部文件。** 經費、底價、評選權重這類內容依採購程序在署內另案評估與簽核，不應該出現在任何對外可讀的地方，包括 PR 說明、issue 與 commit 訊息。

**規則：** 公開儲存庫只寫「要分開評估的項目與變數」（第 5.3 節現在的樣子），金額、人月、單價一律不寫；時程區間可以寫，因為它是規劃假設而不是採購資訊。要寫金額時，寫在署內文件並在這裡註明「另案評估」。

**還留在哪裡：** Git 歷史（提交 `a921476` 起，PR #68 合入）仍含原本的數字；PR #68 的說明與留言沒有金額。公開儲存庫重寫歷史（force-push `main`）會讓其他分支與已 clone 的人全部對不上，而且 GitHub 的快取與 fork 也不會跟著消失，所以沒有這樣做；是否要向 GitHub 申請清除快取或改版 PR 說明，由專案負責人決定。
