# PDF 文件怎麼讓智慧查詢查得到、引用得到

> 給誰看：上架指引、手冊的各組承辦人，資訊室，以及 AI推動辦公室（OASIS）。
>
> 一句話：**上傳 PDF 只解決「下載」。要讓智慧查詢引用，必須先把 PDF 轉成分章分節、每頁有頁碼的機讀版，再由權責單位校對。** 轉檔由工具做，校對要人做，系統會盯著沒校對的文件。
>
> 第十九輪（2026-10-06）實作。範例：2026 年 2 月版《登革熱/屈公病防治工作指引》（114 頁）。

## 1. 為什麼不能直接把 PDF 丟進去

PDF 是「排版」格式，它記的是每個字畫在紙上的哪個位置，沒有記段落、標題或表格欄位。直接把抽出來的文字切塊放進索引，會遇到這些問題（都是在登革熱指引實際看到的）：

| 問題 | 實際長相 | 後果 |
| --- | --- | --- |
| 頁碼、頁首混進內文 | 每頁頂端一行「23」 | 答案裡出現無意義的數字 |
| 目錄點線 | 「第一章 疾病介紹……………3」 | 目錄被當成內容引用 |
| 一句話被換行與換頁切斷 | 「研判必須」｜換頁｜「進入公、私場所…」 | 答案只引到半句話 |
| 表格欄位拆散 | 「泰國 印尼 越南 … 2000 18617 33443 24116」 | 數字對不回國家與年份，引用了會錯 |
| 表單附件 | 訪視紀錄表的欄位名稱 | 欄位名稱被當成規定 |
| 紅字（本版修訂處） | 抽成文字後沒有顏色 | 看不出這版改了什麼 |
| 沒有頁碼可引 | 只能說「依某指引」 | 讀者要在 114 頁裡自己找 |

所以要先「整理」再「索引」，而且整理的結果要讓人看過。

## 2. 處理流程（五步）

```
PDF ──①抽文字──▶ 純文字 ──②整理結構──▶ 章／節／附件＋頁碼標記 ──③存成文件 JSON──▶ content/documents/
                                                                          │
                                         ⑤每頁一塊進專業索引 ◀──④權責單位校對（表格、紅字、抽查）
```

1. **抽文字**：`pdftotext`（不加 `-layout`）。有文字層的 PDF 才抽得出來；掃描檔要先 OCR（本原型不處理，見第 6 節）。
2. **整理結構**（`scripts/lib/pdf-text.mjs`，純函式）：
   - 依頁碼行切頁；封面與目錄不當內容，只拿目錄裡的附件全名。
   - 依「第 N 章」「第 N 節」「附件 N」切段落；登革熱／屈公病這類一章分兩病的，段落 key 帶病名（`ch1-dengue-s1`、`ch1-chik-s1`）。
   - 換行接回句子；同一句跨頁時接回上一頁那段（引用算起始頁）。
   - 每頁在內文插一行頁碼標記 `〔p.N〕`。文件頁把它變成「第 N 頁」分隔線與 `#page-N` 錨點。
   - **表格頁**（一頁大多是短行、少句末標點）整頁換成說明：「本頁為表格，未納入智慧查詢，請看 PDF 原頁」。頁中夾的數字表格同樣處理。
   - **表單、範例、地圖附件**只留標題與「請看 PDF 第 N 頁起」，`index: false`。參考文獻也不入索引。
3. **存成文件 JSON**（`scripts/pdf-to-md.mjs`）：人工欄位（標題、版次、生效日、權責單位、疾病…）寫在 meta 檔，工具產生 `sections`、`machineReadableMarkdown`、`pageCount`、`derivedFrom`。
4. **校對**：權責單位對照 PDF 原頁做完第 4 節的事，把 `derivedFrom.reviewStatus` 改成 `reviewed`。
5. **索引**（`scripts/lib/index-builder.mjs`）：有頁碼標記的段落每頁切一塊，帶 `pdfPage`、網址連到文件頁的 `#page-N`。

## 3. 指令

```bash
# 1) 準備 meta（人工欄位；可以複製 data/pdf-ingest/dengue-chik-guideline-2026-02.meta.json 改）
# 2) 轉換（輸入 PDF 或已抽好的 .txt 都可以）
node scripts/pdf-to-md.mjs 指引.pdf --meta data/pdf-ingest/xxx.meta.json \
  --out content/documents/xxx.json --report data/pdf-ingest/xxx.report.json
# 3) 建置，看評估與待辦
npm run build
```

報告（`report.json`）會列：頁數、段落數、入索引段落數、表格頁、頁中數字表格、表單附件、跨頁接回幾段、警告。**先看報告再看內容**：表格頁清單就是校對時要補的工作量。

來源檔與 meta 放 `data/pdf-ingest/`（不會被建置讀進網站），轉出的文件 JSON 放 `content/documents/`。測試會重跑轉換並比對已提交的 JSON（`tests/pdf-ingest.test.mjs`），所以**不要直接手改轉出的段落**；要改規則就改 `pdf-text.mjs`，要人工補表格就照第 4 節做（補完後把該文件從比對測試移出，或把人工修正寫回來源）。

## 4. 權責單位校對什麼（`reviewStatus: reviewed` 之前）

| 項目 | 做法 | 為什麼 |
| --- | --- | --- |
| 抽查章節 | 每章挑 1–2 頁，對照 PDF 原頁，看段落有沒有缺、順序有沒有亂、標題對不對 | 抽字工具對雙欄、文字框、頁首頁尾的處理不一定對 |
| 表格 | 報告裡的表格頁，需要被查的（例如病例定義對照表、時限表）轉成 Markdown 表格，取代「本頁為表格」那段說明 | 表格常是最多人要查的資訊；機器抽的欄位會錯位 |
| 紅字修訂處 | 對照紅字版，把本版改了什麼填進 `changes[]`（段落、改前、改後），把 `derivedFrom.redTextChanges` 改成 `captured` | 顏色抽不出來；填了 `changes`，文件頁會有「異動對照」，專業版答案會說「取代前版…」 |
| 頁碼偏移 | 印刷頁碼 1 是 PDF 第幾頁？封面＋目錄佔 4 頁就填 `derivedFrom.pdfPageOffset: 4` | 有了偏移量，來源卡的「開啟 PDF」會直接跳到那一頁 |
| PDF 正本 | 把 PDF 放進 `content/assets/{id}/`，`pdfUrl` 改成 `/files/{id}/檔名.pdf` | 機讀版只是索引用的副本，正式內容以 PDF 為準 |
| 生效日 | 封面只寫「2026 年 2 月版」時，確認實際生效日後改 `effectiveAt` | 版本題與「現行版」判斷都看生效日 |

## 5. 系統怎麼盯

- **沒校對（`reviewStatus: machine`）**：
  - 不進 AI 白名單（理由「PDF 機讀版未校對」）。
  - 仍可在**專業版**智慧查詢被找到，但**排序在已審內容之後**（同樣講到時先用已審的），來源卡標黃色「由 PDF 機器轉出，尚未人工校對；請以 PDF 原頁為準」。
  - 產生連動待辦「PDF 機讀版待校對」，列出表格頁與紅字，期限為轉檔日起 30 天。
- **民眾版**本來就不引用文件庫（指引、手冊只供專業版），這點不變。
- **引用格式**：專業版答案的引用標籤會帶頁碼，例如「依〈第五章 群聚疫情防治措施 · 第一節 病例群聚定義〉（第 55 頁）」；來源卡多「頁碼（PDF 印刷頁碼）」一列與「開啟 PDF」按鈕。
- **換版**：PDF 換版就重跑轉換、產生新版文件（新 id，`supersedes` 指向舊版）；`derivedFrom.sha256` 記的是轉換當時的檔案雜湊，可用來確認機讀版是從哪一份 PDF 來的。

**為什麼沒校對的也讓專業版查得到，而不是等校對完才上**：指引常是人一上架就要查的東西，完全擋掉會逼人回去翻 PDF；但機器轉的文字可能錯，所以排序讓位、明白標示、引用帶頁碼方便對照，並用待辦逼校對完成。若治理委員會認為風險太高，把 `index-builder.mjs` 裡 `eligiblePro` 加一條「`derivedFrom.reviewStatus !== 'reviewed'` 就不收」即可改成「校對完才可查」。

## 6. 這個原型沒做、正式環境要補的

- **掃描檔 OCR**：沒有文字層的 PDF 要先 OCR（例如 Tesseract 繁中模型），OCR 結果錯字更多，校對要全篇看。
- **紅字自動擷取**：用能讀顏色的工具（例如 PyMuPDF 讀每個字的顏色）把紅字標成 `<ins>`，自動產生 `changes[]` 草稿。這需要 PDF 原檔，本次只收到抽好的文字檔。
- **表格自動轉換**：可試 Camelot、pdfplumber 等表格擷取，但仍要人工核對。
- **後台上傳介面**：目前是命令列；`pdf-text.mjs` 沒有任何 import，日後可直接放進後台「上架預處理」在瀏覽器跑。
- **語意檢索**：目前是關鍵字（BM25）檢索；PDF 長文件特別適合加向量檢索，但頁碼切塊、校對狀態這些治理欄位要保留。

## 7. 本次範例的現況（2026 年 2 月版登革熱/屈公病防治工作指引）

- 來源：Yulun 提供的抽出文字（`data/pdf-ingest/dengue-chik-guideline-2026-02.txt`），**沒有 PDF 原檔**，所以 `pdfUrl` 先放待補頁、`pdfPageOffset` 未填、紅字未擷取。
- 結果：114 頁、45 段，34 段入索引；表格頁 13 頁（9、16–18、27、82、93–94、98、100、111–112、114），頁中數字表格 2 頁（4、5）；表單附件 9 個、地圖 1 個不入索引；文字型附件（附件一 NS1 快篩費用申報、附件六 農（果）園防治指引）入索引。
- 文件 id：`doc.dengue-chik-guideline.2026-02`，權責單位暫填急性傳染病組，生效日暫填 2026-02-01，均待權責單位確認。
- **與原型虛構文件的衝突**：原型裡另有一條示意版本鏈「登革熱／屈公病防治工作指引（第 15～17 版）」，內容是原型撰寫、第 17 版生效日 2026-07-01，和真的 2026 年 2 月版同名但內容不同（例如群聚定義）。本輪兩者並存（真文件排序在後、標未校對），由 Yulun 決定是否以真文件取代示意鏈；示意鏈牽涉評估集版本題、通函、影音與舊站匯入範例，取代要一併改。
