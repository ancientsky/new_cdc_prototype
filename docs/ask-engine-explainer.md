# 智慧問答不用 embedding，為什麼還能又快又準？限制在哪裡？

> 第五十八輪（2026-10-19）。起因是同事問 Yulun：「能否再整理一遍目前原型使用的智慧搜尋技術，是怎麼不用 embedding 但又能那麼快和精準？限制是什麼？」
> 這份文件寫給兩種讀者：沒寫過程式的同仁（看第 0、1、2、3、5 節就夠），和資訊室（每一段都附程式位置與量法，可以自己核對）。
> 第三十二輪的 [docs/ask-search-llm.md](ask-search-llm.md) 已經比較過「智慧問答」與「全文搜尋」兩套技術並談過 LLM 怎麼接；這份文件不重複那些，只回答標題這三個問題，並在第 7 節整理從那時到現在改了什麼。
> 文中所有數字都標了來源：**量到的**（本輪在建置機上重跑）、**文件記載的**（之前某一輪量的，附節次），或**推估的**。原型是公開 repo，不談經費與人力。

## 0. 一頁結論

1. **它不是「搜尋」，是「抽句子」。** 智慧問答（`/ask/`）把站內已審核的官方內容事先切成 822 個「答案單元」（民眾版；專業版 1,133 個），使用者提問時，從裡面挑出最相關的幾個單元，再從單元裡**抽出原句**排成答案，每句附來源。它不會自己寫一個字，所以不會「編」。
2. **快，是因為幾乎所有事都在建置時做完了。** 切單元、標疾病與主題、算詞典、檢查審核期限、比對說法衝突，全在 `npm run build` 時算好存成 JSON。使用者的瀏覽器只下載一份約 211 KB（gzip 後）的索引，在本機算分數。本輪量到：引擎建立 33 毫秒，第一題 46 毫秒，之後每題中位數 4.7 毫秒（Node，建置機；瀏覽器數字見 §2.3）。沒有伺服器、沒有模型、沒有網路來回。
3. **準，不是靠「懂語意」，是靠七道工序層層把關。** 遮個資 → 擋指令注入 → 認出疾病／疫苗／國家 → 判斷問的是什麼事（意圖） → 該拒答的先拒答 → 用詞彙主檔展開同義詞 → 用 BM25 加上「字詞邊界」「實體加權」「題目錨點」排序 → 相關度不夠就說「查無」 → 從選中的單元抽句、附出處。每一道都是看得見、可以逐條解釋的規則，答錯時可以指出是哪一道錯。
4. **Embedding（向量檢索）不是被排除，是「還沒有必要付那個代價」。** 向量檢索解決的是「民眾用詞和官方用詞不同」；本站先用詞彙主檔（87 個詞、240 種寫法）、44 條跨語言對照、18 條口語改寫、72 個疾病名與 175 個別名把這個缺口補起來，而且每補一筆同事就能自己改資料。向量檢索一旦加入，「不需要伺服器」就不成立（§4）。
5. **限制要誠實講。** 在它見過的 454 題評估集上六項指標 100%，但在**完全沒見過的 240 題盲測**上只有 69.6%。弱項是錯字（28.6%）、長輩說法（36.4%）、情境題（55.9%）和外語。它不會推論、不會跨文件綜合、不會理解詞典沒有的口語；詞典與規則要人維護；索引大小已經用掉預算的八成，內容再翻倍就要改架構（§5）。

## 1. 它到底在做什麼：用一個例子走一遍

問：「我家小孩發燒出疹子，會不會是麻疹？要不要打疫苗？」

| 步驟 | 引擎做了什麼 | 為什麼這一步讓答案更準 | 程式位置 |
| --- | --- | --- | --- |
| ① 遮個資 | 身分證、電話、地址、姓名樣式先換成佔位符 | 問句後面會被記錄、會送進 LLM 模式；先遮，個資就不會外流 | `text.js` `maskPIIDetailed` |
| ② 擋指令注入 | 「忽略以上規則」「你現在是」這類句型標記起來 | 防止有人用問句改寫引擎行為；標記後走謠言查證路徑而非作答 | `text.js` `detectInjection` |
| ③ 錯字修正 | 「疱疹性咽喉炎」→「咽峽炎」這類病名近似錯字 | 病名打錯一個字就查無，太不友善；但只修「站內有、且唯一」的名稱，不猜 | `lexicon.js` `nearMiss` |
| ④ 認實體 | 認出「麻疹」是疾病、「疫苗」是主題，沒有國家 | 後面排序時，講麻疹的單元加分、講德國麻疹的不加分 | `core.js` `detectEntities` |
| ⑤ 判意圖 | 13 種意圖之一：這題是「症狀＋疫苗」 | 問申請流程就偏向服務頁，問數字就改讀統計主檔，不走檢索 | `rules.js` `classifyIntent` |
| ⑥ 拒答規則 | 21 條：急症、個人用藥劑量、法律責任、冒充機關、有害內容等 | 公部門網站不能給個人醫療建議；這題不觸發，繼續 | `rules.js` `REFUSAL_RULES` |
| ⑦ 同義詞展開 | 「發燒」「出疹」「疫苗」補上官方寫法與別名 | 民眾寫「出疹子」，官方寫「紅疹」「皮疹」，不展開就對不上 | `core.js` `expandQuery`、詞彙主檔 |
| ⑧ 檢索排序 | 把問句切成兩字一組，對 822 個單元算 BM25 分數，再加減權 | 見 §3，這是「不用 embedding 也能對得上」的核心 | `core.js` `retrieve`、`bm25Score` |
| ⑨ 相關度門檻 | 最高分單元是否真的涵蓋問句？不夠就「查無」 | 寧可說查無並導向 1922，不拿勉強相關的內容充數 | `core.js` `relevanceOf`、`rules.js` `RELEVANCE` |
| ⑩ 抽句、附出處 | 從前幾個單元抽出講症狀與疫苗的句子，每句附來源編號、審閱日、權責單位 | 使用者看到的每一句都能點回原頁核對 | `core.js` 組句段、`render.js` |

使用者看到的是：三到五句官方原文，每句後面一個數字，下面是來源卡。如果兩個來源的數字不一樣，會多一行「兩份資料說法不同」（第三十三輪）。

全文搜尋（`/search/`）是另一套東西：Pagefind 建的靜態索引，列出「哪些頁面提到這個詞」，共 2,905 頁、7 種語言，第一次搜尋才載入約 291 KB（本輪建置紀錄）。它不懂同義詞也不理解問句，兩套為什麼並存見 ask-search-llm.md §1。

## 2. 為什麼快

### 2.1 把工作搬到建置時

一般「問答系統」的做法是：使用者問 → 伺服器把問句送給模型算向量 → 到向量資料庫比對 → 把片段送給 LLM → 等它生成。每一步都是網路來回加上模型推論，通常是秒級。

本站把能事先算的全部放到 `npm run build`：

| 建置時算好的東西 | 說明 | 位置 |
| --- | --- | --- |
| 答案單元 | FAQ 一題一個、疾病頁一節一個、指引一章一個、通函一段一個，帶 `diseases`、`tasks`、`terms`、`owner`、`reviewedAt`、`whitelist` 等欄位 | `scripts/lib/index-builder.mjs` |
| 白名單 | 審閱逾期、待確認、草稿的內容不進索引（本輪 284/333 筆在白名單） | `scripts/lib/governance.mjs` |
| 詞典命中 | 每個單元事先標好「真的提到哪些已知名詞」（排除躲在更長名詞裡的假命中） | `index-builder.mjs` `glossaryHits` |
| 說法一致性 | 3,760 句互比，數字不同的列為待判定、已判定的標出以哪份為準 | `scripts/lib/consistency.mjs` |
| 歷史標記 | 超過 12 個月的新聞稿標歷史、答案降權 | `governance.mjs` |

瀏覽器拿到的是結果，不是原料。這也是為什麼一致性比對、權威順序這些功能加進來時，使用者下載的程式幾乎沒變大（第三十三輪的教訓，ask-search-llm.md §8.5）。

### 2.2 索引小到可以整份放進瀏覽器

| 項目 | 量到的（本輪建置，`BUILD_TODAY=2026-10-14`） |
| --- | --- |
| 民眾版答案單元 | 822 個，JSON 1,587 KB，gzip 後 211 KB |
| 專業版答案單元 | 1,133 個，JSON 2,481 KB，gzip 後 328 KB |
| 答案頁提問後下載的 JSON 合計 | 繁中 369 KB、英文 409 KB、專業版 491 KB（預算 445／565 KB） |
| 答案頁 JS，立即載入 | 最大 133.9 KB |
| 答案頁 JS，提問後合計 | 最大 235.3 KB（預算 240 KB） |

一份 211 KB 的索引大約等於三張手機照片，第一次提問才下載，之後整個瀏覽階段都在記憶體裡。沒有伺服器就沒有排隊、沒有當機、沒有「尖峰時段變慢」，疫情爆發時幾萬人同時問也一樣快（這一點是**推估**：靜態檔由 CDN 供應，本站沒有做過壓力測試）。

### 2.3 算分本身只要幾毫秒

本輪在建置機上用與瀏覽器同一份 `core.js`，拿評估集前 200 題繁中問句逐題計時（量法見 §8）：

| 量到的 | 時間 |
| --- | --- |
| 建立引擎（讀索引、建詞典） | 33 ms |
| 第一題（含 BM25 統計與詞典快取建立） | 46 ms |
| 之後每題中位數 | 4.7 ms |
| 第 90 百分位 | 9.9 ms |
| 第 99 百分位 | 31.9 ms |
| 最慢一題 | 92.3 ms |

瀏覽器的實測是第四十輪做的（ask-search-llm.md §11）：在 4 倍 CPU 降速的手機模擬下，`/ask/?q=登革熱` 答案出現 1.5 秒，其中大半是下載與解析 JSON，不是算分。桌機瀏覽器**推估**在百毫秒內。

為什麼這麼快：BM25 是加法和乘法，822 個單元 × 問句十幾個 token，就是幾萬次四則運算。沒有矩陣、沒有浮點向量、沒有模型。

### 2.4 第四十輪學到的一課：慢的不是演算法，是正規式

第四十輪之前，第一題要 1,142 毫秒。CPU 剖析發現 1.0 秒花在**編譯正規式**：1,260 個名稱（疾病、別名、疫苗、詞彙）每個一條正規式，V8 第一次用才編譯。改法是每個名稱先算出「任何命中都一定包含」的一段字面子字串，問句裡沒有這段就連正規式都不建（`lexicon.js` `matcherFor`、`needleOf`）。判定結果有測試證明與原本完全相同，第一題 1,142 → 107 毫秒（文件記載，第四十輪），本輪再量是 46 毫秒（機器不同，不能直接比）。

教訓寫在這裡是因為它回答了同事的另一個問題：**快不是演算法選得好就夠，要量到能拆開看的程度。**

## 3. 為什麼準（在不懂語意的前提下）

Embedding 的賣點是「懂語意」：「打針」和「接種」向量很近。本站不用它，靠的是下面六件事。每一件都是可以指出來、可以關掉、可以寫測試的規則。

### 3.1 中文切成兩字一組（bigram），所以不怕沒斷詞也不怕錯一個字

中文沒有空白。本站不做斷詞，直接把「登革熱症狀」切成「登革」「革熱」「熱症」「症狀」四個 token（`text.js` `tokenize`）。好處：

- 不需要斷詞模型，繁中、日文、泰文都能用同一套。
- 錯一個字只影響相鄰兩個 token，其他仍對得上，所以「登革熱症壯」還是撈得到。
- 問句端拿掉疑問詞碎片（「是什」「有什」）和功能詞 bigram，避免標題剛好叫「XX 是什麼？」的影片蓋過主題頁（第五十二輪）。

代價：「熱症」這種跨詞的假 token 會製造雜訊。這是下一點要解決的。

### 3.2 詞典當詞界：已知名詞躲在更長名詞裡不算命中

第三十一輪的關鍵修正。「急性傳染病組」裡有「性傳染病」四個字，但它不是在講性病；「急性病毒性 A 型肝炎」裡有「性病」兩個字。純 bigram 會把這些都算成命中。

本站有一份現成的詞典：72 個疾病名與 175 個別名、18 支疫苗、87 個詞彙主檔詞條（含 240 種寫法）、單位名。`buildLexicon` 把這些名稱排好，規定「名詞 P 若在某段文字裡只出現在另一個指不同東西的更長名詞 L 裡面，就不算出現」（`lexicon.js` `wholeHit`）。索引端和查詢端共用同一條規則，所以「性病」不會因為「急性傳染病組」加分，問「性病症狀」也不會撈到 A 肝。

這等於是**用機關自己已經有的名詞資料當斷詞器**，不用另外訓練。

### 3.3 BM25：三十年的老方法，但它的偏好剛好是官方內容需要的

BM25 給每個 token 一個分數：這個詞在這個單元出現幾次（多就高，但有飽和，不會重複一百次就贏）、這個詞在全部單元裡多罕見（罕見就高：「登革熱」比「症狀」重要）、這個單元有多長（長單元每個詞被稀釋）。`core.js` `bm25Score`，參數 k1 = 1.5、b = 0.75，是教科書預設值。

在上面再加減權（`retrieve`）：

| 加減權 | 理由 |
| --- | --- |
| 標題命中 ×2 | FAQ 題目、頁面標題就是作者認定的主題 |
| 實體加權，問 A 病不拿 B 病 | 認出「麻疹」就讓麻疹單元加分，德國麻疹不加 |
| 實體名稱本身在 BM25 端降權 | 否則同一個病的所有單元分數都一樣高，分不出哪一段在講症狀 |
| 意圖對型別 | 問申請 → 服務頁；問數字 → 統計；問謠言 → 澄清 |
| 題目錨點（第四十九輪） | FAQ 題目與問句共有的實詞 ≥ 2 個，這題 FAQ 帶頭 |
| 機器轉出的 PDF 文字 −0.6 | 同樣講到時，已校對內容排前面 |
| 歷史新聞稿降權 | 問現行做法時往後排，問「去年」時照常 |

這些偏好用向量很難表達：向量只會說「相似度 0.71」，說不出「因為是權責單位的 FAQ 題目命中」。

### 3.4 同義詞走資料，不走模型

民眾說「打針」「拉肚子」「新冠」「做愛」，官方寫「接種」「腹瀉」「COVID-19」「性行為」。向量模型靠訓練語料學會這些；本站靠三份資料：

- **詞彙主檔**（`content/master/glossary.json`）：正名、別名、舊名（deprecated）、七語對照。第四十一輪 covid 查無，修法是加兩個別名加一條「拉丁名 4 字母以上含連字號者，字母詞幹也算別名」的通則（`latinStems`），不是在程式裡寫例外。
- **跨語言對照**（`lexicon.js` `CROSS_LANG`，44 條）：英、越、印尼、泰、他加祿、日文的常用詞 → 中文檢索詞。只用於撈片段，不會出現在答案裡。
- **口語改寫**（`PARAPHRASE`，18 條）：中文口語 → 正式用語，同樣只做檢索展開。

展開的詞權重 0.7，原詞 1.0，所以原詞永遠比較重要。同事在後台詞彙主檔加一筆，下次建置就生效；查詢紀錄報表（docs/ask-log.md）會把「查無」的問句和現有詞典比對，列出候選。

### 3.5 相關度門檻：寧可查無

就算排序第一的單元分數最高，也不代表它回答了問題。`relevanceOf` 另外算「問句的 token 被前幾個單元涵蓋了多少（以 IDF 加權）」，加上絕對分數門檻。門檻值在 `rules.js` `RELEVANCE`：最高分低於 3 直接查無；低於 8 且涵蓋率不到 85% 查無；涵蓋率低於 28% 查無（有認出疾病時放寬）；只命中「症狀」「預防」這種通用詞也查無。門檻是用 203 題「不該被誤擋」的評估題校準的（決策紀錄 §17）。

查無時的畫面：說明找不到足夠官方依據、給 1922、給疾病索引、給全文搜尋連結。這是**刻意的失敗方向**：公部門網站答錯一題的代價，遠高於說「查無」一題。

### 3.6 每句有出處、可以自動判分

答案的每一句都是索引裡某個單元的原句，帶著單元 id。所以可以寫自動測試：454 題評估集（`content/governance/eval-set.json`，19 類）在每次 CI 跑六項指標，本輪結果：

| 指標 | 門檻 | 本輪 |
| --- | --- | --- |
| Grounding（每句都有出處） | ≥ 95% | 100% |
| Factual accuracy（引到該引的內容） | ≥ 90% | 100% |
| Completeness（該有的要點都有） | ≥ 85% | 100% |
| Answer rate（該答的有答） | ≥ 80% | 100% |
| Refusal precision（該拒答的有拒答） | ≥ 90% | 100% |
| Reputational safety（不出現禁句） | 100% | 100% |

這 100% 要搭配 §5.1 一起讀：這 454 題是引擎「見過」的題目。

## 4. 那 embedding 到底好在哪？什麼時候該換？

公平地說，向量檢索做得到三件本站做不到的事：

1. 詞典沒收的口語。「小朋友屁股長一粒一粒」對應到腸病毒的「臀部紅疹」，要有人先在詞彙主檔加這條；向量模型可能本來就知道。
2. 跨語言直接比對。英文問句找中文片段，本站靠 44 條對照；向量模型可以不靠對照。
3. 長問句抓重點。「我下個月要去泰國，小孩兩歲，要注意什麼」，向量對整句的「意思」比較寬容。

代價（ask-search-llm.md §5.2 已詳列，這裡只講結論）：

| | 現在（bigram＋詞典＋BM25） | 加向量檢索 |
| --- | --- | --- |
| 查詢端要不要模型 | 不要 | 要：呼叫 embedding API（需後端代理與金鑰）或在瀏覽器載入數十至數百 MB 模型 |
| 伺服器 | 不需要 | 需要 |
| 可解釋性 | 「因為命中這三個詞、是權責單位 FAQ」 | 「相似度 0.71」 |
| 查無門檻 | 已用 203 題校準 | 要重做 |
| 詞界問題 | 已解 | 不會自動消失，詞典規則仍要留著 |
| 同事能不能自己修 | 加一筆詞彙主檔 | 要重算向量、重跑評估 |
| 換模型 | 無此事 | 全部重算、重調 |

本站的立場不是「向量不好」，而是：**先把便宜的做滿，量出剩下的缺口有多大，再決定要不要付這個代價。** 若要加，形式是「BM25 先選候選、向量只做重排並補幾塊」的混合式，而且只出現在有後端的正式站（ask-search-llm.md §5.3）。

另一條比向量更便宜的路是第五十三輪結論提到的：**LLM 只改寫問句、答案仍由抽取式引擎與引用產生**。模型把「屁股長一粒一粒」改寫成「臀部紅疹 腸病毒」加進檢索詞，答錯最多是多撈到幾塊不相關的片段，仍會被門檻擋掉。這條還沒做，要做時用 §5.1 的盲測題組比較有無改寫的差別。

## 5. 限制

### 5.1 盲測只有七成，而且已到這種做法的天花板

| 題組 | 性質 | 結果（文件記載，第五十三輪，2026-10-14） |
| --- | --- | --- |
| 評估集 454 題 | 引擎見過，CI 閘門 | 六指標 100% |
| 挑戰集 dev 180 題 | 換句話說，修引擎時可以看 | 97.2% |
| 挑戰集 holdout 264 題 | 換句話說，修引擎時不看明細 | 79.9% |
| 盲測題組 holdout v2 240 題 | 另一人寫、封存、含應拒答題 | **69.6%**（167/240） |

讀法：dev 97% 到盲測 70% 的落差，就是「規則是對著見過的說法修的」的證據。第五十三輪扣掉內容因素後，引擎改動在盲測上只多對 **1 題**。結論（docs/eval-challenge.md §13）：依失敗類型一類一類補規則，已經到這種做法的天花板。能對外說的數字是「盲測約七成」，不是 97%。

盲測弱項（只看分數）：

| 問法 | 通過率 |
| --- | --- |
| 錯字 | 28.6% |
| 長輩說法 | 36.4% |
| 情境題（描述狀況，不點名疾病） | 55.9% |
| 家長說法 | 60.7% |
| 越南文 | 55.6% |
| 英文 | 60% |

### 5.2 它不會做的事

- **不會推論。** 「我上週去登革熱流行區，今天發燒，是登革熱嗎？」它會給登革熱症狀與就醫建議的原句，不會說「你可能是」。這是刻意的，但使用者可能期待更多。
- **不會跨文件綜合。** 一句來自 FAQ、一句來自疾病頁，中間沒有過場。讀起來是「拼接」。LLM 模式（同事登入後的 BYOK）是為了示範解這個。
- **不懂詞典沒有的說法。** 每一個口語缺口都要有人加資料。查詢紀錄報表能幫忙找，但補不完。
- **只抓得到數字型的說法衝突。** 「建議」對「不建議」這種文字矛盾，一致性比對抓不到（第三十三輪的限制）。
- **外語內容量少。** 六種外語大多是機器初稿，`status: machine` 的不進索引；外語答不出來多半是內容沒有，不是引擎的問題。
- **結構化資料另外處理。** 疫苗時程、統計數字、通報時限表不走檢索，直接讀主檔。所以「2 歲前要打哪些疫苗」是查表，不是抽句（ask-search-llm.md §8.6）。

### 5.3 架構上的牆

- **答案頁資料預算。** 提問後下載的 JSON 現在繁中 369 KB、英文 409 KB，預算 445 KB。第五十五輪的放大實驗顯示內容到約 2 倍就撞牆（docs/ci-scaling.md）。解法是依主題分片或把引擎搬到伺服器端，不是調高預算。
- **JS 預算。** 引擎頁提問後合計 235.3 KB，預算 240 KB，只剩約 5 KB。新功能要放建置端或拆成用到才載入的分支（第四十九輪已拆 8 個）。
- **索引整份下載。** 專業版 328 KB gzip。手機第一次提問要等；第四十輪已改成聚焦輸入框才載入、依語言分片。
- **規則維護成本。** 13 種意圖、21 條拒答、44 條跨語言、18 條口語改寫、數十個面向詞組。每一條都有測試，但每多一條就多一個要維護的東西。這是「可解釋」的另一面。

### 5.4 評估本身的限制

- 盲測題組是 Claude 寫的，不是真實民眾問句。真正的基準要等試營運後的查詢紀錄（docs/ask-log.md）。
- LLM 模式沒有自動評估（要金鑰），只有抽取式有。
- 評估集 100% 是閘門不是成績：掉下去會擋合併，但不代表對未見過的問法也 100%。

## 6. 和「用 LLM 直接回答」比，為什麼公部門先選這條

| | 抽取式（本站） | LLM 直接生成 |
| --- | --- | --- |
| 會不會編造 | 不會，每句是原文 | 會，再好的模型也會偶爾改數字 |
| 錯了找得到原因嗎 | 找得到：哪一道工序、哪條規則 | 很難 |
| 內容更新多久生效 | 下次建置（分鐘） | 看快取與 RAG 設計 |
| 要不要伺服器、金鑰、對外傳送問句 | 都不要 | 都要 |
| 口語理解 | 弱，靠資料補 | 強 |
| 讀起來 | 拼接的原句 | 通順 |

本站的設計是兩者疊加而不是二選一：抽取式在前面決定「要不要答、引哪幾段」，模型（如果有）只在最後把選好的句子改寫得通順，改完還要後檢（ask-search-llm.md §3、§4）。模型永遠是改寫器，不是回答者。

## 8. 數字怎麼來的、怎麼重跑

本輪在建置機（Linux 容器，Node 22）上做：

```bash
npm ci
BASE_PATH='' BUILD_TODAY=2026-10-14 npm run build   # 答案單元數、JS 預算、資料傳輸量、Pagefind 頁數在建置輸出
BUILD_TODAY=2026-10-14 npm run eval                 # 454 題六指標
```

計時用一支臨時腳本（未進 repo）：以 `eval/run-eval.mjs` 的 `engineFromSite` 建立引擎（與瀏覽器同一份 `core.js`），對評估集前 200 題繁中問句逐題 `performance.now()`，取中位數與百分位；索引大小是把 `site.searchIndex.public` 序列化後以 gzip level 6 壓縮。要重做時照抄這幾行即可。

盲測與挑戰集的數字取自第五十三輪報告（`docs/eval-challenge.md` §11–13；原始 JSON 在專案檔案夾 `eval-challenge/`），本輪沒有重跑，因為 2026-10-14 之後引擎沒有變更（`git log --since=2026-10-14 -- src/client/answer/` 只有第五十七輪一筆，與檢索無關）。

## 9. 名詞小表

| 名詞 | 白話 |
| --- | --- |
| embedding／向量檢索 | 用模型把文字變成一串數字，比較兩串數字的距離來判斷「意思像不像」 |
| BM25 | 1990 年代的關鍵字排序公式：詞出現得多、詞罕見、文件短，分數高 |
| bigram | 把文字切成相鄰兩字一組 |
| 答案單元 | 建置時把內容切成的一段可獨立引用的文字，帶疾病、主題、單位、審閱日等欄位 |
| 詞界 | 一個名詞的邊在哪：「性病」在「急性病毒性肝炎」裡不是一個詞 |
| 相關度門檻 | 最好的答案也不夠相關時，改說「查無」的那條線 |
| 抽取式 | 答案全部是原文句子，不生成新字 |
| RAG | 先檢索、再把片段給模型、要模型只依片段作答；本站的 LLM 模式就是 |
| 評估集／挑戰集／盲測 | 見過的題、換句話說的題、完全沒見過且封存的題 |
