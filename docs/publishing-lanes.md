# 發布車道建議書：送出一次，治理在背後自動發生

> 給誰看：資訊處長、各單位主管、公關室、OASIS、資訊室，以及要決定「新官網上架流程怎麼走」的人。
> 依據：[ARCHITECTURE.md](../ARCHITECTURE.md) §6（後台）、§17（本輪契約）；規劃文件〈盤點、規格與路線圖〉§7.1（內容管理與上架流程）、§7.4（內容生命週期）、§7.7（過時資訊防治）。
> 實作位置：`content/governance/lanes.json`、`scripts/lib/lanes.mjs`、`scripts/lane.mjs`、`.github/workflows/{content-pr,preview-cleanup,lane-sla,pages}.yml`、`.github/CODEOWNERS`、後台 `/admin/publish/`。
> 一句話：**承辦人的體感跟舊後台一樣（填、貼、拖、送出），治理改由 CI 當第一位審核者；內容依風險分三條車道，低風險的事件型內容檢查通過就自動上線、上線後再複核，高風險的內容仍由人先審。**

---

## 0. 給主管的三句話

1. **承辦人不必學 Git。** 按鍵數與舊後台相同（都是 6 步，見第 11 節）；差別只在欄位有預設值、送出前就有自動檢查。分支、Pull Request、檢查、合併、部署，全部是系統的工作。
2. **不是所有內容都要等人審。** 新聞稿、致醫界通函、澄清、職缺、採購公告、宣導 Banner 走「快車道」：CI 通過就自動上線，**上線後 24 小時內由公關室複核**。疾病、疫苗、文件、Q&A 等會被 AI 引用或影響醫療行為的內容走「一般車道」：CI 通過還要 **1 位審核人核准**（SLA 2 個工作天）。疫情態勢與標了「緊急」的稿件走「緊急發布」：10 分鐘內上線並通知複核。
3. **審核的是結果，不是流程。** 預覽網址讓審核人看到的就是上線後的樣子；SLA 逾期會自動提醒；排程發布到點自動上線；每一次改動都留在 Git 歷史，可追溯、可還原。

> 這整套是「Git＋CI 取代傳統後台上架系統」：正本是 Git、合併即發布、沒有另一個 CMS。它與傳統後台的逐項比較、資訊室要維運什麼，見 [git-as-cms.md](git-as-cms.md)。

## 1. 問題陳述：直接上架的後台，抱怨在哪裡

> 說明：現行後台的實際流程與抱怨，請以資訊室與各單位承辦人的訪談為準（**待確認**）。以下是一般「後台按下送出就上線」的內容管理系統最常見的幾種問題，也是本建議書要對症處理的。

| 面向 | 直接上架的後台 | 為什麼是問題 |
| --- | --- | --- |
| 速度 | 要上線的內容常得先走紙本或電子簽核，再由資訊室代為上架 | 新聞稿、澄清稿是「當天、甚至當小時」的事；等簽核等到失去時效 |
| 檢查 | 欄位有沒有填、數字有沒有跟現行版矛盾、附件有沒有 alt，全靠人眼 | 錯誤上線後才被發現；2025 年 MMR 建議修訂後，舊新聞稿與影片仍寫舊版（本原型的 MMR 案例） |
| 風險一視同仁 | 疾病頁與一則徵才公告走一樣的流程（要嘛全審、要嘛全不審） | 全審 → 低風險內容被拖慢；全不審 → 高風險內容缺把關 |
| 追溯 | 改了什麼、誰改的、改之前是什麼，難以還原 | 對外更正、稽核、媒體質疑時說不清楚 |
| 預覽 | 預覽環境與正式環境不同，或沒有預覽 | 審核人看不到真正的樣子；上線後才發現版面破、連結壞 |
| 預定與緊急 | 預定發布要靠人到點去按；緊急發布沒有明確「快速通道」 | 半夜忘了按；緊急時大家不確定能不能跳過流程 |
| 複核 | 上線後沒有人負責回頭看 | 快速上線的內容沒有第二雙眼睛 |

## 2. 設計原則

1. **流程看不見。** 承辦人只做三件事：填對欄位、寫內文、加附件，然後按送出。分支、PR、檢查、合併、部署由系統代做（後台 `/admin/publish/` 的「模擬送出」把這些步驟攤開給你看，正式環境承辦人看不到也不用管）。
2. **CI 當審核者。** 機器能判斷的，就不要讓人審：schema 與跨檔參照、治理規則（逾期、版本鏈、白名單、反向稽核）、評估集版本題、檔案資產（存在、雜湊、alt、授權）、連結。人只審機器不能判斷的：措辭、事實、立場。設定檔中以 `rules.ciIsTheReviewer: true` 明示。
3. **分車道。** 依「錯了的代價」和「是否被 AI 引用、影響醫療行為」分三條車道（第 3 節），而不是依單位或職級。一個 PR 同時含多種型別時，**取最嚴格的車道**（一般 ＞ 快 ＞ 緊急）；程式、文件、設定等非內容變更一律走一般車道。
4. **多語不擋中文。** 翻譯還沒審完，不能卡住中文正本上線。規則：`rules.translationsNeverBlock: true`；一級內容（疾病、疫苗、澄清、態勢）未審核的語言頁本來就不渲染，二級內容（新聞稿、Q&A、專區、申請服務）可先以機器翻譯上線並標示。
5. **上線後仍有人看。** 快車道與緊急發布的內容上線後自動產生「上線後複核」待辦（第 7 節），不是上線就沒事。

## 3. 車道表

車道設定在 `content/governance/lanes.json`（單一事實來源，CI、治理引擎、後台都讀它）。

| | 緊急發布 | 快車道 | 一般車道 |
| --- | --- | --- | --- |
| 內容型別 | 疫情態勢（`situation`）；以及標了 `urgent: true` 的新聞稿、致醫界通函、澄清 | 新聞稿、致醫界通函、澄清、人才招募（`job`）、採購公告（`tender`）、宣導 Banner | 疾病、疫苗、文件、Q&A、專區、申請服務、一般頁面、出版品、檢驗項目、研究計畫、資料集、影音、移轉清單 |
| 自動合併 | 是 | 是 | **否** |
| 需要的人工核准 | 0 位 | 0 位 | **1 位** |
| 審核人 | —（上線後由公關室複核） | —（上線後由公關室複核） | 公關室；**一級內容（疾病、疫苗）：公關室＋OASIS** |
| SLA | 10 分鐘（目標上線時間） | 180 分鐘（PR 開啟後仍未合併就提醒） | 2 個工作天 |
| 上線後複核 | 24 小時內，公關室 | 24 小時內，公關室 | 不需要（已事先審核） |
| 典型例子 | 登革熱本土病例澄清稿、重大疫情通函 | 例行新聞稿、徵才公告 | 疾病頁改版、MMR 建議新版、Q&A 修訂 |
| 為什麼這樣分 | 時效就是一切；錯了要能立刻更正 | 事件型內容、時效高、不是 AI 白名單的核心根據；錯了可以快速更正 | 疾病、疫苗、文件與 Q&A 是 AI 答案的根據，錯了會擴散到每一次問答 |

> 型別與車道的對應如有調整，**只改 `lanes.json`**，不要改程式。調整需經資料治理委員會議定（見第 8 節）。

### 3.1 哪些內容不可以標緊急

`urgent` 只能用於 `news`、`letter`、`clarification`（`lanes.json` 的 `rules.urgentAllowedTypes`）。理由：疾病、疫苗、文件、Q&A 會被 AI 引用，不能跳過人工審核；疫情態勢本來就走緊急車道，不需要再標。違反時：後台預檢直接擋下、schema 驗證失敗（CI 也擋）。

## 4. 時程：「送出到上線 3 分鐘」是怎麼算出來的

以快車道為例（預估值，**實測數字見附錄 B**）。T＝承辦人按下送出的時間。

| 時間 | 發生什麼 | 說明 |
| --- | --- | --- |
| T+0:05 | 建立分支 `content/{id}` | 把上架包（JSON 與附件）commit 上去 |
| T+0:10 | 開 Pull Request | 標題帶內容 id 與標題；CI 啟動 |
| T+0:10–1:40 | CI 檢查（約 90 秒） | `npm ci`（有快取）→ `npm test` → `node scripts/build.mjs --check`（schema、治理、評估集、資產）→ `node scripts/lane.mjs`（車道判定）→ 以 PR 專屬 `BASE_PATH` 建置預覽（含連結檢查）並推到 `previews` 分支 |
| T+1:45 | 車道判定、PR 留言與標籤 | 留言內容：車道、檢查摘要、預覽網址、SLA 到期時間、需要誰審；加標籤 `lane:fast` |
| T+1:50 | 自動合併 | 檢查全過 ⇒ `gh pr merge --squash --delete-branch`，並觸發 `pages.yml` |
| T+1:50–3:20 | `pages.yml` 建置與部署（約 90 秒） | 建置（把 `previews` 分支複製到 `dist/preview/`）、上傳、部署 Pages |
| **T+3:20** | **上線，預覽網址同時可開** | 約 3 分鐘。預覽與正式內容在同一次部署出現 |

一般車道在 T+1:45 之後**停下來等人**：CI 在 T+1:40 推完預覽，隨即觸發一次主站部署，預覽網址約在 **T+3:10** 打得開；審核人看預覽、按核准（`pull_request_review` 事件會讓工作流程重跑一次），核准與檢查都過就合併，再部署約 90 秒上線。排程發布（第 6 節）則在合併後等到時間點之後的下一次建置。

## 5. 預覽網址

每個 PR 都有自己的預覽：`https://ancientsky.github.io/new_cdc_prototype/preview/pr-{N}/`，{N} 是 PR 編號。

- **做法**：CI 以 `BASE_PATH=/new_cdc_prototype/preview/pr-{N}` 建置整站，把 `dist/` 推到 `previews` 分支的 `pr-{N}/` 目錄；主站部署時把 `previews` 分支內容複製到 `dist/preview/`。
- **用途**：審核人看的就是上線後的樣子（版面、連結、附件、圖片、多語頁）；承辦人合併前自己再看一次。
- **何時打得開**：CI 推完預覽後要等主站重新部署一次，約 T+3 分鐘（PR 留言寫「主站重新部署後約 2–3 分鐘可開」）。
- **清除**：PR 關閉 → `preview-cleanup.yml` 刪除該目錄並重新部署主站。**由工作流程自動合併的 PR 不會觸發 `closed` 事件**（GitHub 對 `GITHUB_TOKEN` 動作的規則），所以另有每日排程（01:41 UTC）掃描 `previews` 分支，PR 已不是開啟狀態的目錄一併清掉；實務上自動合併的預覽最多多留一天。
- **限制（重要）**：預覽目錄是**公開的**。原型放在 GitHub Pages，預覽網址知道的人都打得開，內容在核准前就等於已經對外。**正式環境的預覽必須放在內網或加上存取控制**（第 12 節風險）。預覽頁面都帶 `noindex`，且網址不出現在任何站內連結。

## 6. 預定發布與緊急發布

### 6.1 預定發布（`publishAt`）

- 後台「發布時間」欄位：選一個**臺北時間**的日期時間，匯出的 JSON 帶 `publishAt: "2026-10-05T09:00:00+08:00"`。留空＝合併後立即上線。
- **到點前**：PR 照常檢查、審核、合併；但內容**不渲染、不進搜尋索引、sitemap、API、RSS、`llms.txt`**，AI 也不會引用；狀態標為「排程中」。
- **到點後**：主站每 2 小時重建一次（`pages.yml` 排程），所以**實際上線時間會比 `publishAt` 晚 0–2 小時**。需要準時（例如 09:00 記者會同步發稿）時，請將 `publishAt` 設在目標時間**前 2 小時**，或改用快車道當場送出。這是原型的限制；正式環境可改用精準排程（在 `publishAt` 觸發一次部署）。
- **判斷基準**：`publishAt` 以建置當下的**真實時間**判斷，不受 `BUILD_TODAY` 影響（`BUILD_TODAY` 只用來凍結治理日期，供測試與示範）。
- **預檢**：`publishAt` 必須晚於現在，否則後台擋下。

### 6.2 緊急發布（`urgent`）

- 只對新聞稿、致醫界通函、澄清顯示「緊急發布：立即上線並通知複核」勾選框。
- 勾選後走緊急車道：檢查通過即自動合併上線（目標 10 分鐘內），並通知公關室複核（24 小時內）。
- **不是跳過檢查。** CI 一樣要全過；schema 錯、資產缺漏的緊急稿一樣上不了線。緊急車道省的是人工審核的等待時間，不是機器檢查。
- **可稽核。** 每一則緊急發布都會在後台待辦（`post-publish-review`）留下紀錄，濫用會被看見（第 12 節）；建議把使用次數納入季報。
- 緊急與排程不併用（立即上線與排程互相矛盾，後台會警告）。

## 7. 上線後複核怎麼做

快車道與緊急發布的內容上線後，治理引擎自動產生待辦 `post-publish-review`：

| 項目 | 規則 |
| --- | --- |
| 誰 | owner 為公關室，抄送原內容的權責單位 |
| 期限 | 上線時間（`publishAt` 或 `publishedAt`）＋ `postPublishReviewHours`（24 小時） |
| 優先度 | 中；超過期限升為高、標逾期 |
| 看什麼 | 措辭與語氣、事實是否與正本一致（`basedOn`）、數字、附件與圖片、機器翻譯的品質 |
| 完成 | 在內容 JSON 加 `postPublishReview: { status: "done", reviewedBy, reviewedAt }`，走快車道合併即可 |
| 發現問題 | 小錯直接改（仍走原車道）；嚴重錯誤把 `status` 改為 `archived` 下架，並依 [guide-staff.md](guide-staff.md) 第 6 節處理對外更正 |
| 不追溯 | `lanes.json` 的 `rules.postPublishReviewSince` 之前發布的舊內容，不會被補開待辦 |

## 8. CODEOWNERS 與審核權限

- `.github/CODEOWNERS` 把路徑對應到審核單位：`content/diseases/**`、`content/vaccines/**`、`content/documents/**`、`content/faq/**` → 公關室＋OASIS；其餘內容目錄 → 各權責單位。GitHub 的 CODEOWNERS 只認帳號與團隊，**原型沒有團隊**，帳號一律用倉庫擁有者示範，單位對應以註解標示（`lanes.json` 的 `reviewerAccounts` 同理）。
- 一般車道的核准檢查：CI 以 `gh pr view --json reviews` 確認有核准且檢查通過才合併，否則在 PR 留言說明還缺什麼。
- **正式環境要做的事**：建立單位對應的團隊或群組；分支保護（`main` 禁止直接 push、必須通過 CI；**不要**設原生的「合併前需 N 位核准」，它會擋下快車道的自動合併——核准人數交給車道機器人判斷，或用規則集讓機器人帳號繞過並留紀錄，見 [deploy.md](deploy.md)）；管理員繞過規則要留紀錄；審核人名單由資料治理委員會核定，異動走 `lanes.json` 的 PR（自己受車道規範）。
- 調整車道（把某型別從一般車道移到快車道，或反之）：**一律走一般車道的 PR 並經委員會議定**，因為 `content/governance/` 本身就是治理設定。

## 9. SLA 逾期處理

- **一般車道**：PR 開啟後超過 2 個工作天仍未合併 ⇒ `lane-sla.yml`（每小時）在 PR 留言並加 `sla:breach` 標籤（每個 PR 只提醒一次），提醒審核人；建議每週一的待辦檢視一併看帶 `sla:breach` 標籤的 PR。連續逾期由單位主管處理，不會自動改車道。
- **快車道／緊急發布**：PR 開啟超過 SLA（180 分鐘／10 分鐘）仍未合併，代表 CI 失敗或卡住 ⇒ 同樣留言加標籤；承辦人看 PR 留言修正，無法自行處理時找資訊室。
- 這是 CI 在 PR 上的動作，**不是**建置待辦（`lane-sla-breach` 不會出現在 `/admin/todos/`）；逾期的**上線後複核**才是建置待辦（第 7 節）。
- 工作天以週一至週五計，原型不處理國定假日（正式環境需接行事曆）。

## 10. 試行計畫

| 項目 | 建議 |
| --- | --- |
| 單位 | **兩個**：公關室（新聞稿、澄清，走快車道）與一個業務組，例如急性傳染病組（Q&A、疾病頁，走一般車道）。兩種車道都要有人用，才看得出差別 |
| 期間 | **兩個月**（含至少一次需要緊急發布的真實或演練事件；沒有真實事件就做演練） |
| 前置 | 核定 `lanes.json`；建立審核團隊；分支保護；承辦人 30 分鐘教育訓練（講義：[guide-staff.md](guide-staff.md) 第 2 節）；預覽網址的存取控制方案定案 |
| 量什麼 | 見下表 |

| 指標 | 怎麼量 | 建議目標（試行後由委員會核定，非實測） |
| --- | --- | --- |
| 送出到上線時間（快車道） | PR 開啟到 `pages.yml` 部署完成；中位數與 P90 | 中位數 ≤ 5 分鐘、P90 ≤ 10 分鐘 |
| 一般車道等待時間 | PR 開啟到核准 | 90% 在 2 個工作天內 |
| CI 一次通過率 | 第一次推送就全過的 PR 比例 | ≥ 70%（低於此表示欄位預設或預檢要改善） |
| 退回與修正次數 | 每個 PR 的 CI 失敗次數、審核人要求修改次數 | 追蹤，不設目標 |
| 上線後複核完成率與發現率 | `post-publish-review` 在期限內完成的比例；複核後需要修改的比例 | 完成率 100%；修改率追蹤（過高表示快車道範圍太大） |
| 緊急發布使用次數 | 帶 `urgent: true` 的內容數 | 追蹤；每次都在季報說明理由 |
| 承辦人感受 | 試行結束問卷：按鍵數、等待、看不懂的訊息 | 滿意度 ≥ 4/5 |
| 預覽網址使用率 | 審核人實際開預覽的比例（PR 留言互動） | 追蹤 |

試行結束後的決策點：快車道範圍要不要擴大或縮小、一般車道的 SLA 是否合理、預覽網址的存取控制是否到位、哪些 CI 錯誤訊息要改寫成承辦人看得懂的話。

## 11. 溝通要點：按鍵數對照表

對承辦人最重要的一句話：**你要做的事沒有變多。**

| 步 | 舊後台（直接上架） | 新流程（正式環境） | 差別在哪裡 |
| --- | --- | --- | --- |
| 1 | 登入 | 登入 | 相同 |
| 2 | 選欄目 | 選型別 | 新流程選完型別，**權責單位、審閱週期、對象、提供語言、車道**都帶好預設值；舊後台這些要自己記得填，或根本沒有欄位 |
| 3 | 填標題 | 填標題 | 相同；新流程會自動建議內容 ID |
| 4 | 貼內文 | 貼內文 | 新流程可直接貼 Word（自動清理格式），存成 Markdown；**貼完立刻看到自動檢查**：關鍵字與主檔對應、摘要、數字是否與現行版矛盾 |
| 5 | 上傳附件 | 拖附件 | 新流程當場檢查檔名、大小、格式、圖片 alt 與授權、PDF 文字層；錯了在送出前就看到 |
| 6 | 送出 | 送出 | 舊後台：送出後進簽核或直接上線，結果只有「成功」。新流程：送出後系統自動開 PR、跑五項檢查、判定車道；**快車道約 3 分鐘上線，一般車道通知審核人**；PR 留言告訴你狀態與預覽網址 |
| 合計 | **6 步** | **6 步** | 步數相同，差別在預設值與自動檢查 |

> **誠實說明原型與正式環境的差別。** 在這個原型裡，承辦人要多做兩個動作：按「產生上架包」下載 ZIP，再把 ZIP 交給資訊室或自己開 PR（原型沒有後端，不能代開）。正式環境會有後端或表單服務代做這一步，才是上表的「6 步」。後台的「模擬送出」就是在展示這一段「承辦人看不到、系統代做」的事。

對審核人的一句話：**你不用再檢查機器已經檢查過的東西**（欄位、格式、連結、數字矛盾），只看措辭與事實，而且有預覽網址可以看。

對主管的一句話：**風險沒有變高，只是移到上線後複核與自動稽核。**事件型內容快速上線，高風險內容仍由人先審。

## 12. 風險與對策

| 風險 | 嚴重度 | 對策 |
| --- | --- | --- |
| 快車道內容上線後才發現錯誤 | 中 | 範圍限事件型內容；`basedOn` 連動：依據正本修訂會自動加註並開待辦；24 小時內複核；錯誤可立即下架或更正（Git 歷史可還原）；複核發現率納入試行指標，過高就縮小快車道 |
| 緊急發布被濫用 | 中 | 只限三種型別；CI 仍要全過；每次使用都留下 `post-publish-review` 待辦；試行期統計使用次數，建議納入季報；濫用由單位主管處理 |
| 帳號被盜、有人冒名送出 | 高 | 倉庫帳號強制雙因素；分支保護；管理員繞過留紀錄；快車道內容上線後仍有複核；機關正式環境另需身分驗證與簽章 |
| 預覽網址公開，未審核內容被看到 | 高 | 原型放在公開的 GitHub Pages，**只能示範**；正式環境預覽必須放內網或加存取控制；預覽頁帶 `noindex` |
| CI 抓不到措辭或事實錯誤 | 中 | 這正是「人只審機器不能判斷的」；一般車道仍需人審；快車道靠上線後複核與正本連動 |
| 承辦人不會 Git | 中 | 後台產生上架包並（正式環境）代開 PR；不要求承辦人用 Git；資訊室與 OASIS 代開 PR 作為過渡 |
| 排程發布比預定時間晚最多 2 小時 | 低 | 文件與後台明示；準時需求設前 2 小時或當場送出；正式環境改精準排程 |
| 單一平台依賴（GitHub） | 中 | 原型用 GitHub Actions 示範；機關環境需改為機關可控的等價平台（自架 Git 服務與 CI）；流程與設定檔（`lanes.json`、`scripts/lane.mjs`）與平台無關，只有 workflow 檔需要改寫 |
| 多人同時改同一檔案衝突 | 低 | 內容一筆一檔，衝突少；衝突時 PR 無法自動合併，會留言要求承辦人更新 |
| 自動合併的權限過大 | 中 | 自動合併只在 `lanes.json` 允許的車道、且檢查全過時由工作流程執行；`content/governance/`、`scripts/`、`.github/` 等非內容變更一律走一般車道 |
| 時區誤解 | 低 | 後台以臺北時間輸入並輸出 `+08:00`；`lanes.json` 的 `rules.timezone` 為 `Asia/Taipei` |

## 附錄 A：GitHub 上實際跑的工作流程

> 以下以 ARCHITECTURE §17.2 為準。檔案名稱、步驟名稱與數字若與 `.github/workflows/` 不一致，**以實際檔案為準**（整合者校對）。

| 檔案 | 觸發 | 做什麼 |
| --- | --- | --- |
| `content-pr.yml` | `pull_request`（開啟、更新、重新開啟）；`pull_request_review`（提交審核後重跑，讓一般車道核准即合併） | checkout → `npm ci` → `npm test` → `node scripts/build.mjs --check` → `node scripts/lane.mjs`（改動檔案取自 `git diff --name-only origin/main...HEAD`）→ 以 `BASE_PATH=/new_cdc_prototype/preview/pr-{N}` 建置預覽 → 推到 `previews` 分支的 `pr-{N}/`（只保留一個快照提交，避免歷史累積）→ 決定動作（檢查未過＝不合併；自動合併車道＝合併；一般車道＝每位審核人最新一則為 APPROVED 的人數 ≥ 需求才合併）→ 在 PR 留言（或更新同一則）並加標籤 `lane:fast`／`lane:standard`／`lane:emergency` → `gh pr merge --squash --delete-branch` → 觸發 `pages.yml` 重新部署。分叉來的 PR 拿不到寫入權杖，只跑檢查 |
| `preview-cleanup.yml` | PR 關閉；每日 01:41 UTC 排程；手動 | 刪除 `previews/pr-{N}/`（排程時掃描所有已非開啟狀態的 PR），觸發主站重新部署 |
| `lane-sla.yml` | 每小時（:23） | 依 `lane:*` 標籤與建立時間找出開啟超過 SLA 的 PR，留言並加 `sla:breach`（每個 PR 只留一次言） |
| `pages.yml` | push main、每 2 小時排程（偶數整點）、手動 | `npm ci` → `npm test` → 重抓官方資料並把快照 commit 回 main（**只在 02:00 UTC 那一次排程與手動執行時**；`content-pr.yml` 觸發的部署傳 `refresh=false` 不重抓）→ 取出 `previews` 分支 → `npm run build`（複製到 `dist/preview/`）→ 部署 Pages |

**車道判定**（`scripts/lane.mjs`）：輸入變更檔案清單，輸出 JSON（`lane`、`autoMerge`、`requiredApprovals`、`reviewers`、`sla`、`files[]` 每檔的型別與車道、`reasons[]`）。多檔取最嚴格；`content/` 以外的檔案視為一般車道。單檔也可本機試：

```bash
node scripts/lane.mjs content/news/news.2026-09-21-flu-antiviral-revised.json
```

## 附錄 C：後台怎麼體驗

1. 開 `/admin/publish/`，型別選「新聞稿」：欄位下方出現**快車道**徽章與「送出後約 3 分鐘上線，公關室 24 小時內複核」。改選「疾病頁」：徽章變**一般車道**，說明變成「需 1 位審核（公關室、OASIS），SLA 2 個工作天」。
2. 新聞稿會出現「緊急發布」勾選框；勾選後徽章變**緊急發布**。選「Q&A」時沒有這個勾選框。
3. 「發布時間」填一個已經過去的時間，預檢會標紅並擋下「確認並送複核」；換成不允許緊急的型別（例如 Q&A）時，已勾的「緊急發布」會自動取消並說明原因。
4. 填好內文按「送出預處理」，到最下面 (g) 區按「模擬送出」：看到建立分支 → 開 PR → CI 檢查 → 車道判定 → 自動合併或等待審核 → 部署 → 預覽網址 → 上線後複核的時間軸。每一步都註明「正式環境由系統代做」。故意留空必填欄位再按一次，會看到 CI 檢查那一步標紅、後面各步「未執行」。
5. 模擬送出**不呼叫任何 API、不開 PR**；要真的交件請用 ZIP（[guide-staff.md](guide-staff.md) 第 2.6 節）。
