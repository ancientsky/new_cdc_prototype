## 0. 一頁摘要

**結論：架構方向正確、落實程度高，主要風險不在設計而在「可接手性」。** 70 輪累積出 3,308 頁、20 種內容型別、106 個測試檔、39 份文件；治理規則由建置計算、答案引擎只轉述不創作、同事不碰 Git 這三條主軸都已經做成可以動的東西，而且 axe 在 21 個代表頁 × 兩種螢幕全部 0 項違規。接手的人會卡在三個地方：文件按「輪次」而不是按「現況」組織、CSS 與測試檔沒有像 JS 一樣的預算與命名規則、前端資產沒有版本雜湊。

介面上，設計系統一致、三層露出與答案頁是亮點；要改的集中在「手機第一屏被站台外框吃掉三分之一」「鍵盤使用者要經過 22 個 Tab 停留點才到主選單」「傳染病索引與旅遊頁把專業分類與大量小字塞給一般民眾」。

| 面向 | 評價 | 一句話 |
| --- | --- | --- |
| 內容模型與治理 | 穩 | 欄位即治理、建置即驗證，這是整個原型最有價值的部分，不要動 |

## 1. 檢視方法

- **建置**：`npm run build` 在乾淨環境跑一次，記錄輸出數字（3,777 頁、201 MB、JS 預算、連結檢查）。
- **走查**：用 Playwright 在 1280×900 與 390×844 兩種視窗對 26 個頁面截圖（首頁、問答、索引頁、疾病頁、疫苗、旅遊、疫情、新聞、搜尋、謠言、資料、互動、專業版、英文與越南文首頁、404、後台登入等），另外截了手機選單展開、桌機面板展開、拒答卡等互動狀態。
- **量測**：每頁跑 axe（WCAG 2.0/2.1 AA＋best-practice）、數可見的標題層級跳層、連結數、頁尾與頁首連結數、小於 24 px 與小於 44 px 的可點目標、字級小於 14 px 與 12 px 的文字節點、沒有寬高的圖片、重複 id、鍵盤 Tab 停留順序。
- **CSS 使用率**：Chromium coverage 在 18 個頁面取聯集。
- **程式與文件**：目錄與行數統計、模組匯出數、測試命名、文件組織方式。
- **沒做**：Lighthouse、弱點掃描、Node 升級，這三項在平行的三個檢視裡。

數字都在本文件對應小節；截圖留在專案共用檔案 `review-r71/`。

## 2. 架構檢視

### 2.1 整體：一份內容、多個消費者

原型的核心是「`content/` 只存一份，HTML、`v1/` API、`.md` 機讀版、問答索引、治理儀表板全部由 `npm run build` 算出來」。檢視後確認這條線沒有被 70 輪的功能稀釋：

- 20 種內容型別、27 份 JSON Schema，共用欄位集中在 `_common.json`，新型別（`interactive`、`theme`、`article`）都是「多一個 schema、多一個模板」，沒有旁路。
- 治理規則 31 條全部在 `scripts/lib/governance.mjs` 計算，前台只讀 `item.gov`；KPI、待辦、白名單資格都不是人手填的。
- 寫入只有一條路：後台 → 寫入閘道 → Git PR → CI → 合併即發布。後台沒有自己的資料庫。

**這部分的建議是「不要動」。** 接下來任何「加個小後端存一下」的提案，都應該先回到 ARCHITECTURE §0 的三句話。

### 2.2 內容模型

| 觀察 | 數字 | 判斷 |
| --- | --- | --- |
| 型別數 | 20 型別、340 筆已發布內容 | 合理。型別是依「治理規則不同」切的，不是依版面 |
| `page` 型別 | 27 筆 | 是「其他」籃子，目前裝政策頁、制度頁、首長簡介。可以接受，但要在 guide-staff 寫清楚「什麼時候該開新型別、什麼時候用 page」，否則廠商接手會把所有東西塞進 page |
| 共同欄位 | 必填 9 個 | 新同事第一次上架會覺得多；後台已經用預設值與推導清單降低負擔，這是對的做法 |
| 版本 | 文件版本是獨立檔＋`family` | 正確：版本鏈、失效、301 都由此推導 |

### 2.3 建置流程

- 單一程序 43 秒產 3,777 頁；Pagefind 索引 13 秒；連結檢查 454,440 個連結 3 秒。線性（約 18 ms／頁，第五十五輪實測），內容十倍仍在 CI 可接受範圍。
- **守門已有**：schema、跨檔參照、治理、評估集版本題、連結與錨點、外語頁中文比例、JS 預算（公開頁 120 KB、答案頁 240 KB）、產物曝險稽核。
- **守門缺口**：**沒有 CSS 預算**，也沒有「每頁 HTML 大小」預算。JS 有預算所以第三十四輪被迫拆檔；CSS 沒有，所以 `components.css` 從第一輪長到 116 KB 沒有人注意。本輪補一個測試（見 4.4）。

### 2.4 前端資產：CSS 與快取

這是架構面最具體的問題，也是效能檢視那邊會看到的根因之一。

| 量測 | 結果 |
| --- | --- |
| 每頁載入的 CSS | `tokens.css` 2.7 KB、`base.css` 14 KB、`components.css` 116 KB（gzip 24.5 KB），未壓縮、未合併 |
| `components.css` 使用率 | 18 個主要頁面**聯集**只用到 39%；單一頁面用 10–13%（首頁 13%、疾病頁 10%、新聞 2%） |
| 斷點 | 主要有 640、720、760、900、959、1100 px 六種，另有 380、480、520、600、860 零星出現，共 11 個值，寫法不一（`max-width:760px` 與 `max-width: 760px` 並存） |
| 檔名 | `assets/styles/components.css`、`assets/js/ui.js` 固定檔名，**沒有內容雜湊** |
| 字級 token | `--fs-xs` = 0.78 rem ≈ 12.5 px，在 134 條規則裡使用 |

**為什麼有問題**

1. 61% 的 CSS 沒有任何主要頁面用到，多半是只在一兩個專頁出現的元件（旅遊、疫苗時程、國際合作、互動），卻讓每一頁都付這筆成本。同日的效能檢視（第七十二輪，`docs/performance-lighthouse.md`）量到同一件事（單頁約 85–90% 未用），他們的決定是**不拆現有的 `components.css`，理由是全站共用一份、回訪者有快取**，並在建置時壓縮它。本檢視同意「這一輪不拆」，但補一條往前看的規則：**凍結大小、新元件只給一個專區用時另開檔**，由模板的 `styles[]` 帶入——這個機制現在就有（`answer.css`、`careers.css`、`search.css` 已經這樣做），缺的只是規則與預算（4.6）。兩份文件不矛盾：一個講現況怎麼處理，一個講之後怎麼不再長胖。
2. 檔名沒有雜湊，部署後若 CDN 或瀏覽器留著舊的 CSS/JS，新的 HTML 配舊的樣式與腳本會出現「版面壞掉幾分鐘」。GitHub Pages 的 `max-age=600` 讓這件事在原型上不明顯，正式站放到 Azure Front Door 後就會明顯（`docs/deploy.md` 對 Pagefind 已經寫了同樣的教訓，但對自家資產沒有）。第七十二輪的處理是**暫不做檔名雜湊，先在 `headers/` 對 `assets/**` 用 1 小時 `stale-while-revalidate`**；本檢視同意這是正確的過渡做法，但要記清楚它只縮短不一致的時間、不消除它，**內容雜湊仍是正解**，應獨立一輪做（見 5.1）。
3. 十一種斷點沒有一個共同來源。不是每個都要統一，但應該收斂成 token 註解表（例如 640 手機、960 平板、1100 寬版），讓新元件照表挑。

### 2.5 程式結構

| 檔案 | 大小 | 觀察 |
| --- | --- | --- |
| `src/templates/public/_partials.mjs` | 938 行、72 個匯出函式 | 已經是「什麼都放」的工具箱。頁首、來歷條、卡片、分頁、日期、單位名、Banner、警示都在這。沒有壞，但新同事找不到東西 |
| `scripts/lib/governance.mjs` | 1,632 行、29 個函式 | 31 條規則在同一檔。每條規則都有測試，所以安全；要改的是在檔頭放一張「規則編號 → 函式 → 測試」對照表 |
| `src/client/i18n.js` | 478 KB、1,519 個鍵、七語同一檔 | 建置時已拆成每語 14–21 KB，執行期沒問題；但原始檔是七語並排的 JS 物件，翻譯人員無法用一般工具處理。長期應轉為每語一個 JSON＋缺鍵檢查，這會動到所有模板的 `t()`，列為下一輪 |
| `tests/` | 106 個檔，其中 71 個以 `roundNN-` 命名 | 檔名說的是「哪一輪寫的」，不是「測什麼」。要找「疫苗時程的測試在哪」得 grep。見 4.5 |
| `src/client/admin/` | 697 KB 原始碼 | 後台是原型最大的程式體，但只給同事用、不計入公開頁預算，合理 |

### 2.6 文件體系（接手的最大風險）

- `ARCHITECTURE.md` 2,780 行，§0–§10 是契約，§11–§71 是 61 個「第 N 輪」的時間序章節。**沒有一張「現在的系統長什麼樣」的地圖**：要知道「後台登入目前怎麼運作」，得知道它在第十八輪、第二十三輪、第六十三輪各改了一次，然後讀三節。
- `README.md` 同樣按輪次排，最新的在上面，第一次讀的人看不出主線。
- `docs/architecture-decisions.md` 55 條決策，這份組織得好，是真正的 ADR。
- `docs/` 39 份文件沒有索引頁；`guide-staff.md` 2,781 行、`deploy.md` 2,222 行。
- 文件品質本身高，每一輪都把「為什麼」寫進去了，這是這個專案的強項；問題只在**入口**與**現況視角**。

**做法（本輪實作，見 4.6）**：ARCHITECTURE 頂部加「現況地圖」一節，按子系統列「現在的規則在哪一節、程式在哪、測試在哪、最後一次改是第幾輪」；`docs/README.md` 給 39 份文件分組索引；輪次章節保留，但在地圖裡降格為「變更紀錄」。這比把 2,780 行重寫一遍好，因為輪次章節是決策當時的脈絡，刪了反而丟掉「為什麼」。

### 2.7 治理數字在公開示範站的讀法

`/admin/` 與 `/transparency/` 的 KPI 來自建置計算，部分數字在凍結示範日（`BUILD_TODAY=2026-10-01`，Yulun 決定維持）下會一直是紅的：

| KPI | 目前值 | 原因 |
| --- | --- | --- |
| 資料集在更新頻率內更新 | 27.6% | 快照是 9 月抓的，示範站不再重抓 |
| 態勢層資料延遲 | 52 日 | 同上 |
| 一級內容七語涵蓋（人工複核） | 0% | 原型沒有真正的譯審 |
| 待辦 | 166 筆，其中 80 筆是移轉待確認 | 示範資料 |

這些數字**是治理引擎正確運作的證據**，但第一次看到的主管會以為系統壞了。建議在儀表板加一行「示範站凍結於 2026-10-01，以下為當日計算」（本輪實作，4.7）。

### 2.8 與平行檢視的交界（只點到為止）

- **Node.js 26**：`package.json` 的 `engines` 是 `>=22`，程式零框架、只用 `node:test`，升級風險主要在 Playwright 與 esbuild 二進位，由該檢視處理。
- **資安**：本檢視沒有看到新的攻擊面；2.4 的資產雜湊會順帶讓 CSP `script-src` 從 11 段 inline 雜湊減少。
- **效能**：2.4 的 CSS 使用率與 2.5 的 i18n 檔是效能檢視會看到的兩個 LCP／TBT 來源，根因在這裡，修法在那邊。

## 3. UI/UX 檢視

### 3.1 做得好的地方（確認保留）

這些是前幾輪已經做過決定、本輪走查後確認方向正確的，列出來是避免下一個人「順手改掉」：

- **情境式首屏**：流感高峰時首屏就是「現在該做什麼」加一個提問框，不是輪播圖。這比現行官網的 Banner 牆直接回答民眾來的目的。
- **三層露出**：每頁一行「權責 · 最後審閱」、狀況警示、按需展開的來源卡。民眾不覺得吵，專業版展開就有完整版次。
- **答案頁**：每句附來源編號、拒答卡講清楚為什麼不答並給 1922、稽核編號、回報鈕。這是全站最成熟的頁面。
- **404 頁**：把錯誤變成提問框與「舊網址查詢」，是少見的好設計。
- **點開式面板選單、不用 hover mega menu**（第四十七輪）、**四欄頁尾、首頁不放「更多服務」**（第十七輪）、**手機底部四鍵**、**研究與媒體入口而非開發者文件**（第六十一輪）、**互動模組集中在 /play/**（第六十二輪）：全部維持。
- **無障礙**：21 頁 × 2 視窗 axe 0 違規；每頁一個可見 h1、無標題跳層、無重複 id、所有圖片有寬高、放大 200% 不橫向捲動。
- **系統字型、SVG 圖示內嵌、不載入第三方字型與框架**：手機第一次載入沒有外部請求。

## 4. 本輪實作的項目與理由

每一項都寫「改了什麼」「為什麼這樣比較好」「怎麼驗證」。程式由 Opus 5.5 工作者實作，本執行緒監工驗收：建置、既有 106 個測試檔、axe、截圖比對。

### 4.1 手機首屏外框（U1、U9、U10）

- 原型橫幅：手機版（≤ 640 px）標籤、說明、連結排成兩行；橫幅文字加「示範資料凍結於 {日期}」。正式模式本來就不輸出，不受影響。
- 「原型預覽：目前為做法 B」列：只在網址帶 `?hero=` 時由 ui.js 顯示；預設 `hidden`。同事要切換仍可從 `/guide/` 或直接加參數。
- **為什麼**：手機第一屏是民眾最常見的入口，站台外框每少 1 行，「現在該做什麼」就早 1 行出現；開發者用的預覽列不該常駐在民眾頁。

### 4.2 鍵盤捷徑（U2）

- `layout.mjs` 在既有「跳到主要內容」後加第二個 skip link「跳到主選單」（`#main-nav`，七語字串），並讓 `#main-nav` 可聚焦（`tabindex="-1"`）。
- **為什麼**：不改視覺、不改語言列設計，一個停留點就把 22 次 Tab 縮成 2 次；這是 WCAG 2.4.1 的標準做法，也不排除之後再折疊桌機語言列。

### 4.3 首頁影音卡（U3）

- `media` 內容沒有縮圖時，首頁影音卡改為文字卡（標題、時長、依據正本），不再輸出灰底佔位。
- **為什麼**：佔位圖在示範時被當成「圖壞了」；文字卡仍保留影片的主要資訊與連結。

### 4.4 傳染病索引（U4）

- 預設第一個分頁改為「有完整疾病頁」：先列 16 個有頁的疾病（含最後審閱日與現在疫情狀態），再列「其他法定傳染病」收合區。法定類別、傳播途徑、筆畫、注音四個分頁保留；專業版（`data-view=pro`）預設落在法定類別。
- 列高與點擊目標至少 44 px；「尚無獨立頁面」改為小字說明，整列可點到「問問看」。
- **為什麼**：民眾查疾病的起點是「我聽過的那個病」，不是通報分類；把有內容的放前面、沒內容的收合，不丟資訊也不誤導。

### 4.5 旅遊頁 chip（U5）

- `.tv-chip` 內距 8×14 px、字級 `--fs-sm`，最小高度 44 px（手機）；等級表內的疾病分段維持。
- **為什麼**：目標尺寸是新版無障礙規範 2.5.8 的要求（24 px 最低，44 px 建議）；旅遊頁是全站可點目標最密的頁。

### 4.6 字級下限（U6）與 CSS 預算（2.3）

- `--fs-xs` 由 0.78 rem 改為 0.8125 rem（13 px）；專業版小於 12 px 的 6 處改用 token。
- 新增 `tests/css-budget.test.mjs`：`components.css` 不得超過 120 KB（本輪改完 121.3 KB，上限 122,880 bytes，與 JS 預算同一精神：先凍結，再逐輪拆——下一個要加樣式的人會先碰到這條線，這是刻意的）；斷點只能用測試裡白名單的 11 個值，其中 380、480、520、600、860 標為優先收斂對象；`font-size` 不得出現小於 13 px 的硬編碼，疫苗時程圖 SVG 刻度字（12 px、11 px）列白名單，因為版面依它計算。
- **為什麼**：JS 預算的經驗（第三十四輪）證明「有預算才會拆」；字級動 token 而不是逐元件改，是 token 化的回報。

### 4.7 頁尾與儀表板（U8、2.7）

- 頁尾「服務」欄分成「民眾申辦」「機關資訊」兩小組（同一欄、兩個小標），欄數與連結不變。
- `/admin/` 與 `/transparency/` KPI 表上方加一行「示範站凍結於 {BUILD_TODAY}，以下為當日計算」，正式模式不輸出。

### 4.8 文件與測試可找性（2.5、2.6）

- `ARCHITECTURE.md` 新增「現況地圖」一節：按子系統列規則位置、程式、測試、最後修改輪次；輪次章節保留作為變更脈絡。
- 新增 `docs/README.md`：39 份文件分「給誰看」「主題」兩個維度的索引。
- 新增 `tests/README.md`：106 個測試檔的「主題 → 檔名」對照表，並訂新規則：**新測試檔以主題命名，輪次寫在檔頭註解**。既有 `roundNN-` 檔名不改（避免 CI 車道清單與文件連結大改），對照表補足可找性。
- **為什麼**：文件本身品質高，缺的只是入口；加索引而不是重寫，保留每一輪的「為什麼」。

## 5. 沒做的與需要決定的

### 5.1 資產檔名雜湊（2.4）

影響建置、所有模板的資產路徑、CSP 雜湊、`headers/` 與部署文件，應獨立一輪做。在那之前依第七十二輪的做法：`assets/**` 用短快取加 1 小時 `stale-while-revalidate`，不要照 Pagefind 的 immutable 設；`docs/deploy.md` 的快取節與 `docs/performance-lighthouse.md` 以後者為準。

### 5.2 答案句去重（U7）

引擎變更，需跑挑戰集與封存盲測（第五十三輪的規則），與智慧問答相關的下一輪一起做。

### 5.3 需要 Yulun 決定

1. **桌機語言列要不要折成一鍵**（U2 更徹底的做法）：少 6 個 Tab 停留點，但七語可見度下降。本輪只加 skip link。
2. **「民眾」身分鈕在民眾頁上是否改為不可點的狀態標示**（3.3）。
3. **首頁六任務手機版改 3×2 兩欄**（U3）：縮短約 400 px，但每格標題要換行。
4. **i18n 原始檔改為每語 JSON**（2.5）：對翻譯流程是必要的，對程式是一次大改。

### 5.4 評估過、決定不做

深色模式（U12）、手機底部增加第五鍵（U11）、把 `_partials.mjs` 拆檔（風險大於收益，先加目錄註解即可）。

## 6. 教訓（寫給下一個做全面檢視的人）

1. **有預算的東西才會被拆。** JS 有預算所以被拆了三次，CSS 沒有所以長到 116 KB。任何「每頁都載」的資產都該有數字門檻。
2. **用機器量，不用印象講。** 「手機首屏被外框吃掉」是感覺，「290 px／844 px」才能讓人決定要不要改；Tab 停留點、小於 44 px 的目標數、CSS 使用率都是幾十行 Playwright 就能量的。
3. **按輪次寫文件保留了「為什麼」，但一定要另外給「現在」一張地圖。** 兩者缺一不可，不要為了其中一個刪掉另一個。
4. **檢視要先列出「確認保留」。** 不然下一個人會把前幾輪已經想清楚的決定（不用 hover 選單、不放更多服務）當成缺點再改回去。
5. **一般民眾頁不要預設用專業分類。** 法定類別、ICD、通報時限是專業版的事；民眾頁的預設排序要回答「我聽過的那個病在哪」。
