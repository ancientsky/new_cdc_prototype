# LINE「疾管家」能不能用新網站當知識庫：評估與可行做法

> 給誰看：公關室（疾管家的承辦）、資訊室、OASIS。
> 狀態：評估（第三十八輪，2026-10-11）。沒有改程式。起因是同事問：疾管署在 LINE 平台有「疾管家」聊天機器人，它能不能用新網站當知識庫，實際可行的方式是什麼。
> 前提：開發環境連不到 cdc.gov.tw 與 LINE，疾管家**現在**是怎麼做的（純選單、關鍵字規則、還是接了語言模型）本文不知道，第 6 節列了要先問承辦與廠商的問題。帳號 `@taiwancdc` 仍標「待確認」（手冊 §28.5）。

## 0. 三句話結論

1. **可以，而且新網站已經為此準備好了**：內容只有一份正本，建置時同時產出網頁、機讀版 `.md`、`/v1/*.json` 開放資料、給 AI 的 `llms.txt`，以及智慧問答用的「答案索引」。疾管家不需要另外整理一份知識庫，接這些就好。
2. **最實際的做法是「讓疾管家呼叫網站的智慧問答引擎」**：引擎本來就是純函式（同一份程式在瀏覽器與 CI 評估裡都跑），資訊室只要在署內起一個小服務載入同一份索引，疾管家的 webhook 問它，拿到「幾句答案＋出處＋審閱日＋網址」再轉成 LINE 訊息。網站怎麼答，疾管家就怎麼答；拒答規則、相關度門檻、227 題評估集全部共用。
3. **不建議的做法是把網頁丟給廠商自己做向量庫、讓模型自由發揮**：會失去版本鏈、逾期標示、疫情態勢「人工發布不得推論」這些治理訊號，而且兩邊答案會不一致。要用語言模型，接在同一條管線的後面（[ask-search-llm.md](ask-search-llm.md) §7 的署內代理），不是前面。

## 1. 新網站現在就提供哪些「知識出口」

| 出口 | 位置 | 內容 | 適合誰用 |
| --- | --- | --- | --- |
| 機讀版頁面 | 每頁同路徑 `.md`（例：`/diseases/dengue.md`） | 首段固定寫權責單位、最後審閱、下次審閱、授權、ID、正本網址；正文是純 Markdown | 需要「整頁文字」的系統（RAG 文件庫、人工比對） |
| AI 引用指南 | `/llms.txt` | 列出可引用的正本與資料出口，以及引用規則（附網址與審閱日、只引用現行版、態勢不得自行推論、授權 OGDL-1.0） | 任何要讀這個站的 AI 系統，第一個該讀的檔 |
| 開放資料 API | `/v1/*.json`（59 個端點，`/openapi.json` 有規格，`/developers/` 有說明） | 疾病、疫苗與時程主檔、FAQ、新聞、文件版本鏈、澄清稿、疫情態勢、旅遊疫情、申請服務、通報時限表… 每個檔都有 `meta.etag`、`meta.lastModified` | 要結構化資料的系統（例如「現在登革熱態勢是哪一級」直接讀 `situation.json`） |
| 答案索引 | `/v1/search-index.json`（民眾版，約 750 段、1.8 MB）、`/v1/search-index-pro.json`（專業版，2.9 MB） | 智慧問答用的段落：每段有句子陣列、網址＋錨點、權責單位、審閱日、對象、語言（中文 565 段、英文 146 段、越南文 35 段…） | 要「可引用的句子」的系統，也就是疾管家 |
| 舊網址對照 | `/v1/legacy-map.json`、`/v1/redirects.json` | 舊站網址 → 新站網址 | 疾管家選單與罐頭回覆裡寫死的舊網址要全部換掉（[migration-playbook.md](migration-playbook.md) 切換日 T-0 已列） |
| 全文搜尋 | `/search/`（Pagefind，純前端） | 找「含這些字的頁面」 | 不適合機器人（沒有 HTTP 端點，結果是頁面不是句子） |

所有出口都由同一次建置產生（push 到 `main` 或每 2 小時排程），所以疾管家讀到的永遠和網頁一致，不會有「網站改了、機器人還在講舊的」。

## 2. 三種接法，由淺到深

### 做法 A：只換連結（切換日一定要做，不算「知識庫」）

疾管家的圖文選單、關鍵字回覆裡寫死的舊網址，用 `/v1/legacy-map.json` 全部對應到新網址；舊網址本身也會 301 轉址，所以就算漏換也不會 404，但 LINE 訊息裡仍應直接給新網址。零風險、零開發，但機器人還是只會「給連結」，不會回答問題。

### 做法 B（建議先做這個）：疾管家呼叫網站的智慧問答引擎

**原理。** 智慧問答引擎（`src/client/answer/core.js`）是純函式：輸入問句，輸出答案句子與出處。它在三個地方跑的是**同一份程式**：

- 瀏覽器：`/ask/` 頁面從 `/v1/*.json` 載入索引後建立引擎（`src/client/answer/data.js`）。
- CI：`eval/run-eval.mjs` 在 Node 用同一個 `createEngine()` 跑 227 題評估集，不全對就不部署。
- **署內服務（新增）**：一支 Node 程式，啟動時抓同一組 `/v1/*.json`（答案索引、態勢、澄清稿、詞彙、疾病與疫苗主檔、時程、申請服務、通報時限表），呼叫 `createEngine()`，開一個 HTTP 端點給疾管家的 webhook。

**流程。**

```
民眾在 LINE 問「2 歲前要打哪些疫苗」
  → 疾管家 webhook（廠商或署內）
  → POST 署內答案服務 { question, lang: "zh-TW", view: "public" }
  → 引擎：個資遮蔽 → 拒答規則 → 檢索 → 相關度門檻 → 結構化回答（時程主檔）
  → 回 { status: "answered" | "refused" | "no-match",
         sentences: [{ text, url, title, ownerName, reviewedAt }], related: [...] }
  → 疾管家組 LINE 訊息：
       答案 2–4 句
       「資料來源：疫苗接種時程（急性傳染病組審閱 2026-09-20）」＋ 連結
       Quick Reply：相關頁面 2–3 顆
  → 拒答／查無時：回網站同一套拒答文案，附「到官網查」與 1922 連結
```

**為什麼這是最實際的做法。**

- 不用再整理一份知識庫，也不用訓練任何東西。索引是建置產物，網站上線多久，疾管家就能同步多久（服務每 10 分鐘看 `meta.etag` 變了就重載；索引載入是毫秒級，答一題也是毫秒級，LINE webhook 的回覆時限綽綽有餘）。
- 治理規則一字不差地跟著走：醫療建議與個資的拒答規則、相關度門檻（低於門檻說「查無」而不是硬答）、只引用 AI 白名單內容、逾期內容不引用、新舊說法不一致時只用權責單位指定的版本（第三十三輪）、疫情態勢只引用人工發布值。這些都在引擎裡，不是靠廠商的提示詞。
- 答得出與答不出的題目，網站與疾管家一樣。評估集一份、透明報告一份；改規則或加詞彙在一個地方改，兩邊同時生效。
- 資訊室要維運的只有一支無狀態的小服務：沒有資料庫、沒有金鑰、沒有模型費用；壞了疾管家退回原本的選單即可。

**要注意的限制。**

- 引擎是抽取式：只會把站上現有的句子拿出來，不會改寫、不會聊天。問法離站上用詞太遠會「查無」（[ask-search-llm.md](ask-search-llm.md) §5.1），這在 LINE 上會比網頁明顯，因為民眾打字更口語。對策是從查無紀錄補詞彙與 FAQ，與網站同一套流程。
- 中文為主：答案索引目前中文 565 段、英文 146 段，其他語言很少；疾管家若要答英文以外的語言，先只回連結。
- LINE 訊息很短：答案要截成 2–4 句、一則訊息，出處放最後；網頁上的「專業檢視」「相關頁面」在 LINE 改成 Quick Reply 按鈕。
- 答案服務必須放在署內或署的雲端，由資訊室管；不能讓廠商的伺服器直接抓 GitHub Pages 當正式來源（正式站的網址與託管由資訊室決定，見 [deploy.md](deploy.md) §7）。

**要做的事（估一個人一到兩週）。**

| 誰 | 做什麼 |
| --- | --- |
| 原型（OASIS） | 把 `eval/run-eval.mjs` 建引擎的那段抽成「從 `/v1/*.json` 建引擎」的共用函式，加 `scripts/answer-service.mjs`（HTTP 端點、etag 重載、LINE 訊息長度的截句）、測試與 OpenAPI 片段 |
| 資訊室 | 署內部署這支服務（Node 22，一個容器或一台小 VM），開一條內網路徑給疾管家 webhook，設逾時（例如 2 秒內沒回就退回選單）與每分鐘次數上限 |
| 疾管家承辦／廠商 | webhook 加一條規則：選單沒命中的自由文字 → 問答案服務；設計 LINE 訊息版型（答案、出處、Quick Reply）；查無時的文案 |
| 公關室 | 核對 `@taiwancdc`；決定試行範圍（建議先開疫苗時程、疾病症狀與預防、旅遊疫情三類，其他照舊） |

### 做法 C：加上語言模型（做法 B 之後，而且只接在後面）

如果疾管家已經或打算接語言模型（例如要「用自己的話回答」「多輪對話」），正確的位置是做法 B 的**後面**：答案服務先檢索並過門檻，再把這幾句交給署內的 LLM 代理改寫，改寫結果逐句對回原句、對不上的句子丟掉、丟到沒句子就退回抽取式答案。這就是網站現有 LLM 模式（BYOK）的流程，也是 [ask-search-llm.md](ask-search-llm.md) §3、§7 與決策紀錄 §25 寫定的契約：模型是改寫者，不是回答者；拒答與查無的問題模型看不到。

兩種「先給廠商、廠商自己做」的變體，都不建議當正式做法：

- **廠商把 `.md` 與 `/v1/*.json` 抓去做自己的向量庫**：技術上一天就能接（這正是 `.md` 與 `llms.txt` 存在的目的），但版本鏈、逾期、白名單、態勢不得推論這些規則變成「請廠商遵守 `llms.txt`」，沒有程式保證；兩邊檢索不同，答案會不一樣，出錯時查不出是哪一邊。只適合廠商評估期間試用。
- **模型直接讀整頁、自由回答**：公部門健康資訊站的硬性約束（[ask-search-llm.md](ask-search-llm.md) §7.3：不得生成站上沒有的醫療建議、每句可追溯、可稽核）在這種做法下無法成立。

## 3. 三種做法的比較

| | A 只換連結 | B 呼叫問答引擎 | C 再加語言模型 |
| --- | --- | --- | --- |
| 民眾得到什麼 | 一個連結 | 2–4 句答案＋出處＋連結 | 更口語的 2–4 句＋出處 |
| 答案與網站是否一致 | — | 完全一致（同一份程式與索引） | 一致（改寫後逐句對回） |
| 治理規則怎麼保證 | — | 在引擎裡，程式保證 | 同左，再加後檢 |
| 新內容多久生效 | 立即（轉址） | 最晚建置後 10 分鐘 | 同左 |
| 署內要維運什麼 | 無 | 一支無狀態 Node 服務 | 同左＋LLM 代理（金鑰、配額、快取、稽核） |
| 費用 | 無 | 一台小主機 | 另加模型用量 |
| 主要風險 | 漏換連結 | 口語問法查無偏多 | 模型改寫失真（有後檢，但仍要人抽查） |
| 什麼時候做 | 切換日 | 切換後試行兩個月 | B 的查無率與滿意度量過之後，若真的需要 |

## 4. 建議的順序

1. **現在**：公關室核對 LINE 帳號；原型補答案服務（上表 OASIS 那列），本機用 `npm run dev` 就能試。
2. **切換日**：做法 A，疾管家所有舊網址換新。
3. **切換後兩個月試行**：做法 B，先開三類問題，其餘照舊選單；每週看查無清單與民眾回饋，補詞彙與 FAQ 到**網站**（不是補到疾管家）。
4. **試行結束**：用數字決定要不要做法 C（查無率、答對率、民眾是否常追問「所以我該怎麼做」這類需要改寫的問題）。

## 5. 為什麼不直接把「智慧問答」搬進疾管家、或反過來把疾管家搬進網站

兩個管道的使用情境不同：網站的問答頁可以顯示整段、專業檢視、相關頁面與回報錯答；LINE 一則訊息幾十字，使用者在手機上、常是轉傳來的。所以是**同一個引擎、兩種呈現**，不是二選一。網站的 `/ask/` 保留完整版，疾管家拿精簡版；內容與規則只維護一份。

## 6. 要先問疾管家承辦與廠商的問題

1. 疾管家現在的回答機制：純圖文選單？關鍵字規則？有沒有接語言模型？誰維護規則？
2. webhook 在哪裡跑（廠商主機還是署內）？能不能呼叫署內內網的 HTTP 服務？逾時上限幾秒？
3. 目前每月訊息量、尖峰每分鐘量（決定答案服務要幾個副本）。
4. 現在有沒有記錄「使用者問了什麼、機器人沒答出來」？格式為何？（可以直接變成網站的查無清單來源。）
5. 合約上，把回答邏輯改成「呼叫署的服務」算不算變更？費用與時程？
6. 多語需求：疾管家現有哪些語言？（答案索引英文以外很少，要先說清楚。）

## 7. 風險與對策

| 風險 | 對策 |
| --- | --- |
| 民眾把機器人回答當醫療建議 | 引擎的拒答規則照用；每則答案結尾固定一句「如有症狀請就醫或撥 1922」；出處與審閱日每則都附 |
| 口語問法查無太多，民眾覺得機器人很笨 | 試行期只開三類題，其他走選單；查無清單每週回補詞彙與 FAQ；量化後再決定要不要做法 C |
| 答案服務掛了 | 無狀態、可多副本；webhook 逾時 2 秒退回選單；監控與網站 CI 同一個值班信箱 |
| 兩邊內容不一致 | 結構上不可能：同一份索引、同一份程式；若廠商另做向量庫（不建議），至少要用 `meta.etag` 同步並只收 `isCurrent` 的文件 |
| 個資 | 引擎先遮蔽身分證、電話等再檢索；答案服務不記原問句明文（與 [ask-search-llm.md](ask-search-llm.md) §7.2 相同），LINE userId 不傳給答案服務 |
| 帳號冒用 | 網站只連結核對過的官方帳號（手冊 §28.5），疾管家回覆裡只給官網網址 |
