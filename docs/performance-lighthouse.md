# Lighthouse 效能檢測（第七十二輪，2026-11-12）

> 給資訊室與 OASIS 同事：原型網站用 Chrome Lighthouse 量了一輪，分數幾乎全滿；這份文件說明怎麼量、量到什麼、哪些改了、哪些刻意不改，以及「分數滿了為什麼還要看別的數字」。
> 相關：答案頁的效能預算與 `perf:ask` 見 [deploy.md](deploy.md) §15；安全標頭與快取規則的伺服器設定見 [deploy.md](deploy.md) §10、§12.2 與建置輸出的 `dist/headers/README.md`。

## 1. 目的與結論

同事請我們用 Chrome Lighthouse 詳細檢測全站效能。結論：**一般頁面（首頁、疾病頁、新聞、疫苗時程表、出國、FAQ…）手機與桌機的效能分數都是 99–100、無障礙 100、最佳實務 100**；**唯一不滿分的是帶問題的答案頁 `/ask/?q=登革熱`（手機 92、桌機 93）與搜尋結果頁桌機（98）**，原因是提問後要下載約 400 KB 的索引與資料、以及答案插入時版面往下推（CLS）。SEO 在原型模式只有 61–66，是因為原型刻意 `noindex`（不讓搜尋引擎收錄示範站），正式模式建置後疾病頁與新聞頁 SEO 100、首頁 92（唯一扣分是一組沒有 `href` 的隱藏連結，本輪已修）。本輪處理四件：**CSS 沒有壓縮**（建置時壓縮，每頁少下載約 7 KB）、**部署設定沒有快取規則**（由建置輸出 nginx／`_headers`／IIS 設定）、**首頁隱藏連結沒有 `href`**（原型模式首頁 SEO 61 → 69，正式模式 92 → 100）、**答案與搜尋結果出現時版面往下推**（帶 `?q=` 時先撐一個視窗高：`/ask/?q=` 桌機 93 → 99、CLS 0.152 → 0；`/search/?q=` 桌機 95 → 100；見 4.9）。另外記下兩件事：(1) **Lighthouse 對答案頁只算到一部分**——它的 TBT 只算到 TTI，`perf:ask` 量到答案畫出來為止，TBT 約是 Lighthouse 的兩倍，答案頁以 `perf:ask` 為準；(2) **量測腳本本身出過錯**：第一次的基準量測把 `/ask/?q=登革熱` 量成了沒有問題的 `/ask/?q`，答案頁因而顯示「100 分」，本輪改寫成正式腳本後才量到真的數字（4.5）。

## 4. 逐項發現與處置

### 4.1 SEO 61–66：原型的 `noindex`（設計如此）＋首頁隱藏連結沒有 `href`

- **發現：** 原型模式每頁都扣 `is-crawlable`——這是刻意的：示範站有 `<meta name="robots" content="noindex">` 與 robots.txt 封鎖，避免搜尋引擎把示範內容當成疾管署官方資訊（docs/deploy.md、ARCHITECTURE 26.1）。正式模式唯一剩下的扣分是首頁 `crawlable-anchors`：`src/templates/public/home.mjs` 的「從其他語言來的提示」區塊（第四十輪 #74）預先渲染了各語言的按鈕 `<a … data-from-alt hidden>`，**沒有 `href`**，等前端驗證網址參數後才補上。
- **處置：本輪改。** 連結預先帶 `href`＝該語言首頁（例如 `/en/`）；前端（`src/client/ui.js`）照舊在驗證 `?from=` 後把它覆寫成「該語言的同一頁」。
- **為什麼這樣比較好：** 沒有 `href` 的 `<a>` 在 HTML 裡不算連結——搜尋引擎不跟、鍵盤 Tab 不到、輔助科技不會唸成連結。預設指向該語言首頁，即使前端沒執行（或 `from` 不合法被擋），點下去也是有意義的目的地，而區塊本身仍預設 `hidden`，讀者看到的行為不變。
- `is-crawlable` 不改：原型就是不該被收錄。

### 4.2 擋住首次繪製的 CSS（`render-blocking-insight`）

- **發現：** 每頁都有 `tokens.css`＋`base.css`＋`components.css` 擋住首次繪製，Lighthouse 估計手機可省 410–590 ms。JS 從第三十四輪起就在建置時逐檔壓縮（`scripts/lib/minify.mjs`），CSS 卻是原樣複製到 `dist/`（`src/styles` 的註解是寫給同事看的「哪一輪、為什麼」）。
- **處置：本輪改。** 建置時用 esbuild 壓縮 `dist/assets/styles/*.css`（`minifyCssDir`），原始碼與註解留在 `src/styles`。與 JS 共用 `MINIFY=off` 關閉開關（除錯時想在 dist 看原始 CSS）。
- **為什麼這樣比較好：** CSS 一定要在畫面出來前下載完（否則先閃一下沒樣式的頁面），能做的就是讓它變小。用 esbuild 是因為它已經是 devDependency（JS 壓縮在用），不新增套件；它只做安全轉換（去註解與空白、縮寫同值寫法），不重排規則、不刪「看起來沒用到」的規則。實測三支擋畫面的 CSS（gzip 後）：tokens 1,436 → 909 B、base 4,363 → 3,124 B、components 24,580 → 19,035 B，合計 **30.4 KB → 23.1 KB（−24%）**；後台 `admin.css` 11.4 → 9.2 KB。
- **實測結果（第 5 節）：** 每頁少下載約 7 KB（傳輸 −10～13%），但 **FCP、LCP 與 Lighthouse 的「擋畫面估計」幾乎不變**。原因：Lighthouse 模擬的慢速 4G 每次往返 150 ms，三支 CSS 各要一次請求，擋畫面的成本主要是往返次數，不是位元組；估計值本身以 50 ms 為單位、同一頁三次之間就會在 250–600 ms 之間跳。所以這項改動的價值是「省流量」（每位讀者、每次沒有快取的瀏覽），不是讓分數變好——分數本來就滿了。
- **沒有做的：** (1) 把關鍵 CSS 內嵌到 `<head>`（critical CSS）：要每頁算一份、還會讓 CSP 的 `style-src` 更難收緊。(2) 把 `tokens.css`＋`base.css`＋`components.css` 合併成一支、少兩次請求：這才是真的會動到擋畫面估計的做法，但 HTTP/2 下三個請求是平行的、第二頁起都在快取裡，收益只在「第一次、沒快取、慢網路」；且主題 CSS 依賴 token 的載入順序。列為「之後再看」，正式主機確定 HTTP 版本與快取設定後再量。

### 4.3 `components.css` 每頁約 85–90% 沒用到（`unused-css-rules`）

- **發現：** 全站共用一支 `components.css`，任何一頁只用到 10–15%，Lighthouse 估計可省 20–24 KB。
- **處置：記錄不改。**
- **不改的理由：** 拆成「每個區塊一支」或「每頁只放用到的規則」，讀者在第一頁之後翻到別的區塊就要再下載新檔；一支共用、快取後 3,300 多頁都不用再抓，對「看好幾頁」的實際讀者比較划算。每頁裁剪還要在建置時分析每一頁的 HTML，而且前端動態加上的 class（展開、切換語言、互動模組）很容易被誤刪，換來的是難查的版面錯誤。壓縮後 gzip 19 KB，在慢速 4G 下約 0.1 秒。等 `components.css` 明顯長大（例如 gzip 超過 40 KB）再考慮依區塊拆分。

### 4.4 快取策略（`cache-insight`）

- **發現：** `/assets/js`、`/assets/styles`、`/img` 檔名沒有內容雜湊、快取時間短。GitHub Pages 不能自訂標頭（固定 `max-age=600`），所以原型無法改；但將來自架主機（nginx／IIS／Azure）時，`dist/headers/` 只輸出安全標頭，快取建議只寫在 deploy.md §12.2 而且只講 `/pagefind/`。
- **處置：本輪改（輸出設定檔）；檔名雜湊之後再看。** `scripts/lib/emit-headers.mjs` 新增 `CACHE_RULES`，建置時寫進 `dist/headers/headers.json` 的 `cache` 區塊，並產生對應的 nginx `location`、Netlify／Cloudflare `_headers` 規則與 IIS `web.config` 片段（在 `dist/headers/README.md`）：

| 規則 | `Cache-Control` | 路徑 | 為什麼 |
| --- | --- | --- | --- |
| 預設 | `no-cache` | HTML、`.md`、`/v1/**`、`pagefind-entry.json`、`pagefind.js`、`pagefind-worker.js`、`wasm.*.pagefind` | 每次問伺服器「有沒有變」，沒變回 304（ETag／Last-Modified），幾乎不花流量；**緊急發布要立刻看得到**。GitHub Pages 現在是最多晚 10 分鐘，這比它更即時 |
| 1 小時 | `public, max-age=3600, stale-while-revalidate=86400` | `/assets/**`、`/img/**`、`/files/**` | 檔名沒有雜湊、JS 的 `import` 路徑也沒有版本，**不能 immutable**（否則改版後讀者可能拿新 HTML 配舊 JS）。1 小時內翻頁不再下載；過期後先用舊檔顯示、背景更新 |
| 一年 | `public, max-age=31536000, immutable` | Pagefind 的 `index/`、`fragment/`、`filter/`、`pagefind.*.pf_meta` | 檔名就是內容雜湊，內容變檔名就變 |

- **為什麼由建置輸出：** 規則跟著程式走（哪些目錄有雜湊、哪些沒有，是建置決定的），寫在文件裡要資訊室自己翻成三種伺服器語法，很容易漏或寫錯（例如 nginx 子 `location` 一加 `add_header` 就把安全標頭整組弄丟——產生的設定檔已在每個 `location` 重列安全標頭）。
- **之後再看：檔名含內容雜湊（fingerprinting）。** 這是 `/assets` 能快取一年的正解，但要建置時把每個檔改名，並改寫每個 JS 模組裡的 `import './x.js'` 與模板裡的 `<script src>`／`<link href>`；GitHub Pages 不吃自訂標頭，現在做也看不到效果。等正式主機定案（Azure／nginx，見 architecture-decisions 對 #129–#133 的說明）再做。

### 4.5 答案頁：Lighthouse 只算到一部分，而且第一次還量錯了

- **發現一（量錯）：** 基準量測的 `/ask/?q` 與 `/search/?q` 兩列都是 100 分、95 KB／18 個請求——後來發現是臨時腳本把網址截掉了 `=登革熱`，量的是沒有問題的頁面。改用本輪的 `scripts/perf-lighthouse.mjs`（網址照實傳入、報告檔名與摘要都記實際網址）重量：答案頁手機 **92**、桌機 **93**，搜尋頁桌機 98（3 節）。
- **發現二（停錶太早）：** 即使網址正確，Lighthouse 的 TBT 也只算到 TTI（「看起來可以互動」），答案頁提問後 `import()` 引擎、下載索引、檢索的工作只算到一部分：Lighthouse 手機 TBT 339 ms，`perf:ask` 量到答案畫出來為 690 ms（傳輸量兩邊一樣約 516–524 KB）。
- **處置：記錄；本輪不改答案頁。** 答案頁的效能以 `npm run perf:ask` 為準（第四十輪寫的就是這個，deploy.md §15），建置時另有答案資料傳輸量預算（445 KB）。答案頁是全站最重的頁（JSON 約佔傳輸的 3/4），分片的討論見 deploy.md §17。
- **為什麼要寫下來：** 只看 Lighthouse 分數，會以為答案頁「92 分，還好」；只看第一次的量測，會以為它 100 分。兩個錯都來自「沒有確認量的是不是使用者真正等待的那件事」。

### 4.6 `/travel/` 與疫苗時程表：DOM 大（觀察項）

- **發現：** `/travel/` HTML 原始 504 KB（gzip 94 KB）、6,482 個元素（約 230 個國家、259 張 `c-level` 卡、1,413 個連結），手機仍 FCP 1.5 s、100 分，Style & Layout 414 ms。`/vaccines/schedule/` HTML 102 KB、1,278 個元素，有一個 373 ms 的 long task（Style & Layout 686 ms），手機三次中一次 93 分。
- **處置：記錄不改。** 分數仍滿、CLS 接近 0；但這兩頁是「內容一多就先變慢」的頁。之後若 `/travel/` 國家卡再加欄位、或時程表再加語言欄，先考慮預設收合（`<details>`）或 `content-visibility: auto`。

### 4.7 `/admin/` 轉到登入頁多花約 1.1 秒（手機）

- **發現：** `/admin/` 先轉址到 `/admin/login/?next=…`，手機多一次往返約 1.1 s。
- **處置：記錄不改。** 後台是內部頁，正式環境在內網反向代理後面（deploy.md §14），也不是 Lighthouse 該優化的對象。

### 4.8 主執行緒時間主要花在樣式與版面，不是 JS

- **發現：** 手機各頁主執行緒以 Style & Layout 為主（340–690 ms），Script Evaluation 只有 38–71 ms；沒有網頁字型、沒有第三方腳本，圖片都是有寬高與 lazy loading 的小 SVG，CLS 全站 0。
- **處置：記錄。** 這代表 JS 預算（第三十四輪起的建置閘門）已經發揮作用；接下來影響體感的是 CSS 規則數與 DOM 大小，而不是 JS。新增元件時，優先用既有 class、避免深層選擇器與大量 `:has()`。

### 4.9 答案與搜尋結果插入時版面往下推（CLS，本輪重量才發現；已修）

- **發現：** `/ask/?q=登革熱` 桌機 CLS **0.152**（超過 Google 建議的 0.1，桌機 93 分主要扣在這裡）、手機 0.033；`/search/?q=登革熱` 桌機 0.093。Lighthouse 指出被推動的是答案下方的「同一答案，三個管道」區塊（`section.c-channels`）：答案或搜尋結果出現時，原本空著的區塊突然長高，把下面的內容往下推。
- **處置：本輪改。** 版面的 `EARLY_JS`（`<head>` 裡、CSS 之前執行的小段 inline script）在網址帶 `?q=` 時於 `<html>` 加 `data-q`；`components.css` 讓 `html[data-q] .c-answer[aria-busy="true"]` 與 `html[data-q] #search-results:empty` 先撐 `min-height:100vh`。這樣首次繪製時下方的區塊就已經在視窗外，結果畫出來時它在畫面外移動，讀者看不到跳動；結果畫完就放開。`answer/ui.js` 的 `busy()` 同步切 inline `min-height`（頁內再問時也適用）；搜尋查無結果時 `search.js` 把預留高度放掉，查無提示才不會被推到一個視窗以下。沒有 `?q=` 的頁面完全不受影響（實測 `/ask/`、`/search/` CLS 仍為 0）。
- **為什麼不是先試過的作法：** 第一版只在 `ui.js`／`search.js` 裡用 JS 設 `min-height`——模組腳本跑的時候頁面多半已經畫出來，撐高本身就是一次跳動（`/ask/?q=` 桌機只從 0.152 降到 0.109，`/search/?q=` 反而變成 0.255）。要在**首次繪製之前**決定，所以搬到 `EARLY_JS`＋CSS。改 `EARLY_JS` 會換掉 CSP 的 inline script 雜湊，但雜湊由建置掃 dist 重算，不用手改。
- **結果（3 次中位數）：** `/ask/?q=登革熱` 桌機 93 → **99**（CLS 0.152 → **0.000**）、手機 CLS 0.033 → 0.000（分數 92–93 不變，差在 TBT）；`/search/?q=登革熱` 桌機 95 → **100**（CLS 0.135 → 0.037）、手機 CLS 0.030 → 0.055（99 分；剩下的小位移是精選結果卡）。代價：查無結果（`/search/?q=zzzqqq`）桌機放開預留高度時 CLS 約 0.10（97 分），這個情境比有結果少得多，先接受。
- **為什麼值得做：** CLS 是讀者真的會感覺到的「正要點，東西跑掉了」；它也是答案頁從 93 回到 100 最便宜的一步。

## 6. 怎麼自己再跑

```bash
BASE_PATH='' node scripts/build.mjs            # 一定要根路徑建置：腳本在 / 提供 dist/
npm run perf:lighthouse                         # 預設 11 頁 × 手機／桌機 × 3 次，印出 markdown 表
LH_PAGES=/,/diseases/dengue/ LH_FORMS=mobile LH_RUNS=5 npm run perf:lighthouse   # 只量幾頁、多跑幾次
LH_MIN_PERF=90 npm run perf:lighthouse          # 任一頁效能中位數 < 90 ⇒ exit 1（不設＝只回報）
npm run perf:ask                                # 答案頁的真實成本（Lighthouse 量不到的部分）
```

| 環境變數 | 預設 | 說明 |
| --- | --- | --- |
| `LH_RUNS` | 3 | 每頁每種裝置次數，取中位數 |
| `LH_PAGES` | `/`、`/ask/`、`/ask/?q=登革熱`、`/diseases/dengue/`、`/news/`、`/vaccines/schedule/`、`/search/?q=登革熱`、`/travel/`、`/play/`、`/faq/`、`/en/` | 逗號分隔 |
| `LH_FORMS` | `mobile,desktop` | 裝置 |
| `LH_OUT` | `.local/lighthouse/` | 每次量測的 `.json`＋`.html` 報告（`.local/` 在 `.gitignore`，不會進版控） |
| `LH_JSON` | `<LH_OUT>/summary.json` | 中位數摘要 |
| `LH_MIN_PERF` | 不設 | 效能分數門檻 |
| `CHROME_BIN` | `/opt/pw-browsers` 內最新 Chromium，再找 Playwright 的 | 指定瀏覽器 |

- 報告 `.html` 可直接用瀏覽器開，與 DevTools 的 Lighthouse 面板相同。
- **GitHub Actions：** Actions → 「Lighthouse (manual + monthly, report only)」→ Run workflow，可填 `runs` 與 `pages`；每月 2 日 04:00（台灣時間）也會自動跑。表格在該次執行的 Summary，完整報告在 artifact `lighthouse-report`（保留 30 天）。**這個工作流程不擋任何合併或部署。**
- 量線上站：DevTools → Lighthouse 面板，或 `npx lighthouse https://<網域>/ --preset=desktop`。線上與本機的差別是網路往返與 CDN，資源大小相同。

## 7. 教訓

1. **Lighthouse 100 分 ≠ 使用者不用等。** 延後到 `import()` 之後的工作（答案頁、搜尋頁），Lighthouse 的 TBT 根本沒算到。量「使用者要等的那件事」（答案畫出來）才是誠實的數字——這是第四十輪寫 `perf:ask` 的原因，這次又印證一次。
2. **量測腳本也要驗收。** 第一次基準量測的臨時腳本把 `/ask/?q=登革熱` 截成 `/ask/?q`，答案頁「100 分」差點寫進結論。正式腳本的報告要記下實際量的網址，數字「好得不像真的」時先打開報告看網址與請求數。
3. **先量再改。** 這次 15 頁 × 2 裝置 × 3 次量下來，真正值得動手的只有三件小事；若一開始就照「效能優化清單」拆 CSS、加 critical CSS、改圖片格式，會花很多力氣在分數已滿的地方。
4. **現在影響體感的是 CSS 與 DOM，不是 JS。** 主執行緒以 Style & Layout 為主；JS 預算已把腳本壓到每頁 40–70 ms。之後新增元件要注意 CSS 規則數與 DOM 大小。
5. **會跳的指標不放進必要 CI。** 連「擋畫面估計」這種單項，同一頁三次就差 100–350 ms。 效能分數、TBT 在共用 runner 上會跳 ±30%；放進必要檢查只會讓無關的 PR 隨機紅燈。用手動／排程的工作流程看趨勢，數字貼在 PR 說明。
6. **建置知道的事由建置輸出。** 快取規則跟 CSP 雜湊一樣：哪些檔名有雜湊是建置決定的，就由建置寫成伺服器設定，不靠人看文件翻譯。
