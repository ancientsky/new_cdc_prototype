# 同事操作手冊

> 給誰看：各組 Steward（承辦人）、公關室、資訊室、OASIS、疫情中心。
>
> 本手冊的「OASIS」＝署內任務編組 **AI推動辦公室**（Office of AI Strategy, Innovation, and Synergy），主檔 `unit.oasis`。
>
> 一句話：**你只要做三件事——填對欄位、處理待辦、確認預處理。其餘由系統在每次建置時自己算。**
> 後台入口：`/admin/`（原型為純前端，產生的上架包——ZIP 或 JSON——才是正式交付物）。

## 0. 先搞懂運作方式

正式環境沒有「另一套 CMS」（為什麼、和傳統後台差在哪，見 [git-as-cms.md](git-as-cms.md) 的比較表）。內容就是 `content/` 底下的 JSON 檔，流程是：

**改檔 → 開 Pull Request → CI 自動驗證 → 複核者核准 → 合併即發布。**

第九輪起，「複核者核准」依內容風險分三條**發布車道**：新聞稿、通函、澄清、職缺、採購、Banner 走**快車道**（CI 通過自動合併，上線後公關室 24 小時內複核）；疾病、疫苗、文件、Q&A 等走**一般車道**（CI 通過還要 1 位審核人核准，SLA 2 個工作天）；疫情態勢與標了「緊急」的稿件走**緊急發布**。承辦人的操作不變，車道由系統依型別判定（2.8、2.9）。完整說明見 [publishing-lanes.md](publishing-lanes.md)。

CI 會跑三道關卡，任何一道不過就不能合併：（1）schema 與參照檢查，缺必填欄位、`owner` 不存在、`basedOn` 指向不存在的內容都會擋，**附件與圖片的檔案宣告（存在、雜湊、大小、格式、alt、授權）也在這一關**；（2）治理規則測試；（3）評估集，其中**版本題必須全對**。後台頁面是同一流程的操作介面，目的是讓你不用手寫 JSON 與 Markdown，產生上架包後放進 `content/` 即可（第 2 節）。

## 2. 上架 SOP（新增或改寫一則內容）

**誰：** 承辦 Steward。**何時：** 任何新內容發布前。
**一句話：** 在 `/admin/publish/` 填欄位、寫內文、加附件與圖片 → 按「產生上架包」得到 ZIP → 解壓到 repo → 開 PR → CI 綠燈 → 複核 → 合併即發布。檔案的完整規則見 [assets-policy.md](assets-policy.md)。

### 2.1 流程總覽

1. 到 `/admin/publish/`，選型別（疾病、Q&A、新聞稿、通函、文件，以及第二輪新增的影音、專區、申請服務、出版品、檢驗項目、研究計畫、人才招募、採購公告），填標題。新型別的專屬欄位見第 8 至 13 節；**人才招募與採購公告已各自成為獨立型別，操作見第 16、17 節**。
2. 寫內文（2.2）；加附件與圖片（2.3）。
3. 填欄位（2.4）。
4. 按「送出預處理」，確認結果（2.5）。
5. 走完複核四步（承辦人確認預處理 → 公關室內容審核 → 多語審核 → 發布；後台「複核區」`/admin/review/`，見 21.2）。多語一級內容必須有第二人審。
6. 按「產生上架包」，把 ZIP 交進 repo、開 PR（2.6）。要先看看送出之後會發生什麼，按「模擬送出」（2.8）；要排程或標緊急見 2.9。
7. **怎麼確認：** PR 的 CI 綠燈；合併後約數分鐘，到網站看該頁頁首有「權責單位 · 最後審閱」，附件區列出你加的檔案、圖片有顯示，頁底「本頁的資料與授權」顯示「本頁可被 AI 引用」（若有申請）。

### 2.2 內文的三種編輯方式

內文欄（中文正本）上方有三個頁籤，**看的是同一份資料，切換時即時轉換**，哪種方式都可以：

| 頁籤 | 適合誰 | 怎麼用 |
| --- | --- | --- |
| **所見即所得** | 不會 Markdown 的同事 | 像 Word 一樣直接打字。工具列：標題 2／3、粗體、斜體、項目與編號清單、連結、表格（3×3，第一列為表頭）、圖片、引用、分隔線、復原。快捷鍵 Ctrl+B（粗體）、Ctrl+I（斜體）、Ctrl+K（連結）。從 Word 或網頁**貼上**時會自動清掉字型、顏色、樣式，只保留標題、段落、清單、表格、連結、粗斜體——貼上後請檢查標題層級是否正確 |
| **Markdown** | 熟悉的同事、要精修時 | 直接編輯原始文字；標題用 `##`、`###`，圖片 `![替代文字](/files/…)`，表格用 `\|` 分欄 |
| **預覽** | 送出前確認 | 用網站正式樣式渲染；已選但還沒進 repo 的圖片以暫時預覽顯示。預覽是唯讀的 |

**存檔一律是 Markdown。** 所見即所得只是輸入方式，匯出時會被轉成 Markdown 寫進 JSON。理由：（1）Markdown 是純文字，Git 可以逐行看出「這次改了什麼」，複核者能 diff；（2）反向稽核、翻譯 `sourceHash`、AI 檢索與機讀版（`.md`）都吃純文字，不會被樣式與隱藏格式干擾；（3）不會有「這段是從 Word 貼來的怪格式」的問題，七語頁面一致呈現。所見即所得**不支援**的東西（底色、字型大小、對齊、合併儲存格）本來就不該用在官網內文，轉換時會被拿掉，如果需要請改用標題、清單與表格。

### 2.3 附件與圖片怎麼加

在編輯區下方的**附件與圖片面板**操作：

0. **先填「內容 ID」**（頁面下方的欄位）：圖片路徑 `/files/{內容 id}/…` 會用到它；沒填就無法插入圖片。
1. **加檔案**：把檔案拖進面板，或按「選擇檔案」，可一次多檔。副檔名不在允許清單、檔案內容與副檔名不符（例如把別種檔案改成 `.pdf`）、含腳本的 SVG、超過 30 個檔，會被**當場拒收**並說明原因。**瀏覽器不保存檔案內容**：重新整理頁面後，欄位會還原，但檔案要重新拖進來（檔名相同會自動接回原本那一列，列上有「需重新選取檔案」提示）。
2. **檔名**：面板會自動正規化（轉小寫、空白換連字號、去掉不合法字元）並提示；**中文檔名要自己改成英文檔名**，例：「新聞稿.pdf」→ `press-release.pdf`。規則見 [assets-policy.md](assets-policy.md) 第 2 節。
3. **種類（`kind`）怎麼選**（面板依副檔名預設——圖檔預設內文圖片、csv／json 預設資料檔、其餘預設附件；xlsx 預設為附件，若是要給人再利用的資料請手動改為資料檔）：

   | kind | 什麼時候選 | 結果 |
   | --- | --- | --- |
   | `attachment` 附件 | 讀者要下載的檔：新聞稿全文 PDF、手冊、表單、海報 | 列在頁面「附件」區；`label` 必填，例：「新聞稿全文（PDF）」 |
   | `image` 內文圖片 | 要放在文章中間的圖（圖表、示意圖、照片） | 以 Markdown 引用；**alt 必填**，另需 `license`，非本署素材要 `source` |
   | `data` 資料檔 | CSV、JSON、XLSX 等可再利用的資料（只能是這三種副檔名） | 列在附件區並標資料檔；`label` 必填；**同時要登錄資料目錄**（見 assets-policy 第 6 節） |

4. **替代文字（`alt`）怎麼寫**（只有圖片，欄位標「必填」）：寫這張圖要傳達什麼，而不是「圖片」。圖表寫結論與關鍵數字：「近八週類流感門診就診比率由 1.2% 上升至 2.9%，第 38 週起明顯上升」。≤ 150 字。
5. **圖片的授權（`license`）與來源（`source`）**：授權必填。本署自製填 `OGDL-1.0`（欄位有下拉建議）；外購、CC 或第三方素材，授權填原授權，並填來源（作者、出處網址）。沒有授權證明的圖不要放。
6. **PDF 的文字層怎麼確認**：面板在瀏覽器裡**無法判斷** PDF 有沒有文字層，所以附件列上有一個勾選框「這個檔案是機器可讀的（PDF 有文字層…）」（對應 `machineReadable`），**預設是勾選的，請你自己確認再交**：用 PDF 閱讀器開啟，拖選一段文字、或按 Ctrl+F 搜尋檔內一個詞——能選到、能搜到才算有文字層。掃描成圖片的 PDF 要**取消勾選**，並**另附 `.md`、`.docx` 或 `.odt` 文字版**（也當作附件加進面板；取消勾選後，該列會出現「無障礙替代檔」下拉，選它作為 `accessibleAlt`）。取消勾選又沒有替代版，預檢會警告、建置後系統會開待辦 `attachment-no-accessible-version`。就算勾選，建置也會做簡易偵測，偵測不到文字層會警告。詳見 [assets-policy.md](assets-policy.md) 第 4 節。
   - **有文字層只代表「能下載、能搜尋」，不代表智慧查詢會引用 PDF 裡的內容。** 指引、手冊這類要讓專業版智慧查詢查得到的 PDF，另外走第 20 節「PDF 轉機讀版」。
7. **把圖放進內文**：游標停在要放圖的位置，按該圖片列的「插入圖片到內文」（或在所見即所得工具列按「圖片」，從清單選已加入的圖，也可按「從電腦選圖片…」選檔後直接插入），會插入 `![alt](/files/{內容 id}/檔名)`。
8. **改檔名、移除檔案**：改檔名時，內文裡的引用會跟著改。移除時如果內文還引用著這個檔，面板會警告，要再按一次「確認移除」才會移除；移除後請把內文的引用一併處理，否則建置會失敗。
9. 面板會自動算大小與 SHA-256 雜湊、檢查是否超過限制（PDF 與文件類 ≤ 20 MB、圖片 ≤ 2 MB、資料檔 ≤ 50 MB，一筆內容 ≤ 30 檔），超限、缺 alt、缺授權、缺 label 等直接在該列標紅。

### 2.4 填欄位

- **權責單位 `owner`**：必填，必須是 `content/master/units.json` 內的單位 id。
- **審閱週期 `reviewPeriodMonths`**：預設值依型別（疾病 12、疫苗 6、Q&A 6、文件 12、新聞稿 0＝事件觸發）；要縮短可以，要延長須有理由。**不要手填下次審閱日**，系統用 `reviewedAt` ＋ 週期算。
- **對象 `audience`**：`public`、`professional` 可複選。
- **任務 `tasks`**：決定出現在哪個任務入口。
- **敏感度 `sensitivity`**：只有 `public` 才可能進 AI 白名單。
- **依據正本 `basedOn`**：見下節。
- **發布時間 `publishAt`（選填）與緊急發布 `urgent`**：見 2.9。表單型別選定後，欄位下方會顯示**車道徽章**（快車道、一般車道、緊急發布）。
- **提供語言 `languages`**：每個語言勾一種狀態——`source`（中文正本）、`reviewed`（已審核）、`machine`（機器翻譯）、`pending`（待翻）、`none`（不提供）。**一級內容（疾病、疫苗、澄清、態勢）只有 `reviewed` 的語言才會產生該語言頁。**
- **AI 白名單 `aiWhitelist.requested`**：勾選代表「申請」；實際是否生效由系統算。

### 2.5 送出預處理，確認結果

按「送出預處理」（在瀏覽器內執行）。確認六件事：關鍵字與實體是否正確對應主檔（未對應的建議新增）、摘要 ≤ 120 字、結構化欄位建議（潛伏期、通報時限、年份）、一致性檢查（與主檔或現行版數字是否矛盾）、多語初稿（鎖定詞彙已替換）、**資產預檢**（缺 alt、缺授權、超過大小限制、檔名不合法、內文引用了未宣告的檔——列在附件列上與結果頁「送複核前仍需補齊」，有紅字就先修，不要等 CI 擋；孤兒檔是直接放檔進 repo 才會發生，上架包不會產生）。

### 2.6 上架包（ZIP）怎麼交

1. 預處理結果最下面的 (g) 區按「產生上架包（.zip）」，下載 **ZIP**。內容是：
   ```
   content/{型別資料夾}/{檔名}.json         內容 JSON（assets 欄位已填好 mime、bytes、sha256；檔名是內容 id 去掉「型別.」前綴，例：content/news/2026-09-18-flu-antiviral-extended.json）
   content/assets/{id}/press-release.pdf    附件與圖片原檔
   content/assets/{id}/chart-ili.png
   ```
   畫面上的「放哪裡」樹狀圖會列出每個檔該放的位置，以及 git 與 PR 指引。只想要 JSON 時（沒有附件）可用「只下載 JSON」或「複製 JSON」。
2. **解壓到 repo 對應路徑**：ZIP 內的路徑就是 repo 根目錄下的路徑，直接在 repo 根目錄解壓（`unzip package.zip -d .`，或請資訊室協助），**不要改資料夾名稱**（`content/assets/` 下的資料夾名稱必須等於內容 id）。
3. 開分支、commit、開 PR（沒有 git 環境的同事，把 ZIP 交給資訊室或 OASIS 代為建立 PR，PR 說明寫明承辦單位與上架包檔名）。
4. **CI 會檢查什麼**（任何一項不過都不能合併）：
   - schema 與參照（欄位、`owner`、`basedOn`）；
   - **資產檢查**：每個宣告的檔案存在；`sha256`、`bytes` 與實際檔案相符；副檔名與 `mime` 一致；檔名合法；大小與格式在限制內；SVG 沒有 `<script>`／`on*=`；圖片有 alt 與 license；內文每個 `/files/` 引用都已宣告；
   - **孤兒檔**：`content/assets/{id}/` 有檔但沒宣告 ⇒ 警告並開待辦 `asset-orphan`；
   - 治理規則測試與評估集（版本題全對）；
   - 全站連結檢查（`/files/` 視為站內連結，必須存在）。
5. **hash 不符怎麼辦**：建置失敗訊息會同時印出「宣告值」與「實際值」。通常是你在包裝後又改過檔案（重新匯出 PDF、壓縮圖片）。處理方式二選一：（a）在本機執行 `npm run build -- --fix-assets`（只想補寫、不輸出網站：`node scripts/build.mjs --check --fix-assets`），它會把 `bytes`、`sha256`、`mime`（圖片另有寬高）補寫回 JSON、其餘格式不動，再 commit；（b）把訊息中的實際值貼回 JSON。**先想一下為什麼檔案變了**：若是你有意改（勘誤），補寫即可；若不是你改的，可能是傳輸中損毀或被別人換檔，請查清楚再補。
6. 複核者看 PR：JSON 的 diff（Markdown 內文可逐行比較）、檔案清單、alt 與授權、PDF 是否有文字層（下載打開確認一次）。核准、合併即發布。

### 2.7 常見錯誤

| 看到什麼 | 原因 | 怎麼辦 |
| --- | --- | --- |
| 檔名不合法：`新聞稿.pdf`（建議 `press-release.pdf`） | 檔名有中文、空白或大寫 | 重新命名成小寫英數與連字號；改名後 JSON 的 `file` 欄位與內文引用都要同步改 |
| 圖片 `chart.png` 缺少 alt | 面板沒填、或直接改 JSON 漏掉 | 補 `alt`（寫傳達什麼）；Markdown 的 `![…]` 文字與 `assets.alt` 擇一非空即可 |
| 圖片必須填 license（建置失敗） | 圖片沒填 `license` | 本署自製填 `OGDL-1.0`；外來素材填原授權並補 `source` |
| 待辦 `image-license-missing` | 非本署素材（`license` 不是 `OGDL-1.0`）缺 `source`，或授權不在許可清單 | 補來源（作者、出處網址）；授權不在清單的請 OASIS 確認；沒有授權證明就換圖 |
| 待辦 `attachment-no-accessible-version` | PDF 標 `machineReadable: false`（掃描檔、無文字層）又沒附文字版 | 找回原始檔重新匯出 PDF，或另附 `.md`／`.docx`，並填 `accessibleAlt`（assets-policy 第 4 節） |
| 警告：宣告 `machineReadable: true`，但偵測不到文字層 | 掃描檔卻標了有文字層（建置只警告，不擋） | 改為 `false` 並附 `.md`／`.docx` 可及性版本，或重新匯出有文字層的 PDF。偵測只是簡易檢查，沒警告不代表標籤與閱讀順序正確，複核者會抽查 |
| 缺 `bytes`／`sha256`／`mime`（建置失敗） | 手寫 JSON 或匯出時漏掉 | 執行 `npm run build -- --fix-assets` 補寫 |
| 檔案內容與副檔名不符 | 把別種檔案改副檔名 | 用正確格式重新匯出 |
| 內容是 `draft`／`review` 時網站上看不到檔案 | 只有 `published` 與 `archived` 的檔案才複製到站台 | 正常現象；內容發布後就會出現 |
| `sha256` 不符 | 打包後檔案被改過 | 見 2.6 第 5 點，`--fix-assets` 或貼回實際值 |
| 超過大小限制 | PDF 超過 20 MB、圖片超過 2 MB、資料檔超過 50 MB | 圖片縮圖壓縮、PDF 最佳化；大型資料改登錄資料目錄外部連結 |
| 孤兒檔（`asset-orphan`） | `content/assets/{id}/` 有檔，但 JSON 沒宣告 | 要用就補宣告；不用就 `git rm`。孤兒檔不會上線 |
| 引用未宣告（內文 `![](/files/{id}/a.png)` 找不到宣告） | 打了引用但沒加進 `assets`，或檔名拼錯 | 在 `assets` 補一筆（kind 為 image），或改正引用的檔名 |
| `content/assets/` 下的資料夾沒有對應內容 | 資料夾名稱與內容 id 不一致（改了 id 沒搬資料夾） | 資料夾名稱要等於內容 id |
| SVG 含 `<script>` 或 `on*=` | 從網路或繪圖軟體匯出帶了互動腳本 | 用「另存為純 SVG」或改用 PNG；不得含腳本 |
| 連結檢查說 `/files/…` 不存在 | 連結打錯，或檔案沒宣告所以沒複製到站台 | 對照 `assets` 的 `file` 與連結 |

### 2.8 車道與送出

**你只要記得：** 型別一選，欄位下方就出現**車道徽章**和一句話，告訴你這則內容送出後會怎麼走。車道由系統依型別判定，你不用選、也不能自己改（設定在 `content/governance/lanes.json`，改動須經資料治理委員會）。

| 車道 | 型別 | 徽章下的說明 | 送出後 |
| --- | --- | --- | --- |
| **快車道** | 新聞稿、致醫界通函、澄清、人才招募、採購公告、宣導 Banner | 送出後約 3 分鐘上線，公關室 24 小時內複核 | CI 全過就自動合併上線，**不用等人**；上線後公關室複核 |
| **一般車道** | 疾病、疫苗、文件、Q&A、專區、申請服務、出版品、檢驗項目、研究計畫、影音… | 需 1 位審核（公關室；疾病與疫苗為公關室＋OASIS），SLA 2 個工作天 | CI 全過後**等審核人**看預覽網址、核准，才合併上線 |
| **緊急發布** | 疫情態勢；或新聞稿、通函、澄清勾了「緊急發布」 | 立即上線並通知複核 | CI 全過就上線（目標 10 分鐘內），公關室 24 小時內複核 |

**「模擬送出」按鈕**（預處理結果最下面 (g) 區，「產生上架包」旁邊）：把送出之後系統會做的事排成時間軸給你看——建立分支 → 開 Pull Request → CI 檢查（schema、治理規則、評估集、檔案資產、連結）→ 車道判定 → 自動合併（或等待審核，列出審核人與 SLA）→ 部署 → 預覽網址 → 上線後複核。每一步都註明「正式環境由系統代做」。

- 它是**展示**：不開 PR、不呼叫任何 API、不下載檔案。要真的交件，請用「產生上架包」的 ZIP（2.6）。
- 必填欄位沒補齊時按它，會看到「CI 檢查」那一步標紅、列出沒過的項目，後面各步標「未執行」——和正式環境 CI 擋下你的 PR 是同一個結果，**送出前補齊最省事**。
- 預覽網址格式 `https://ancientsky.github.io/new_cdc_prototype/preview/pr-{N}/`（{N} 是 PR 編號）。正式環境開 PR 後，PR 留言裡就有這個網址，審核人與你都用它檢查版面、連結、附件。PR 關閉後預覽自動清除。
- 在 PR 上你會看到：標籤 `lane:fast`／`lane:standard`／`lane:emergency`、CI 摘要留言、SLA 到期時間、需要誰審。一般車道超過 SLA 沒人處理，系統會加 `sla:breach` 標籤提醒；你不需要自己追，但可以直接找審核單位。
- **多語不擋中文**：翻譯還沒審完的語言先不上線，不會卡住中文正本；一級內容（疾病、疫苗、澄清、態勢）未審核的語言頁本來就不渲染。

### 2.9 排程發布與緊急發布

**排程發布（`publishAt`，選填）**

1. 「發布時間」欄位選日期與時間（**臺北時間**）。留空＝合併後立即上線。
2. 預檢規則：**必須晚於現在**，否則欄位下方標紅、「確認並送複核」會被擋下。
3. 匯出的 JSON 帶 `publishAt: "2026-10-05T09:00:00+08:00"`。
4. **到點前**：內容照常檢查、審核、合併，但網站不顯示，搜尋索引、sitemap、API、RSS 也沒有，AI 不會引用；狀態標為「排程中」。
5. **到點後**：主站每 2 小時重建一次，所以實際上線時間會晚 0–2 小時。要在記者會同時發稿，請把時間設在目標時間前 2 小時，或當場送出（快車道約 3 分鐘）。
6. 要取消或改時間：改 `publishAt`（或刪掉）再走一次 PR；排程中的內容改動仍依其型別走原車道。
7. 快車道內容的「上線後複核 24 小時」從**實際上線時間**起算。

**緊急發布（`urgent`）**

1. 只有**新聞稿、致醫界通函、澄清**會顯示「緊急發布：立即上線並通知複核」勾選框；其他型別不會出現（疾病、疫苗、文件、Q&A 會被 AI 引用，不可跳過人工審核）。換成其他型別時，已勾的會自動取消。
2. 勾選後徽章變**緊急發布**。**CI 檢查一樣要全過**——省下的是人工等待，不是機器檢查。
3. 緊急與排程不併用（立即上線與排程互相矛盾，後台會警告）。
4. 上線後公關室收到 `post-publish-review` 待辦（24 小時內）；**每一次緊急發布都有紀錄**，請只在真正趕時間的情況使用（例如重大疫情澄清、更正錯誤資訊）。

**上線後複核待辦（公關室）**：在 `/admin/todos/` 看 `post-publish-review`。確認措辭、事實與 `basedOn` 正本一致後，在該內容 JSON 加 `postPublishReview: { "status": "done", "reviewedBy": "公關室內容總編輯", "reviewedAt": "2026-10-05" }` 並走快車道合併；有問題小錯直接改、嚴重錯誤把 `status` 改為 `archived` 下架。逾期升為高優先度。

### 2.10 修改已上架的頁面（看到錯字、數字錯了怎麼改）

**誰：** 任何承辦同事。**何時：** 網站上已發布的頁面有錯或要更新。**一句話：** 在公開頁頁尾點「同事修改這頁」，後台表單會帶入現行版，改好後走一般流程，PR 只會顯示你改的那幾行。

1. 在網站上打開那一頁，展開頁尾「本頁的資料與授權」，點 **「同事修改這頁（後台，需登入）」**（連到 `/admin/publish/?edit={內容 id}`）。這條連結只對站內同事有用，公開讀者點進去只會看到後台登入。
2. 後台表單標題變成「修改已上架：…」，上方藍框顯示內容 id、發布日、最後審閱日與**會被覆寫的檔案路徑**（例：`content/faq/dengue-painkiller.json`）；標題、內文、欄位、依據正本、多語設定都已帶入現行版。疾病頁的八個區塊會合成一份內文，每個區塊一個 `## 區塊標題`，只改你要改的那段、不要刪標題。
3. 直接修改。藍框下方會即時列出「目前改動的欄位」，沒改到的會寫「目前與現行版相同」——送出前看一眼，確認沒有誤觸。
4. 照一般流程「送出預處理」→ 確認結果 → 「產生上架包」。上架包裡的 JSON **就是同一個檔名**，解壓到 repo 會覆寫它；開 PR 後，複核者看到的 diff 只有你改的那幾行（發布日不變、審閱日改成今天、白名單核准狀態與舊站網址等表單沒有的欄位原樣保留）。
5. 走該型別原本的車道（2.8）；合併即上線，頁首的「最後審閱」會更新。
6. **改不到的**：附件原檔（已在 repo 裡，表單選不到；要換檔請把新檔放進 `content/assets/{id}/` 並更新 `assets` 的 `sha256`，見 2.6 第 5 點）、新聞 200 則以外的舊新聞（API 只含近 200 則，請資訊室直接改 JSON）、`draft`／`review` 狀態還沒上線的內容（不在 API 裡）。
7. **想取消**：藍框的「取消修改（清空）」會清掉表單並回到一般上架頁。

**為什麼不是在網站上直接按「儲存」？** 新官網沒有可寫的後台資料庫（[git-as-cms.md](git-as-cms.md)）：正本是 Git 裡的檔案，每一次改動都要經過 CI 檢查與車道複核才上線。「同事修改這頁」做的事是**替你把現行版填進表單、匯出時只改你動過的欄位**，省掉找檔案、手改 JSON 的步驟，但審核與追溯不省。

### `basedOn` 怎麼填

凡是**由別的正本衍生出來**的內容——新聞稿、Q&A、衛教影片文稿、懶人包——都要填 `basedOn`，值是正本的 `id`（文件填 `family`，例如 `doc.mmr-recommendation`，系統會自動追到現行版）。不填，正本修訂時系統就不知道這則內容要連動，會變成沒人看得到的舊資訊。原創內容（正本本身）可以不填。拿不準時多填不吃虧。

## 3. 正本修訂 SOP（MMR 案例走一遍）

**背景：** 2025-04-16 起，MMR 成人評估對象從「1981 年（含）以後出生」改為「1966 年（含）以後出生、不具麻疹免疫力者」。2025-01-09 的新聞稿仍寫 1981。

**誰、做什麼：**

1. **急性傳染病組 Steward** 在 `content/documents/` 新增一個**獨立檔案** `mmr-recommendation.2025-04-16.json`（不要覆蓋舊檔）：`family` 同 `doc.mmr-recommendation`、新的 `version`、`effectiveAt`、`supersedes` 指向舊版 id、填 `changes`（逐段前後差異）、貼上 `machineReadableMarkdown`。`supersededBy` 與 `isCurrent` **不要填**。
2. 開 PR，CI 通過後合併。

**系統自動做的事（同一次建置）：**

| 對象 | 自動結果 |
| --- | --- |
| 舊版（108.05.14） | 標為失效；頁首紅色橫條「已由新版取代」；`noindex`；`.md` 首行警示；退出白名單與搜尋索引；`v1/documents.json` 內 `isCurrent:false`；`redirects.json` 增一筆 301 |
| 2025-01-09 新聞稿（`basedOn` 指向此 family） | 頁首橘色加註「所依據的指引已於 2025-04-16 修訂，現行版請見…」；退出白名單；產生給 owner 的待辦，期限 **7 日** |
| 全站文字 | 反向稽核規則（在 `master/diseases.json` 的 `auditRules`）掃到仍寫「1981 年（含）以後出生」的內容，各開一筆待辦 |
| 專業專區 | 版本異動清單顯示新舊版與「查看異動對照」 |
| 評估集 | 版本題「幾年次以後出生的成人需要評估接種 MMR？」若仍引用舊版，建置失敗 |

**待辦怎麼關：** 待辦沒有「結案」按鈕，要把原因消除。公關室處理新聞稿，三種做法擇一：（a）改寫內文為現行規定，並更新 `reviewedAt` 為今天（須 ≥ 新版生效日）；（b）內文保留歷史但加上明確「已修訂」說明，更新 `reviewedAt`；（c）若已無保留價值，`status` 改 `archived`。送 PR，合併後待辦自動消失、白名單資格恢復。

## 4. 疫情發布 SOP

**誰：** 疫情中心狀態發布負責人。**何時：** 依監測週期（原型為每週），下次審閱日不得超過 7 日後。

1. `/admin/situation/` 逐項選四級狀態：`stable`、`rising`、`peak`、`declining`。**這是人工判斷，系統與模型不得代填。**
2. 填本週數字、趨勢、一句話建議、**發布依據**（例如「連續 4 週上升且超過流行閾值」）、資料日、下次審閱日。
3. 選**首頁卡樣版**（每個疾病可不同，存在該筆的 `cardStyle`）。四種樣版用同一份欄位，不必多填資料：

   | 樣版 | `cardStyle` | 長相 | 適合 |
   | --- | --- | --- | --- |
   | 標準（預設） | `standard` | 大數字＋指標名稱＋一句話建議 | 一般情況 |
   | 趨勢圖 | `chart` | 標準再加一條近週趨勢線（頭尾標週次） | 有連續「近週數字」、想讓人看到走勢；沒有近週數字會自動退回標準 |
   | 行動優先 | `advice` | 建議放最大，數字退到一行小字 | 高峰期要民眾馬上做一件事（打疫苗、清積水） |
   | 精簡 | `minimal` | 只有疾病、狀態與一行指標，不顯示建議 | 平穩期、不想佔首頁版面 |

   右側預覽即時切換，「並排比較四種樣版」可一次看四張再決定。
4. 預覽首頁卡片，確認文字；匯出 JSON 覆蓋 `content/situation/current.json`，舊版存入 `situation/history/`。
5. **確認：** 首頁「現在的疫情」顯示新資料日與你選的樣版；`/v1/situation.json` 的 `dataDate` 已更新。逾期未發布，態勢卡會自動出現黃色警示。

> **為什麼樣版是資料欄位，不是改程式？** 原本首頁卡只有一種長相，要換就得改模板、走程式 PR。改成把樣版名稱放在 `current.json` 每筆的 `cardStyle`，疫情中心在表單勾選就能換，和發布狀態走同一條 PR；前台、API、歷次發布都留有紀錄，資訊室不必為每次換版重新部署程式。四種樣版共用同一組欄位，所以不會為了版面多出要維護的資料。
>
> 名稱說明：這個表單與選單原本叫「態勢發布」，2026-10-05 起改稱「疫情發布」，和首頁「現在的疫情」用同一個詞；資料檔與網址（`situation/`、`/admin/situation/`）不變。

## 5. AI 暫停 SOP（目標：15 分鐘內）

**觸發條件：** 發現錯誤正在擴散、引用到失效或錯誤來源、資料來源異常、重大事件前需凍結。任何 Steward 或 OASIS 值班人可啟動。

| 時間 | 動作 |
| --- | --- |
| T+0 | 發現者通知 OASIS 值班與公關室；到 `/admin/ai-status/` 按「暫停」並填原因 |
| T+5 | 資訊室把 `content/governance/ai-status.json` 的 `paused` 改為 `true` 走緊急 PR（免複核，事後補審），合併發布 |
| T+10 | 確認前台：全站深色橫幅、答案頁退回傳統列表（標題、摘要、更新日）、提供 1922 |
| T+15 | 公關室視情況對外說明；權責單位開始修內容 |

**恢復：** 內容修正、評估集重跑通過後，把 `paused` 改回 `false`，原因欄寫明處置，PR 合併。每次暫停與恢復都會公開在[透明報告](https://ancientsky.github.io/new_cdc_prototype/transparency/)的暫停紀錄。

## 6. 錯答回報處理 SOP

1. 民眾或專業人員按「回報錯誤」，系統帶入稽核編號。正式環境進入 `/admin/reports/`，依頁面的 `owner` 自動對應 Steward。
2. 公關室 1 個工作天內確認分派。Steward 用稽核編號還原當時答案與引用來源。
3. 判斷屬於哪一類：（a）內容本身錯 → 走上架／修訂 SOP；（b）內容對但 AI 整理不當 → 通知 OASIS 加進評估集，並檢討檢索與拒答規則；（c）引用到失效版 → **視為嚴重缺陷**，立即暫停 SOP，同時加版本題。
4. 回覆回報人（若有留聯絡方式）；統計列入季報「已修正回報」。
5. **確認：** 修正後該題加入評估集並通過。

## 7. 季報怎麼產

季報不用手工做。每次建置都會重算 KPI（`/v1/governance/kpi.json`）與評估報告（`/v1/governance/eval-report.json`），[透明報告頁](https://ancientsky.github.io/new_cdc_prototype/transparency/)直接顯示。每季最後一週：

1. OASIS 擴充並凍結本季評估集版本，跑完整評估（含 LLM-as-judge 與 10% 人工抽樣）。
2. 公關室補寫文字說明，資訊室彙整暫停紀錄與紅隊結果。
3. 資料治理委員會審閱後，以當季最後一次成功建置為準發布（網址不變、內容標明季別）。
4. 把 JSON 另存歸檔（`docs/` 外的歸檔位置由 OASIS 決定）。

## 8. 影音上架 SOP

**誰：** 製作影片的單位 Steward（公關室協助）。**何時：** 任何影片、動畫、Podcast、短影音要放上官網或 YouTube 之前。**原則：影片和文字內容一樣有版本、有權責、會過時。**

1. 到 `/admin/publish/`（或「影音管理」頁的「上架新影音」）選型別「影音」。
2. **兩個必填欄位，缺一不能送複核：**
   - **依據正本 `basedOn`**：影片內容根據哪份建議、指引或手冊？選文件 family（例如 `doc.mmr-recommendation`），系統會自動追到現行版。沒有依據正本的影片，正本改了就沒人知道它過時。
   - **逐字稿 `transcriptMarkdown`**：完整的口語稿，每段可加 `[00:30]` 時間標記。逐字稿是 AI 唯一能引用的影片內容，也是聽障民眾與外語翻譯的基礎。少於 50 字視為沒有，會被擋下並產生「無逐字稿」待辦。
3. 其他欄位：影音類型、YouTube id（可空；貼完整網址會自動取 id，空白則前台顯示示意海報）、**製作日期**、**依據版本標示**（例如「114.04.16 建議」，選了依據正本會自動帶入現行版次）、章節（每行「秒數 標題」，也可寫 `1:30`）、字幕語言。
4. 按「送出預處理」，逐字稿會經過三道檢查：
   - **反向稽核**：逐字稿是否還在講已宣告失效的說法（例如 MMR 影片說「1981 年以後出生」），命中以紅框顯示並指出在逐字稿第幾行。
   - **數字一致性**：潛伏期、通報時限（口語「二十四小時」會先轉成 24）與疾病主檔、疾病頁比對。
   - **製作日 vs 依據正本現行版生效日**：製作日**早於**現行版生效日，紅框「製作日早於依據正本現行版生效日」——這支影片一上架就是過時的，請先依現行版重製。
5. **YouTube 說明欄格式（固定）**：第一行必須是

   `製作日期 {producedAt} · 依據 {basedOnVersionLabel} · 正本 {正本網址}`

   上架表單結果區 (m) 與「影音管理」頁的「產生說明欄文字」鈕都會產出這一行；影片片頭畫面也要印同樣的製作日期與依據版本。
6. **影片檔不進 repo**：影片放 YouTube（`youtubeId`），官網不收影片與音訊檔（[assets-policy.md](assets-policy.md) 第 3 節）。若有自製的海報圖或章節示意圖，用第 2.3 節的面板以 `image` 加進來（要 alt 與 `license`，alt 描述畫面重點，不是「影片封面」）；講義或圖卡 PDF 以 `attachment` 加進，並確認有文字層。**逐字稿一律寫在 `transcriptMarkdown` 欄位，不要只附 PDF**，因為只有欄位內的文字能進索引與反向稽核。
7. 按「產生上架包」，依第 2.6 節解壓到 repo（JSON 在 `content/media/`），開 PR。

### 正本修訂後，影片怎麼處理

正本修訂當天，引擎自動把依據它的影片標為過時（影片頁加註「本影片依 … 製作，建議已於 … 修訂」、退出 AI 白名單），並在「連動待辦」的「影音過時」頁籤開待辦給 owner（7 日內）。承辦人三選一：

1. **更新說明欄**：影片大致仍可用、只有少數數字或條件變動。改說明欄第一行，並在置頂留言補充修訂要點。
2. **加資訊卡**：差異集中在特定時間點，在 YouTube 該秒數加資訊卡，連到正本現行版。
3. **下架**：核心結論已不成立。影片設為不公開，`status` 改 `archived`，排入重製；重製版依現行版製作後，待辦自動消失。

處理後把 `reviewedAt` 與（必要時）`basedOnVersionLabel` 更新並開 PR。MMR 示範：候診衛教動畫（2025-01，依 108.05.14）已自動標過時，2026-10 重製版依 114.04.16 製作後不再過時。

## 9. 專區與外部連結維護 SOP

**專區（`topic`）** 取代現行官網的小 Banner 連結列（防災須知、PrEP、匿名篩檢、抗生素抗藥性…）。

1. 上架表單選「專區」：類型、簡介、**連結列（每行「標題 | 網址」）**、起迄日、相關內容 id（搜尋站內疾病、FAQ、文件、影片）。`https://` 開頭系統自動判為外部連結，`/` 開頭為站內。
2. 有 `endAt` 的專區，到期自動從首頁專區列退場，專區頁保留並標「已結束」，不需要人工下架。
3. **外部連結由 CI 每日檢查**（`npm run fetch -- --check-links`，對每條 https 連結送 HEAD）。結果寫回連結的 `status`（`ok`／`broken`／`unchecked`）與 `lastCheckedAt`；`broken` 自動產生「連結失效」待辦（約 7 日）。
4. 承辦人看到待辦：到 `/admin/links/` 找到該條連結，確認是暫時性故障還是網址已改，更新或移除後開 PR；下一次每日檢查通過，待辦自動消失。
5. 站內連結不在此檢查範圍，由建置時的參照檢查保證。

## 10. 公告上架與截止 SOP

**適用：** 「其他訊息」（`newsType: other`，`news` 型別）。**人才招募與採購公告已在第七輪移出**：人才招募改為 `job` 型別（第 16 節，人事室），採購公告改為 `tender` 型別（第 17 節，秘書室）；`news` 的 `newsType` 不再有 `recruit`、`procurement`。以下截止規則仍適用於其他訊息，招募與採購的階段與截止自動退場另依第 16、17 節。

1. 上架表單選「其他訊息」：**截止日（必填）**、字號、相關網址（外部連結，會被每日檢查）。審閱週期預設 0（事件觸發），不必理會審閱到期。
2. **截止後完全不需要人工**：截止日一過，系統自動標「已截止」、退出首頁與進行中列表（其他訊息保留在 `/notices/` 的「已截止」列表），也不會產生待辦。
3. `/admin/notices/` 看公告的截止倒數；已截止而未封存者會出現「建議封存」。封存是年度清理，不是時限：把 `status` 改成 `archived` 並開 PR。已截止超過 90 天仍上架者，會計入 KPI「已截止超過 90 天仍上架的公告」。
4. 公告更正、延長截止日：直接改 `deadlineAt` 並更新 `reviewedAt`，新聞稿頁首會顯示最後審閱日。

## 11. 檢驗項目表維護 SOP

**誰：** 檢驗及疫苗研製中心 Steward。**內容：** 每個疾病一筆 `labtest`，列出各檢體的容器、量、保存、運送、採檢時機與可做檢驗，以及檢驗單位。專業版索引會把每個檢體轉成一句結構化句，可被問答直接引用。

1. 上架表單選「檢驗項目」：選疾病（傳染病主檔）、檢驗單位（至少一個）、送驗時限（小時）。
2. **檢體每行一筆：** `名稱 | 容器 | 量 | 保存 | 運送 | 時機 | 檢驗`，前五欄必填，「檢驗」以「、」分隔（例：`NS1 抗原、RT-PCR`）。缺欄位預處理會以紅框指出第幾行。
3. 預處理會把**送驗時限與主檔通報時限比對**，送驗時限大於通報時限就警告。兩者本來就不同時（例如通報 24 小時、檢體 48 小時內送達）請在備註說明；CI 的引擎有同樣檢查，不一致會產生低優先的「檢驗不一致」待辦。
4. 病例定義或送驗單改版時，同步更新 `caseDefinitionDoc`、`formDoc`。主檔通報時限改了，`/report/` 的通報時限表會自動跟著改，不必另外維護。

## 12. 申請服務頁維護 SOP

**範圍：** 個案資料申請、檢驗委託、接種證明（黃皮書）、疫苗基金捐款、旅遊醫學門診、研究資料申請等（`service`，前台路徑 `/apply/{slug}/`）。

1. 上架表單選「申請服務」：服務類型、**對象**（民眾、醫療院所、研究者、地方衛生局…，決定在 `/apply/` 歸到哪個群組）、**步驟（每行「標題 | 說明 | 誰 | 天」）**、應備文件、承諾處理天數、費用、法源、表單（每行「標題 | 網址 | 格式」）、線上申請網址。
2. 步驟的「天」是整數；各步驟天數合計大於承諾處理天數，預處理會警告。承諾天數是對民眾的公開承諾，改動前先與主管確認。
3. 表單盡量提供機讀格式（odt、csv）；格式欄填 `odt`、`csv` 等，系統標記為可機讀。
4. 服務頁的步驟、應備文件、處理天數會進問答索引，民眾問「怎麼申請、要帶什麼、幾天」時可直接回答，所以改了流程就要改這頁，不要只改公文。

## 13. 出版品登錄 SOP

**範圍：** 疫情報導（1985 年起卷期）、年報、手冊、海報、統計（`publication`）。

1. 上架表單選「出版品」：類型、**系列（必填）**、卷、期、版次、ISBN、ISSN、GPN、摘要、**篇目（每行「篇名 | 作者(、分隔) | 頁碼」）**。ISBN／ISSN／GPN 格式不對預處理會提醒。
2. **審閱週期預設 0**：出版品是紀錄，不會逾期。內容有誤以勘誤或新版次處理，不改原件。
3. 作者欄只放發表時署名的作者；原型示範資料不放真人姓名。
4. 登錄後會出現在 `/publications/` 與 `feeds/publications.xml`，書目完整度（ISBN、GPN）是圖書館與研究者引用的基礎。

## 15. 舊站內容移轉 SOP

**適用：** 把現行官網（舊站）上的專區、欄目或疾病頁移轉到新站，並確保**每一個舊網址都有明確的去處**。做法是「**推導清單 → 只寫例外**」：舊站每個疾病頁的子頁結構相同，所以每一種法定傳染病（原型主檔收 72 種，正式為 99 種）的移轉清單由系統依**標準模板**自動推導，同事**只需要補模板沒有的例外**（疾病特有的專區頁、專屬指引與公告）。第一個完整示範是結核病專區（`content/migration/tuberculosis.json`），第六輪另有登革熱、流感、麻疹、腸病毒四份「只寫例外」的範例。
**誰：** OASIS 維護模板與彙整進度；各組 Steward 確認名下疾病的清單、補例外；資訊室處理伺服器轉址。
**為什麼要做：** 舊網址是加密 ID，不可能自動對應；漏掉一個，民眾的書籤、LINE 轉傳的連結、其他機關的引用和搜尋排名就少一個。每種疾病各寫 40 筆既不可能也不必要，因為其中約 20 項是每個疾病都一樣的標準子頁。完整道理與伺服器設定見 [migration-playbook.md](migration-playbook.md)。

### 15.1 兩種清單：推導的與人工的

| | 推導清單 | 人工清單 |
| --- | --- | --- |
| 來源 | 系統依 `content/migration/_disease-template.json` 對主檔每一種疾病自動產生 | `content/migration/{slug}.json`，同事手寫 |
| 數量 | 72 份（主檔每一種傳染病各一份；已有新站疾病頁者依對應推導，尚無疾病頁者標 `no-page`） | 只在有例外時才有（結核病、登革熱、流感、麻疹、腸病毒…） |
| 內容 | 標準子頁：疾病介紹各分頁、預防接種、Q&A、衛教單張與影片、工作手冊、病例定義、治療指引、統計、檢驗、通報定義、新聞稿列表、相關連結 | **只寫模板沒有的**：疾病特有專區頁、專屬 PDF、特定公告與名單 |
| 狀態怎麼來 | 新站有對應就算移轉：疾病頁區塊或主檔欄位命中 ⇒ `merged`；關聯的 Q&A、文件、影音、資料集、檢驗、新聞命中 ⇒ `migrated`；沒命中 ⇒ `pending` | 同事逐筆寫 `status` 與 `target` |
| 疾病頁還沒建立 | 整份清單標 `no-page`，所有項目 `pending` | — |
| 衝突時 | 被覆蓋 | **同 `key` 以人工為準**；人工沒寫的 key 仍由模板補（結核病也會自動補上模板有而人工沒列的項目） |
| `verified` | 一律 `false`，由 Steward 確認後才改（見 15.8） | 同左 |

人工清單用 `"extends": "migration-template.disease"` 明示自己是例外清單。**不要在人工清單重寫模板已有的標準子頁**；只有「模板的某一格對不到、或要指定到某一份具名文件」時，才用同 `key` 覆蓋。

### 15.2 流程總覽

| 步驟 | 誰 | 產出 | 在哪裡 |
| --- | --- | --- | --- |
| 1 看推導清單 | Steward | 知道自己疾病有哪些標準子頁已移轉、哪些 `pending` | `/admin/migration/`（15.4） |
| 2 補內容讓推導命中 | Steward | 補疾病頁區塊、Q&A、文件、影音、資料集等，`pending` 自然變 `migrated`／`merged` | `content/`、`/admin/publish/` |
| 3 盤點舊頁中的例外 | OASIS＋Steward | 模板沒有的疾病特有頁面清單 | 舊站導覽、log、Search Console |
| 4 寫人工清單（只寫例外） | Steward（OASIS 協助） | `content/migration/{slug}.json`（5–8 筆是常態） | repo |
| 5 後台確認 | Steward | `verified: true` | `/admin/migration/` |
| 6 上架新內容、補治理欄位 | Steward | 新頁（含 `owner`、`reviewedAt`…） | `/admin/publish/` |
| 7 檢查轉址 | Steward＋資訊室 | 新頁揭露、`/legacy/` 查得到、伺服器 301 | 新頁、`/legacy/`、伺服器 |
| 8 上線後看 404 報表 | OASIS＋Steward | 補進清單的新項目 | `scripts/analyze-404-log.mjs` |
| 9 到期關閉與揭露 | 資訊室＋OASIS | 舊站下線、揭露自動隱藏 | `showLegacyUntil` |

舊頁的**內容本身**要搬進新站時，步驟 2、6 可以改用匯入工具批次產生草稿（15.14），再由 Steward 逐頁確認。

### 15.3 模板由誰維護

- **維護單位：** OASIS（模板檔的 `owner`）。模板是全站共用的規則，不是任何一個疾病的內容；改動前請在 PR 說明影響到幾份清單。
- **檔案：** `content/migration/_disease-template.json`（底線開頭代表模板，不是清單）。每一筆含 `key`、`oldTitle`、`oldPath`、`oldUrlPattern`（含 `{id}` 佔位）、`oldType`，以及 `mapTo`——描述「新站哪裡有對應就算移轉」：
  - `disease-block`：對應疾病頁的某個區塊（例：發病症狀 ⇒ `symptoms`）；
  - `master-field`：對應主檔欄位（例：潛伏期、通報時限）；
  - `related`：對應關聯內容（Q&A、文件、影音、資料集、檢驗、新聞、專區），可指定 `docType` 等條件；
  - `page`：對應站內固定頁（例：通報定義 ⇒ `/report/`）。
- **何時改模板：** 舊站所有（或絕大多數）疾病頁新增或移除了一種標準子頁；新站新增了可以承接某種舊頁的內容型別。**單一疾病的特殊頁面不要放模板**，寫人工清單。
- **改完怎麼驗：** `npm run check` 通過後看 `/admin/migration/` 的總體進度與 `no-page` 數是否合理；`key` 一旦被人工清單引用就不要改名。

### 15.4 後台怎麼看 72 份清單

打開 `/admin/migration/`：

1. **總體進度**：整體已移轉／已併入／待移轉筆數與進度條；`no-page`（疾病頁尚未建立）有幾份。
2. **摘要表**：每種疾病一列——法定類別、疾病頁有無、已移轉／已併入／待移轉、進度條、標示「人工」或「推導」、下載 JSON。預設依**待移轉最多**排序，先處理差距最大的。可篩選「有頁／無頁」「人工／推導」與單位。
3. **展開單一清單**：逐筆看舊標題、舊網址、狀態、對應新頁、權責單位；「下載 JSON」（也在 `/v1/migration/{slug}.json`）可當成人工清單的起點，刪掉不需要覆蓋的項目後存成 `content/migration/{slug}.json`。
4. **待辦**：每份清單只開**一則**聚合待辦「{疾病}：N 個舊頁待移轉」（`no-page` 清單為「{疾病}：疾病頁尚未建立，N 個舊頁待移轉」），優先度依法定類別（第一、二類高、第三類中、第四與五類低）；在 `/admin/todos/` 的 `migration-pending` 頁籤處理，不再一筆一筆開。
5. 推導清單的項目一律 `verified: false`，這是正常的：確認的人是 Steward，見 15.8。

### 15.5 何時需要人工清單？只寫例外

先看自己疾病的推導清單。符合以下任一種情況才需要建人工清單：

| 情況 | 例子 | 怎麼寫 |
| --- | --- | --- |
| 舊站有**疾病特有的專區頁** | 登革熱防治專區、病媒蚊密度調查、流感疫苗專區、麻疹群聚專區、腸病毒停課與通報 | 新增 `key`（加疾病前綴，如 `dengue-zone`，避免與模板 key 撞名） |
| **具名的專屬 PDF／公告**要指定到某一份文件 | 接觸者追蹤指引、歷版指引、通函 | 新增項目，`target` 填具名文件（`document` 要寫含版本日期的 id，如 `doc.xxx.2026-09-10`） |
| 模板某格**對錯了**或要指定到別處 | 模板把「治療指引」對到任意 guideline，但這個疾病要指定某份 | 用**同 `key`** 覆蓋 |
| 舊頁**過時不移轉** | 歷年海報、逾期計畫 | `dropped`，`note` 寫理由 |

步驟：

1. 複製 `content/migration/dengue.json` 當範本；改 `id`（`migration.{slug}`）、`title`、`scope`（`{ "kind": "disease", "disease": "disease.xxx" }`）、`owner`、`diseases`、`legacyRoot`、`showLegacyUntil`；保留 `"extends": "migration-template.disease"`。治理共同欄位（`reviewedAt`、`reviewPeriodMonths` 等）和其他內容一樣要填。
2. 在 `sourceNote` 寫明「本清單只寫模板沒有的例外」。
3. 每個例外一筆 `items`（5–8 筆是常態，超過 15 筆要想想是不是該改模板）。欄位與狀態規則見 15.7。
4. `npm run check`；再看 `/admin/migration/` 該疾病的列已標「人工」，且模板的標準子頁仍在（未被你覆蓋的 key 照常推導）。

### 15.6 盤點舊頁

1. 從舊站該專區的導覽開始，把頁面列出來，**先對照模板，已涵蓋的標準子頁不必再列**，只記錄模板沒有的：疾病介紹的每個子頁籤、Q&A、新聞稿列表、指引與手冊的 PDF、衛教素材、統計、檢驗與通報說明、相關連結。
2. 補上「有流量但導覽找不到」的頁面：請資訊室提供過去 12 個月的 access log 與 Search Console 熱門頁面，凡是有流量的舊網址都要在清單內。
3. 每一頁做判斷（規劃文件 §7.4 第 4 點的四因子：使用者需求、相關性、重複性、優先度）：**保留、合併進別頁、封存、不再提供**。
4. 舊網址的 ID 請照官網原樣貼上（22 字元，區分大小寫）。**不確定 ID 時保留 URL 模式，ID 寫成 `{id}`**，但這種項目上線前一定要補成真實 ID（見 15.8）。

### 15.7 逐筆對應（欄位與狀態規則）

1. 清單頂層欄位請見 15.5；本節說明每一筆 `items` 的寫法。
2. 每個例外舊頁一筆 `items`：`key`（清單內唯一，小寫英數與連字號）、`oldTitle`、`oldPath`（麵包屑，以「／」分隔）、`oldUrl`、`oldType`（`page`、`qa`、`pdf`、`news-list`、`media`、`list`、`external`）。
3. 決定 `status` 與 `target`：

| 舊頁情況 | `status` | `target` | 伺服器結果 |
| --- | --- | --- | --- |
| 整頁搬到新的一頁 | `migrated` | 新內容 id | 301 到新頁 |
| 併入新頁的一個段落 | `merged` | 新內容 id，加 `anchor`（如 `symptoms`） | 301 到新頁（含錨點） |
| 新頁還沒做好 | `pending` | 可空 | 暫時由舊站唯讀提供；**會產生 `migration-pending` 待辦** |
| 已封存供查閱（例如舊版本） | `archived` | 封存頁的內容 id（必填） | 301 到封存頁 |
| 刻意不再提供 | `dropped` | 空 | 410 |

4. `target` 的規則：必須是已存在的內容 id（`migrated`／`merged`／`archived` 必填；`pending`／`dropped` 可空），否則建置失敗。**一個舊頁只能對到一個新頁**（一對多不可）；同時涵蓋兩個主題時，選主要用途那個，另一個在新頁以「相關內容」連過去，並在 `note` 記下取捨。
5. 舊的 PDF（手冊、指引）的 `target` 填**文件（`document`）的 id**，不是 PDF 檔；沒有文件頁的先上架一筆文件（見 15.9）。**`target` 要寫含版本的完整 id（例 `doc.tb-guideline.2025-09-01`），不是版本族 id（`doc.tb-guideline`）。**舊版本的 PDF 優先對到該版本自己的文件頁。`anchor` 只用在疾病頁已有的區塊 key（如 `symptoms`、`vaccine`）；文件章節目前沒有錨點，不要填，否則連結檢查會出現 `missing-anchor` 警告。
6. 選填：單筆的 `owner`（缺省沿用清單的權責單位）、`dueAt`（`pending` 的預定完成日，缺省為清單 `reviewedAt` 後 60 日）、`verifiedAt`／`verifiedBy`（確認日與確認者職稱，不放真名）。
7. `note` 寫給同事看的說明，例如「併入疾病頁『症狀』區塊」；`newRequirements` 寫這筆移轉後新增的治理要求（`owner`、`reviewedAt`、`basedOn`、`machineReadable`、`languages`），新頁會用 chip 顯示。

### 15.8 後台確認 `verified`

**誰：** 該專區權責單位的 Steward。這一步是對外承諾「這個舊網址就是這一頁，新頁就是對的」，不能由 OASIS 代填。

1. 打開 `/admin/migration/`，找到你的疾病（推導與人工清單都在這裡），看進度：已移轉、已併入、已封存、待確認、**待核對（`verified: false`）**。
2. 逐筆打開 `oldUrl` 確認它真的是這個舊頁，再打開新頁確認內容涵蓋舊頁；錨點段落確實存在。
3. 該筆確認無誤，在清單 JSON 把 `verified` 改為 `true`（**推導清單沒有 JSON 檔可改：先從後台下載該疾病清單、存成人工清單，再改 `verified`**，這時你會得到一份完整確認過的清單），並填 `verifiedAt` 與 `verifiedBy`（職稱），開 PR。
4. **`oldUrl` 含 `{id}` 佔位的，在這一步補成真實的舊網址**；補完才會進伺服器轉址檔。切換前「`{id}` 佔位」筆數必須為 0。
5. 確認時順便檢查：這個舊頁的 `owner` 對嗎？內容是否已過時需要審閱？移轉是檢視內容的好時機，不要把過時內容原樣搬過去。

### 15.9 上架新內容、補治理欄位

每筆 `migrated`／`merged` 的 `target` 都是一則新站內容，**移轉不等於搬運**：進新站就要符合治理要求。

| 舊站內容 | 新站型別 | 移轉時一定要補的欄位 |
| --- | --- | --- |
| 疾病各子頁籤 | 疾病頁（`disease`）的區塊 | `owner`、`reviewedAt`、`reviewPeriodMonths`；`legacyUrls` |
| 手冊、指引、病例定義 PDF | 文件（`document`） | `family`、`version`、`effectiveAt`、`machineReadableMarkdown`（機讀版）；舊版另建獨立檔並以 `supersedes` 串起；PDF 放在該版自己的 `content/assets/{id}/`，沒有文字層的另附 `.md`（`accessibleAlt`） |
| Q&A | `faq` | `basedOn`（依據的疾病頁或文件）、`reviewedAt` |
| 新聞稿 | `news` | `basedOn`（若由正本衍生） |
| 專區、連結列 | `topic` | 連結（外部連結會被每日檢查） |
| 補助、申請說明 | `service` | 步驟、應備文件、處理天數 |
| 影片 | `media` | `basedOn`、逐字稿、製作日期 |

各型別的上架步驟照第 2 節與第 8 至 13 節。舊站的 PDF、圖片與表單，電子檔取得後放進 `content/assets/{內容 id}/` 並在 `assets` 宣告（規則見 [assets-policy.md](assets-policy.md)），取代原本的 `/pending/` 連結；掃描檔要先處理可及性（assets-policy 第 4 節）。新內容裡的舊網址放在 `legacyUrls`（或由清單 `target` 帶出），不要自己在內文寫死舊網址。尚未能遷移的附件，內文連到 `/pending/?ref=<內容 id>&doc=<文件名稱>`，不要連回舊網址。

### 15.10 檢查轉址

PR 合併後（或在本機 `npm run build`）：

1. **新頁**：打開 `target` 的頁面（例如 `/diseases/tuberculosis/`），頁首治理列有「本頁取代舊網站 N 個頁面」；展開看每筆舊標題、舊網址、狀態與新增的治理要求。N 與清單中指向這頁的筆數一致。
2. **`/legacy/`**：把一個舊網址貼進去，應該顯示對應新頁的連結。
3. **404 頁**：在網址列輸入舊路徑，應顯示「舊網址已搬家，3 秒後帶你到新頁」。（這是原型的備援；正式站由伺服器 301。）
4. **後台**：`/admin/migration/` 的進度與你預期一致；`/admin/todos/` 的 `migration-pending` 頁籤只剩你確定還沒做的項目。
5. **正式伺服器**（資訊室）：把 `redirects/nginx.map`（或 IIS、`_redirects` 版本）匯入測試機，用真實舊網址檢查一跳到位。方法見 [migration-playbook.md](migration-playbook.md) 第 2.5、3.2 節。推導清單的舊網址都是 `{id}` 佔位（標 `pattern`），不會進伺服器檔；補成真實 ID 並確認後才會進。

### 15.11 上線後看 404 報表

**誰：** OASIS 每週跑；Steward 處理分派給自己的項目。

```bash
node scripts/analyze-404-log.mjs access.log --map dist/v1/legacy-map.json --migration content/migration
```

報表三類，各怎麼處理：

| 報表分類 | 意思 | 你要做什麼 |
| --- | --- | --- |
| 可直接 301 | 對照已有，但伺服器沒命中 | 交資訊室查規則是否已部署、比對方式是否一致 |
| 待補對照 | 符合舊站網址模式但清單沒有 | 把報表附的 `items` 草稿貼進清單（`verified: false`），確認 `target` 後依 15.8 改 `true`，開 PR |
| 真的不存在（建議 410） | 不符合任何舊站模式 | 次數高的先確認不是漏盤的舊頁；確認後列入 410 名單 |

節奏：上線後前兩週每天、到第 90 天每週、之後每月。**報表是待辦來源，不是看完就算**：每週一併入 `/admin/todos/` 的檢視，OASIS 把「待補對照」分派到對應 Steward。

### 15.12 到期關閉與揭露

1. 清單的 `showLegacyUntil` 到期（建議上線日 + 12 個月）：**新頁上的「本頁取代舊網站 N 個頁面」自動隱藏，不需要任何人操作。**
2. 到期前 60 天：OASIS 確認 `migration-pending` 已清零（要嘛移轉完成，要嘛決定 `dropped`），公關室預告舊站關閉。
3. 資訊室在到期日下線舊站唯讀本體。
4. **伺服器上的 301 不關。** 也不要刪除或停用 `content/migration/*.json`——它是轉址檔的來源。需要整理清單時，先比對轉址檔條數，確認沒有減少。

### 15.13 常見問題

| 問題 | 回答 |
| --- | --- |
| 一個舊頁的內容其實分到兩個新頁怎麼辦？ | 選主要用途那一頁當 `target`，另一頁在新頁以相關內容連過去；`note` 記下取捨。一個舊網址不能轉到兩個地方 |
| 舊頁已經過時，要不要搬？ | 不要原樣搬。先審閱：過時就 `dropped`（410）或 `archived`；仍有用就更新後再上架，`reviewedAt` 填實際審閱日 |
| 舊網址的 ID 我現在查不到 | 保留 `{id}` 佔位並維持 `verified: false`，向資訊室索取舊站資料表或 log；補上之前不會進伺服器轉址檔 |
| 可以把所有沒對應的舊頁都轉首頁嗎？ | 不行。搜尋引擎會當成 soft 404，民眾也找不到東西。沒對應就回 410 |
| 清單裡的項目比新頁數量多很多，正常嗎？ | 正常。舊站拆很細，新站一頁八個區塊，多對一是常態；用 `anchor` 對到段落 |
| 要不要通知別人我們換網址了？ | 要。切換前由公關室通知引用我們連結的機關與媒體，並更新 1922 話術、LINE 疾管家與衛教影片說明欄中的網址 |
| 我的疾病沒有人工清單，進度卡住不動？ | 看推導清單的 `pending` 項目：多半是新站缺 Q&A、文件、影音或資料集。補上內容（含關聯疾病 id）後，下次建置自動轉為已移轉；不需要改清單 |
| 推導清單說「已併入」，但我覺得對不上？ | 推導只確認「新站有對應內容」，不保證內容涵蓋舊頁。Steward 在 15.8 逐筆確認時才是真正的把關；對不上就建人工清單用同 `key` 覆蓋 |
| 疾病頁還沒建立，清單也要管嗎？ | 要。`no-page` 清單所有項目 `pending`，只開一則待辦，優先度依法定類別；先建疾病頁，推導項目就會陸續命中 |

### 15.14 用匯入工具產生草稿

**適用：** 一批舊頁（例如整個專區）的內容要搬進新站，手工複製貼上太慢。**誰：** OASIS 跑工具；Steward 確認草稿；公關室抽樣檢視新聞。完整說明、匯出格式與規則檔見 [legacy-import.md](legacy-import.md)。

1. **請資訊室匯出**：每頁一個 `.html` 加同名 `.json` 側檔（`url`、`title`、`category`、`publishedAt`、`updatedAt`、`breadcrumbs`、`attachments`），附件放 `files/`。欄位規格見 legacy-import.md 第 2 節。
2. **OASIS 跑工具**：`node scripts/import-legacy.mjs <匯出目錄> --out <輸出目錄>`（輸出目錄**不要**指到 `content/`）。得到草稿、附件、`report.md`／`report.json`、`migration-patch.json`。
3. **先看報告摘要**：頁數、平均信心、需人工檢視數。「未對應類別」「型別不明」這類問題先**補規則檔再重跑**（`content/migration/import/_import-rules.json`），比逐頁修便宜。
4. **分三級處理**：
   - 現行一級內容（疾病介紹、指引、Q&A…）：Steward **逐頁確認**，信心高低都要看；
   - 近年新聞、信心 ≥ 0.8（報告標 `auto-ok`）：公關室抽樣檢視約 10%，沒問題就批次改 `status: published` 開 PR，走快車道；
   - 久遠內容、歷史版本（`archive`／`drop`）：不轉上線，依移轉清單封存或回 410。
5. **逐頁確認怎麼看**：開草稿 JSON 與報告該頁的問題清單：標題與型別對不對、內文有沒有漏（表格、清單）、Word 殘留、**圖片 alt（`needsAlt` 必補）與授權**、數字是不是現行版、`owner`／`audience`／`basedOn`。信心 **< 0.6** 的一定要逐頁看。
6. **補完才上線**：把草稿放進 `content/` 對應資料夾（附件放 `content/assets/{id}/`）、`status` 改 `published`、更新 `reviewedAt` 為你實際審閱的日期，依 2.6 開 PR；車道由型別決定（2.8）。
7. **更新移轉清單**：OASIS 加 `--apply-migration` 重跑（或直接套用 `migration-patch.json` 的建議），把清單項目的 `status`／`target` 更新；**`verified` 仍由你在 `/admin/migration/` 逐筆確認**，工具不會替你勾。
8. 後台 `/admin/import/` 可看每批報告（批次摘要與逐頁表），也可下載草稿 JSON。

**注意：** PDF 不整批轉換（只宣告為附件，沒文字層會開待辦）；草稿是機器產生的「第一版」，不是審閱過的內容。

## 16. 人才招募上架 SOP（人事室）

**適用：** 疾管署對外的職缺公告：約聘、約僱、聘用研究員、公費醫師、技工工友駐衛警、公務人員商調、計畫助理、臨時人員。第七輪起，人才招募**不再是新聞稿的一種**，而是獨立的 `job` 型別（`content/jobs/`、路徑 `/careers/{slug}/`），權責單位固定為**人事室**（`unit.personnel`）。採購公告見第 17 節。
**誰：** 人事室 Steward 建檔與維護；**用人單位**提供職務內容並在甄試時協助；資訊室不介入。
**一句話：** 人事室只填日期與結果，其餘的階段（即將開放、報名中、已截止、審查與甄試中、結果公布、歷史）由系統依日期自己算，截止後**完全不需要人工下架**。
**重要界線：** 本站（原型）上的「線上報名」是**模擬**，不送出任何資料、不存任何人的報名資料（見 [careers-privacy.md](careers-privacy.md)）。正式站的報名系統在站外或後端，本站只負責公告、時程、狀態與結果公布。

### 16.1 公告建檔：誰填什麼

**用後台 `/admin/jobs/edit/`「人才招募上架與異動」表單上架**（操作見 16.10）：選「新增職缺」，填完 A 區，右側檢核全過後匯出 JSON，存成表單顯示的檔名、開 PR 即可。不需要手寫 JSON。

- **原本：** 人事室要照下表自己寫 JSON 檔，`/admin/publish/` 不提供這個型別，寫錯日期或欄位名要等 CI 失敗才知道。
- **改成：** 表單逐欄填寫，邊填邊在右側看到前台階段（報名中、即將開放…）、關鍵日期與「發布前請補齊」清單；匯出的檔案共同欄位（owner、license、aiWhitelist…）都已自動帶好。
- **為什麼比較好：** 錯誤在填表當下就看得到，不用來回跑 CI；檢核規則與建置用的是同一份程式（見 16.10），所以表單說過就一定過。

檔案是 `content/jobs/{yyyy-mm-dd}-{slug}.json`（日期用公告日；`id` 為 `job.{yyyy-mm-dd}-{slug}`、必填欄位 `slug` 必須等於 id 去掉前面 `job.{日期}-` 的部分，路徑即 `/careers/{slug}/`；**id 建了就不要改**，表單對既有職缺會鎖定 id 與 slug）。下表是各欄位的意思與人事室、用人單位的分工（表單的欄位就是這些）：

| 欄位 | 誰提供 | 說明 |
| --- | --- | --- |
| `title`、`jobType`（職類）、`refNo`（公告字號，選填）、`contact` | 人事室 | 職類八選一；`contact` 寫人事室承辦窗口（職稱與公務電話、信箱，不放私人聯絡方式） |
| `hiringUnit` | 人事室，依用人單位需求 | 用人單位的 unit id（例：`unit.acute-infectious`）；結果逾期待辦會抄給它 |
| `positions`、`workplace`、`salaryNote` | 用人單位提出需求，人事室核對 | 名額（整數）、工作地點、薪點或薪資範圍（文字，依機關職務與待遇規定，不要自己創造數字） |
| `duties[]`、`qualifications[]` | **用人單位**撰寫，人事室審核措辭 | 工作內容、資格條件；一條一項，避免「其他經本署認定者」這類無法判斷的句子 |
| `requiredDocuments[]` | 人事室 | 應備文件；檔案只列名稱，不收原件內容 |
| `applyStart`、`deadlineAt` | 人事室 | 報名開始日與截止日；`deadlineAt` 當日仍可報名，隔日起自動轉「已截止」 |
| `applyMethod`、`applyUrl` | 人事室 | 報名方式，見 16.2 |
| `examPlan[]` | 人事室與用人單位協調 | 每個階段（書面審查、筆試、口試、實作、體能）的日期與備註；日期未定可先不填 `date`，只寫 `note`；**甄試日期不得早於報名截止日**（否則建置失敗） |
| `resultPlannedAt` | 人事室 | 結果預計公布日；已截止頁面會顯示「結果預計 {日期} 公布」，也是結果逾期待辦的基準 |
| `attachments[]` | 人事室 | 簡章、報名表等；PDF 請同時提供機讀版（`machineReadable`），與其他文件一樣；檔案放 `content/assets/{id}/` 並在 `assets` 宣告（第 2.3 節）。**報名者的附件絕不放進 repo** |
| `legacyUrls[]`、`legacyIds[]` | 人事室 | 若是從舊站移轉的職缺，`legacyUrls` 填舊網址、`legacyIds` 填第七輪前以新聞稿發布時的舊內容 id（`news.*`，系統據此把舊 `/news/{slug}/` 301 到新職缺頁；見 [migration-playbook.md](migration-playbook.md)） |
| `result`、`waitlistUpdates` | 人事室 | 錄取結果與遞補，見 16.5、16.6 |
| `manualStatus`、`manualStatusNote` | 人事室 | 只有「取消」（`cancelled`）與「已補實」（`filled`）兩種人工覆蓋，`manualStatusNote` 寫理由，見 16.9；平常不要填 |

其餘共同欄位（`reviewedAt`、`reviewPeriodMonths`、`languages`…）依第 2 節；招募公告是事件型內容，`reviewPeriodMonths` 預設 0，不會因為審閱到期而產生待辦。`title`、`summary` 可附英文；職缺內容以中文為準。

建檔後 `npm run check`：缺必填欄位、`slug` 與 id 不一致或重複、`hiringUnit` 不在單位主檔、`applyStart` 晚於 `deadlineAt`、甄試日期早於報名截止都會失敗。

### 16.2 報名方式二選一

| 做法 | 設定 | 民眾看到 | 適用 |
| --- | --- | --- | --- |
| **A. 本站模擬報名** | `applyMethod: "online"`，**不填** `applyUrl` | 報名中顯示「線上報名」按鈕 → `/careers/{slug}/apply/`；頁面上方有橫幅「原型示範：資料只存在你的瀏覽器，不會送出」 | **只用於原型示範與教育訓練**，讓同事與委員看到完整流程 |
| **B. 外部報名系統** | 填 `applyUrl`（人事行政總處求才系統、機關自有報名系統等），`applyMethod` 依實際方式 | 報名中顯示連到外部系統的按鈕，標示「前往外部報名系統」；不產生 `/apply/` 頁 | **正式站的做法**；也適用 email、郵寄、親送（此時不填 `applyUrl`，在 `requiredDocuments` 與 `contact` 寫清楚收件方式，`applyMethod` 選 `email`／`mail`／`in-person`） |

**為什麼正式站不能用 A：** 報名資料含身分、學歷、聯絡方式，屬個人資料。靜態網站沒有後端，不該也不能收；正式的報名系統必須在站外或後端，有存取控管、保存期限與刪除機制。本站的責任是公告、狀態與結果公布。完整原則見 [careers-privacy.md](careers-privacy.md)。

填了 `applyUrl` 之後：外部連結每日被檢查，失效會產生 `job-apply-url-dead` 待辦（人事室處理：向外部系統管理者確認、更新網址或在 `contact` 補替代方式）。**報名中或即將開放的職缺優先度為「高」、期限 1 日**（民眾此刻無法報名）；其他階段為中優先。

### 16.3 截止自動退場（不需人工）

截止日一過，系統在下一次建置（每日排程）自動：

- 階段轉為「已截止」，頁面顯示「已截止，結果預計 {`resultPlannedAt`} 公布」，「線上報名」按鈕消失；
- 退出首頁與 `/careers/` 的「開放中」清單，改列「審查與甄試中」頁籤（已截止，含 `examPlan` 日期已到者）；
- 本站模擬報名頁改顯示「已截止」。

人事室**不需要**改 `status`、不需要下架、不需要記得去看。唯一要做的是在甄試後上架結果（16.5）。

### 16.4 甄試日期與結果預計公布日

- `examPlan[]` 每一階段填日期；階段日期過了，系統會把職缺標為「審查與甄試中」。日期有變動，用表單 B 區改期（16.10），會留下一筆異動紀錄；`note` 可再補原因（例：「配合颱風假順延」）。
- **`resultPlannedAt` 一定要填。** 它讓民眾知道何時回來看，也是待辦的基準：已截止（或甄試中）的職缺，今天超過 `resultPlannedAt` 7 天、仍無 `result`，系統開 `job-result-overdue` 待辦（中優先，給人事室，抄送用人單位）。沒填 `resultPlannedAt` 就不會有這個提醒。
- 預計日無法達成時，**不要等到逾期**，先改 `resultPlannedAt` 並更新 `reviewedAt`；待辦會在下次建置消失。

### 16.5 結果上架規則（遮罩是建置閘門）

甄選結束後，在同一個職缺檔加上 `result`：

```json
"result": {
  "publishedAt": "2026-10-20",
  "refNo": "疾管人字第1150001號",
  "admitted": [ { "seq": 1, "candidateNo": "1150924-012", "nameMasked": "陳○明" } ],
  "waitlist": [ { "rank": 1, "candidateNo": "1150924-027", "nameMasked": "林○", "validUntil": "2027-04-20" } ],
  "note": "請正取人員於收到通知後 7 日內辦理報到。"
}
```

規則（**違反即建置失敗，不是提醒**）：

1. **只公布報名編號與遮罩姓名。** `candidateNo` 是報名編號（報名系統產生，3 至 24 個英數字與連字號，例：`1150924-012`；**不得是身分證字號或居留證號**，任何位置出現 `A123456789` 這類樣式都會被擋）；`nameMasked` 必須含遮罩字（`○`、`◯`、`〇`、`＊` 任一），例：「陳○明」「林○」。**不得出現 3 個以上連續中文字的完整姓名樣式**（例：「陳小明」會被擋）。`result.note` 與遞補的 `note` 也會掃描身分證字號樣式；同一職缺內報名編號不得重複。不公布電話、信箱、地址、出生年月日、學校、成績與名次以外的任何個人資料。
2. **正取數不得超過名額。** `admitted` 的筆數不得多於 `positions`（超過同樣是建置失敗）；超過代表名額填錯或結果誤植，請在上架前先改清楚。後台 `/admin/jobs/` 的「結果上架檢核」會逐項顯示：遮罩檢核（通過／未通過、哪一筆）、正取數 ≤ 名額、備取有效期。
3. `seq` 與 `rank` 請依序從 1 起算、不重複（結果頁依它們排序）。
4. 備取名單填 `validUntil`（備取有效期，通常為公布後 3 至 6 個月，依簡章）；**過了有效期的備取名單自動不顯示**（見 16.6）。
5. 結果頁寫的是「公告」，不是通知：個別通知與報到文件依簡章另外處理，不放在網站。
6. **AI 不會唸名單。** 結果與遞補不進 AI 白名單；問「誰錄取」時，答案引擎只給結果頁連結，並說明本站只公布報名編號與遮罩姓名。這是刻意設計，請勿試圖把名單寫進 `note` 或 `summary` 繞過。

有 `result` 的職缺：階段轉為「結果公布」，進入 `/careers/` 的「錄取結果」頁籤；`/v1/jobs.json` 與 RSS（`feeds/careers.xml`）各出現一筆「錄取結果」。

### 16.6 備取與遞補公告

1. 正取人員放棄時，在 `waitlistUpdates[]` 加一筆：`date`（遞補日）、`candidateNo`、`nameMasked`、`note`（例：「遞補第 1 名」）。**遮罩與編號規則與正式結果完全相同**，一樣會被建置閘門檢查。不要改動原有的 `admitted`，以保留公告歷程。
2. 結果頁的「遞補紀錄」會依日期顯示；RSS 同步多一筆。
3. 備取 `validUntil` 前 14 天（且該備取尚未遞補），系統開 `job-waitlist-expiring` 待辦（低優先）：確認是否還需要遞補、或可以結案。
4. `validUntil` 當日之後，該筆備取**自動不顯示**於結果頁，不需要人工刪除；原始檔案仍留在 Git 歷史。

### 16.7 90 天後自動進歷史

結果公布（`result.publishedAt`）超過 90 天，職缺自動從「錄取結果」頁籤移到「歷史」頁籤；已取消、已補實的職缺直接列在「歷史」。**內容與結果仍保留**（保存期限與下架另依 [careers-privacy.md](careers-privacy.md) 第 5 節）。不需要人工操作。

### 16.9 常見問題

| 問題 | 回答 |
| --- | --- |
| 要延長報名怎麼辦？ | 到 `/admin/jobs/edit/` 選這個職缺，在 A 區把報名截止日改成新日期（甄試日、結果預計公布日不能早於新截止日，表單會提醒一起延後），再到 B 區寫一句說明、按「加入異動紀錄」：系統自動記成「展延」一筆，前台職缺頁出現「公告異動」與頁首提示，列表卡標「有異動」。已被標為「已截止」的職缺，只要今天 ≤ 新截止日就自動回到「報名中」。**原本**只改日期、民眾看不出改過；**現在**異動紀錄跟著檔案走，民眾看得到歷程 |
| 要取消這次招募？ | 表單 C 區選「停止甄選（cancelled）」並寫理由：會自動加一筆「取消」異動紀錄（文字可改）。階段轉為「已停止甄選」，列入「歷史」，不再有結果逾期待辦；頁面保留供查閱並顯示取消原因。**已取消的職缺不得有 `result`**（表單會擋，建置也會失敗；請先移除結果，或改選「已補實」） |
| 缺額已經補足，不需要再招？ | `manualStatus: "filled"`（已補實），`manualStatusNote` 寫理由；效果同取消但標示不同 |
| 同一個職缺要重新招募？ | **新建一個檔**，用新日期與新 slug（例：`job.2026-12-01-epidemic-research-assistant-2`），不要改舊檔的日期或重用舊 id。舊檔保持原狀（已有結果就留著結果；沒有結果而不再進行的標 `cancelled`）。新舊兩檔各自有時間軸，民眾與搜尋引擎看到的都是正確的歷史 |
| 要公布錄取名單（結果上架）？ | 表單 D 區勾「公告甄選結果」，填結果公告日、字號，逐列輸入正取（序號、報名編號、遮罩姓名）與備取（再加有效期限）；正取放棄時用「新增遞補公告」。每打一個字就用建置同一份個資規則檢核，不合格的列標紅並寫出原因，正取超過名額也會擋。右側全過才匯出開 PR |
| 結果上架後發現名單錯了？ | 在表單 D 區直接更正名單，再到 B 區寫一句說明（例：「更正正取第 2 名報名編號」）加入異動紀錄，類型自動為「更正」，前台會列出更正日期與說明；Git 歷史保留更正前的版本。涉及錄取資格爭議，依機關規定另行處理 |
| 建置因為 `nameMasked` 失敗，但我已經遮了？ | 檢查是否有連續 3 個以上中文字（例：「歐陽小○」前三字連續為中文字，會被視為完整姓名樣式，請改成「歐陽○○」）、遮罩字是否為 `○`／`◯`／`〇`／`＊` 之一、`candidateNo` 是否像身分證字號 |
| 我想在結果頁加上錄取者的服務單位或學歷？ | 不行。只公布報名編號與遮罩姓名。需要時走個別通知 |
| 外部報名系統換網址？ | 改 `applyUrl`；被檢查到失效時會有 `job-apply-url-dead` 待辦提醒 |
| 看不到我的職缺在首頁？ | 先確認 `applyStart` 是否已到、`deadlineAt` 是否未過、`status` 是否為 `published`；再看 `/admin/jobs/` 顯示的階段與原因 |

### 16.10 後台表單：上架、改期、取消、公布名單

**在哪裡：** `/admin/jobs/edit/`（從 `/admin/jobs/` 上方按鈕進入；職缺表每列的「異動」連結會直接帶入那一則）。左邊填表，右邊即時顯示「預覽與檢核」與「匯出」。草稿只存在這台電腦的瀏覽器（localStorage `cdc.admin.jobs-edit`），不會送出任何資料。

**第一步：選職缺。** 最上方下拉選「新增職缺」或某個既有職缺。選既有職缺會帶入全部欄位，`id` 與 `slug` 鎖定不可改（改了前台網址會變、舊連結會壞）。

| 區塊 | 什麼時候用 | 怎麼填 | 會產生什麼 |
| --- | --- | --- | --- |
| **A 公告內容** | 上架新職缺；修改內容 | 欄位同 16.1 的表。資格、工作內容、應備文件一行一項；甄試階段可增刪列；附件每行「標題 \| 網址 \| 格式」。新增時 `slug` 必填（小寫英數與連字號），`id` 自動為 `job.{今天}-{slug}` | 整份職缺 JSON |
| **B 時程異動** | 延長報名、改甄試日、改結果預計公布日、更正公告文字 | 先在 A 區改日期，B 區會列出「原公告 → 改為」對照；寫一句給民眾看的說明（留空就用對照文字）、選填異動字號，按「加入異動紀錄」 | `amendments` 追加一筆：日期＝今天，類型自動判定——截止日變晚＝**展延**，其他日期變動＝**改期**，日期都沒變只有說明＝**更正** |
| **C 取消／補實** | 停止甄選；缺額已補足 | 單選「維持自動／停止甄選／已補實」，寫理由 | `manualStatus`、`manualStatusNote`，並自動追加一筆**取消**異動紀錄（文字可在 B 區表格修改） |
| **D 甄選結果** | 公布正取、備取；遞補 | 勾「公告甄選結果」，填公告日與字號，逐列輸入正取（序號、報名編號、遮罩姓名）、備取（順位、報名編號、遮罩姓名、有效期限）、報到須知；正取放棄時「新增遞補公告」 | `result`、`waitlistUpdates`。每列即時做個資檢核，不合格的列標紅並寫出原因；正取數超過名額也會擋 |

**右側「預覽與檢核」會看到：** 依建置日推算的階段（報名中、即將開放、審查與甄試中…）、關鍵日期一覽（改過的日期以黃底標出並附原日期）、異動紀錄（依前台的新到舊順序）、甄選結果檢核，以及「發布前請補齊」清單：必填缺漏、報名開始日晚於截止日、甄試日早於截止日、結果預計公布日早於截止日、取消卻有結果、slug 格式不符或與既有職缺重複、改了日期卻還沒加入異動紀錄、個資檢核未過。清單空了才建議匯出。

**匯出與上線：**

1. 右側「匯出」顯示應存的檔名 `content/jobs/{yyyy-mm-dd}-{slug}.json`。按「下載 .json」或「複製」。
2. 新增職缺：把檔案放進 `content/jobs/`；既有職缺：**整份覆蓋**同名檔（表單已保留原檔的 keywords、英文譯文等表單沒有的欄位）。
3. 開 Pull Request。職缺走**快車道**：CI（schema、日期先後、個資閘門）全過就自動合併，約 3 分鐘上線，不用等人核准。
4. 上線後 24 小時內完成上線後複核（`post-publish-review` 待辦給公關室，副本人事室）；發現小錯就用表單再改一版、再開 PR。

**這次改了什麼、為什麼比較好（給資訊室同事）：**

| 項目 | 原本 | 改成 | 為什麼比較好 |
| --- | --- | --- | --- |
| 上架 | 人事室手寫 JSON；`/admin/publish/` 不提供職缺 | 專用表單 `/admin/jobs/edit/`，匯出完整 JSON | 不必懂 JSON 欄位名；共同欄位自動帶好，少一類「欄位拼錯」的 CI 失敗 |
| 改期與取消 | 直接改 `deadlineAt` 或填 `manualStatus` 就算了，頂多另附更正公告 PDF | 改成**資料欄位** `amendments[]`（日期、類型、一句話說明、字號），表單自動判類型 | 民眾在職缺頁「公告異動」區看得到每次改了什麼、何時改的；列表卡標「有異動」，14 天內頁首有提示；`.md` 機讀版與 API 也帶著同一份紀錄，不再只能靠 Git 歷史追 |
| 個資檢核 | 結果寫好推上去，建置失敗才知道哪一列漏遮 | 表單與 CI 呼叫**同一份函式**（`src/client/careers-rules.js` 的 `jobPiiErrors()`；建置端 `scripts/lib/validate.mjs` 直接 import 它） | 規則只有一份，不會兩邊各改各的；表單說過就一定過，表單擋下的建置也一定擋。名單是公開資料，早一步擋下就少一次個資外洩風險 |
| 日期先後 | 只有建置時檢查 | 表單即時檢查（規則與建置一致），並提醒「改了日期還沒加異動紀錄」 | 延長報名時最常忘了一起延後甄試日與結果日，現在填表當下就看到 |

**程式在哪裡（維護用）：** 頁面模板 `src/templates/admin/jobs-edit.mjs`；DOM 綁定 `src/client/admin/jobs-edit.js`；不碰 DOM 的純函式 `src/client/admin/jobs-edit-core.js`（組物件 `buildJob()`、異動判定 `amendmentFor()`、問題清單 `problemsOf()`、檔名 `exportFilename()`），測試在 `tests/jobs-admin.test.mjs`。前台「公告異動」區在 `src/templates/public/careers.mjs`。

**注意：** 異動說明與報到須知是公開文字，**不要寫姓名、身分證字號或電話**；已上線的異動紀錄不要刪除，寫錯就再加一筆「更正」。

## 17. 採購公告 SOP（秘書室）

**適用：** 財物、勞務、工程的採購公告，獨立為 `tender` 型別（`content/tenders/`、路徑 `/procurement/{slug}/`），權責單位固定為**秘書室**（`unit.secretariat`）。
**誰：** 秘書室 Steward 建檔與維護；**需求單位**（`requestingUnit`）提供案名與需求摘要。
**一句話：** 本站只做**入口與狀態**；**正式公告以政府電子採購網為準**。本站的案件頁是「方便民眾與廠商找得到」，不是法定公告的替代品。

### 17.1 與政府電子採購網的關係

- 依政府採購法，招標、決標等應公告事項的法定公告在**政府電子採購網**（pcc）。本站不重複作為法定公告，也不修改其內容。
- 每則採購檔必須盡量填 `pccUrl`（該標案在採購網的網址）；頁面上顯示明確的外連按鈕「前往政府電子採購網」與文字「正式公告以政府電子採購網為準」。
- 本站與採購網**不一致時，以採購網為準**，秘書室應立即更正本站。
- 本站不收投標文件、不辦理線上投標；投標依招標文件規定（電子領標與投標在採購網或機關指定方式）。
- 原型沒有與採購網的資料交換，日期與狀態由秘書室手動填；正式上線的自動介接見 [roadmap-mapping.md](roadmap-mapping.md)。

### 17.2 公告建檔

用 `/admin/tenders/edit/` 表單建檔（操作見 17.6）：表單填完會產生整份標案 JSON，存成 `content/tenders/{yyyy-mm-dd}-{slug}.json`（id 為 `tender.{yyyy-mm-dd}-{slug}`）後開 PR。下表是表單各欄位對應的 JSON 欄位，資訊室同事審 PR 或手動修檔時可對照。

- **原本：** `/admin/publish/` 不提供採購公告，承辦人照下表手寫 JSON，日期先後、slug 格式、得標廠商有沒有夾帶個資，都要等 PR 跑 CI 才知道錯。
- **改成：** 秘書室在 `/admin/tenders/edit/` 填表單，右側即時算出前台會顯示的階段、列出「發布前請補齊」，再匯出 JSON。
- **為什麼比較好：** 表單用的檢核和 CI 是同一套規則（階段推導與身分證字號樣式共用 `src/client/careers-rules.js`），錯在填寫當下就看得到；承辦人不必懂 JSON 語法，資訊室收到的 PR 也比較少來回退件。

| 欄位 | 誰提供 | 說明 |
| --- | --- | --- |
| `title`、`tenderNo`（標案案號）、`method`、`category`、`budgetNtd` | 秘書室 | 採購方式四選一：公開招標、限制性招標、公開取得報價或企劃書、共同供應契約；類別：財物、勞務、工程；預算為整數（元） |
| `requestingUnit` | 秘書室，依需求單位 | 需求單位 unit id |
| `announcedAt`、`deadlineAt`（投標截止）、`openingAt`（開標，可後補） | 秘書室 | 依招標文件；開標日確定後補上 |
| `pccUrl` | 秘書室 | 政府電子採購網網址 |
| `attachments[]`、`contact`、`legacyUrls[]`、`legacyIds[]` | 秘書室 | 招標文件、公告附件（PDF 附機讀版；檔案放 `content/assets/{id}/` 並宣告，第 2.3 節）；聯絡窗口寫職稱與公務電話 |
| `slug` | 秘書室 | 必填，等於 id（`tender.{yyyy-mm-dd}-{slug}`）去掉前面 `tender.{日期}-` 的部分，路徑即 `/procurement/{slug}/` |
| `awardRule`、`briefingAt`、`scope[]`、`specialTerms[]`、`contractPeriod` | 秘書室（選填） | 決標方式、說明會日期、採購標的重點、特別規定、履約期限 |
| `manualStatus`、`manualStatusNote` | 秘書室 | 只有 `cancelled`（取消／廢標）與 `failed`（流標）兩種人工覆蓋，`manualStatusNote` 寫原因 |
| `award` | 秘書室 | 決標資訊，見 17.4 |
| `amendments[]` | 表單自動產生 | 公告異動紀錄（`date`、`kind`：extend／reschedule／correction／cancel／other、`text`、選填 `refNo`），見 17.6；只追加、不刪舊紀錄 |

採購公告同樣是事件型內容，`reviewPeriodMonths` 預設 0。建置會擋：`announcedAt` 晚於 `deadlineAt`、`openingAt` 早於投標截止、`award.date` 早於開標日、已有 `award` 卻又填 `manualStatus`。

### 17.3 狀態怎麼來：公告 → 投標截止 → 開標 → 決標／流標

| 階段（`gov.tenderStage`） | 條件 | 畫面 |
| --- | --- | --- |
| 招標中 `open` | 今天 ≤ `deadlineAt` | 顯示投標截止倒數 |
| 已截止 `closed` | 過 `deadlineAt`，尚未到開標日（或沒填 `openingAt`） | 「已截止，待開標」 |
| 已開標 `opened` | 過 `openingAt`，尚無 `award` | 「已開標，決標結果待公告」 |
| 已決標 `awarded` | 有 `award` | 顯示決標日、得標廠商、決標金額 |
| 流標 `failed`／已取消 `cancelled` | `manualStatus` 人工填 | 顯示狀態與原因 |

**截止、開標都不需要人工改狀態**，日期到了系統自己算。人工只做三件事：開標日確定時補 `openingAt`、決標後補 `award`、流標或取消時填 `manualStatus`。

### 17.4 決標與流標

1. **決標：** 在採購檔新增 `award`：`date`（決標日）、`winner`（得標廠商名稱，以採購網決標公告為準；**只放法人或廠商名稱，不放自然人的身分證字號、電話、住址**）、`amountNtd`（決標金額，可省略）、`note`。新增後階段轉「已決標」，RSS `feeds/procurement.xml` 多一筆決標項。
2. **流標：** 填 `manualStatus: "failed"`；若重新招標，**新建一個檔**（新日期、新案號或「第二次公告」案號），舊檔保持流標，不要改舊檔來當新案。
3. **取消：** 填 `manualStatus: "cancelled"`，內文寫原因。
4. **決標逾期待辦：** 開標日（`openingAt`）後 30 天仍無 `award`，且不是流標或取消，系統開 `tender-award-overdue` 待辦（給秘書室）。處理方式：補決標資訊；若實際為流標或取消，改填 `manualStatus`；若已延後決標，在 `contact` 或內文註記並更新 `reviewedAt`，待辦會在補上結果後消失。**沒填 `openingAt` 的案件不會有這個提醒，請盡早補開標日。**

### 17.5 常見問題

| 問題 | 回答 |
| --- | --- |
| 本站與採購網的日期不一樣 | 以採購網為準，立即更正本站日期並更新 `reviewedAt` |
| 招標文件有更正、展延投標截止日 | 先在採購網公告更正，再到 `/admin/tenders/edit/` 選這筆標案，在 A 區改投標截止日（與開標日），到 B 區寫一句異動說明、按「加入異動紀錄」（見 17.6 的「展延或改期」）。表單會在 `amendments` 留一筆「展延」紀錄，前台案件頁的「公告異動」區與列表卡的「有異動」標籤都看得到；已進「已截止」的案件在今天 ≤ 新截止日時自動回「招標中」。更正公告檔仍可放 `attachments` |
| 沒有 `pccUrl`（例如共同供應契約的小額採購） | 可以不填，但在 `contact` 與內文寫清楚辦理方式；頁面不會出現採購網外連 |
| 是否要在這裡公告得標廠商的聯絡方式？ | 不要。只放廠商名稱與決標金額，其餘以採購網為準 |
| 舊站已經有的採購公告？ | 依移轉清單 `content/migration/procurement.json` 逐筆確認；舊的 `/news/{slug}/` 網址會 301 到新的 `/procurement/{slug}/` |
| 我要改採購類別或案號 | 直接改欄位；公告 id 不改 |

### 17.6 後台表單：上架、展延、流標／取消、決標

`/admin/tenders/edit/`（從 `/admin/tenders/` 表格上方的「上架新標案／異動既有標案」按鈕，或每列的「異動」連結進入）。左邊是表單，右邊是「預覽與檢核」和「匯出」。最上面的「要做什麼」選「新增標案」或選一筆既有標案；選既有標案會帶入全部欄位，id 與網址代稱（slug）鎖定不能改。

**共通的最後一步：** 右側「發布前請補齊」清空後，按「複製」或「下載 .json」，依畫面上顯示的檔名新增或整檔覆蓋 `content/tenders/` 的檔案，開 PR。採購公告走**快車道**：CI（schema、日期先後、slug 重複、個資樣式）通過就自動合併上線；上線後公關室 24 小時內複核（待辦副本給秘書室），秘書室並與政府電子採購網核對日期、金額、得標廠商。草稿可按「儲存草稿（本機）」暫存在這台電腦的瀏覽器（localStorage `cdc.admin.tenders-edit`），換電腦不會跟著走。

**1. 上架新標案（A 區）**

填標案名稱、摘要、網址代稱、案號、需求單位、採購方式、決標原則、分類、預算、公告日、投標截止日、開標日、說明會、採購網連結、採購範圍與特別條款（每行一項）、履約期間、附件（每行「標題 | 網址 | 格式」）、聯絡窗口。共同欄位（owner 秘書室、公開、OGDL-1.0、AI 白名單、審閱週期 0…）由表單自動帶，不用填。

- **原本：** 複製一個舊檔來改，常忘了改 id 裡的日期、slug 和 id 不一致，或預算多打了逗號，CI 才擋。
- **改成：** 表單依「公告日＋slug」自動組 id 與檔名，金額自動去逗號，slug 格式不對或和既有標案重複會立刻警告；採購網連結空白時提醒。
- **為什麼比較好：** 檔名、id、slug 三者永遠一致，前台路徑不會撞；承辦人看得到前台會顯示的階段，不用猜。

**2. 展延或改期（B 區）**

在 A 區改投標截止日、開標日或說明會日期，B 區會列出新舊日期對照。填「異動說明（給廠商看的一句話）」與選填的異動公告字號，按「加入異動紀錄」，表單在 `amendments` 追加一筆：截止日變晚＝「展延」（extend），其他日期變動＝「改期」（reschedule），沒改日期只寫說明＝「更正」（correction）。說明留白會依日期差異自動擬一句（例：「投標截止日由 2026-10-15 展延至 2026-10-22」）。改了日期卻沒加紀錄，右側會提醒。

- **原本：** 直接改 `deadlineAt`，舊日期就消失了；看過舊公告的廠商在本站找不到「什麼時候、改了什麼」。
- **改成：** 改日期的同時留一筆異動紀錄；前台案件頁在時程之後多一個「公告異動」區（依日期由新到舊，含種類、日期、說明、字號），最新一筆在 14 天內時頁首還有提示；列表卡在招標中／已截止／已開標時加「有異動」標籤；`.md` 機讀版也列出。
- **為什麼比較好：** 廠商與民眾一眼看到變更，減少「網站日期跟我記的不一樣」的來電；異動紀錄跟著檔案進 git，誰在哪天改了什麼都查得到。預覽區會提醒「以政府電子採購網為準，本站更正後請核對採購網」。

**3. 流標或取消（C 區）**

選「流標」或「廢標／取消」並寫原因。表單會自動在異動紀錄加一筆「流標／取消」（cancel），文字可以改；改回「維持自動」就移除這筆。已有決標資訊的標案不能再選流標／取消（會警告，CI 也會擋）。重新招標仍照 17.4：**另建新標案**，舊檔保持流標。

- **原本：** 手動加 `manualStatus`，前台只看得到階段變成「流標」，看不出是哪天公告的。
- **改成：** 一個選項同時設定 `manualStatus`、`manualStatusNote`，並留下有日期的異動紀錄。
- **為什麼比較好：** 狀態與公告時間點一起保存；決標逾期待辦會因為流標而自動消失，不必另外處理。

**4. 公告決標（D 區）**

填決標日、得標廠商（法人名稱）、決標金額（選填）、備註。表單會檢查：決標日不得早於開標日與投標截止日、得標廠商必填、得標廠商與備註不得含身分證字號樣式。

- **原本：** 手寫 `award` 物件，日期先後與個資只在 CI 檢查。
- **改成：** 填寫當下就檢查，預覽立刻顯示階段變成「已決標」。
- **為什麼比較好：** 個資樣式在進 PR 之前就看得到警告，不必等 CI 擋下後再從 git 歷史清除；決標逾期待辦在合併後自動消失。

**資訊室備忘：** 頁面模板 `src/templates/admin/tenders-edit.mjs`；畫面綁定 `src/client/admin/tenders-edit.js`；組物件與檢核的純函式在 `src/client/admin/tenders-edit-core.js`（不碰 DOM，`tests/tenders-admin.test.mjs` 直接測，匯出的 JSON 也在測試裡跑過 `validateSite`）。異動紀錄的欄位定義在 `schemas/tender.json` 的 `amendments`。

## 18. 疫苗接種時程表維護 SOP

**誰：** 急性傳染病組（預防接種）Steward。**內容：** `content/master/immunization-schedule.json`，一筆一個「劑次 × 對象」，是 `/vaccines/schedule/` 時程地圖與問答「幾歲能打哪些公費疫苗」共用的資料。疫苗頁的「公費對象」表仍是各疫苗的正本；時程表是跨疫苗的索引，兩邊要一致。

1. **先看地圖有沒有「待承辦人確認」。** 首版 42 筆全部由現行兒童預防接種時程表（11401 版）、本站疫苗頁與 2026 年政策新聞整理，`verified` 都是 false。請逐筆對照疾管署正式公告，確認無誤就把 `verified` 改 true；數字不對就直接改 `ageMinMonths`／`ageMaxMonths`／`dose`／`group`，並把 `source` 換成正式公告網址。
2. **年齡一律填月。** 滿 5 歲填 60、65 歲以上填 780 且 `ageMaxMonths: null`；「滿 5 歲至入國小前」填 60–83。地圖與問答都用月齡比對，不要寫「5 歲」。
3. **公費／自費分三種。** `public` 看年齡就公費；`conditional` 還要看身分（原住民、高風險、醫事人員…），條件寫在 `group`；`self` 自費，部分縣市補助寫在 `note`。
4. **政策改了怎麼改。** 例如 2026-01-15 成人肺炎鏈球菌改為 1 劑 PCV20／PCV21：先改疫苗頁 `content/vaccines/pneumococcal.json` 的 `publicFunded` 與內文（這是正本），再改時程表對應的 `sched.pcv-*` 三筆，兩邊 `startAt` 填同一天；舊的 Q&A（`faq.pcv-elderly`）也要改。送出後 CI 的驗證會擋住疫苗 id 打錯、年齡上限小於下限。
5. **新增疫苗。** 先在 `content/master/vaccines.json` 加一筆（`hasPage: false` 也可以），再加時程表項目；有疫苗頁後把 `source.url` 指回該頁。
6. **測試答案。** 改完在 `/ask/` 問「65 歲以上可以打哪些公費疫苗」「滿一歲的小孩要打什麼疫苗」，答案應一疫苗一句、每句有來源；評估集 VA011–VA014 在 CI 會自動跑。

## 19. 後台登入與權限（所有同事）

**原則：** 後台用機關 SSO 登入，不另設帳號密碼；你的單位與角色由 AD 群組帶入，不是在後台自己選。詳細設計與為什麼見 [admin-auth.md](admin-auth.md)。

### 19.1 登入與登出

1. 打開任何後台頁（例如 `/admin/mine/`），沒登入會自動到 `/admin/login/`，登入後回到原本那頁（前台頁尾「同事修改這頁」也一樣）。
2. 原型沒有後端：在登入頁**選一個示範帳號**按「以機關 SSO 登入（模擬）」，等於正式環境 SSO 回傳你的身分。要測特定單位或角色組合，用「自訂示範身分」。
3. 右上角顯示 **姓名 · 職稱 / 單位 · 角色**；按「登出」結束。8 小時或閒置 30 分鐘會自動失效，再進去會回到登入頁。

### 19.2 單位視角

- 承辦人、複核者、疫情發布：右上「單位視角」鎖在自己單位，不能切。
- 內容總編輯（公關室）、治理幕僚（OASIS）、平台管理（資訊室）：可以切到別的單位或「全部單位」。每次切換都會留稽核。

### 19.3 哪些頁有角色限制

| 後台頁 | 允許的角色 |
| --- | --- |
| 複核區 | 複核者、內容總編輯、治理幕僚 |
| 疫情發布 | 疫情發布（疫情中心）、治理幕僚 |
| AI 開關 | 平台管理（資訊室）、治理幕僚 |
| 評估 | 治理幕僚、平台管理、內容總編輯 |
| 其他後台頁 | 任何已登入角色（限自己單位） |

進不去會看到「這一頁不在你的角色權限內」，並寫入稽核。業務上真的需要，請單位主管向資訊室申請調整群組，**不要**借別人的身分。

### 19.4 稽核

登入、登出、被拒絕、切換視角、階段失效都會記錄。原型存在你的瀏覽器，登入頁最下方可看；正式環境寫到集中式日誌，資訊室保管，使用者不能刪。

### 19.5 單位介紹頁（權責單位可點）

- 全站每個「權責單位」現在都是連結，連到 `/about/units/{單位}/`：簡介、主要業務、該單位在本站維護的全部內容、聯絡。
- 簡介是原型撰寫、標「尚待該單位確認」；主要業務依處務規程整理（待逐字核對）。右側連到現行官網的「組織與職掌」與另一頁單位介紹（現行官網沒有各單位獨立網址）。各單位 Steward 確認後，在 `content/master/units.json` 把 `intro` 改正確、`introVerified` 改 `true`（走 PR；內容清單是自動算的，不必改）。
- 單位改名（例如組織調整）只改 `units.json` 的 `name`，全站自動跟著改，因為內容檔只存單位 id。

**資訊室備忘：** 角色、頁面規則、示範帳號與 session 規則在 `src/client/admin/auth-rules.js`（純函式，Node 與瀏覽器共用）；進頁閘門在 `src/client/admin/common.js` 開頭；登入頁 `src/templates/admin/login.mjs` ＋ `src/client/admin/login.js`；單位頁模板 `src/templates/public/units.mjs`，連結元件 `unitLink`（`src/templates/public/_partials.mjs`）。測試 `tests/round18-ui.test.mjs`。

## 20. PDF 指引與手冊：讓智慧查詢查得到、引用得到（第十九輪）

**誰：** 文件 `owner` 的 Steward 負責校對；OASIS（AI推動辦公室）負責轉檔工具與規則；資訊室協助跑轉檔（沒有命令列環境的同事）。完整設計與理由見 [pdf-ingest.md](pdf-ingest.md)。

**先分清楚兩件事：**

| 你要的 | 做法 |
| --- | --- |
| 讓人下載 PDF | 照 2.3 當附件上傳，確認有文字層 |
| 讓專業版智慧查詢**引用 PDF 裡的條文，並告訴讀者在第幾頁** | 除了上傳，還要把 PDF 轉成機讀版（本節） |

只上傳 PDF，智慧查詢看不到裡面的內容：PDF 是排版格式，抽出來的文字有頁碼、目錄點線、斷句、拆散的表格，直接拿來回答會引到半句話或錯位的數字，也說不出在第幾頁。

### 20.1 流程

1. **準備**：PDF 正本（要有文字層；掃描檔先請資訊室 OCR）、紅字版（若有），以及填好的 meta 檔（標題、版次、生效日、權責單位、疾病、讀者對象；可複製 `data/pdf-ingest/dengue-chik-guideline-2026-02.meta.json` 改）。
2. **轉檔**：`node scripts/pdf-to-md.mjs 指引.pdf --meta xxx.meta.json --out content/documents/xxx.json --report xxx.report.json`。工具會依章／節／附件切段、每頁插頁碼、標出表格頁與表單附件。
3. **看報告**：表格頁、頁中數字表格、表單附件各有幾個。這就是校對的工作量。
4. **開 PR 上架**：這時文件已上架、文件頁可讀；專業版智慧查詢查得到，但排在已審內容之後，來源卡標黃色「由 PDF 機器轉出，尚未人工校對；請以 PDF 原頁為準」。同時產生連動待辦「PDF 機讀版待校對」（30 天）。
5. **校對**（20.2），完成後把 `derivedFrom.reviewStatus` 改成 `reviewed` 開 PR。待辦消失、文件可進 AI 白名單。

### 20.2 校對清單

- [ ] 每章抽 1–2 頁對照 PDF 原頁：段落有沒有缺、順序對不對、章節標題對不對。
- [ ] 報告列的表格頁：會被查的表格（時限、劑量、定義對照）轉成 Markdown 表格，取代「本頁為表格」說明；不需要被查的維持原狀（讀者會被引導看 PDF）。
- [ ] 紅字修訂處：逐條填進 `changes[]`（段落、改前、改後、added／changed／removed），`derivedFrom.redTextChanges` 改 `captured`。
- [ ] 頁碼偏移：印刷頁碼第 1 頁是 PDF 第幾頁，減 1 填 `derivedFrom.pdfPageOffset`（封面＋目錄 4 頁就填 4）。填了之後「開啟 PDF」會直接跳到引用那一頁。
- [ ] PDF 正本放進 `content/assets/{id}/`，`pdfUrl` 改成 `/files/{id}/檔名.pdf`。
- [ ] 封面只寫「某年某月版」時，確認生效日（`effectiveAt`）。

### 20.3 常見問題

- **為什麼表單附件不能查？** 表單欄位名稱（「發病日」「訪視日期」）不是規定，被引用會誤導。表單只留標題與「請看 PDF 第 N 頁」。
- **新版 PDF 來了怎麼辦？** 重新轉檔成新的一版（新 id、`supersedes` 指向舊版），舊版自動標失效、退出查詢。
- **可以直接改轉出來的文字嗎？** 可以改表格與錯字，但請在 PR 說明寫明；測試會比對轉檔結果，改了要一併更新測試（請 OASIS 協助）。
- **民眾版會引用嗎？** 不會。指引、手冊一向只給專業版引用；民眾版仍引用各疾病頁與 Q&A。

### 21.2 複核區怎麼用

1. 送出預處理後的內容在這裡排隊，四步：**承辦人確認預處理 → 公關室內容審核 → 多語審核 → 發布（自動）**。
2. 每筆顯示目前步驟與各語言狀態。輪到你時按「通過」進下一步；有問題按「退回」並**寫清楚原因**（哪一段、要改成什麼），承辦人會在我的內容看到。
3. 多語規則：一級內容（疾病、疫苗、澄清、態勢）簽約審核、必審，未審的語言頁不顯示；二級內容（Q&A、新聞稿、通函等）先發布並標機器翻譯，每月抽審 10%。

## 22. 首頁宣導 Banner 上下架 SOP（公關室）

**誰：** 公關室總編輯決定檔期；宣導內容的權責單位提供文字與圖。Banner 走**快車道**（CI 通過自動上線，公關室 24 小時內複核）。

1. 一則 Banner 一個檔：`content/banners/{年-月-主題}.json`。必填：`headline`（一句話）、`cta`（按鈕文字＋連到站內哪一頁）、`startAt`、`endAt`；選填 `subline`、`priority`（數字小的先輪播）、圖片與 `imageAlt`。
2. **圖只當氛圍，字都放在 `headline`／`subline`**：圖上不要壓字（讀屏與翻譯都讀不到）。圖片照 2.3 的規則放，`imageAlt` 寫畫面內容。
3. **上下架不用人按**：建置時依 `startAt`／`endAt` 自動判斷「即將開始／進行中／已結束」，首頁只顯示進行中（主 Banner＋最多 3 則輪播）。要提早下架就把 `endAt` 改成今天開 PR。
4. 公開的 `/campaigns/` 頁列出所有 Banner（進行中、即將開始、已結束），就是宣導的資料目錄，可以拿來檢查檔期有沒有撞期。
5. 疫情高峰改用做法 B 首頁時，宣導卡自動退到疫情卡下方，不必調整 Banner。

## 23. 圖片與影片：怎麼讓智慧查詢找得到（第二十輪）

**一句話：智慧查詢只讀文字。** 圖裡的字、影片裡講的話，系統都看不到；要被查到、被引用，就要有一份**人確認過的文字版**放在內容欄位裡。PDF 的做法見第 20 節，原理相同。

### 23.1 影片（先上 YouTube，官網貼連結）

只把 YouTube 連結貼在某頁的內文裡，智慧查詢只看得到那一行連結。要讓影片內容被查到，**每支影片在官網建一筆「影音」內容**（第 8 節），重點是：

| 做什麼 | 為什麼 |
| --- | --- |
| 填 `youtubeId`（貼完整網址會自動取 id） | 官網影音頁點擊才載入 YouTube（`youtube-nocookie`），不影響隱私與速度 |
| **逐字稿 `transcriptMarkdown` 必填**，每段加 `[mm:ss]` 時間標記 | 這是智慧查詢**唯一**能引用的影片內容；答案的來源會連到影音頁的那一秒（`#t=秒數`），讀者直接看到那段 |
| 章節（每行「秒數 標題」） | 引用時顯示「影片名 · 章節名」，也和 YouTube 說明欄的時間戳記一致 |
| `basedOn` 填依據正本、`producedAt` 填製作日 | 正本改版時影片自動標「過時」、退出 AI 白名單並開待辦，不會讓舊影片講舊規定 |
| 字幕語言 `captions` | 有哪些語言字幕；外語逐字稿放 `i18n` |

逐字稿從哪來：最省力的是**用 YouTube 自動字幕下載（.srt），整理成逐字稿後由承辦人逐句校對**（自動字幕的專有名詞、數字常錯），或直接用製作時的腳本。不要只附 PDF 逐字稿，只有欄位內的文字能進索引、反向稽核與翻譯。

### 23.2 圖片

先分兩種：

- **裝飾或示意圖**（照片、氛圍圖）：填 `alt`（畫面在表達什麼）就好。智慧查詢不需要它。
- **承載資訊的圖**（海報、懶人包、圖卡、流程圖、圖表）：官網規則是「圖片不承載唯一資訊」（可及性要求，也是 AI 的要求）——**圖裡的每一句重要文字，都要在內容欄位裡另有純文字版**：
  1. 海報、單張、圖卡建成「出版品」（`publication`），文字版寫在 `abstractMarkdown`（範例：`publication.poster-tb-seven-languages`）；嵌在文章裡的圖，就把重點寫進內文段落。這兩處都會進索引。
  2. `alt` 只寫圖的重點（≤ 150 字），**不要**把整張海報的字塞進 alt：alt 是給螢幕報讀用的，太長反而難用，而且不進答案索引。
  3. 圖表：結論與關鍵數字寫進內文或 alt；背後的數字以資料檔（`data`）或資料集提供，問「幾例」時答案引擎讀資料集，不讀圖。
  4. 多語海報：中文文字版放 `abstractMarkdown`，各語言標題與摘要放 `i18n`；目前智慧查詢只引用出版品的來源語言文字版，外語問句會以中文來源回答並標示。
- **文字版從設計稿來，不要從圖片 OCR 反推**：設計稿的文字才是正本；OCR 可以當草稿，但一定要人逐句對過。
- 舊站轉過來、只有圖沒有字的頁，匯入工具會標 `image-only` 並在摘要留「（待補：海報文字版）」，這些就是要補的清單（[legacy-import.md](legacy-import.md) 10.10）。

### 23.3 檢查方法

上架後到專業版或民眾版問一句圖或影片裡才有的話（例如海報上的「咳嗽超過兩週」）。答不出來，通常是文字版沒填或沒進白名單；到 `/admin/catalog/` 看該筆內容的白名單狀態與原因。
