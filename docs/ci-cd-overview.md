# CI／CD 流程總覽：從按下「送出」到上線，每一道關卡做什麼、花多久、和傳統上架差在哪

> 給誰看：OASIS、資訊室、要和廠商談架構的同事。這是一份「拿去談」的整理，數字都有來源與重跑方法。
> 依據：[git-as-cms.md](git-as-cms.md)（為什麼用 Git＋CI）、[publishing-lanes.md](publishing-lanes.md)（車道）、[deploy.md](deploy.md) §2 與 §14（GitHub 與自架 GitLab＋寫入閘道）、[ci-scaling.md](ci-scaling.md)（成長曲線實測）、[eval-challenge.md](eval-challenge.md)（問答評估）、[a11y.md](a11y.md)。
> 寫法：先流程圖，再每一關的基準數字，最後是比較與質疑。**經費不寫在這裡**（[transition-faq.md](transition-faq.md) §8）。

目錄：1 流程圖（原型與正式）・2 每一道關卡做什麼・3 基準數字與重跑方法・4 和傳統上架方式的比較・5 常見質疑與回答・6 我們反過來要問 CMS 廠商的・7 已知的限制與下一步

## 1. 流程圖

### 1.1 原型（GitHub，現在就在跑）

```
承辦人在 /admin/publish/ 填表單、按「送出」
  │
  ▼ 系統代開分支、寫 content/*.json、開 Pull Request（承辦人看不到 Git）
  │
  ▼ content-pr.yml（每個 PR）
  │   1 個資掃描（身分證、手機、個人信箱…）                 1 秒
  │   2 建置檢查 --check：schema、跨檔參照、治理規則、評估集    4 秒   ← 內容的閘門
  │   3 程式品質：lint、格式、型別、全部測試（1,154 個）        ~90 秒  ← 程式的閘門
  │   4 無障礙 axe：24 頁 × 3 種視窗（桌機、320 px、文字 200%）  ~160 秒
  │   5 車道判定：改了哪些檔 → 緊急／快／一般、要誰審、SLA
  │   6 建預覽版並推到 previews 分支 → /preview/pr-N/
  │   7 PR 留言：檢查表、預覽網址、審核人、SLA 到期
  │
  ├─ 快車道（新聞稿、通函、澄清、職缺、採購、Banner；名單內的承辦人）：全綠 → 自動合併
  ├─ 緊急車道（態勢、標 urgent）：全綠 → 自動合併，10 分鐘內
  └─ 一般車道（疾病、疫苗、文件、Q&A、程式）：全綠 → 等 1 位核准 → 合併
  │
  ▼ pages.yml（合併後）
  │   純內容合併：內容測試（約 25 秒）→ 建置整站（3,759 頁、7 語、全文索引、答案索引、連結檢查）→ 部署；完整測試平行跑、不擋部署（第六十輪）
  │   程式合併：lint、格式、型別、全部測試 → 建置整站 → 部署
  │
  ▼ 上線（快車道實測：送出到上線 3 分 05 秒，2026-10-04）
```

每 2 小時另有一次排程建置：讓 `publishAt` 到點的內容上線、審閱逾期的內容退出 AI 白名單並掛警示；每天 10:00 重抓官方資料快照。

### 1.2 正式環境（規劃：署內 GitLab＋寫入閘道，deploy.md §14）

```
承辦人（AD 帳號登入）──▶ 後台 /admin/* ──▶ 寫入閘道（Node，只聽內網）
                                              │ 驗身分與角色、驗內容、寫稽核（只增不改、鏈式雜湊）
                                              ▼
                                        署內 GitLab（服務帳號；承辦人沒有 GitLab 帳號）
                                              │ 合併請求 ＝ 送審；核准 ＝ 合併（四眼原則）
                                              ▼
                                        GitLab CI（自架 runner）：同一套檢查、同一套建置
                                              ▼
                                        靜態檔部署到對外主機／CDN；舊網址 301 由反向代理處理
```

與原型的差別只有三處：登入換成 AD、Git 平台換成 GitLab、CI runner 自架。**檢查、車道、建置腳本完全相同**，所以原型量到的數字可以直接當正式環境的基準線（runner 規格不同時按比例換算）。

## 2. 每一道關卡做什麼

| 關卡 | 檢查什麼 | 擋下什麼樣的錯 | 誰維護規則 |
| --- | --- | --- | --- |
| schema 與參照 | 每筆內容的欄位、型別、必填；`basedOn`、`owner`、`vaccine` 等跨檔參照存在 | 缺權責單位、審閱日格式錯、引用不存在的指引 | OASIS（schemas/） |
| 治理規則 | 審閱逾期、版本鏈（新版出來舊版要標失效）、AI 白名單、個資、附件雜湊與授權 | 新聞稿引用已失效的指引版本；逾期內容還在 AI 回答裡 | OASIS |
| 說法一致性 | 同一疾病不同內容裡同單位的數字互相矛盾 | 疫苗頁說 15 分鐘留觀、Q&A 說 30 分鐘 | 建置自動找、權責單位判定 |
| 評估集 | 449 題「問這題應引用這筆內容」，版本題 19 題必須全對 | 改了內容後 AI 開始引用錯的版本 | OASIS，權責單位出題 |
| 連結檢查 | 站內 44 萬個連結與錨點、外部 32 個網域 | 壞連結、移走的附件 | 自動 |
| 全文索引自檢 | 抽 80 頁 160 個字串，搜得到的比例 ≥ 98% | 索引漏頁 | 自動 |
| 多語輸出檢查 | 外語頁不得出現未翻譯的詞彙鍵值；中文比例門檻 | 英文頁出現 `term.xxx` | 自動 |
| 效能預算 | 公開頁 JS ≤ 120 KB、問答頁 ≤ 240 KB、答案資料 ≤ 445 KB | 一次改動讓手機版變慢 | OASIS |
| 個資掃描 | 身分證、居留證、手機、個人信箱、名單姓名 | 甄選結果貼了姓名 | 自動；例外清單由 OASIS 核 |
| 無障礙 axe | WCAG 2.2 AA 規則集，24 個代表頁 × 3 種視窗 | 對比不足、表單沒標籤、橫向捲動 | 資訊室／OASIS |
| 動態弱點掃描 DAST（不擋，每週＋手動） | OWASP ZAP baseline 對建置後的靜態站做被動掃描，報告放 job summary 與 artifact | 缺安全標頭、Cookie 設定、資訊洩漏 | 資訊室；見 [security-testing.md](security-testing.md) |
| 程式測試 | 1,154 個測試：治理引擎、車道、寫入閘道、答案引擎、後台頁面（含瀏覽器端到端） | 規則改壞、閘道權限漏洞、引擎退步 | 工程 |

重點：**前 10 項是內容的閘門，最後 1 項是程式的閘門。** 承辦人的一筆內容 PR 真正需要的是前 10 項（合計約 1 分鐘內）；程式測試是改程式時才需要的。原型目前兩種 PR 都全跑（所以 PR 車道要 6–8 分鐘），第五十六輪把它們分開（第 7 節）。

## 3. 基準數字與重跑方法（2026-10-15）

| 項目 | 數字 | 來源／重跑 |
| --- | --- | --- |
| 內容閘門（`build --check`） | 4 秒（GitHub runner） | Actions run #77 步驟 10；本機 `npm run check` |
| 整站建置 | GitHub runner 39 秒；本機 4 核 70 秒；約 18 ms／頁 | run #257；`time npm run build` |
| 全部測試 | 1,154 個，CI 104 秒（4 核並行）；逐檔加總 464 秒 | `npm test`；逐檔計時見 ci-scaling §2.3 |
| 無障礙 | 24 頁 × 3 視窗 162 秒；阻擋項 0 | run #77 步驟 13；`npm run a11y` |
| PR 車道（程式 PR） | 5.7 分鐘 | run #77 |
| 快車道送出到上線 | 3 分 05 秒（2026-10-04 實測，當時 CI 60 秒） | publishing-lanes 附錄 B |
| 純內容 PR 車道（第五十六輪分流後） | test 1 分 47 秒＋lane 40 秒 | 探針 PR #116（2026-10-16） |
| 合併到上線（`pages.yml`） | 3.0–4.8 分鐘，80 次無例外 | 2026-10-21 至 10-27 的執行；deploy §34.1 |
| 多人同時合併時最晚一位的等待 | 最多兩次建置約 9–10 分鐘（第六十八輪起保證收斂；之前連續合併可能無限取消） | deploy §34.2 |
| 審核通過到合併 | 改前整套重跑約 2.5 分鐘；第六十八輪沿用同一 commit 的結果，約 1 分鐘（待第一次實跑補數字） | deploy §34.3 |
| 評估集 | 449／449；版本題 19／19 | 每次建置都印 |
| 盲測題組（換句話說） | holdout 264 題 74.2%；封存盲測 holdout2 240 題 69.6% | eval-challenge §10、§13；`npm run eval:challenge`、`npm run eval:holdout2` |
| 答案引擎單題延遲 | 107 ms（本機，`perf:ask`） | round40-grokbot #80；`npm run perf:ask` |
| 全文索引召回 | 100%（160／160） | 每次建置都印 |
| 連結 | 44 萬個，錯誤 0 | 每次建置都印 |
| JS 預算 | 公開頁 65／120 KB；問答頁 235／240 KB | 每次建置都印 |
| 內容成長 | 內容 ×4、×10 時建置 85、143 秒，線性 | ci-scaling §3 |
| Git | 205 個 commit、34 MB；CI checkout 2–3 秒 | `git count-objects -vH` |

這些數字是**驗收可以直接抄的**：合約寫「測試全綠、評估集版本題全對、無障礙阻擋項 0、內容 PR 閘門 ≤ 1 分鐘、合併到上線 ≤ 5 分鐘」，每一項都有指令可以當場重跑。

## 4. 和傳統上架方式的比較

完整比較表在 [git-as-cms.md](git-as-cms.md) §2，這裡只列「流程」與「速度」兩個面向。

| | 傳統後台（CMS） | Git＋CI（本原型） |
| --- | --- | --- |
| 送出後發生什麼 | 寫進資料庫，立刻對外 | 開 PR → 機器檢查 → 依車道自動合併或等人核准 → 建置部署 |
| 承辦人等多久 | 0 秒 | 快車道 3 分鐘；一般車道等審核人（SLA 2 個工作天）；緊急 10 分鐘內 |
| 錯誤什麼時候被發現 | 上線後，靠人看到 | 上線前，機器擋下，PR 留言說哪一條規則、怎麼修 |
| 搜尋索引、相關連結、多語、AI 引用 | 瀏覽時即時算（資料庫查詢），或沒有人算 | 發布時一次算完並檢查 |
| 預覽 | 常與正式不同，或沒有 | 每個 PR 一個預覽網址，看到的就是上線的樣子 |
| 誰改了什麼、改之前是什麼 | 看 CMS 有沒有做版本 | 每次合併都是一筆紀錄，可一鍵回復 |
| 流量尖峰 | 資料庫與應用伺服器要撐 | 靜態檔＋CDN，沒有東西可以掛 |
| 平台壞了 | 網站跟著掛 | 網站照常，只是暫時不能更新；資訊室可手動建置 |
| 內容變多 | 資料庫查詢變慢（民眾等） | 建置變慢（建置機等，與內容成正比，[ci-scaling.md](ci-scaling.md)） |

一句話：**CMS 把「檢查與重算」的成本推給上線後的人和瀏覽時的伺服器；Git＋CI 把它們集中在發布那一刻由機器做完。** 代價是發布要等幾分鐘，換到的是錯誤上線前被擋、每一步可追溯、網站本身沒有可以被攻擊或撐爆的後端。

## 5. 常見質疑與回答

| 質疑 | 回答 | 證據 |
| --- | --- | --- |
| 「內容越來越多，Git 做 CI 會慢到爆炸」 | 會變慢的是建置與測試，不是 Git；建置與頁數成正比、沒有平方項；Git 的 checkout 是淺層、秒級、不隨歷史成長 | ci-scaling §2–4：334 次執行逐步計時、×4／×10 實驗 |
| 「原型的 CI 已經越來越慢了」 | 十天內容 +11%，測試檔 +190%，變慢的是程式測試與 axe；內容 PR 不該跑這些，第五十六輪分流 | ci-scaling §2.2 |
| 「要等幾分鐘才上線，承辦人不能接受」 | 快車道 3 分鐘，與現行後台「按下去、再去瀏覽器確認」差不多；緊急 10 分鐘內有明確規則，現行流程反而沒有 | publishing-lanes §4、附錄 B |
| 「承辦人要學 Git」 | 不用。表單一樣是填欄位、貼內文、拖附件、按送出；分支、PR、合併都是閘道做的 | publishing-lanes §11 按鍵數對照 |
| 「CI 掛了網站就不能更新」 | 對，但網站本身照常服務；緊急內容由資訊室 `npm run build` 手動部署。CMS 掛了是整站掛 | git-as-cms §4 |
| 「測試這麼多，誰維護」 | 測試是規則的可執行說明；改規則必須改測試，否則 CI 擋。這正是「規則只能在治理引擎一處」的保證 | deploy §3、transition-faq §3.2 第二題 |
| 「為什麼不用資料庫，資料庫比較快」 | 快的是讀取，而我們的讀取是靜態檔（更快）；慢的是發布時的檢查與重算，資料庫方案不是把它變快，是沒人做 | ci-scaling §6.4 |
| 「廠商走了怎麼辦」 | 正本是 JSON＋Markdown，建置是 Node 腳本，CI 是 YAML，全在署內 GitLab；換廠商不需要資料移轉 | transition-faq §3.4 |
| 「要不要用 Anthropic 那種新的版本控制」 | 不用。那是一天 3 萬次合併、100 GB 歷史的解法，文章自己說只對極大 monorepo 有意義；我們能借的只有「CI 要什麼拿什麼」的觀念 | ci-scaling §5 |
| 「大檔案會把 Git 撐爆」 | 影片與大型原始檔不進 Git，走物件儲存，Git 只放連結與雜湊；附件有分組大小上限，建置時檢查 | assets-policy.md §3 |
| 「幾個組室同時上架，最後一個要等一小時？」 | 不會。每個 PR 的檢查各自平行；`main` 不要求分支更新到最新，合併不排隊；部署一個 group 排隊不取消，最晚一位從合併到上線最多兩次建置（約 9–10 分鐘），不論多密集都收斂 | deploy §34；80 次 `pages.yml` 執行 3.0–4.8 分鐘 |

## 6. 我們反過來要問 CMS 廠商的

1. 一筆內容改了之後，搜尋索引、相關連結、七種語言的對應頁、AI 問答的引用，**是什麼時候、由誰重算的？** 有沒有檢查？
2. 新聞稿引用了一份已經出新版的指引，系統**會不會擋**？怎麼知道哪一版是現行的？
3. 一筆內容審閱逾期了，網站上**看得出來嗎**？AI 問答還會引用它嗎？
4. 每一次修改，能不能回答「誰、什麼時候、改了什麼、改之前是什麼」，**並一鍵回復**？
5. 審核人看到的預覽，**和上線後一模一樣嗎**？
6. 疫情記者會流量尖峰時，資料庫與應用伺服器要擴到多大？誰負責？
7. 內容格式是開放的嗎？合約結束時，**不靠你們**能不能把全部內容連同歷史拿走？
8. 上面這些的驗收，能不能寫成**機器可以重跑的檢查**？（我們的全部可以：第 3 節。）

## 7. 已知的限制與下一步

- **內容 PR 目前也跑全部程式測試與 axe**（6–8 分鐘）。第五十六輪分流：純內容 PR 只跑內容閘門、個資掃描、內容相關的快速測試與一次預覽建置；程式 PR 才跑全部。目標內容 PR 1 分鐘內。
- **純內容合併後 `pages.yml` 又跑一次完整測試**（2 分 18 秒，2026-10-25 實測）。第六十輪改成：純內容合併只跑內容測試就建置部署，完整測試平行跑不擋部署（deploy.md §29.3）；`main` 的規則集與車道核對也在同一輪補上（§29.1、§29.2）。
- **一個 PR 建三次站** → 改成一次；Chromium 每次重裝 → 快取。
- **審核人標示**：程式與文件變更的審核人原本一律顯示公關室；改為 OASIS（內容 PR 仍是公關室或權責單位）。
- **智慧問答的答案資料預算**（445 KB）在內容約 2 倍時會先碰到，要改成按主題分片或伺服器端回答；與 CI 無關，但要排進搬第一個專區的工作（ci-scaling §3）。
- **多人同時合併**：第六十八輪把部署 concurrency 改為排隊不取消、審核後沿用同一 commit 的檢查結果（deploy.md §34）；正式環境要用 GitLab 的 `resource_group` 做同一件事，部署完成時清 CDN 快取。
- **正式環境的數字要在試點期重量**：runner 規格、GitLab 的 API 延遲、反向代理，都和 GitHub 不同；流程相同所以斜率可比，絕對值要重測。
