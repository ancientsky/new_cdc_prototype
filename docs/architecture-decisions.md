# 為什麼這樣做：架構決策紀錄

> 給誰看：要評估、接手或擴充這個原型的人。每一項決策都寫「決定、理由、代價、什麼時候該重新考慮」。
> 原始約定見根目錄 [ARCHITECTURE.md](../ARCHITECTURE.md)。

## 決策總表

## 1. Git 當 CMS

**決定：** 內容與資料以 JSON 檔存在 `content/`，改動走 Pull Request，CI 驗證後合併即發布。
**理由：** 機關最怕「誰在什麼時候改了什麼」說不清楚。Git 免費提供作者、時間、差異、審核與回溯；PR 的複核者就是流程中的覆核關卡；CI 把必填欄位、參照完整性和評估集變成機器強制，而不是靠公文提醒。後台頁面（`/admin/`）只是這個流程的操作介面，匯出的 JSON 才是交付物。
**代價：** 非技術同事需要後台介面協助，不能直接編輯檔案；大量圖片與影片不適合放在 Git。
**何時重考慮：** 同時編輯者多到 PR 衝突頻繁，或需要即時發布（分鐘級）時，可在 Git 前加一層有權限控管的編輯器，但資料仍以 Git 為準。
**給資訊室的完整比較：** [git-as-cms.md](git-as-cms.md)（與傳統後台上架系統逐項比較、要維運什麼、代承辦人送出服務、風險）。

## 2. 靜態生成

**決定：** `npm run build` 把內容算成 HTML、`.md`、`v1/*.json`、`sitemap`、`llms.txt`，部署到 GitHub Pages（純靜態）。
**理由：** 疾管署網站在疫情期間流量會暴增，靜態檔由 CDN 供應最耐壓；沒有資料庫與應用伺服器，攻擊面最小；任何時間點的網站都能完整重建與還原。對 AI 爬蟲而言，靜態 HTML 加機讀版也最友善。
**代價：** 內容變更要等建置（約數分鐘）才上線；無法有伺服器端個人化——所以個人化（角色、訂閱）放在瀏覽器 localStorage。
**何時重考慮：** 需要即時登入個人化、即時通知寄送時，加獨立服務，不改變靜態主體。

## 3. 抽取式優先

**決定：** 預設答案引擎不生成新句子：把白名單內容切成「答案單元」，用中文 bigram 加詞彙同義詞與 BM25 檢索，直接挑出原文句子，每句附來源編號。
**理由：** 公部門的 AI 回答若有一句沒有依據，就是一次公信力事故。抽取式讓「每句都有出處」成為結構性保證，而不是靠提示詞祈禱。同時它不需要金鑰、不花錢、在瀏覽器就能執行，同一份程式碼（`src/client/answer/core.js`）也能在 Node 跑評估集。
**代價：** 答案不如生成式流暢，跨文件整合能力弱。
**緩解：** 提供 LLM 模式，但加上後檢（見下）。

## 4. BYOK LLM

**決定：** 使用者可自行輸入 Anthropic API 金鑰，存瀏覽器 localStorage，由瀏覽器直接呼叫；頁面標示供應商與模型。系統提示限制只能依檢索片段作答，輸出 `{sentences:[{text, cite:[chunkId]}]}`；後檢刪除沒有 cite 或 cite 不在檢索片段內的句子，全部被刪就退回抽取式。
**理由：** 機關不必先決定採購哪家模型、不替使用者承擔 token 費用、對話不經過本站伺服器；後檢確保「模型不能說片段以外的話」。
**代價：** 一般民眾不會用；金鑰存在瀏覽器有被惡意擴充功能讀取的風險，所以只當進階功能且在介面上提醒。
**何時重考慮：** 機關有正式採購的模型服務與資安審查後，改由受控的後端代理，並維持相同的後檢。

## 5. 治理在建置時計算

**決定：** 下次審閱日、逾期、失效版本、衍生內容待辦、白名單資格、翻譯是否過期、KPI，全部由 `scripts/lib/governance.mjs` 在建置時從欄位推導，掛回 `item.gov`；模板與前端只讀不算。
**理由：** 規則只寫一份，網頁、API、`.md`、JSON-LD、AI 索引才不會互相矛盾。時間相關的狀態（逾期）靠每日排程重建自動更新。治理規則有 `tests/` 的單元測試，每條至少一個案例。
**代價：** 狀態最快每日更新一次；要立即生效（如 AI 暫停）需要走緊急 PR。
**何時重考慮：** 若需要分鐘級狀態，可把「暫停」這類少數開關改成執行期讀取的小檔案，其餘不變。

## 6. 每日排程抓官方資料

**決定：** GitHub Actions 每日 02:00 UTC（台灣 10:00，每 2 小時排程中的那一次）執行 `npm run fetch`，抓旅遊疫情、國家等級、CKAN 資料目錄到 `data/snapshots/`，每檔記錄來源與抓取時間（provenance）；抓不到就沿用既有快照，不讓建置失敗。
**理由：** 沒有後端也能有新鮮資料；快照讓建置可重現；失敗降級讓外部服務中斷不會拖垮網站。
**代價：** 資料最多延遲一天；若來源改格式，快照會停在舊資料——因此資料集有「時效逾期」待辦與 `provenance.mode` 標示，不會悄悄過期。

## 7. 失效版本用 noindex 與 301，不用 robots.txt

**決定：** 被取代的文件頁輸出 `<meta name="robots" content="noindex">`，退出站內搜尋索引與 sitemap，並在 `redirects.json` 記一筆 301；`robots.txt` 只擋 `/ask/` 和 `/admin/`。
**理由：** `robots.txt` 擋住的是「抓取」，不是「收錄」。爬蟲被擋就讀不到頁面上的 `noindex`，網址仍可能因外部連結留在搜尋結果裡。要讓舊版從搜尋與 AI 檢索消失，必須讓爬蟲能讀到 noindex 與導向。
**代價：** 舊版頁面仍可被直接連到（這是特性：專業人員需要查閱歷史版本），所以頁首必須有紅色橫條。

## 8. 版本用獨立檔案表示

**決定：** `doc.mmr-recommendation.2019-05-14` 與 `.2025-04-16` 是兩個檔案，以 `family` 串起來；`supersededBy`、`isCurrent` 由引擎算。
**理由：** 覆蓋舊檔就沒有異動對照，也沒有「AI 不能引用舊版」可言。Git 歷史雖保存了舊內容，但舊內容不再有穩定網址與 id。
**代價：** 檔案數增加；用 `family` 與命名規則控制。

## 9. 態勢狀態由人工發布

**決定：** `stable` `rising` `peak` `declining` 四級由疫情中心在後台填寫，附發布依據與資料日；模型不得產生，答案頁的態勢卡只讀 `v1/situation.json`，不生成數字。
**理由：** 這是專業判斷與機關對外宣告，責任歸屬必須明確。

## 10. Banner 圖不放文字

**決定：** 首頁「本期宣導」的 Banner 圖只當氛圍，標題、副標、行動按鈕全部是 HTML 文字；Banner 本身也是一筆有權責單位、上下架日與關聯內容的 `banner` 內容，列在 `/campaigns/`。
**理由：** 文字燒進圖片就讀不出來：螢幕閱讀器念不到、搜尋與 AI 抓不到、七語無法翻譯、手機縮圖後看不清，更重要的是正本修訂時沒有人知道圖裡那句話要改。把文字留在 HTML，Banner 才能和其他內容一樣被治理（過期自動下架、依據正本修訂自動加註）。
**代價：** 設計師要接受「圖負責情緒、字負責資訊」，不能把完整海報當 Banner；真的需要海報時放在出版品或專區頁，並附文字版。

## 11. 影片一定要逐字稿

**決定：** `media` 型別必填 `transcriptMarkdown` 與 `basedOn`；逐字稿少於 50 字視為沒有，產生待辦。逐字稿進 AI 索引（可引用到「影片＋章節時間」）、參與反向稽核與數字一致性檢查。
**理由：** AI 與搜尋引擎看不到影片裡的聲音。沒有逐字稿，影片是治理上的黑洞：它可能還在說 MMR「1981 年以後出生」，反向稽核掃不到、白名單管不到。逐字稿同時是聽障民眾與外語翻譯的基礎。
**代價：** 影片製作單位要多交一份稿；用上架表單的預處理與字幕檔轉錄降低成本。影片製作日早於依據正本現行版生效日者，引擎自動標「過時」，這是刻意設計的壓力：逼製作單位面對「影片也會過期」。
**什麼時候重新考慮：** 影音量大到逐字稿成為瓶頸時，可引入語音轉文字初稿，但仍須人工確認後才算「有逐字稿」。

## 12. 八圖示只給專業版

**決定：** 現行官網的「應用專區」八個圖示（通報、檢驗、宣導素材、統計專區、申請、研究、出版品、疫苗基金）放在 `/services/` 與 `/pro/`；民眾首頁只放一行「更多服務」，不放八圖示。
**理由：** 先期構想訪談的結論是民眾腦中沒有「應用專區」這個概念，他們帶著問題來；八圖示佔據首屏只會把問題框與疫情狀態擠下去。醫療與研究人員反而需要這種機關導向的入口，且他們會直接找圖示。
**代價：** 少數想辦申請的民眾要多一步：從「更多服務」或搜尋進入；用 `/apply/` 依對象分組、答案頁的 `apply` 意圖補足。

## 13. 世界地圖用預先產生的 110m 路徑 JSON，不在執行期載入地圖函式庫

**決定：** `/travel/` 的世界地圖是 inline SVG。路徑由開發期腳本 `scripts/gen-world-map.mjs`（`npm run gen:map`）一次產生到 `src/data/world-paths.json`（Natural Earth 投影、`world-atlas` 110m、不含南極洲、座標取到 1 位小數，約 110 KB、174 個國家／地區），連同產物一起 commit。`world-atlas`、`topojson-client`、`d3-geo`、`i18n-iso-countries` 只放在 `devDependencies`；建置時 `_travel-map.mjs` 只讀 JSON，正式依賴仍只有 `ajv`、`ajv-formats`、`marked`。
**理由：** (1) 這張圖只做一件事：依等級上色、點國家進目的地頁，不需要縮放、拖曳或圖磚，載入 Leaflet、D3 或 Mapbox（數十到數百 KB 的 JS，圖磚還有外部請求與用量條款）是為不需要的能力付費。(2) 靜態網站、無後端、離線也要能建置：路徑是資料，產生一次就固定，建置結果可重現，不受 CDN 或套件版本影響。(3) 純 SVG 與 HTML 是第一等公民：每國一個 `<a><path><title>`，鍵盤可 Tab、螢幕閱讀器念得到「國名：等級」，不需要 JS 就能運作，顏色直接用站內 `--tv-*` 設計變數，深淺主題與列印都跟著走。(4) 不引入新的供應鏈風險：執行期零第三方程式碼。
**代價：** 110m 精度粗，面積小的地區沒有多邊形（目前主檔缺香港、澳門、新加坡、馬爾地夫），地圖上點不到，需靠「查目的地」或等級表進入；邊界爭議地區（如科索沃、北賽普勒斯、索馬利蘭）依 Natural Earth 預設呈現，無 ISO 數字碼者不收錄。國界若有變動要重跑腳本並人工檢視差異。地圖只是索引，**不是唯一入口**：等級表與搜尋提供同樣資料，這也是無障礙的文字替代。
**什麼時候重新考慮：** 需要縮放到區域或城市層級、疫情點位或熱度圖、或小國家的點選成為重要需求時：先改用 50m 路徑（約 3–4 倍大小）並為微型國家補圓點標記；仍不足才評估執行期地圖函式庫，並考慮只在該頁以動態載入。

## 14. 借 TinaCMS 的編輯設計，不把 TinaCMS 裝進來

**背景：** TinaCMS 是目前 Git-based CMS 裡編輯體驗口碑最好的一個：內容存在 repo（Markdown／MDX／JSON），編輯器把頁面放中間、表單放側欄，點頁面上的區塊就跳到對應欄位（它稱 contextual／visual editing），存檔即 commit，另有「editorial workflow」在編輯器裡開分支與 PR。這些和本原型「Git 是唯一正本、PR 是唯一上架路徑」的前提一致，所以值得看。
**決定：** 只借設計，不裝套件。第二十二輪把四個設計做進既有 `/admin/publish/`：（1）右側即時頁面預覽；（2）點預覽區塊跳欄位、游標在欄位時預覽亮起；（3）群組欄位摺疊且摺疊列顯示目前值；（4）存檔按鈕與狀態永遠看得到（含 Ctrl+S）。另加前台「編輯這頁」浮動按鈕（TinaCMS 的鉛筆按鈕）。
**為什麼不裝：** (1) TinaCMS 的編輯器要有 GraphQL 後端——Tina Cloud（SaaS，內容與登入經第三方）或自架 backend（Node 常駐服務＋資料庫層），本原型與規劃的正式環境是**純靜態、無常駐後端**，多一個服務就多一套要維運、要資安檢核的東西（[git-as-cms.md](git-as-cms.md) 第 3 節）。(2) 它的 visual editing 需要前端用 React 並以 `useTina` 包住每個頁面；本站模板是建置期 Node 樣板＋少量原生 JS，為了編輯器把前台改成 React 是本末倒置。(3) 登入與權限：TinaCMS 自帶使用者系統或走 Tina Cloud，與「機關 SSO ＋ AD 群組決定單位×角色」（[admin-auth.md](admin-auth.md)）不相容，要客製。(4) 本原型的正本不是「一篇文章」而是**帶治理欄位的 JSON**（owner、reviewedAt、basedOn、languages、assets…），上架時的預處理（實體對應主檔、一致性檢查、車道判定、資產預檢）才是重點，TinaCMS 的表單引擎幫不上忙。(5) 供應鏈：執行期不引入第三方框架是本原型一貫原則（第 13 節）。
**代價：** 預覽是「示意版面」（用後台樣式畫出同樣的資訊結構），不是跑真正的頁面模板；要做到像素級一致，得把 Node 端模板搬到瀏覽器或用 iframe 載 PR 預覽網址。沒有「在真實頁面上直接打字」：本原型的內文是 Markdown 欄位，表單裡的所見即所得已經涵蓋。
**什麼時候重新考慮：** 若正式環境決定要有常駐後端（例如代承辦人開 PR 的服務擴大成完整 API），且前台改以 React／Next 建置，TinaCMS（或同類：Decap、Sveltia、Keystatic）可重新評估；屆時本輪定義的「欄位 ↔ 預覽區塊」對應（`FIELD_MAP`）與治理欄位 schema 仍可沿用。

## 15. 原型公開示範但不給索引；民眾端不提供 BYOK，示範限同事且金鑰只活在分頁

**背景：** 2026-10-10 外部檢視（grokbot）指出：原型以疾管署名義公開在 GitHub Pages，有示意的疫情數字，搜尋引擎與 AI 爬蟲都能抓；答案頁的「進階」要民眾貼 Anthropic 金鑰並長期放在 `localStorage`，而 GitHub Pages 專案站同帳號所有專案共用同一 origin 的 localStorage。
**決定：** (1) 新增站台模式，預設 `prototype`：每頁 `noindex, nofollow`、`robots.txt` 全擋、每頁頂端「非官方原型」橫幅；正式站以 `SITE_MODE=production` 建置才拿掉，AI 政策版 robots 仍保留為 `robots.production.txt`。(2) BYOK 不下架（它是展示「生成式答案也要逐句引用、後檢」的唯一方式），但金鑰改存 `sessionStorage`、欄位只在有後台工作階段的瀏覽器出現、模型名稱由設定帶入。正式站若要生成式答案，走機關受控後端代理，金鑰只在伺服器端（§4 的「何時重考慮」）。
**為什麼不乾脆拿掉 robots 政策版：** 附錄 H 的三類 AI 爬蟲分流是正式站要用的規格，拿掉就沒地方示範；改成雙檔輸出，原型擋、正式放，兩邊都看得到。
**為什麼不用 `X-Robots-Tag`：** GitHub Pages 不能自訂回應標頭，只能用 meta 與 robots.txt；正式環境的標頭基準在 deploy.md §10。
**代價：** 原型期間 Google 等已索引的頁面要等重新爬取才會退出（可在 Search Console 手動移除）；橫幅佔每頁頂端一行。

## 16. 無障礙目標採新版網站無障礙規範 AA（WCAG 2.2 AA），機器可判的項目由 CI 把關

**決定：** 站台的無障礙目標從「AA（WCAG 2.1）」提升為「新版網站無障礙規範 AA 等級（對應 WCAG 2.2 AA）」；機器能判定的項目用 `npm run a11y`（Playwright＋axe-core）放進 PR 的必要檢查，`serious`／`critical` 失敗就擋合併，`moderate`／`minor` 只警告；機器判不了的項目在 [a11y.md](a11y.md) 明列「待人工稽核」。

**理由（Why）：**
1. **法定基準換了。** 數位發展部 2026-05-29 修正「網站無障礙規範」、2026-11-30 施行，新增 WCAG 2.2 項目（例如 2.5.8 目標尺寸 24×24 px）。官網上線時就是新基準，現在把基準對齊，比上線後補救便宜。
2. **不靠人記得。** 第一次外部掃描就在每一頁找到 critical（`aria-pressed` 用在連結），代表 PR 審查靠人眼看不出這類問題；把檢查變成 CI 步驟，退步就會被擋。
3. **只擋 serious／critical。** axe 的 moderate 常是版面風格的主觀判斷（例如示範橫幅不在 landmark 內），全擋會讓同事為了過關亂改；警告保留可見度但不卡發布，與本站其他閘門「錯的才擋」的原則一致。
4. **誠實標示限制。** 自動工具只能抓一部分問題，通過不等於合規；因此自我評量表保留「待人工稽核」，避免在無障礙聲明頁過度宣稱。

**代價：** 每個 PR 多約數分鐘（安裝 Chromium＋建置一份 `BASE_PATH=''`＋掃 30 次）；多了 `playwright`、`@axe-core/playwright` 兩個開發依賴；axe 版本升級可能新增規則造成新的失敗（需要時在腳本鎖版本）。

**什麼時候重新考慮：** 掃描時間過長（可改只掃有改動的樣板）；axe 誤報造成同事困擾（針對單一規則加例外並寫下原因，不整體關閉）；取得人工稽核或第三方檢測報告後，用報告取代「待人工稽核」欄位。
