## 這份文件是什麼

規劃文件告訴我們**要做什麼**；做原型的過程中，我們遇到一批規劃沒有寫到、但正式上線一定會碰到的問題，也各自做出了可以運作的解法。這份文件把它們整理成「規劃文件回補」：每一項寫明做法、為何需要、對應規劃哪一章（或規劃哪裡沒寫）、原型在哪裡看得到、正式上線還缺什麼。

用途有兩個：（1）下一版規劃文件修訂時，可以直接把這裡的條目併入；（2）向主管或委員會說明「原型的價值不只是畫面，而是把規劃的空白填成可以討論的具體做法」。

## A. 資料管線與外部資料

### 1. 官方旅遊警示等級當「事件日誌」，加背景提醒與合理性閘門

- **做法**：官方 `CountryEpidLevel/ExportJSON` 每一列是一則警示事件（含「解除」），不是現行表。`fetch-data.mjs` 以「每國×疾病×區域取最新一則、最新為解除就不列」判定現行；同一疾病同一等級涵蓋 ≥ 50% 國家（且 ≥ 20 國）歸為「全球背景提醒」，不逐國列，各國排序改用排除背景後的「針對性等級」；事件寫入 `country-epid-events.json` 推出新增／調升／調降／解除；live 分布超出閘門（第三級 > 5、第二級 > 60、第一級 > 250）就沿用人工校對快照並記錄原因。
- **為何需要**：直接把原始資料當現行表，會出現幾十個第二級國家與 2020 年的 COVID 第三級；2023-11 的一次性全球重發還會讓 245 筆第一級「新冠併發重症」淹沒真正需要旅客注意的警示。
- **對應規劃章節**：§1.8 與 §2（旅遊疫情是全站唯一 API 型出口，視為範本）；附錄 A（旅遊疫情 schema：「國家、疾病、等級、生效日、建議」，假設資料就是現行表）；§6.3 出國意圖。**規劃把這張表當作乾淨資料，沒有處理語意問題。**
- **原型位置**：`scripts/fetch-data.mjs`、`data/snapshots/country-epid-level.json`、`country-epid-events.json`；ARCHITECTURE §12.1；[governance-model.md](governance-model.md) 規則 16；[deploy.md](deploy.md) 疑難排解。
- **正式上線還缺什麼**：向疫情中心／檢疫組確認 ExportJSON 的欄位語意，最好由官方補上「結束日」或「是否現行」欄位；背景提醒的文案與 50% 門檻由旅遊醫學專家審定；閘門數字要由資料擁有者核定，並建立「閘門觸發」的通知流程。

### 2. CI 每日把官方資料快照 commit 回 repo

- **做法**：GitHub Actions 每日 03:00 UTC 跑 `npm run fetch`，把旅遊疫情、國家等級、CKAN 目錄存成 `data/snapshots/*.json`，每檔帶 provenance（來源、抓取時間、`meta.mode: live|snapshot|derived`），排程與手動執行時 commit 回 `main`；抓不到時沿用上一份並記錄 `meta.lastLiveAttempt`。
- **為何需要**：靜態網站沒有後端，快照讓建置可重現（任何一個 commit 都能重建「當時的網站」）；抓取失敗降級而不是讓建置失敗，外部服務中斷不會拖垮官網。
- **對應規劃章節**：§5.1 資料層（資料目錄、OpenAPI 閘道）；§7.5「資料集在更新頻率內更新」；§8.1 2027 Q2 知識檢索層。規劃只談目錄與閘道，沒談「怎麼穩定取得外部資料」。
- **原型位置**：`.github/workflows/pages.yml`、`data/snapshots/`、`scripts/fetch-data.mjs`、[architecture-decisions.md](architecture-decisions.md) 第 6 項。
- **正式上線還缺什麼**：正式環境不該把資料 commit 進內容 repo（雜訊太大），應改為排程任務寫入物件儲存或資料庫並保留歷史；機器人帳號的權限與稽核；抓取失敗連續 N 天的告警；對方改格式的偵測。

### 3. 建置時全站連結檢查與 `/pending/` 落地頁

- **做法**：每次建置後掃 `dist/**/*.html`（含 JSON-LD 內的 url），站內連結必須指到存在的檔案，找不到的錨點為警告，沒有 basePath 的連結為錯誤（`LINK_CHECK=error` 時建置失敗）。內容裡尚未遷移的文件（表單、PDF、附件）一律連到 `/pending/?ref=<內容 id>&doc=<文件名稱>`，該頁 `noindex`、顯示權責單位與回到來源頁，不連到失效網址。
- **為何需要**：內容量大時壞連結一定會出現；更糟的是「為了不壞連結而放一個佔位網址」，會被當成真連結。`/pending/` 把「還沒遷移」變成一個誠實、可統計的狀態。
- **對應規劃章節**：§3.2 C5（無內容盤點與下架機制）；§7.4 第 4 點（上線前盤點）；§8.2 2028–2029 內容遷移。
- **原型位置**：`scripts/lib/check-internal-links.mjs`、`src/templates/public/pending.mjs`、`dist/v1/governance/link-report.json`、`tests/links.test.mjs`。
- **正式上線還缺什麼**：`/pending/` 的引用清單要轉成遷移待辦並指派（與第 21 項的清單整合）；PDF 實際遷移與機讀化；錨點警告的處理標準。

## B. 內容生命週期自動化

### 4. 外部連結健康：每日檢查、失效自動變待辦

- **做法**：專區連結、申請網址與表單、公告報名網址、影片網址、出版品 PDF 彙整為 `site.gov.externalLinks[]`；`npm run fetch -- --check-links` 對每條 https 連結送 HEAD，結果寫回 `status`（`ok`／`broken`／`unchecked`）與 `lastCheckedAt`；`broken` 產生 `link-broken` 待辦（約 7 日），KPI 顯示健康度。
- **為何需要**：機關型網站大量連到外部（衛生局、其他部會、報名系統）；對方改網址你不會知道。不自動檢查，壞連結由民眾發現。
- **對應規劃章節**：§3.2 C5；§3.1 A4（子網站與外部連結拼接）；§7.4（生命週期）。規劃的生命週期只涵蓋「內容本身」，沒有涵蓋「內容所連的外部資源」。
- **原型位置**：`scripts/fetch-data.mjs`（`checkLinks`）、`/admin/links/`、`v1/governance/links.json`、KPI `link-health`、`tests/check-links.test.mjs`。
- **正式上線還缺什麼**：對方拒絕 HEAD（403／405）時的誤判處理與改用 GET；重新導向的處理（301 後自動建議更新連結）；檢查頻率與對外站台的禮貌上限；需要登入的連結如何處理。

### 5. 到期自動退場：公告截止、專區結束、Banner 上下架

- **做法**：人才招募與採購公告的 `deadlineAt` 一過，引擎自動標「已截止」、退出首頁與進行中列表（保留在「已截止」頁籤），不開待辦、不退白名單；專區 `endAt` 過後標「已結束」並退出首頁專區列；Banner 有 `startAt`／`endAt` 與權責單位，過期自動下架、即將開始者顯示在 `/campaigns/`。
- **為何需要**：這類內容的壽命是「事件日期」而不是「審閱週期」；若要承辦人記得去下架，一定有人忘記，首頁就會掛著三個月前的招募公告。
- **對應規劃章節**：§1.1（第一層導覽含採購、人才）；§7.4 內容生命週期（只列疾病、疫苗、Q&A、新聞稿的審閱週期，**沒有事件型內容的退場規則**）。
- **原型位置**：`scripts/lib/governance.mjs`（`gov.closed`、`gov.ended`）、`/notices/`、`/admin/notices/`、`/campaigns/`、KPI `notices-closed-unarchived`；[governance-model.md](governance-model.md) 規則 9、12。
- **正式上線還缺什麼**：與人事行政總處、政府電子採購網的資料交換（目前只是自填截止日）；封存的年度清理流程；截止後的法定保存期間。

### 6. 影音過時規則：製作日早於依據正本現行版生效日 ⇒ 過時

- **做法**：每支影片必填 `basedOn`（依據正本）、`producedAt`（製作日）與 ≥ 50 字逐字稿；製作日早於依據正本現行版 `effectiveAt` 時，引擎自動在影片頁加註「本影片依 … 製作，建議已於 … 修訂」、退出白名單、開高優先待辦；YouTube 說明欄第一行固定格式 `製作日期 … · 依據 … · 正本 …`。
- **為何需要**：MMR 事件的根因就是「AI 重製的影片沿用已失效的條件」。影片是治理黑洞：搜尋與 AI 看不到影片內容，也沒有失效標記。
- **對應規劃章節**：§7.7 MMR 事件（三個缺口：衍生內容連動、下架方式、AI 產製素材）。規劃提到「AI 製作影片」但沒有給出影片的欄位與判定規則。
- **原型位置**：`content/media/`、`schemas/media.json`、`/media/`、`/admin/media/`、待辦 `media-outdated`；[guide-staff.md](guide-staff.md) 第 8 節；[architecture-decisions.md](architecture-decisions.md) 第 11 項。
- **正式上線還缺什麼**：真實影片 id 與字幕檔；YouTube 說明欄的批次更新（需 YouTube API 與帳號授權）；影片製作單位的作業流程簽核。

### 7. 逐字稿納入反向稽核與索引

- **做法**：逐字稿分章節（`[00:30]` 時間標記）切成答案單元，`url` 帶 `#t=秒數`，可被 AI 引用到「影片＋章節時間」；同時參與反向稽核（宣告失效的說法，如 MMR「1981 年」）與數字一致性檢查（口語「二十四小時」會先轉成 24 再比對主檔）。
- **為何需要**：沒有逐字稿，反向稽核掃不到影片；有了逐字稿，影片裡的失效說法會和網頁文字同樣被抓到。逐字稿也是聽障民眾與外語翻譯的基礎。
- **對應規劃章節**：§7.7（反向稽核的需求來源）；§6.5（多語）。規劃的反向稽核只談網頁文字。
- **原型位置**：`scripts/lib/index-builder.mjs`、`scripts/lib/governance.mjs`（反向稽核掃描範圍）、`/admin/publish/` 預處理、`content/master/diseases.json` 的 `auditRules`。
- **正式上線還缺什麼**：語音轉文字的初稿流程（仍須人工確認才算「有逐字稿」）；七語逐字稿；每個 auditRule 由各組提供與審定。

### 8. 通報時限表由主檔產生，檢驗送驗時限做一致性檢查

- **做法**：`/report/` 的法定傳染病通報時限表由 `master/diseases.json` 自動產生（類別、時限、病例定義連結）；`labtest.sendWithinHours` 大於主檔 `notifyWithinHours` 時開低優先「檢驗不一致」待辦；專業版索引把每個檢體寫成一句結構化句，可被直接引用。
- **為何需要**：同一個事實（登革熱通報時限）分散在手冊、病例定義、Q&A、新聞稿，會出現互相矛盾的版本。把它變成主檔欄位，其餘全部是主檔的消費者。
- **對應規劃章節**：§3.4 R2（無「答案單元」）；§7.3 傳染病主檔（含通報時限）；附錄 A（型別 schema）；§6 AI-4。規劃有主檔欄位，**沒有寫「由主檔產生頁面」與「跨型別一致性檢查」**。
- **原型位置**：`/report/`、`/lab/`、`schemas/labtest.json`、待辦 `labtest-inconsistent`；[guide-staff.md](guide-staff.md) 第 11 節。
- **正式上線還缺什麼**：99 種法定傳染病主檔完整欄位；認可檢驗機構名單；NIDRS 實際連結與權限。

### 9. 機關型區塊的結構化型別（影音、專區、申請、出版品、檢驗、研究）

- **做法**：現行官網首頁的 Banner 輪播、影片輪播、小 Banner 專區列，以及應用專區八項，全部納入同一套治理欄位，各有 schema、頁面、索引與 JSON-LD（`GovernmentService`、`PublicationIssue`…）；首屏仍以問題框與疫情狀態為先，八圖示只放專業版（[architecture-decisions.md](architecture-decisions.md) 第 12 項）。
- **為何需要**：不把機關型區塊納入，這些頁面就會變成治理的化外之地，改版後又成了孤島。
- **對應規劃章節**：§1.1（第一層導覽、應用專區）；§1.3；附錄 A（型別 schema 只列疾病、Q&A、新聞稿、文件、資料集、旅遊疫情六種）；§5.3（先期構想）。
- **原型位置**：`schemas/{media,topic,service,publication,labtest,research}.json`、ARCHITECTURE §11、`/services/`、`/apply/`、`/publications/`、`/lab/`、`/research/`。
- **正式上線還缺什麼**：全量專區盤點；與線上申請系統、GRB 研究資訊系統的整合；出版品 1985 年起全卷期回補。

## C. AI 回答與評估

### 10. 抽取式優先的答案引擎（預設不生成）

- **做法**：預設引擎把白名單內容切成答案單元，以中文 bigram、詞彙同義詞與 BM25 檢索，直接挑出原文句子，每句附來源編號；生成式模型是選用。
- **為何需要**：公部門 AI 回答若有一句沒有依據就是公信力事故。抽取式讓「每句都有出處」成為結構性保證，不靠提示詞；同一份程式碼在瀏覽器和 Node（評估集）執行，不需要金鑰與經費。
- **對應規劃章節**：§6.1 第 1 點（只轉述、不創作）；附錄 C（RAG 架構假設生成式回答）。規劃預設是 RAG 生成，**沒有把「不生成」列為一個有價值的基準線**。
- **原型位置**：`src/client/answer/core.js`、`eval/run-eval.mjs`；[architecture-decisions.md](architecture-decisions.md) 第 3 項。
- **正式上線還缺什麼**：用同一個評估集比較抽取式與 LLM 版本的完整度與滿意度，決定正式預設；更大的語料與同義詞維護機制。

### 11. BYOK LLM 與輸出後檢

- **做法**：使用者可自備金鑰，瀏覽器直連供應商；系統提示限制只依檢索片段作答，輸出 `{sentences:[{text, cite:[chunkId]}]}`；後檢刪除沒有 cite 或 cite 不在檢索片段內的句子，全部被刪就退回抽取式；介面標示供應商與模型。
- **為何需要**：機關不必先決定採購哪家模型就能示範生成式的價值，同時把「模型不能說片段以外的話」做成程式碼而非期望。
- **對應規劃章節**：§6.1 第 1、3 點；附錄 C 第 3–4 點（生成與防護）；§5.1 模型策略。
- **原型位置**：`src/client/answer/llm.js`；[governance-model.md](governance-model.md) 第 5 節。
- **正式上線還缺什麼**：機關正式採購的模型與資安審查後，改為後端代理（金鑰不落在瀏覽器）；個資遮蔽與提示注入偵測移到伺服器端；對話紀錄去識別與保存期限。

### 12. 評估集閘門：版本題只要錯一題，建置失敗

- **做法**：`content/governance/eval-set.json` 的題目分類（版本題、拒答題、各意圖）；`CI=true` 時版本題未全對，`npm run build` 以非零狀態結束，不能部署；`/admin/eval/` 在瀏覽器跑同一份評估，`/transparency/` 顯示結果。
- **為何需要**：「引用到失效版本」是規劃定義的嚴重缺陷，只有變成發布閘門才有保障；人工在上線前才檢查，無法防止之後某次內容改動讓舊版悄悄回到答案裡。
- **對應規劃章節**：附錄 D（評估指標）；§6.1 第 4 點（上線門檻）；§7.5 末列「評估集版本題正確率 100%」。規劃把它列為指標，**沒有寫成與 CI 綁定的硬閘門**。
- **原型位置**：`eval/run-eval.mjs`、`content/governance/eval-set.json`、`.github/workflows/pages.yml`；[guide-staff.md](guide-staff.md) 第 0 節。
- **正式上線還缺什麼**：擴充到 ≥ 500 題（含疫情高峰與對抗性題）；LLM-as-judge 與 10% 人工抽樣；紅隊測試流程；季度凍結評估集版本。

## D. 呈現與整合

### 13. 三層露出的實作細節

- **做法**：所有治理資訊都在 DOM、`.md` 機讀版與 JSON-LD 裡；視覺分四層——預設層（頁首一行來歷）、狀況層（逾期、失效、AI 暫停警示）、按需層（`details/summary` 的來源卡、本頁資料與授權）、專業層（頂部分眾切換或 `?view=pro`，身分記在瀏覽器本機）。稽核編號藏在回報表單自動帶入。
- **為何需要**：把全部治理欄位攤在頁面上，官網看起來像後台；全部藏起來，民眾與 AI 無法判斷內容可不可信。
- **對應規劃章節**：附錄 G（三層露出原則）；§6.1 第 3 點。規劃給了原則，原型補上實作細節（`data-view`、`aria-describedby`、一次只開一張卡、版面順序）。
- **原型位置**：ARCHITECTURE §8、`src/templates/layout.mjs`、`src/templates/public/_partials.mjs`、`src/client/ui.js`。
- **正式上線還缺什麼**：真實使用者測試（尤其是高齡與行動裝置）；高對比與螢幕閱讀器實測；專業層是否需要登入。

### 14. Banner 當作有治理的內容：圖不放文字，兩種擺法預覽

- **做法**：Banner 是一筆有權責單位、上下架日、關聯內容的 `banner` 內容；圖只當氛圍，標題與行動按鈕全部是 HTML 文字；首頁依疫情狀態自動選兩種擺法之一（A：右側「本期宣導」卡；B：流感高峰時宣導卡退到態勢卡下方），`?hero=A` 或 `?hero=B` 可強制預覽，`/campaigns/` 並排示意。
- **為何需要**：燒在圖裡的字讀不到、搜不到、翻不了、正本修訂時沒人知道要改。兩種擺法的預覽讓公關室與主管在決策前看得到實際畫面。
- **對應規劃章節**：§5.3（先期構想的首頁）；§3.2 C1（無權責單位）；wireframe 首頁。
- **原型位置**：`content/banners/`、`/campaigns/`、`src/templates/public/home.mjs`；[architecture-decisions.md](architecture-decisions.md) 第 10 項。注意：這是**版面預覽**，不是上線後的流量 A/B 實驗。
- **正式上線還缺什麼**：與公關室排程工具整合；真正的 A/B 實驗需要分析工具與隱私評估；正式圖片與替代文字。

### 15. 疫苗接種點導向 vaxmap：不自己列院所，只做深連結

- **做法**：本站所有接種點入口（疫苗頁、Banner、答案頁行動鈕）一律以深連結導向 vaxmap-next（`#g=flu`、`#g=covid`、`#g=pcv`、`#g=antiviral`，語言互帶；無地圖群組的疫苗連到接種資訊專區）。院所與庫存的正本只在 vaxmap。
- **為何需要**：庫存每天變，本站自己列就是過期資訊；兩邊各維護一份疫苗名稱與對象最後會互相矛盾。
- **對應規劃章節**：§6.3 疫苗意圖（「附近接種點（vaxmap）」）；§1.8 與 §3.1 A4（子網站各自為政）；§8.3 子網站納入同一版型與 API。規劃只寫了「串 vaxmap」，沒有寫整合方式與資料所有權。
- **原型位置**：`site.config.mjs`（`vaxmapUrl`）、`src/templates/public/_partials.mjs`（`vaxmapLink()`）、`src/client/answer/core.js`（`vaxmapHref()`）；[vaxmap-integration.md](vaxmap-integration.md)。
- **正式上線還缺什麼**：vaxmap-next 目前是概念原型、非官方站，正式要指向官方 vaxmap 並建立反向連結；共用 `vaccines.json`；資料日與庫存免責文字統一；兩站的 Owner／Steward。

### 16. 目的地決策式旅遊頁

- **做法**：`/travel/` 的主角是「查目的地」；每個國家（約 231 個）有 `/travel/{ISO2}/`，含針對性等級、持續時間（超過 3 年標「長期建議」）、旅程三階段建議（出發前、旅途中、返國後，由疾病主檔規則生成，不手寫）、該國近 30 天疫情資訊。
- **為何需要**：民眾的問題是「我要去越南，要注意什麼」，不是「哪些國家是第二級」。
- **對應規劃章節**：§6.3 出國意圖（例句「帶 2 歲小孩去越南」，頁面組成：目的地疫情等級 → 建議疫苗與防護 → 旅遊醫學門診）。規劃給了組成，原型補上資料契約。
- **原型位置**：`/travel/`、`/travel/{ISO2}/`、`src/templates/public/travel.mjs`；ARCHITECTURE §12.2。
- **正式上線還缺什麼**：旅遊醫學門診清單與預約連結；旅程建議規則由專家審定；兒童與孕婦等特殊族群規則。

### 17. 「變化而非狀態」：近 30／90 天事件統計與自適應視窗

- **做法**：由事件流統計近 30 天新增、調升、調降、解除；30 天事件不足 10 則時自動改看 90 天，並明示目前使用的視窗。首頁與 `/travel/` 都顯示。
- **為何需要**：旅客與媒體關心的是「最近有什麼變化」；「第二級國家共 29 個」每天都一樣，沒有資訊量。
- **對應規劃章節**：§6.4 疫情態勢層（趨勢箭頭、近四週數字）；§6.3。規劃的趨勢概念只用於國內態勢。
- **原型位置**：`/v1/country-changes.json`、`/travel/`、首頁任務卡；ARCHITECTURE §12。
- **正式上線還缺什麼**：事件的官方「已讀／已通知」語意；視窗門檻（10 則）由疫情中心核定。

### 18. 世界地圖：預先產生的 110m 路徑、純 SVG

- **做法**：開發期腳本一次產生 `src/data/world-paths.json`，建置時輸出 inline SVG；三級三色、無建議留白、每國一個 `<a><path><title>`，鍵盤可達，等級表是文字替代。
- **為何需要**：不引入地圖函式庫與圖磚外部請求，零第三方執行期程式碼；符合靜態網站與無障礙。
- **對應規劃章節**：§6.4（「點進去是趨勢圖與地圖」）；附錄 G；§9 供應鏈風險。
- **原型位置**：`scripts/gen-world-map.mjs`、`src/templates/public/_travel-map.mjs`、`tests/travel-map.test.mjs`；[architecture-decisions.md](architecture-decisions.md) 第 13 項。
- **正式上線還缺什麼**：香港、澳門、新加坡等小地區點選；邊界爭議地區的對外說明用語（需外交部／機關確認）。

### 19. 子站與外部入口的統一規範

- **做法**：子網站（nidss、vaxmap、data）以外部連結出現時一律標示「開新視窗 ↗」，語言互帶，並由外部連結檢查納入健康度。
- **為何需要**：規劃指出子站各自為政；整合前的過渡期，至少讓使用者不迷路。
- **對應規劃章節**：§3.1 A4；§8.3。
- **原型位置**：`_partials.mjs` 的外部連結元件、[vaxmap-integration.md](vaxmap-integration.md) 第 0 節原則 3。
- **正式上線還缺什麼**：共用版型、帳號與搜尋（第三階段）。

## E. 內容移轉與網址治理（**規劃最大的空白**）

### 20. 同網域換站的 301 策略（逐筆對照，不轉首頁）

- **做法**：舊網址 → 新網址用伺服器 301 逐筆對照；一對一優先，多對一帶錨點，一對多不可；刻意移除回 410；版本族穩定網址用 302；不鏈式；大小寫與尾斜線正規化；識別型 query 納入比對；附件轉到新文件頁而非新 PDF。完整規則見 [migration-playbook.md](migration-playbook.md) 第 2 節。
- **為何需要**：舊站網址是 22 字元加密 ID，無法規則推算；不處理，上線當天所有書籤、外部連結、搜尋收錄與 AI 引用全部斷線。
- **對應規劃章節**：§8.2 第二階段「2029 Q1 新官網上線；舊站轉址與封存」只有一行；§5.2 提到遷移或封存；§3.3 T6（加密 ID）；附錄 H（robots 與 `/Uploads/` 301）。**規劃沒有寫轉址策略。**
- **原型位置**：`dist/v1/redirects.json`（`kind: legacy | superseded | family-latest | migration`）、`content/*/*.json` 的 `legacyUrls`。
- **正式上線還缺什麼**：全站盤點與 ID 取得（開發環境連不到舊站，目前 ID 為佔位）；伺服器／CDN 實際設定與測試；410 清單的產生；RSS 與英文區的對照；回復計畫。

### 21. 移轉清單與進度（migration manifest）

- **做法**：每個專區或欄目一份 `content/migration/{slug}.json`，逐筆記錄舊標題、舊網址、類型、狀態（`migrated`／`merged`／`archived`／`pending`／`dropped`）、對應新頁、錨點、說明與「移轉後新增的治理要求」；權責單位在後台逐筆確認 `verified`；`pending` 自動開待辦；`/admin/migration/` 顯示進度。
- **為何需要**：「遷移」若只是一個工作項目，就無法追蹤、無法分派、也無法向委員會報告進度。清單把它變成可驗收的資料。
- **對應規劃章節**：§7.4 第 4 點（上線前一次性盤點，四因子判斷保留／合併／封存）；§8.2 內容遷移；§7.5 品質指標（尚無移轉相關指標）。規劃有「四因子盤點」的原則，**沒有盤點結果的承載格式**。
- **原型位置**：`content/migration/tuberculosis.json`、`schemas/migration.json`、`/admin/migration/`、`/admin/` 的「移轉進度」卡；ARCHITECTURE §13.1。
- **正式上線還缺什麼**：全站清單（結核病只是第一個，其餘 98 種疾病與所有欄目）；四因子（使用者需求、相關性、重複性、優先度）的分數欄位尚未納入清單 schema，建議下一版加；移轉進度 KPI 納入 §7.5。

### 22. 404 自動轉址與 `/legacy/` 舊網址查詢

- **做法**：404 頁載入 `v1/legacy-map.json`，命中舊網址就顯示「舊網址已搬家，3 秒後帶你到新頁」並轉過去；未命中顯示同站搜尋與 1922。`/legacy/` 讓人貼舊網址查新頁，並說明轉址政策與關閉日。
- **為何需要**：伺服器轉址上線前的過渡、以及伺服器規則漏掉時的最後一道人工兜底。
- **對應規劃章節**：§8.2（舊站轉址與封存）；規劃未涉及使用者端的兜底。
- **原型位置**：`src/templates/public/notfound.mjs`、`src/templates/public/legacy.mjs`、`/legacy/`、`dist/v1/legacy-map.json`。
- **正式上線還缺什麼**：靜態主機的 404 頁 HTTP 狀態仍是 404，搜尋引擎不會因此移轉評價，**正式站必須是伺服器 301**；404 頁不可成為唯一機制。

### 23. 轉址對照輸出三種伺服器格式

- **做法**：由 `redirects.json` 轉出 `redirects/nginx.map`、`redirects/web.config.rewritemap.xml`（IIS）、`redirects/_redirects`（Netlify／Cloudflare Pages）；`{id}` 佔位項目不進伺服器檔。
- **為何需要**：資訊室拿到的是可直接匯入的檔案，而不是一份要人工轉換的試算表；來源只有一份（清單），不會出現「文件寫一套、伺服器設另一套」。
- **對應規劃章節**：§8.2；§5.1 資料層（主資料公開，但未含轉址）。
- **原型位置**：`dist/redirects/*`（由 `scripts/lib/emit-api.mjs` 產生）；[migration-playbook.md](migration-playbook.md) 第 3 節。
- **正式上線還缺什麼**：在正式伺服器（現行舊站為 ASP.NET MVC，最可能是 IIS）實測；筆數上限與效能；識別型 query 的 key 格式驗證。

### 24. 404 log 分析：自動分類「可直接 301／待補對照／真的不存在」

- **做法**：`scripts/analyze-404-log.mjs` 讀伺服器 access log（Nginx combined 或 IIS W3C 自動判斷），抓 404 路徑與次數，對照 `legacy-map.json` 與 migration 清單，輸出 Markdown 報表三類；「待補對照」附可貼進 migration JSON 的 `items` 草稿。
- **為何需要**：盤點一定會漏；上線後真實流量是最完整的漏網清單。把它變成固定節奏的待辦，漏盤的頁面在幾週內補完。
- **對應規劃章節**：§8.2；§7.5（尚無此類指標）。
- **原型位置**：`scripts/analyze-404-log.mjs`、`tests/fixtures/access-404.log`、[migration-playbook.md](migration-playbook.md) 第 7 節。
- **正式上線還缺什麼**：log 的取得與去識別（含 IP）；排程執行與報表寄送；與工單系統整合；404 率與轉址命中率 KPI 納入 §7.5。

### 25. 舊網址揭露與到期自動隱藏（`showLegacyUntil`）

- **做法**：疾病頁等內容頁頁首治理列一句「本頁取代舊網站 N 個頁面」；按需層展開每筆舊標題、舊網址、狀態與新增的治理要求；專業層連到 `/legacy/?u=`；超過 `showLegacyUntil` 自動隱藏，不需人工。
- **為何需要**：讓同事與民眾看見「舊內容沒有不見，而且現在有了權責與審閱日」；同時避免這些揭露永遠掛在頁面上。
- **對應規劃章節**：附錄 G（三層露出）；§7.4 第 3 點。
- **原型位置**：`src/templates/public/_partials.mjs`（`legacyDisclosure`）、`src/templates/public/disease.mjs`；ARCHITECTURE §13.3。
- **正式上線還缺什麼**：`showLegacyUntil` 的正式日期（建議上線日 + 12 個月）；七語文案；使用者是否真的看得懂。

### 26. 版本族穩定網址（302）與失效版文件的舊網址（301）

- **做法**：每個文件版本族有穩定網址 `/documents/{family}/`，永遠 302 到現行版；失效版的舊網址 301 到現行版（原頁保留存取、`noindex`、頁首紅色警示）。
- **為何需要**：公文、衛教單張與外部機關引用的是「那份文件」，不是「第十五版」；版本更新後，引用不該壞，也不該停在舊版。
- **對應規劃章節**：§5.1 文件庫（版本鏈）；§7.4 第 3 點；§3.2 C2（版本寫在檔名）。規劃沒有寫穩定網址這個概念。
- **原型位置**：`v1/redirects.json` 的 `kind: family-latest`、`superseded`；[governance-model.md](governance-model.md) 規則 2。
- **正式上線還缺什麼**：歷史版本回補（現行官網的舊 PDF 與其版次）；公文引用格式規範。

## F. 工程慣例

### 27. 時間相關狀態靠每日重建；用 `BUILD_TODAY` 模擬時間

- **做法**：逾期、截止、失效、白名單資格等「隨時間改變的狀態」全部在建置時算；每日排程重建讓狀態每日更新；`BUILD_TODAY=2027-08-01 npm run build` 可模擬時間前進，檢查「若沒人處理，三個月後長什麼樣」。
- **為何需要**：靜態網站沒有執行期，必須有人推動時鐘；模擬時間讓治理規則可被測試與展示。
- **對應規劃章節**：§7.4 第 2 點（逾期自動退出白名單）；附錄 B。規劃未說明「誰在什麼時候重算」。
- **原型位置**：`.github/workflows/pages.yml`、[deploy.md](deploy.md) 環境變數、[architecture-decisions.md](architecture-decisions.md) 第 5 項。
- **正式上線還缺什麼**：若正式 CMS 為動態，改為查詢時計算或事件驅動；排程失敗告警與值班。

### 28. 資料與內容一致性的硬閘門：Schema＋參照＋測試＋評估集＋連結

- **做法**：CI 任一項失敗即不部署——JSON Schema 與跨檔參照（`owner`、`basedOn`、`supersedes`、移轉清單 `target` 必須存在）、治理規則測試、評估集版本題 100%、站內連結檢查 `[links] error 0`。
- **為何需要**：把「缺欄位不得發布」從公文變成機器強制。
- **對應規劃章節**：§7.1–§7.5 規範了欄位與指標，**沒有定義發布閘門由哪些檢查構成**。
- **原型位置**：`scripts/lib/validate.mjs`、`tests/`、`.github/workflows/pages.yml`、[deploy.md](deploy.md)「發布前的閘門」。
- **正式上線還缺什麼**：與正式 CMS 工作流（上架→預處理→複核→發布）整合；閘門例外的核准流程（緊急修正）。

## G. 規模化與多語（第六輪）

### 29. 推導移轉清單：99 種疾病共用一份模板，人工只寫例外

- **做法**：舊站每個疾病頁的子頁結構相同，所以把標準子頁樹寫成一份模板（`_disease-template.json`，20 項，每項有 `mapTo` 描述「新站哪裡有對應就算移轉」）；治理引擎對傳染病主檔**每一種疾病**推導一份移轉清單：有疾病頁且命中 ⇒ 已併入／已移轉，沒命中 ⇒ 待移轉，沒有疾病頁 ⇒ 整份 `no-page`。人工清單（結核病、登革熱、流感、麻疹、腸病毒）只寫模板沒有的疾病特有頁，同 `key` 覆蓋推導結果。待辦每份清單只開一則，優先度依法定類別（第一、二類高、第三類中、第四與五類低）。清單可從 `/v1/migration/{slug}.json` 下載當人工清單的起點。
- **為何需要**：手寫會讓「全站移轉」永遠做不完——99 種疾病乘以約 40 筆近 4,000 筆，且大半重複；逐筆開待辦又會一次灌進上千則，沒人處理。推導讓「進度」立刻有全貌（72 份清單、1,400 多項、56 份 `no-page`），人力只花在真正有判斷的例外。
- **對應規劃章節**：§7.4 第 4 點（上線前盤點）、§8.2（舊站轉址與封存）；規劃沒有寫「如何在 99 種疾病規模下維持可管理」。補充於本文第 21 項（移轉清單）。
- **原型位置**：`content/migration/_disease-template.json`、`schemas/migration-template.json`、`content/migration/{tuberculosis,dengue,influenza,measles,enterovirus}.json`、`/admin/migration/`、`v1/migration/`；[governance-model.md](governance-model.md) 規則 17；[migration-playbook.md](migration-playbook.md) 第 10 節；[guide-staff.md](guide-staff.md) 第 15 節；ARCHITECTURE §14.1。
- **正式上線還缺什麼**：舊站 ID 對照（推導清單的舊網址目前全是 `{id}` 佔位，需資訊室匯出 ID 與標題對照後批次補）；模板需對照舊站真實結構核對一次（目前依規劃 §1.2 與既有認識重建）；非疾病欄目（新聞稿、出版品、影音、宣導、法規）的模板；`no-page` 疾病的處理決策（建頁或整頁移除）；推導「命中」只表示新站有關聯內容，不表示涵蓋度，仍需 Steward 逐筆確認。

### 30. 內容來源語言 `sourceLang`：來源可以是英文，中文是必備譯文

- **做法**：共同欄位新增選填 `sourceLang`（七語之一，預設 `zh-TW`）。來源語言的 `languages[sourceLang].status` 為 `source`，頂層欄位即為該語言文字；其他語言放 `i18n.{lang}`，**包含 `i18n['zh-TW']`**。`sourceLang` 不是中文時，中文譯文必填且狀態只能是 `reviewed` 或 `machine`（建置失敗保證：中文官網不能沒有中文）。`sourceHash`、譯文過期、頁首「本頁以英文為準，中文為譯文」、搜尋與答案索引語言，全部依 `sourceLang`。
- **為何需要**：規劃把所有內容預設為中文正本、其他語言為翻譯。但舊站的國際合作區塊只有英文版（對象是國外同仁與組織）；若硬把英文改成「譯文」，正本就變成事後補的中文，與事實相反，治理（誰是正本、誰審閱、哪邊過期）也會對不上。
- **對應規劃章節**：規劃的多語言策略段落（以中文為正本、其他語言為翻譯）；其中未涵蓋「英文為來源」的內容，建議在下一版補「來源語言」的概念。
- **原型位置**：`schemas/_common.json`（`sourceLang`）、`L()` 與 `langAvailable`（`src/templates/public/_partials.mjs`）、`tests/sourcelang.test.mjs`、國際合作區塊內容（`topic.international-cooperation`、`page.international-*`、英文新聞）；[governance-model.md](governance-model.md) 規則 18；ARCHITECTURE §14.2。
- **正式上線還缺什麼**：英文來源內容的審閱人與審閱流程（誰有資格當正本審閱者）；中文譯文的審核責任與期限；若未來有以日文、越南文等為來源的內容，需要各語言的審閱人名單；CMS 欄位設計（來源語言與譯文的編輯介面）。

### 31. 國際合作區塊：英文為來源的雙語專區

- **做法**：把舊英文站（`/En`）的 International Cooperation 變成新站的一組內容：入口專區、IHR 國家聯絡窗口、多邊與雙邊合作（含夥伴國表格與地圖）、國際訓練與申請、全球衛生安全、英文出版品、英文新聞與申請服務頁。全部 `sourceLang: 'en'`，附 zh-TW `reviewed` 譯文；`/international/` 入口以英文為準，頁首標示權威版本；主選單不增項，放在研究與媒體入口、頁尾，英文版主選單另列。對應的舊英文站頁面另有移轉清單（`scope.kind: 'category'`），全部 `verified: false`。
- **為何需要**：國際合作是機關對外的正式門面（IHR 窗口、WHO、雙邊 MOU），對象是外國衛生機關；舊站只放英文、沒有權責與審閱日，窗口資訊過期卻沒人知道。納入治理後，聯絡窗口與合作狀態有 owner、審閱日、逾期自動警示。
- **對應規劃章節**：§1.8 子網站整合與英文站；規劃未處理「英文為正本」的內容，國際合作區塊是第一個這樣的案例。
- **原型位置**：`content/topics/international-cooperation.json`、`content/pages/international-*.json`、`content/news/*international*`、`content/services/international-training-application.json`、`content/migration/international-cooperation.json`、`/international/`；ARCHITECTURE §14.3–§14.4。
- **正式上線還缺什麼**：IHR 窗口的實際電話、信箱與 24 小時值班資訊（原型為示意）；雙邊合作清單的法律與外交審查（簽署年、狀態需外交單位確認後才能公開）；與外交部、WHO 窗口的共同審閱流程；英文新聞稿的發布授權；其他語言（如日文）是否需要。
