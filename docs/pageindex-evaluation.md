# PageIndex 評估：對新架構有沒有幫助？

> 給誰看：Yulun、AI推動辦公室（OASIS）、資訊室，以及想知道「為什麼不直接用某個開源 RAG 套件」的同仁。
>
> 一句話：**PageIndex 解決的是「一份幾百頁的長文件，怎麼讓模型翻到對的那一節」；本站的問題是「一千多個短項目，怎麼在瀏覽器裡 5 毫秒內給有出處的答案」。兩件事不同，所以不用它當檢索引擎；但它「先建章節樹、再讓模型選節去讀」的做法值得借到專業版 LLM 模式的第二階段，而且本站的文件 JSON 已經有這棵樹，不需要裝套件。**
>
> 第五十九輪（2026-10-19）。只有文件與一次實測，沒有改程式。起因是 Yulun 問：「有一個 pageindex 的技術，不知對新的架構有沒有幫助？」（https://github.com/VectifyAI/PageIndex ）

## 1. PageIndex 在做什麼（讀原始碼後的整理）

PageIndex（Vectify AI，MIT 授權，2025 年 9 月發表）自稱「不用向量、靠推理的 RAG」。它分兩步：

1. **建樹（index）**：把一份 PDF 變成一棵「章／節／頁碼範圍」的樹，每個節點有標題、起訖頁、（可選）一段模型寫的摘要。
   - **Flash 模式**（2026 年 8 月起的預設）：用版面統計（字體大小、位置、編號型態）抽標題，這一步**不用模型**；之後才用模型為每個節點寫摘要、把太細或太粗的節點合併或拆開。
   - **Classic 模式**：整份文字分批送模型，請模型產生目錄並對回頁碼。
   - 若 PDF 本身有書籤（embedded bookmarks），優先拿書籤當骨架。
2. **查詢（retrieve）**：**沒有固定演算法**。它把三個工具交給一個模型代理（agent）：`browse_documents`（列出有哪些文件、名稱與描述）、`get_document_structure`（拿整棵樹含摘要）、`get_page_content`（讀指定頁的原文），再用一段指示叫模型「先看樹找到相關的節，再讀那幾頁，只引用讀到的內容，引用到頁」。模型自己決定看哪幾節、讀幾頁、要不要再翻。

所以它的「準」來自兩件事：長文件的章節結構被保留（不像向量 RAG 把文件切成無上下文的小塊），以及模型願意多翻幾次。代價也來自同一處：每一題都是一段多回合的模型對話。

| | 本地版（開源） | 雲端版 |
| --- | --- | --- |
| 處理 | 有文字層的 PDF；掃描檔不行 | 掃描檔、圖多的文件、OCR、看圖 |
| 建樹 | 自己的機器；摘要與修樹要模型金鑰 | 廠商主機 |
| 儲存 | 本機目錄 | 廠商雲端 |
| 引用 | 頁級 | 區塊級 |
| 跨文件 | 只有「列文件名稱與描述」讓模型挑 | 「PageIndex File System」：整個文件庫再建一層樹 |

它的基準測試（財報問答 FinanceBench、長文件問答 MMLongBench）都是「幾十到上千頁的專業文件、一題的答案在某一節的內文裡」這種題型。

## 3. 實測：不用模型的 Flash 建樹，拿真實疾管署 PDF 跑

### 3.1 怎麼跑

開發環境沒有模型金鑰，也連不到疾管署網站，所以只能測「不用模型」的那一半：`page_index_flash(pdf, summary=False, optimize=False)`。這正是它的標題偵測能力本身，而這一步的品質決定後面模型有沒有一棵正確的樹可以翻。

測試檔是本專案已有的 10 份真實 PDF：第四十六輪 Yulun 提供的 9 份《疫情報導》文章（2013 與 2026 年版，2–17 頁）與 repo 內的 `teb-42-19-1.pdf`。沒有長指引的 PDF 原檔（第十九輪的登革熱指引只拿到抽好的文字），這是本次實測的限制。

建樹本身很快（每份 0.2–2 秒，不用模型），但在這批中文公文與期刊版面上，**10 份裡沒有一份的樹可以直接拿來用**。原因看得出來：它的標題偵測是為英文論文與財報的版面統計（字級跳動、粗體、數字編號）調的；疫情報導的「前言／材料與方法／結果／討論」與內文同字級，而內文的「一、」「（一）」「1.」條列反而長得像標題。這和第十九輪的經驗一致：中文公文的結構要靠「第 N 章／第 N 節／附件 N／一、（一）」這些**可枚舉的編號規則**切，不是靠版面統計。

PageIndex 的完整流程會接著讓模型「修樹」（合併、拆開、重寫標題），可能救回一部分；但那一步每個節點都要呼叫模型，而且修出來的樹仍是「模型認為的結構」，沒有人校對。本站的做法是工具切、權責單位校對、`reviewStatus` 記錄，這條治理鏈比較適合官方文件。

### 3.3 和本站 PDF 匯入工具的差別

| | 本站 `scripts/lib/pdf-text.mjs`（docs/pdf-ingest.md） | PageIndex Flash |
| --- | --- | --- |
| 切章節 | 「第 N 章／第 N 節／附件 N」編號規則；一章分兩病時 key 帶病名 | 版面統計；書籤優先 |
| 頁碼 | 每頁插 `〔p.N〕`，網頁有 `#page-N` 錨點，引用帶印刷頁碼與 PDF 頁偏移 | 節點有起訖頁 |
| 表格 | 整頁表格標示「請看 PDF 原頁」，不讓錯位的數字進索引 | 無特別處理，頁面原文照給模型 |
| 表單、地圖附件 | 只留標題，`index: false` | 無 |
| 跨頁句子 | 接回上一頁那段 | 無（讀頁時由模型自己接） |
| 校對 | 權責單位校對後 `reviewStatus: reviewed`；未校對者不進白名單、專業版降序、產生待辦 | 無 |
| 紅字修訂 | 欄位已留（`changes[]`），待工具補 | 無 |

兩者都沒做 OCR（PageIndex 本地版也只收有文字層的 PDF）。本站工具缺的是「第 N 章」以外的編號型態（例如純「壹、貳」或英文 1.1／1.2）；要擴充時，加規則比換成版面統計划算，因為規則可以在報告裡列出「哪一頁沒切到」讓人看。

## 4. 哪裡可以借、哪裡不要用

### 4.1 不要：當作智慧問答的檢索引擎

理由在第 2 節的表：本站的速度、無伺服器、可解釋、拒答、治理欄位全在「檢索是建置產物、瀏覽器本機算」這個前提上（決策紀錄 §17、§25）。PageIndex 把檢索變成模型對話，和「民眾版不經模型」的原則（docs/ask-search-llm.md §0）直接衝突。

### 4.2 不要：取代 PDF 匯入工具

第 3 節的實測。另外，它的輸出是一棵樹加頁碼，沒有本站文件 JSON 需要的治理欄位；就算樹是對的，還是得再寫一層轉換與校對流程。

### 4.3 可以借：「樹＋讓模型選節」當作專業版 LLM 模式的第二種取片段方式

docs/ask-search-llm.md §7 的正式站架構是：BM25 先取前 8 塊片段 → 給模型改寫答案 → `groundingGuard` 把沒出處的句子刪掉。對短頁面這樣夠；對 114 頁的指引，有兩種問題 BM25 的「前 8 塊」會答得零碎：

- **要讀整節才答得完整**：「群聚疫情的防治措施有哪些」答案是第五章第二節整節，不是 8 個片段。
- **跨節綜合**：「登革熱和屈公病的群聚定義差在哪」要同時看兩節。

PageIndex 的做法正好補這裡：給模型一棵「章／節／頁碼」樹，讓它挑 1–3 節，把那幾節整段讀進去再作答。本站**已經有這棵樹**：`content/documents/*.json` 的 `sections[]` 帶章節 key（`ch5-dengue-s2`）、標題與 `pages`；答案單元也帶 `pdfPage`。所以要做的不是裝套件，而是在 `retrieve` 之後多一個步驟：

```
問句 → 既有流程（遮個資、拒答、實體、意圖）
     → BM25 命中的前幾塊若多數落在同一份長文件（sections 數 ≥ 12）
       → 把該文件的章節樹（標題＋頁碼範圍，約 1–2 KB）給模型，請它選 1–3 節
       → 把選到的節整段（而不是 8 小塊）放進 <sources>
     → 既有的改寫、groundingGuard、句級出處
```

這條路的前提與限制：

- **只在有後端代理的正式站專業版**出現（§7 第二階段之後），GitHub Pages 原型與民眾版不變。
- 每題多一次模型呼叫（選節）；整節內容比 8 塊長，要設上限（例如一節最多 3,000 字，超過就退回片段）。
- 要在挑戰集加「長文件整節題」與「跨節綜合題」各十題，用 dev／holdout 比較有無這一步的差異，否則很容易高估。
- 出處仍然到頁：`groundingGuard` 的數字比對、引用比對規則不變。

### 4.4 可以借：後台「問這份 PDF」的校對輔助

權責單位校對 PDF 機讀版時（docs/pdf-ingest.md §4），常要在 PDF 裡找「這段在第幾頁」「表格原文是什麼」。一個「對這一份文件問問題、答案附頁碼」的後台小工具就是 PageIndex 的典型用途，而且文件是單一、長、有樹的。這個工具一樣可以用本站的章節樹加模型做，不必裝套件；排程上在正式站 LLM 代理之後，不是現在。

### 4.5 真的要用套件本身時的條件

- 只用**本地版**；模型呼叫一律走署內代理（它用 LiteLLM，可以指到任何相容端點）。
- 不用雲端版、不上傳文件到廠商。
- 建樹的結果要經權責單位看過才當索引，與 PDF 機讀版同樣的 `reviewStatus` 規則。
- 它的程式碼約 1.2 萬行 Python，相依套件含 LiteLLM、OpenAI Agents SDK、MCP；本站目前沒有 Python 執行環境，引進等於多一條技術線。

## 5. 風險與代價（公部門的角度）

| 風險 | 說明 |
| --- | --- |
| 答案品質變成「模型翻得好不好」 | 它沒有硬門檻；模型翻錯節就引用錯節，或在沒讀到時自己補。本站 `groundingGuard` 的規則要保留在它外面。 |
| 延遲 | 每題數秒。對後台校對工具可以接受，對民眾問答不行。 |
| 版本與供應商相依 | 樹的摘要與選節品質隨模型改變；換模型要重建樹、重跑評估。 |
| 資料外送 | 本地版仍把頁面原文送給模型供應商；指引是公開文件所以可接受，但內部文件、未公開草稿不行。雲端版整份文件外送，不採用。 |
| 提示注入 | 它在建樹時有一段「把文件當資料、遮掉 override 字樣」的防護（`page_index_classic.py` 開頭），但只擋英文關鍵字。官方文件來源可控，風險低；若日後讓它讀外部文件要另評。 |
| 維運 | 多一套 Python 服務與相依；本站現在整條鏈是 Node。 |

## 6. 怎麼決定要不要做 4.3

1. 正式站 LLM 代理上線後，從智慧問答查詢紀錄（docs/ask-log.md，已遮個資）抽出命中文件庫的問句，人工分三類：片段就答得完、要整節、要跨節。
2. 若後兩類合計明顯（例如超過文件庫命中的三成），把它們寫進挑戰集，做 4.3，用 holdout 比較。
3. 若不明顯，維持現狀；長文件的完整閱讀交給文件頁的章節導覽（docs/pdf-ingest.md §8）。

## 8. 名詞

| 詞 | 意思 |
| --- | --- |
| 樹索引（tree index） | 把文件整理成「章 → 節 → 頁碼範圍」的階層，取代「切成小塊各算向量」 |
| 推理式檢索（reasoning-based retrieval） | 不算相似度，讓模型看目錄自己決定讀哪裡 |
| Flash | PageIndex 用版面統計、不用模型抽標題的建樹模式 |
| 書籤（bookmarks） | PDF 檔內建的目錄；有的話 PageIndex 優先用 |
| 頁級／區塊級引用 | 引用到「第幾頁」或「第幾頁的哪一段」 |
| 向量 RAG | 把文件切塊算向量、問句算向量、取最相似的塊給模型；docs/ask-search-llm.md §2、§5 |
