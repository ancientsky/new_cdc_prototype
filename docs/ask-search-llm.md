# 「智慧問答」與「全文搜尋」的技術比較，以及加上 LLM API 要怎麼搭配（還要不要做 RAG？）

> 第三十二輪（2026-10-10）。起因是 Yulun 問：「智慧問答和全文搜尋使用的技術請整理比較；假如加上 LLM 的 API，要怎麼搭配目前使用的技術？還需要做 RAG 嗎？」
> 這份文件寫給同事看，特別是資訊室；程式位置都有列出來，想核對的人可以直接翻。契約層的補充見 ARCHITECTURE §38，決策理由見 [architecture-decisions.md §25](architecture-decisions.md)。
> 本輪**只做設計與文件，沒有改程式**。

## 0. 三句話結論

1. **兩套東西回答的問題不一樣，技術也不一樣。** 智慧問答（`/ask/`）是「把站內的官方句子挑出來回答一個問題」，用的是自己寫的中文 bigram＋詞典＋BM25 檢索引擎，在瀏覽器裡跑；全文搜尋（`/search/`）是「列出站上哪些頁面提到這個詞」，用 Pagefind 在建置時產生的靜態倒排索引，也在瀏覽器裡跑。兩者都不需要伺服器、不需要模型、不需要金鑰。
2. **本站其實已經有一條 RAG。** 智慧問答的「LLM 模式」（同事示範用 BYOK，`src/client/answer/llm.js`）就是標準的 RAG：先用抽取式引擎檢索（Retrieval），再把檢索到的片段塞進提示詞（Augmented），要模型只依片段作答並逐句標出處（Generation），最後用程式做後檢（grounding guard），有一句沒依據就刪，全刪就退回抽取式。所以問題不是「要不要做 RAG」，而是**「要不要把 RAG 的 R 從 BM25 升級成向量（embedding）檢索」**，以及**「正式站的 G 要放在哪裡、誰付錢、金鑰在哪」**。
3. **建議：** 正式站若要接 LLM，(a) 保留現在的順序「遮蔽個資 → 拒答規則 → 檢索 → 相關度門檻 → **才**叫模型 → 後檢 → 退回抽取式」，LLM 永遠只是最後一段的「改寫器」，不是「回答者」；(b) 把呼叫從瀏覽器 BYOK 搬到機關後端代理，金鑰只在伺服器，加快取、限流、稽核；(c) 向量檢索**先不做**，等透明報告的「查無」與零結果查詢顯示 BM25＋詞典真的不夠再加，而且加的方式是「BM25 候選＋向量重排」的混合式，不是整個換掉；(d) `/search/` 不接 LLM。

## 1. 兩套技術的比較表

| | 智慧問答 `/ask/` | 全文搜尋 `/search/` |
| --- | --- | --- |
| 回答什麼 | 「我該怎麼辦？」給一段**官方原句組成**的答案，每句附來源編號；不確定就說「查無」 | 「站上哪些頁面提到 X？」給一份可篩選、可排序的**頁面清單** |
| 索引的單位 | 「答案單元」：FAQ 一題、疾病頁一個區塊、文件一個章節、通函一段……（`content/` 建置時切出；本輪實測民眾版 730 塊、專業版 1,070 塊，各一份 `v1/search-index.json`／`-pro.json`） | 整頁 HTML 的 `<main>`（有 `data-pagefind-body` 的頁才收，約 2,300 頁，七個語言各一份索引） |
| 索引何時建 | 建置時（`scripts/lib/emit-api.mjs` 輸出 JSON）；瀏覽器載入後在記憶體建 BM25（`core.js` `bm25For`） | 建置時（`scripts/lib/pagefind.mjs` 呼叫 Pagefind Node API 產生 `dist/pagefind/` 分片） |
| 誰在跑 | 瀏覽器（同一份 `core.js` 也在 Node 跑評估集與測試） | 瀏覽器 Web Worker（Pagefind 的 WebAssembly） |
| 中文怎麼切 | 字元 bigram（兩字一組）＋第三十一輪的**詞典詞界**（疾病名、別名、詞彙主檔、疫苗名、單位名；`buildLexicon`） | 索引端在相鄰 CJK 字之間補空白、查詢端轉成精確片語（等於子字串比對；ARCHITECTURE 31.4） |
| 排序 | BM25（標題權重 ×2）＋實體加權（問 A 病不拿 B 病）＋意圖對型別加權（問申請 → 服務頁）＋機器轉出降權等（`retrieve`） | Pagefind 相關度，`pageLength` 0.25 壓低長頁；片語結果再用無引號查詢的分數排序 |
| 同義詞 | 有：詞彙主檔別名、deprecated 舊名、跨語言對照（`expandQuery`） | 沒有：字面比對（「登革熱」≠「骨痛熱病」） |
| 理解問句 | 有：個資遮蔽、注入偵測、實體（病／疫苗／國家／年齡）、時間範圍、意圖分類（症狀／疫苗／旅遊／統計／謠言／申請／檢驗／通報……）、拒答規則 | 沒有：查詢就是字串＋篩選條件（型別、對象、單位、年份） |
| 失敗模式 | 寧可**查無**：相關度門檻（`RELEVANCE`，決策紀錄 §17）不夠就拒答，給 1922、索引與「用全文搜尋找」 | 寧可**多列**：零結果才提示清除篩選、「改用智慧查詢」 |
| 結構化資料 | 有：疫情態勢、統計、通報時限表、疫苗時程、旅遊建議、職缺／標案直接讀主檔，不走檢索 | 無 |
| 每次查詢的下載 | 索引整份載入，第一次提問才載（本輪實測 gzip 後民眾版約 195 KB、專業版再加約 325 KB） | 只載命中的分片，實測 180–270 KB gzip（ARCHITECTURE 31.2） |
| 安全承諾 | 每句是白名單內容原文、附出處、有「查無」門檻、有拒答規則、有 AI 暫停開關 | 索引只含已輸出的公開頁，草稿／失效版自然不在；查詢字串不離開瀏覽器 |
| 可解釋性 | 完整：回傳 `intentReasons`、`guards`、`relevance`、`auditId`，評估集 230 題（19 類）在 CI 跑六指標 | Pagefind 分數，不另外解釋；CJK 召回有回歸測試（`tests/round28-search.test.mjs`） |
| 程式位置 | `src/client/answer/core.js`（引擎）、`ui.js`、`render.js`、`llm.js`（LLM 模式）、`judge.js`（判分） | `scripts/lib/pagefind.mjs`（建索引）、`src/client/search.js`、`search-query.js`（介面與查詢改寫） |

兩者共同點：**都是靜態站的一部分**——內容只有一份（`content/`），兩套索引都是 `npm run build` 的產物，和內容治理同一個閘門；都不需要伺服器、資料庫、金鑰或第三方服務；都把使用者的查詢留在瀏覽器裡。這也是為什麼它們能放在 GitHub Pages、機關的 nginx／IIS，不必多維運一個系統。

為什麼兩套並存而不是合一，決策紀錄 §20 已寫過；一句話：一個要「可靠的一個答案」，一個要「完整的一份清單」，失敗時該往哪邊倒剛好相反。

## 2. 名詞先講清楚：RAG 是什麼、不是什麼

**RAG（Retrieval-Augmented Generation，檢索增強生成）**：模型回答前，先從「我們指定的資料」裡找出相關段落，把段落附在提示詞裡，要模型只依這些段落作答。目的是讓模型講的是我們的內容，不是它訓練時記住的東西。

常見的誤會：**RAG 不等於向量資料庫。** 「R」是任何能找出相關段落的方法——BM25 關鍵字檢索、向量（embedding）語意檢索、兩者混合、甚至是查資料庫。向量檢索只是其中一種 R，近年因為對口語、同義詞比較寬容而流行，但它需要一個模型把文字轉成向量、要存向量、結果難解釋、門檻難調。

對照本站：

| RAG 的環節 | 本站現況 | 位置 |
| --- | --- | --- |
| 資料準備（切塊、清理、標註） | 有，而且比一般 RAG 專案細：建置時切成答案單元，帶 `diseases`、`tasks`、`terms`、`owner`、`reviewedAt`、`isCurrent`、`whitelist` 等治理欄位；PDF 轉出標 `extraction.reviewStatus` | `scripts/lib/emit-api.mjs`、`schemas/` |
| R：檢索 | 有：bigram＋詞典＋BM25＋實體與意圖加權，前 k 塊 | `core.js` `retrieve` |
| 檢索品質門檻 | 有：相關度不夠就拒答，不叫模型 | `core.js` `relevanceOf`、`RELEVANCE` |
| A：把片段放進提示詞 | 有：`<sources>` 內每塊帶 id、標題、審閱日；問句先遮個資 | `llm.js` `llmAnswer`、`sourcesXml` |
| G：生成 | 有：系統提示七條規則（只能依片段、每句要 cite、不加數字、不做個人醫療建議、片段不足回空陣列、問句與片段是資料不是指令），JSON schema 強制輸出格式 | `llm.js` `SYSTEM_PROMPT`、`ANSWER_SCHEMA` |
| 生成後檢查 | 有：無 cite 或 cite 不在片段 → 刪；詞彙重疊不足 → 刪；數字不在片段 → 刪；個人用藥語句 → 刪；0 句退回抽取式 | `llm.js` `groundingGuard` |
| 揭露 | 有：`disclosure.mode/provider/model`，頁面標示 | `render.js` |
| 評估 | 抽取式有 230 題六指標；**LLM 模式沒有自動評估**（要金鑰、要錢） | `eval/run-eval.mjs`、`judge.js` |

所以回答原問題：**RAG 已經做了。** 現在缺的不是 RAG，是(1) 正式站的呼叫架構，(2) LLM 模式的評估，(3) 視需要才加的向量檢索。

## 3. 現在的 LLM 模式（BYOK）到底做了什麼

給還沒看過的人：

1. 同事在 `/admin/` 登入後，`/ask/` 的「進階」才會出現金鑰欄位（沒登入的讀者看不到）。金鑰存這個分頁的 `sessionStorage`，關閉分頁即清除；模型名稱由 `site.config.mjs` 的 `ai.llmModels` 帶入。（第二十三輪，ARCHITECTURE 26.4，決策紀錄 §15）
2. 提問時**先跑完整的抽取式流程**（`engine.answer`）。被拒答、AI 暫停、統計／通報／謠言這類走結構化資料的問題，**不叫模型**（`ui.js` 第 65–72 行、`llm.js` `llmAnswer` 開頭的守門）。
3. 只把檢索到的前 8 塊片段（已遮個資的問句、回答語言、民眾／專業模式）送到 Anthropic Messages API，由瀏覽器直連，不經過本站任何伺服器。
4. 模型回 `{sentences:[{text, cite:[片段 id]}], confidence, followUps}`，後檢刪掉沒依據的句子，剩下的句子沿用抽取式的來源卡（含治理欄位），前面加上「AI 生成・供應商／模型」揭露。
5. 非中文語言且沒有該語言審核片段時，改走**翻譯模式**：把抽取式的中文句子交給模型翻譯，詞彙主檔 `locked` 的詞先換成佔位符、譯完換回該語言的官方譯名，數字不符的句子整句不顯示（`llmTranslate`、`lockTerms`）。

它的定位是「展示生成式答案也要逐句引用、要後檢」的樣品，**不是**正式站的架構（決策紀錄 §4「何時重考慮」、§15）。

## 4. 加上 LLM API：可以接在哪幾個位置

把現在的管線畫出來，LLM 能插的位置有五個（Ⓐ–Ⓔ）。原則：**越靠近使用者看到的答案，風險越高、越要後檢；越靠近建置時（離線），風險越低、也越便宜。**

```
使用者問句
   │
   ├─ 個資遮蔽 ─ 注入偵測 ─ 實體／時間 ─ 意圖 ─ 拒答規則      ← 規則，不叫模型
   │                                                       Ⓐ 查詢改寫（口語→站內用語、補同義詞）
   ├─ 同義詞展開（詞彙主檔）
   ├─ 檢索 BM25＋詞典＋加權 → 前 k 塊                        Ⓑ 混合檢索／重排（embedding）
   ├─ 相關度門檻 → 不夠就「查無」，到此為止
   ├─ 結構化資料（態勢、統計、時程…）直接回答，到此為止
   ├─ 組句（抽取式）→ 預設答案                              Ⓒ 依片段改寫成通順答案（現有 LLM 模式）
   │                                                       Ⓓ 翻譯（現有翻譯模式）
   └─ 來源卡、揭露、相關頁面、「用全文搜尋找」
                                                           Ⓔ 離線：建置時用模型補同義詞、產 FAQ 草稿、
                                                              評估集判分、PDF 校對建議（不碰線上答案）
/search/ Pagefind ─────────────────────────────────────── 不接 LLM（見 §6）
```

### Ⓐ 查詢改寫（建議做，低風險）

**問題**：BM25 認字不認意。「打針會不會發燒」「出國要不要先打針」這類口語，詞典沒有就撈不到。現在靠 `PARAPHRASE`／`CROSS_LANG` 寫死的規則與詞彙主檔補。
**做法**：把問句（遮完個資後）給模型，要它回「這個問題用疾管署站內用語會怎麼說」＋「可能相關的疾病／疫苗名」，輸出 JSON，只拿來**加進檢索詞**，不拿來回答。模型答錯最多是多撈到幾塊不相關的片段，仍會被相關度門檻與實體加權篩掉。
**為什麼便宜**：輸入幾十字、輸出幾十字；而且可以**離線預先做**：把透明報告裡的「查無」與零結果查詢批次丟給模型，產生「口語 → 站內用語」對照表，人審後寫進詞彙主檔的 `aliases` 或 `PARAPHRASE`，線上不用叫模型。這條最符合本站「同事在主檔加一筆就好」的習慣。
**不做的**：不讓模型改寫後直接取代原問句（會讓使用者看不懂為什麼撈到這些）。改寫只「加詞」，原詞權重維持 1、加的詞 0.7（`queryWeights` 現有邏輯）。

### Ⓑ 混合檢索／重排（先不做，等指標）

見 §5。

### Ⓒ 依片段改寫答案（已有；正式站改走代理）

現有 LLM 模式。它解決的是抽取式的兩個弱點：句子是原文拼接、讀起來生硬；跨文件整合弱（一句來自 FAQ、一句來自疾病頁，沒有過場）。要保留的原則：

- **順序不能動**：拒答、查無、結構化回答都在模型之前決定；模型拿不到被拒答的問題，也不能把「查無」變成「有答案」。這是「LLM 不是回答者」的結構性保證，不靠提示詞祈禱。
- **後檢不能拿掉**：`groundingGuard` 四條規則（cite、重疊、數字、醫療建議語）是公部門不出事的底線。模型再好也會偶爾改數字。
- **退回抽取式**：任何錯誤（網路、金鑰、429、拒絕回應、JSON 壞、全被刪）都回到抽取式答案，使用者永遠有答案。
- **揭露**：模式、供應商、模型名稱、生成時間要顯示；現在已有。

### Ⓓ 翻譯（已有；同樣改走代理）

非中文六語的內容量遠少於中文，翻譯模式是「有中文答案就至少有機器翻譯」的保底。鎖定詞彙、數字守門、標 `translationNote: 'machine'` 都已做。正式站可考慮改成**離線**：建置時對白名單內容批次翻譯成草稿，走多語複核流程（後台已有多語初稿功能），線上就不必即時翻。

### Ⓔ 離線用途（建議優先做，零線上風險）

模型最划算、最安全的用法是不出現在使用者面前：

- **評估集判分**：現在 `judge.js` 是規則判分（mustInclude 等）；可加一個「LLM 當裁判」的選項，對抽取式與 LLM 模式的答案評「有沒有回答到問題」「有沒有超出片段」。這同時解決「LLM 模式沒有自動評估」的缺口。裁判結果是報告，不是線上行為。
- **同義詞／口語對照建議**（Ⓐ 的離線版）。
- **FAQ 草稿**：從通函、指引產 Q&A 草稿進後台待審，承辦人改完才發布。內容走既有車道與複核。
- **PDF 轉出校對建議**：第十九輪的 PDF 匯入把機器轉出標 `machine`；模型可以指出斷句錯誤、表格殘留，給校對者參考。
- **評估「查無」清單**：把 no-match 問題分群，告訴內容單位該補哪些內容。

這些都在建置機或同事的電腦跑，金鑰在 CI secret 或同事手上，不在瀏覽器。

## 5. 要不要加向量（embedding）檢索？

### 5.1 現在的 R 哪裡會不夠

BM25＋bigram＋詞典已處理：錯別字寬容（bigram）、同義詞與舊名（詞彙主檔）、「字藏在別的詞裡」（第三十一輪詞界）、問 A 病不拿 B 病（實體加權）、意圖對型別（申請 → 服務頁）。它不會處理的：

1. **詞典沒有的口語**：「打針」「拉肚子」「發燒要不要去醫院」——站內寫的是「接種」「腹瀉」「就醫」。目前靠 `PARAPHRASE` 規則一條一條補。
2. **跨語言問中文內容**：英文問句找中文片段，目前靠 `CROSS_LANG` 少量對照。
3. **長問句的重點**：「我下個月要去泰國，小孩兩歲，要注意什麼」——實體（泰國、年齡）抓得到，但「要注意什麼」撈不到具體片段。

向量檢索對 1 與 2 有幫助；對 3 幫助有限（重點是結構化資料，不是檢索）。

### 5.2 加向量檢索的代價（在這個站的架構下）

- **查詢端要有模型**：使用者的問句要即時轉成向量，這一步**不能在靜態站的瀏覽器裡免費做**——要嘛呼叫 embedding API（需要金鑰 → 需要後端代理；民眾端不能 BYOK），要嘛在瀏覽器載入一個小型 embedding 模型（多語中文可用的模型通常數十到數百 MB，首次載入成本遠超目前整站 JS 預算 120 KB，離線與低頻寬使用者會放棄）。**換句話說，向量檢索讓「不需要伺服器」這個特性消失。**
- **索引端**：約 730（民眾）／1,070（專業）塊片段在建置時算向量很便宜，可存成靜態 JSON（以 1,000 塊 × 1024 維估：float16 約 2 MB，量化成 int8 約 1 MB，可分語言分片），這部分與目前「索引是建置產物」的做法相容。
- **可解釋性變差**：BM25 可以說「因為片段有這三個詞」；向量只能說「相似度 0.71」。第十七節的「查無」門檻要改用相似度分數重調，目前「不誤擋 203 題」的方法要重做。
- **詞界問題不會自動消失**：向量模型對「性病」「急性病毒性 A 型肝炎」也可能算出高相似度（都是傳染病），第三十一輪的詞典邊界仍要留在混合式裡當硬規則。
- **多一個模型版本相依**：換 embedding 模型要全部重算、重調門檻；評估集要重跑。

### 5.3 建議：先量，再決定；要做就做「混合＋重排」

1. **先量**：透明報告已有拒答率，把 `no-match` 的問句（已遮個資）與 `/search/` 零結果查詞集中看三個月。分成「站內真的沒有」（補內容）、「有但用詞不同」（補詞彙主檔／Ⓐ 離線對照）、「兩者都做了還是撈不到」。只有第三類多到影響答題率，才值得上向量。
2. **要做的話是混合式**：BM25＋詞典先取前 20–30 塊候選（保留實體、意圖、詞界這些硬規則），再用向量相似度**重排**並補入 BM25 完全撈不到但相似度高的幾塊；相關度門檻改成「BM25 涵蓋率 或 向量相似度 任一達標」。這樣既有的可解釋性與拒答規則都保留，向量只負責補口語缺口。
3. **部署前提**：查詢端向量化需要後端代理（與 §7 的 LLM 代理同一個），所以向量檢索**只會出現在有後端的正式站**；GitHub Pages 原型與無後端的部署維持純 BM25。程式上以「`retrieve` 的候選重排 hook」實作，沒有代理時 hook 為空。
4. **評估**：加一個 `paraphrase`（口語改寫）類別到評估集，先用它量 BM25＋Ⓐ 離線對照能解決多少，剩下的才是向量的真正貢獻。沒有這個對照，很容易高估向量的效果。

## 6. `/search/` 全文搜尋要不要接 LLM？不要

- 全文搜尋的價值是**完整與可控**：記者、研究者、衛生局同仁要的是「2026 年所有提到登革熱的新聞稿」，少一筆就是錯；模型的摘要或改寫只會模糊這個保證。
- 它的弱點（不懂同義詞、泰文沒斷詞）用離線手段補更划算：Ⓐ 的離線同義詞對照同樣可以在 `search-query.js` 查詢時擴成多個片語取聯集（目前多片語是取交集，要分開處理）；泰文用 `Intl.Segmenter('th')` 在索引端斷詞（決策紀錄 §20 已列）。
- 若使用者在 `/search/` 其實是在問問題，現有「改用智慧查詢」的導流已經處理。

## 7. 正式站要接 LLM 時的架構

### 7.1 三種部署模式

| 模式 | 誰能用 | 金鑰在哪 | 適用 |
| --- | --- | --- | --- |
| **純抽取式**（預設） | 所有人 | 沒有金鑰 | GitHub Pages 原型、沒有後端的部署、AI 暫停時 |
| **後端代理** | 所有人（或先限專業版） | 機關伺服器環境變數／金鑰保管 | 正式站 |
| **BYOK** | 登入後台的同事 | 同事瀏覽器分頁 | 原型示範、評估、比較模型 |

三種模式共用同一份 `core.js` 與 `llm.js` 的提示詞、schema、後檢；差別只在 `callClaude` 的目的地（Anthropic API 直連 vs. 機關代理）與金鑰來源。這與第三十輪寫入閘道的做法一致：**前端與規則不變，只換最底層的連線**。

### 7.2 代理要做的事（給資訊室）

1. **金鑰只在伺服器**，由環境變數或機關金鑰保管服務帶入；前端只知道代理網址（`site.config.mjs` 新增 `ai.proxyEndpoint`，與第三十輪 `forms` 端點同樣可設定）。
2. **只轉送我們定義的請求**：代理收的是 `{question, lang, view, chunkIds}` 這類**結構化**內容，由代理自己從建置產物 `v1/search-index.json` 取片段、組提示詞、呼叫模型；不讓前端自由送提示詞。這樣注入面在伺服器可控，提示詞版本也統一。
3. **快取**：以「問句正規化後的雜湊＋片段 id 集合＋模型版本＋提示詞版本」當鍵；內容重建（`reviewedAt` 變）就自然失效。公衛問題高度重複，快取命中率高，是成本最大的槓桿。
4. **限流與配額**：每 IP／每工作階段每分鐘上限；每日總量上限到了自動退回抽取式（使用者仍有答案），並進 AI 狀態頁。
5. **稽核**：記 `auditId`（引擎已產生）、時間、模型、token 用量、後檢刪了幾句與原因、是否退回；**不記原問句明文**（已遮個資的問句可記雜湊或關鍵字）。這份紀錄餵透明報告與評估。
6. **逾時與退回**：模型回應超過 N 秒（建議 8–10 秒）即放棄，顯示抽取式；前端現在已先顯示抽取式再用 LLM 結果覆蓋，使用者不會空等。
7. **AI 暫停開關**：既有 `aiStatus.paused` 要同時讓代理拒收，不只前端不叫。

### 7.3 公部門健康資訊站的硬性約束（這些不是選項）

- **逐句引用、片段外不說**：後檢保留。
- **沒有來源就拒答**：相關度門檻在模型之前。
- **不做個人診斷與用藥建議**：系統提示第 3 條＋後檢 `ADVICE_RE`。
- **揭露**：頁面標示「AI 生成」、供應商、模型、時間；透明報告有 LLM 模式的答題率、退回率、後檢刪句率。
- **資料駐留與個資**：送到模型的是**遮完個資的問句＋站上公開的官方片段**，不送使用者身分、IP、工作階段。即便如此，問句本身可能含健康狀況（「我發燒三天」），屬敏感資料的邊緣；要向資安與法制確認：(1) 供應商的資料處理地區與保留政策（API 預設不以客戶資料訓練的條款要有書面）；(2) 是否要求境內服務（Anthropic 等供應商的雲端區域選項、政府雲是否有合格的模型服務）；(3) 代理端的日誌保留期限。原型不替機關決定供應商（與電子報寄信服務同一個理由，決策紀錄 §19）。
- **成本**：每題約「系統提示＋8 塊片段（數千 token）＋輸出幾百 token」。實際單價請查供應商當期價目，不在這裡寫死；控制手段依序是快取、`effort: low`（現有）、限制片段數與長度、配額退回。先在 BYOK 模式用評估集跑一輪，記下每題平均 token，再乘以預估流量。
- **可用性**：模型服務中斷不能讓網站沒答案——抽取式永遠在。
- **評估**：LLM 模式要過同一份評估集的六指標（Grounding ≥95% 等），加上 Ⓔ 的 LLM 裁判做第二意見；提示詞或模型換版要重跑。

### 7.4 分階段建議

| 階段 | 做什麼 | 線上風險 | 需要 |
| --- | --- | --- | --- |
| 0（現況） | 抽取式＋同事 BYOK 示範 | 無 | — |
| 1 | Ⓔ 離線：LLM 裁判跑評估集；查無／零結果問句批次產同義詞對照，人審後進詞彙主檔；評估集加 `paraphrase` 類 | 無（不碰線上） | 一把金鑰、CI secret |
| 2 | 後端代理（7.2）、`ai.proxyEndpoint`、快取、限流、稽核；先開專業版或內部試用 | 低（有後檢與退回） | 機關伺服器、資安審查、供應商合約 |
| 3 | 視指標：Ⓐ 線上查詢改寫；Ⓑ 混合檢索重排（需代理） | 中 | 階段 1 的量測結果支持 |

每一階段都能停，停下來網站照常運作。

## 8. 常見問題

**Q：直接把整站內容丟給模型，不要檢索，不是更簡單？**
不行。模型的上下文有上限、每題成本與整站內容量成正比、而且「哪一句來自哪一頁」就沒了，逐句引用做不到。檢索是為了把要看的範圍縮到幾塊並留下出處，不是過渡期的權宜。

**Q：有了 LLM，抽取式可以拿掉嗎？**
不能。它是(1) 沒金鑰／沒後端時的答案，(2) 模型失敗時的退路，(3) 相關度門檻與拒答規則的宿主，(4) 評估集的基準。LLM 模式的輸入就是它的輸出。

**Q：向量資料庫（Pinecone、pgvector 之類）要不要先建？**
不要。約一千塊片段的向量放靜態 JSON 就夠，相似度在代理端算是毫秒級；等語料大到數萬塊再談資料庫。先建資料庫是把「有沒有必要」跳過去。

**Q：模型要不要「記住」上一題（多輪對話）？**
目前每題獨立。多輪會讓檢索失焦（第二題「那疫苗呢」需要上一題的疾病），而且對話歷史會進入提示詞、增加個資風險。若要做，做法是把上一題抽出的**實體**（疾病、國家、年齡）帶進下一題的 `presetDisease` 這類結構化欄位，而不是把對話文字餵給模型。

**Q：不同語言要分別接嗎？**
不用。片段是中文、問句任何語言、答案語言由 `<answer_language>` 指定，現有流程已是如此；翻譯模式負責沒有生成答案時的保底。

## 8.5 資料治理還不完整時：重複與新舊說法不一致（第三十三輪補充）

上面的設計假設「白名單裡的內容彼此一致」。實際上不同組室可能各寫一題類似的 Q&A，舊新聞稿也沒有 `basedOn` 連到正本。第三十三輪補了三道安全網，三條路共用同一份判斷（ARCHITECTURE §39、決策紀錄 §26、同事 SOP 見 guide-staff §37）：

| | 智慧問答 | 全文搜尋 | LLM 模式 |
| --- | --- | --- | --- |
| 兩份內容數字不同（建置時偵測的候選） | 較可信者排前面，答案上方加註「站內兩處說法不同」與兩邊連結 | 兩頁都列（清單的承諾是完整），由頁面本身與待辦處理 | 告訴模型只能用優先那份的數字；後檢刪掉用錯數字的句子；加註照樣顯示 |
| 權責單位已判定（confirmed） | 錯的那句從答案索引移除 | 頁面照列，直到權責單位改好內容 | 拿不到錯句 |
| 超過 12 個月的新聞稿 | 降權（除非問新聞、去年、年份），來源卡標「歷史新聞稿 · 發布日」 | 標「歷史資料」，可勾「只看現行內容」排除 | 片段標 `historical="true"`，規則要求只在問過去時使用並寫出日期 |

重點是**偵測交給程式、判定交給人、未判定時誠實揭露**：程式和模型都不自己決定哪個說法正確。

## 8.6 「2 歲前要打哪些疫苗」：資料都在，為什麼答不出來？LLM 能不能救？（第三十七輪補充）

同事實測（2026-10-11）：智慧問答查無、全文搜尋不完整，但時程主檔明明有每一劑的月齡。

**答不出來的原因不在資料，在「問句理解」**。這類問題要先把「2 歲前」翻成條件「月齡 0–23」，再去時程主檔篩出每一列；引擎有這條結構化路徑，但年齡規則沒列「N 歲前」，把它當成「2 歲那一年」，篩出來的只有三種疫苗。醫事人員檢視又把疫苗問句一律當專業問題，連結構化路徑都沒走，改做全文檢索，就查無了。第三十七輪補了規則（ARCHITECTURE §43）。

**全文搜尋（Pagefind）為什麼不完整**：它找的是「含這些字的頁面」，不會做「月齡 ≤ 23」這種數值篩選；「2 歲前」三個字在時程表裡幾乎不會原樣出現。這不是調參數能補的，是工具的性質不同（§1、§6）。

**如果只是把 bigram 或全文搜尋的結果交給 LLM 摘要，一樣答不出來**，原因有三：

1. **模型只能整理它拿到的片段**。現在的 LLM 模式（§3）拿到的就是引擎檢索或結構化的結果；拿到的是「2 歲那一年」的三句，模型只會把三句改寫得更通順，不會自己補出 B 肝、五合一。後檢（`groundingGuard`）還會刪掉片段裡沒有的句子，這是故意的：寧可少答，不可編造。
2. **查無時根本不會叫模型**（`ui.js` 只在有檢索結果時才呼叫）。
3. **檢索單位是「段落」，問題要的是「表格篩選」**。時程主檔有 42 列，BM25 取前 8 塊片段，就算撈對了也放不下整張表；這種「依條件列出全部」的問題，正確做法是結構化查詢，不是檢索加摘要。

**LLM 真正能幫的位置是「問句 → 結構化條件」**（§4 Ⓐ 的延伸）：

```
問句（遮個資）→ 模型輸出 JSON { minMonths: 0, maxMonths: 23, groups: [], topic: "vaccine-schedule" }
            → 程式驗證 JSON 欄位與範圍 → matchSchedule() 查主檔 → 逐列附來源
```

- 模型**不寫答案**，只負責「聽懂」；答案仍由程式從主檔列出，每句可追溯到主檔的一列，不會出現模型編的劑次或月齡。
- 規則先跑，規則解析不出年齡時才叫模型（大部分問句不花錢）；模型的輸出要通過欄位驗證（月齡 0–1440、上限 ≥ 下限），不合格就回到規則結果。
- 更省的做法是**離線**：每月把透明報告裡「查無」與「有年齡詞但沒解析出年齡」的問句批次給模型，請它歸納新說法（「上幼兒園前」「斷奶前」），人審後補進規則或詞彙主檔，線上不用叫模型。這和 §4 Ⓔ 的建議一致，建議先做這個。

**一句話**：資料完整、問句理解錯時，換更強的摘要模型沒有用；要補的是「把人話轉成查詢條件」這一步，可以靠規則，也可以靠模型，但答案一律由程式從主檔產生。

## 9. 名詞表

| 名詞 | 意思 |
| --- | --- |
| 抽取式（extractive） | 答案的每一句都是原文裡的句子，只做挑選與排列，不生成新句 |
| 生成式（generative） | 模型自己寫句子 |
| BM25 | 關鍵字檢索的標準公式：詞在這塊出現越多、在全站越少見，分數越高；標題加權、長文正規化 |
| bigram | 兩字一組的切法（「登革熱」→「登革」「革熱」）；不需詞庫，但不懂詞界 |
| 詞界（第三十一輪） | 用站上的疾病名、別名、詞彙主檔、疫苗名、單位名判斷「性病」是不是真的出現，還是藏在「急性病毒性A型肝炎」裡 |
| 倒排索引 | 「哪個詞出現在哪些頁」的表；Pagefind 與 BM25 都用 |
| embedding／向量 | 把一段文字變成一串數字，意思相近的數字也相近；用來做語意比對 |
| RAG | 先檢索再生成；R 可以是 BM25、向量或混合 |
| grounding guard（後檢） | 模型回答後用程式檢查每一句有沒有依據，沒有就刪 |
| BYOK | Bring Your Own Key，使用者自己貼金鑰 |
| 代理（proxy） | 機關自己的伺服器，前端打它、它再打模型服務；金鑰只在它那裡 |
| 相關度門檻 | 檢索到的片段若不夠像答案就拒答「查無」（決策紀錄 §17） |

## 10. 第四十輪：多語預設問句、服務意圖、拒答揭露（issue #70、#75、#77、#78、#84）

這一輪的起點是民眾**第一次按的問題**：首頁 chip1–4 與語言頁「給移工與外籍人士」卡片。七語共 35 句，以前一句都沒有在評估集裡，所以印尼文卡片問句被當成提示注入（#70）、泰文與他加祿文查無時顯示英文（#70）、外語卡片問句拿到不相干的英文片段（#75），都沒有被擋下。現在 35 句都是評估集 HP 題（`preset` 欄位記 i18n key），`tests/round40-presets.test.mjs` 會比對題目與介面字串；改了預設問句卻沒同步評估集，測試就會失敗。

**提示注入（#70）**：印尼文的「dan」是「和」，舊規則 `\bDAN\b` 加上不分大小寫，讓「pekerja migran dan penduduk asing」被拒答。現在「DAN」只在越獄語境才算（大寫，且前面有 act as／you are／啟用／扮演等，或後面有 mode／prompt／模式），而且分大小寫。中文的「忘記…指示」中間只容許 2 個字，避免「忘記打第二劑，要照醫師指示補打嗎」被誤判。回歸測試是七語各 20 句以上的正常問句，一句都不能命中注入規則（`tests/round40-injection-multilingual.test.mjs`）。

**拒答與查無的文案（#70）**：`REFUSAL_TEXT` 加了 id／th／tl 的提示注入、查無、沒有來源、沒有澄清、急症、個人診斷、用藥、預測、隱私與有害文案，ja／vi 只補了前四種。`REFUSAL_TEXT_STATUS` 記每個語言的狀態：zh-TW 是 `source`，en 是 `reviewed`，其他五語是 `machine-draft`，都要等多語審核。沒有翻譯的拒答類型，外語頁退回英文，中文頁退回中文（`refusalCopy`）。

**「未產生答案」（#84）**：拒答、查無，或沒有句子、統計、澄清、態勢時（`render.js` 的 `isNoAnswer`），卡片下方不再掛「AI 整理」標章與「模型：抽取式整理」，改成中性的「未產生答案」說明（七語）。畫面上的拒答說明是固定文字，標成 AI 整理等於宣稱 AI 回答了，揭露反而不實。稽核編號與回報表單照留，方便追查拒答是否合理。

**服務意圖（#78）**：問「怎麼查／在哪裡／去哪裡申請／如何取得／where can I get／how do I get」時（`rules.js` 的 `SERVICE_CUE`，規則 `svc.where-how`），意圖給 `apply`，優先回服務頁步驟。「在哪裡打疫苗」不算（`VAX_WHERE_RE`），那是接種地點，見下面的「在哪裡」。光是意圖對還不夠：申請步驟只在服務本身也對得上問句時才硬塞（`serviceMatches`：標題有詞重疊，或關鍵詞至少有 2 個不同的詞重疊，且分數不低於最高片段的 `SERVICE_MIN_RATIO = 0.6`）。以前「外籍勞工健康檢查」會因為單位名「健康服務中心」裡的「健康」，被塞進結核病補助申請步驟。「怎麼辦」沒有放進服務意圖，因為它是處置問句。

**逐字稿與謠言原文（#78）**：建索引時，逐字稿句子的「旁白：」「字幕：」「narrator:」前綴會去掉（`stripSpeaker`），片段標 `role: 'narration'`。問句沒提到影片時，答案引擎把這類片段乘上 `NARRATION_WEIGHT = 0.6`（其他影片片段照舊 0.85），正本有講的就不引影片。澄清稿與澄清型新聞稿裡引述謠言原文的句子，記在片段的 `noCite`（索引號）：句子仍留在片段裡，問謠言時檢索得到，但組句時跳過。判斷方式是：「」引號前 12 字內有「網傳、流傳…」，或引號內容與謠言原文的 bigram 重疊 ≥ 0.5。不是在問謠言時，澄清稿一律乘上 `CLARIFICATION_WEIGHT = 0.5`。

**最低資訊量（#75）**：`core.js` 的 `MIN_INFO = { latinWords: 4, contentWords: 2, cjkChars: 6, thaiChars: 10 }`。拉丁字母語言至少 4 個詞，其中非功能詞（不在 EN_STOP／VI_STOP、長度 ≥ 3）至少 2 個；中日文去掉標點後至少 6 個字；泰文至少 10 個字。這是為了擋掉「They should check.」這種離開上下文就沒意義的短句。結構化句（態勢、時程、旅遊、申請步驟）是欄位串接，不受此限。

**外語先對應主題，再檢索（#75）**：疾病、疫苗、國家本來就由詞彙主檔對應到 ID；這一輪在 `countries.json` 加了 `aliases`（Vietnam、Việt Nam、ベトナム、เวียดนาม…）。主檔以外的主題，由 `lexicon.js` 的 `CROSS_LANG` 第三欄 `true` 標成「主題錨點」，`topicAnchorsOf(q)` 取出，目前有移工、健保、接種紀錄、來臺旅遊四個。外語問句有錨點時，同語言片段要真的提到錨點（前 3 名的標題算 2 分、內文算 1 分），而且中文片段的錨點強度不比它高，才用同語言片段；否則改用中文片段並標 `showing-source`。中文片段也沒提到錨點，就是站內沒有這個主題 ⇒ 查無。舉例：「I am visiting Taiwan next month」在站內還沒有來臺專區時回查無，不拿出國旅遊或移工內容充數；同輪新增英文來源的來臺專區（`topic.visiting-taiwan`）後，錨點直接命中它的標題。外語問句的相關度低於 `RELEVANCE.lowBelow` 也一律查無（`low-relevance-foreign`），比給一句不相干的英文好；例外是「主題已確認」：同語言前 3 塊有一塊的**標題**就在講錨點主題（錨點強度 2），這時相關度偏低只代表用詞不同（what should I do、precautions），不套相關度門檻（guard `topic-confirmed-gate-skipped`）。

**合併後的兩個修正**：一是錨點的英文說法要涵蓋內容端的寫法（coming to／moving to／arriving in／travelling to Taiwan、Visiting or moving to Taiwan），否則問句命中錨點、片段卻對不上；二是問「在哪裡打」時，前 3 塊片段裡的接種地點句不受「句子要含問句詞」的篩選（Government-funded vaccination … at health centres 不含 flu／vaccine 這兩個詞，合併後分語言索引的 idf 改變，它就被擋掉了）。

**「在哪裡」（#75）**：問句命中 `VAX_WHERE_RE` 時，答案句會把提到衛生所、合約院所、診所、學校、clinic、health centre 的句子排到最前面（`QUERY_POINTS.where`），行動列也把「查詢接種地點」排第一：vaxmap 有這個疫苗的群組就連 vaxmap，沒有就連疫苗主檔的 `whereUrl`。

**補接種問句與新手爸媽 FAQ（#77）**：「漏打／錯過／補打／延遲接種」（`core.js` 的 `CATCHUP_RE`）不走年齡時程表。以前「寶寶疫苗漏打了怎麼辦」會列出整張嬰幼兒時程，蓋掉真正的答案。新增 4 則 FAQ：補接種、未滿 6 個月與流感疫苗、懷孕／哺乳接種、嬰兒 RSV 預防。全部是 `verification: pending`，權責是 `unit.preventive-medicine`，來源標官方網址但 `verified: false`，因為開發環境連不到官網，沒有逐字核對。內容只寫無爭議的原則：不必從頭重打、未滿 6 個月不能打流感疫苗、活性減毒疫苗孕期不建議、RSV 用藥「依現行政策」，具體間隔、對象與公費與否都列在 `pendingItems`。測試另外列了一份肯定式危險說法清單，FAQ 內文與答案句都不得出現（`tests/round40-newparent-faq.test.mjs`）。

**已知限制**

- ja／tl／id／th 的同語言語料很少，各只有 2–3 個片段。外語問句大多顯示中文原文並標 `showing-source`，這是誠實的結果，不是翻譯；要改善得靠多語內容，不是靠引擎。
- 主題錨點是手寫清單（4 個），新主題要人工加；離線把透明報告裡外語查無的問句批次歸納，是比較省的補法（§8.6 同一思路）。
- 五語的拒答與介面字串是機器初稿，`REFUSAL_TEXT_STATUS` 標 `machine-draft`，要經多語審核才算定稿；ja／vi 只翻了四種拒答類型，其餘退回英文。
- 來臺專區只有英文原文（zh-TW、vi、id 為 machine），其他語言問來臺仍會查無或顯示中文；英文問移工健檢時，來臺專區的移工段（同語言）會比中文移工 FAQ 先被引用，評估集兩者都接受，但要求答案含「入境後 3 個工作日」。
- 新 FAQ 的 `aiWhitelist.approvedBy` 是原型佔位（比照第二十八輪抗蛇毒血清），上線前要由權責單位實際核准。FAQ 的 `publishedAt` 是 2026-10-11，CI 固定 `BUILD_TODAY=2026-10-01`，所以 CI 跑評估時 NP001–NP005 會因為內容尚未生效而略過，本機與 `site.today=2026-10-11` 的測試會檢查。
- 新 FAQ 的疾病／疫苗標籤會影響排序：「未滿 6 個月與流感疫苗」原本標了 `disease.influenza`，一般流感疫苗問句（打完要觀察多久）都被它搶走，所以只留 `vaccine.influenza`。新增內容時，標籤要依「這則回答的是誰的問題」來標，不是依「內文提到什麼」。

## 11. 第四十輪：全文搜尋漏收（Issue #79）與智慧問答頁手機效能（Issue #80）

### 40.1 「兒童健康手冊」搜不到（#79）

**現象**：`/search/?q=兒童健康手冊` 顯示「沒有符合的頁面」，但 `/apply/vaccine-injury-compensation/` 的「應備文件」清單明明寫著「預防接種紀錄（兒童健康手冊、接種證明或接種單位證明）」。

**怎麼查的**：建好本機索引後，在 Node 裡直接載入 `dist/pagefind/pagefind.js` 查詢（與瀏覽器同一支程式、同一份索引，見 `scripts/lib/pagefind.mjs` 的 `loadPagefindForNode`），再用小型 fixture 逐一排除假設：

| 假設 | 結果 |
| --- | --- |
| `/apply/` 在排除名單 | 否，該頁有進索引（「預防接種受害救濟」搜得到） |
| 清單在 `<main>` 外 | 否，在 `<main data-pagefind-body>` 內 |
| 全形括號「（」、頓號「、」讓補空白中斷 | 否，fixture 中括號旁的字串照樣搜得到 |
| 片語太長、`<code>`／`<abbr>` 內的字 | 否，12 字片語、行內標籤兩側都搜得到 |
| **Pagefind 不收某些元素** | **是**。取該頁在索引裡的內容，「應備文件」標題之後直接接「表單下載」，整份勾選清單不見了 |

逐一測試元素後確認：**Pagefind 建索引時整段丟掉 `<label>`、`<form>`、`<nav>`、`<footer>`、`<noscript>`、`<template>`、`<svg>` 的內容**。申請頁的勾選清單是 `<label><input type="checkbox"><span>文件名稱</span></label>`——對螢幕閱讀器與點擊範圍是正確寫法，卻讓文件名稱整段不進索引。所以「病歷摘要」「收據寄送地址」「停留天數」等所有申請頁的應備文件都搜不到；「健康手冊」能搜到 17 筆是因為那 17 頁在別處（不是 `<label>` 裡）寫了這四個字。

**修法**（都只改「餵給 Pagefind 的副本」，`dist` 的 HTML 與無障礙行為不變）：

1. `spaceCjkInMain()` 把 **`<form>` 外面**的 `<label>` 改寫成 `<span>`。`<form>` 裡的 `<label>`（「請描述問題」這類欄位名稱）維持被丟掉——每頁都有的回報表單收進來只是雜訊。
2. 順手補：行內標籤（`<strong>`、`<a>`、`<code>`、`<abbr>`…）兩側的中文原本只在同一個文字節點內補空白，「<strong>2 年內</strong>提出」在索引裡是「內提」一個詞。Pagefind 目前剛好還找得到，但那是靠它內建斷詞的運氣；現在跨行內標籤也補，字元級片語不再依賴詞典。區塊標籤（`<p>`、`<li>`）兩側不補，Pagefind 本來就在那裡斷開。
3. **建置後自我檢查**（`verifyPagefindRecall`，deploy.md §12.5）：從整站真實輸出抽頁、抽 4–8 字中文，用同一套查詢轉換查剛建好的索引，來源頁必須在結果中；建置摘要印召回率，低於 98% 時 CI 失敗。
4. **查無時的最後退路**：完整字串查無 → 拆成前後兩半（第二十八輪已有，確認會啟動）→ 仍查無時逐步去掉前後的字（`shorterQueries`：長的先、同長度保留後段優先，因為中文名詞的中心語在後面；最短到原長度一半），第一個有結果的就用，狀態列明說：「找不到「兒童健康手冊們」，改以「兒童健康手冊」搜尋。「兒童健康手冊」找到 1 筆結果」。使用者加了引號的片語不縮。

**前後**：「兒童健康手冊」0 → 1 筆（正確的申請頁）。整站抽樣（503 個中文頁 × 4 段，共 2,012 個字串）召回 99.8% → 100%；漏掉的 4 個全是申請頁勾選清單裡的字。測試：`tests/round40-search-recall.test.mjs`（純函式、用 Pagefind Node API 建小索引的 fixture、對照組證明 Pagefind 預設丟 `<label>`、整站抽樣、Playwright 端到端）。

### 40.2 智慧問答頁手機效能（#80）

**量測**：`scripts/perf-ask.mjs`（Playwright＋CDP，412×823 手機視窗、4 倍 CPU 降速，對 `BASE_PATH=''` 的建置；伺服器像 GitHub Pages 一樣 gzip；TBT 取 Chrome trace 主執行緒 > 50 ms 的工作，量到答案出現後 2.5 秒，比 Lighthouse 嚴格）。用法見 deploy.md §15。改前 3 次、改後 3 次與 5 次的中位數（同一台機器；TBT 每次量約有 ±10% 的跳動）：

| 情境 | 指標 | 改前 | 改後 |
| --- | --- | --- | --- |
| `/ask/?q=登革熱` | TBT（主執行緒被卡住） | 4,602 ms | 621–681 ms |
| | 長工作合計 | 4,852 ms | 871–1,031 ms |
| | 傳輸量 | 544.5 KB（JSON 421） | 490.4 KB（JSON 365） |
| | 答案出現 | 5.3 s | 1.4–1.6 s |
| `/en/ask/?q=dengue` | TBT | 2,089 ms | 432–437 ms |
| | 傳輸量 | 543.6 KB | 526.4 KB（英文頁多一片英文索引） |
| `/ask/`（沒有 q） | 傳輸量 | 121.6 KB（JS 88） | 86.7 KB（JS 53），不下載任何 JSON |

傳輸量降得比 TBT 少，是因為索引分片只省了外語片段與縮排（gzip 後中文頁 204 → 148 KB），其餘引擎資料照舊要下載；再降的方向見 40.3。

**最大的根因不是檔案大小，是正規式編譯**。用 Node 的 CPU profile 看 `engine.answer('登革熱')`：1.1 秒裡 1.0 秒花在 `detectEntities` 與 `expandQuery`——它們對 1,260 個疾病、詞彙、國家名稱逐一執行正規式，其中一半是帶 `\p{L}` 與 `iu` 旗標的拉丁名稱。V8 的正規式在「第一次執行」時才編譯，而且單位元組（英文）與雙位元組（中文）字串各編一次、跑過一次後升級成機器碼再編一次；問一題就把上千個正規式各編兩三次，真正命中的只有兩三個。4 倍降速下就是 3.6 秒的 TBT。

**改法**：

1. **名稱比對器加預篩**（`lexicon.js` 的 `matcherFor`）：每個名稱算出一段「任何命中都一定包含」的字面子字串（名稱裡最長、中間不會插入可省略空白的那段，轉小寫），問句不含它就直接判定不命中，不執行也不編譯正規式；連 RegExp 物件都等第一次需要才建立（帶 `\p{L}`＋`iu` 的正規式光建立就要展開大小寫等價的字元集，上千個名稱在 Node 上約 150 ms）。判定與原本完全相同——測試拿全部名稱 × 評估集全部問句（含大寫版）逐一比對命中與否與命中位置；評估集 232 題結果不變。Node 上 `answer()` 第一次 1,142 → 107 ms，`createEngine` 180 → 25 ms。
2. **答案索引依語言分片**：`v1/search-index.<lang>.json`（與 `-pro`）只含該語言的片段、精簡 JSON。答案頁只下載當頁語言＋中文正本（引擎查不到審閱譯文時退回中文）；中文頁要抓的索引 1.88 MB → 1.14 MB（gzip 204 → 148 KB）。原本的 `search-index.json` 照舊輸出（對外 API 相容），`meta.shards` 列出分片；`/developers/` 與 `openapi.json` 已補。專業版只下載專業索引（`poolFor` 本來就是有專業索引就只用它）。後台評估重跑用 `loadEngine(view, { allLangs: true })` 讀完整檔。
3. **引擎用到才載入**：`data.js` 不再靜態 import `core.js`（`render.js` 改從 `text.js`／`rules.js` 取兩個小函式），引擎程式與資料在第一次 `loadEngine()` 時並行下載。沒有 `?q=` 的初始畫面只有問題框；使用者聚焦、按下或開始輸入就預取（引擎程式＋主要資料立刻抓，旅遊、申請服務等次要資料交給 `requestIdleCallback`），但不建引擎——`createEngine` 是一段長工作，放在打字當下會讓輸入卡頓，等送出時才建。引擎程式下載失敗時顯示「暫時無法載入」與全文搜尋連結，下次提問重試。
4. **建置閘門**：`checkAskDataBudget()` 依 `deps-manifest.js`（與前端共用的清單）算每種語言答案頁提問時要下載的 JSON、gzip 後加總，超過 445 KB 建置失敗（實測最大英文頁 387 KB，留 15%）；JS 預算的引擎頁改成「立即載入」與「提問後合計」分列，240 KB 套在合計。TBT 建置時量不到，寫成可選 e2e（`ASK_PERF=1`）。

### 40.3 下一步：TBT 若還要再降，把引擎搬進 Web Worker（這次沒做）

剩下約 0.9 秒的長工作是：解析約 2.6 MB 的 JSON、第一次提問時建 BM25 倒排（逐塊斷詞）、`createEngine`，以及畫答案。`createEngine(deps)` 與 `engine.answer(q, opts)` 本來就是純函式（輸入資料、輸出純物件），搬進 Worker 不必改引擎：

1. 新增 `answer/worker.js`（module worker）：`import { createEngine } from './core.js'`，自己 `fetch` 同一份 v1 JSON（清單用 `deps-manifest.js`），收到 `{ id, q, lang, view, disease }` 就 `postMessage({ id, result })`。JSON 解析、斷詞、BM25 都在 Worker 執行緒，主執行緒只剩畫畫面。
2. 主執行緒的 `loadEngine()` 回傳一個同介面的代理物件：`engine.answer()` 改成回 Promise（`ui.js`、`factcheck.js`、`stats.js` 的呼叫端加 `await`；`render` 不動）。`ui.js` 的側欄用到 `deps.diseases`／`deps.datasets`，改成主執行緒自己抓這兩個小檔，或由 Worker 隨結果回傳需要的那幾筆。
3. 結果傳回主執行緒前要拿掉不可序列化或很大的附屬屬性：`retrieved` 陣列上掛著 `model`（整個 BM25 模型）與 `qWeights`，structured clone 會連它們一起複製。LLM 模式（`llm.js`）只需要 `retrieved` 的句子與出處。
4. CSP：module worker 由 `script-src 'self'` 涵蓋（沒有 `worker-src` 時退回 `script-src`），不需新增來源；Worker 內的 `fetch` 受 `connect-src 'self'` 約束，與現在相同。
5. 退路：瀏覽器不支援 module worker（Safari 14 以前）或 Worker 建立失敗時，照現在的方式在主執行緒建引擎；評估集（Node）與後台評估重跑不經 Worker。
6. 驗收：`node scripts/perf-ask.mjs` 的 TBT 應降到接近沒有 q 的初始畫面（約 0.2 秒），答案內容以評估集與 `tests/round40-ask-perf.test.mjs` 的端到端確認不變。

傳輸量若要再降：引擎讀 `faq.json`（gzip 41 KB）只用到每題的 id、題目、疾病、任務與白名單旗標，可在建置時另出一份精簡清單；旅遊等級兩檔（共 45 KB）只有旅遊類問題用到，可改成引擎遇到旅遊意圖時才補抓（要動 `core.js` 的同步介面，與引擎負責人一起改）。

另一條路是把 BM25 的斷詞結果在建置時算好（索引裡直接放每塊的詞頻），省掉第一次提問時的斷詞；但那會讓索引變大、且動到引擎的檢索資料結構，留給負責引擎的同事評估。

### 40.4 學到的經驗

- **先量再改，量要能拆開看**。直覺會以為 TBT 高是因為 JSON 太大，但 CPU profile 顯示答案那 1.1 秒裡約 1.0 秒是正規式編譯，JSON 解析加建引擎在 Node 上只有約 0.2 秒；只做分片，最大的那塊完全不會動。
- **「看得到卻搜不到」要用整站抽樣抓**。#79 不是某個詞的問題，而是某種 HTML 寫法（`<label>`）被搜尋引擎丟掉；只測「登革熱」這種挑過的詞永遠測不到。抽樣自我檢查放在建置裡，下一個新元件出同樣的問題會直接在 CI 看到。
- **同一份清單給執行端與預算端**。資料傳輸量門檻讀的 JSON 清單就是前端真正抓的那份（`deps-manifest.js`），不會出現「前端多抓了一個檔、預算沒算到」。
- **改「餵給工具的副本」，不改使用者看到的頁**。Pagefind 的限制用索引副本補（`<label>` → `<span>`），頁面的無障礙寫法不必遷就搜尋工具。

## 12. 第四十一輪：covid 與 做愛 查不到——民眾用語與官方用語之間的橋

### 12.1 症狀

在 `/ask/` 問「covid」或「做愛」，答「找不到足夠的官方依據」；但問「covid-19」「新冠」「性行為」都答得出來。站上明明有內容，只是民眾的說法和站上的寫法差了一點點。

### 12.2 兩個原因

1. **covid：拉丁名稱是整字比對。** 引擎認疾病名時，英文名稱要「整個字」對上（`lexicon.js` 的 `matcherFor`：前後不能緊接字母或數字），否則「EV」會命中「EV71」、「flu」會命中「influenza」。代價是：詞彙主檔與疾病主檔裡新冠的別名只有「COVID-19」「新冠」「新冠肺炎」，民眾只打「covid」時，沒有任何名稱整字對得上，也沒有任何中文 bigram 可比，就沒有疾病、沒有檢索詞，相關度閘門判定查無。
2. **做愛：站上內容一律寫「性行為」。** 檢索是字元 bigram 的字面比對（第 2 節），「做愛」這兩個字在站上任何片段都沒有出現，詞彙主檔也沒有任何詞條把它連到「性行為」，所以問句和內容完全沒有交集。

兩個都不是引擎「算錯」，而是**詞典缺了一座橋**：民眾怎麼說、官方怎麼寫，中間要有人告訴系統它們是同一件事。

### 12.3 修法：優先改資料（詞彙主檔），引擎只加一條通則

**資料（主要的修法）：**

- `term.covid-19` 加別名 `COVID`、`Covid`、`新冠病毒`；`disease.covid-19` 加別名 `COVID`（疾病主檔的別名會進答案索引的關鍵字與疾病頁 JSON-LD 的 `alternateName`，所以這裡也補）。「武漢肺炎」維持在 `deprecated`（舊名，問了會提示正名）。
- 新增 `term.sexual-contact`：正名「性行為」，別名「做愛、性交、上床、嘿咻、房事、親密行為、性接觸」，`domain: general`、`refs: []`（性行為不是一種病，相關內容散在愛滋、梅毒、A 型肝炎、M痘、PrEP 與性傳染病專區，讓檢索自己找）。外語譯名是 Claude 草擬，`machineTranslated` 列出六個語言待多語審核人核對。
- 新增 `term.cross-immunity`（交叉免疫；別名「短暫性交叉免疫」「交叉保護」）。這一筆是**詞界**：登革熱教材寫「短暫性交叉免疫力」，裡面剛好有「性交」兩個字。加了「性交」別名之後，索引端（`index-builder` 的 `glossaryHits`）會把登革熱教材標上性行為的術語，專業模式問「性交」就可能答出登革熱。有了較長的已知詞「短暫性交叉免疫」，第三十一輪的詞典邊界規則（短詞只出現在「指別的東西」的較長已知詞裡就不算）就會把它遮住，和「急性病毒性A型肝炎」遮住「性病」是同一個機制。

**引擎通則（`lexicon.js` 的 `latinStems`，`core.js` 建實體比對器與同義詞比對器時呼叫）：**

- 形如 `^[A-Za-z]{4,}-\d+[A-Za-z0-9]*$` 的拉丁名稱（COVID-19），把字母詞幹（COVID）也當成同一個疾病／詞條的別名，實體偵測與同義詞展開都認得；同義詞展開會補上 COVID-19、新冠等全部形式，BM25 找得到片段。
- 不套用 H5N1、EV71：沒有連字號、或字母不到 4 個的代號，砍掉數字就變成別的東西（H、EV）。SARS-CoV-2 這種數字後面還有連字號的也不套用。
- **歧義檢查**：詞幹本來就是任何已知名稱（疾病、詞彙、疫苗、國家）就不動——是同一個東西表示資料已經有了，是別的東西就不能搶；兩個不同對象推出同一個詞幹（假設將來有 XXXX-1 與 XXXX-2 是兩種病）也一律不加，寧可查無也不答錯。實體那一輪判定有歧義的詞幹，同義詞展開那一輪也跳過。
- 目前站上符合這個形式的只有 COVID-19，而資料已經補了 COVID 別名，所以這條規則在現有資料上不改變任何結果；它是給下一個「XXXX-數字」名稱（新的病毒株、新疾病）用的保險，`tests/round41-synonyms.test.mjs` 用合成資料驗正向與歧義兩種情況。

### 12.4 為什麼優先改資料，而不是在程式裡加例外

- **看得到、審得到。** 詞彙主檔是 OASIS 與多語審核人每天在管的資料，`/glossary/` 公開頁與後台都看得到；寫在程式裡的例外只有工程師看得到，下一個人不知道它存在。
- **一處改，多處受益。** 詞條同時餵給：智慧問答的同義詞展開與詞典邊界、答案索引的術語欄（片段帶上口語別名，民眾用口語問可以直接命中）、預處理的舊名提醒、七語譯名。程式例外只修一個地方。
- **引擎是每一頁都要下載的程式。** 答案引擎的 JS 已經用到 240 KB 預算的 238.7 KB（第 11 節、guide-staff 第 38 節），每一條特例都會吃預算；資料不吃 JS 預算。
- 程式只該處理「有規律、不分領域」的情況（像 COVID-19 → COVID 這種命名形式），而且要附歧義檢查；「做愛＝性行為」這種語意對應不可能由規則推出來，只能靠人寫進詞典。

### 12.5 已知限制與下一步

- **不在詞典裡的詞，系統仍然看不見。** 這輪補的是被回報的幾個詞；民眾還會用很多我們沒想到的說法（台語、注音文、錯字、新流行語）。引擎是字面比對，沒有人寫進詞典的對應，它不會自己學會。
- **這輪平行建置的問句紀錄（query log）是找出下一批詞的方法**：記下哪些問句被判查無，承辦與 OASIS 定期看「查無且重複出現」的問句，判斷是內容缺口（要寫內容）還是用語缺口（加別名或新詞條），照 guide-staff 第 41 節的 SOP 補上，並加一題評估集守住。
- 中英混打的「covid疫苗」仍認不出疾病：拉丁名稱整字比對時，後面緊接的中文字也算「字母」（Unicode `\p{L}`）。目前靠「新冠疫苗」「COVID-19 疫苗」等詞條與 bigram 檢索仍答得出來；若問句紀錄顯示常見，再在詞彙主檔加「COVID 疫苗」這類中英混排別名（混排名稱的比對允許中英之間有無空白）。
- 「做愛」類問句目前多半引用 A 型肝炎的傳染途徑與預防（站上把口肛性行為寫得最完整的內容），也算正確，但更理想的是導到性傳染病專區；若要調整，應由內容端在專區加「性行為與感染風險」的段落，而不是在引擎加權。
- 評估集 `2026.10-r12` 新增 BD009–BD016（covid／Covid／新冠病毒；做愛／上床／性交／做愛會得什麼病；專業模式「性交」不得答出登革熱教材）。

## 13. 第四十八輪：主題錨點、近親疫苗、連接詞、低相關判斷、外語主題確認、待確認標示（issue #93–#96、#101、#102）

這一輪的回報有一個共同點：**資料其實都在站上，引擎卻挑錯片段或不敢答**。修法維持第 12 節的原則——能用通則就不寫特例，能靠資料就不靠程式，而且每條新規則旁邊都留了「第四十八輪（issue #NN）：…」的註解。

### 13.1 主題錨點（#94）：為什麼不把問句寫死

**問題**：「哺乳可以打疫苗嗎」「RSV 什麼時候打」「晚了才打還有效嗎」這類問句，站上有專門的 FAQ，但 BM25 會被「疫苗」「打」這種高頻詞拉去別的頁面（時程表、孕婦流感 FAQ）。

**做法**（`core.js` 的 `zhAnchors`）：從答案單元（FAQ、疾病、疫苗、服務、主題頁）的關鍵字建一張「詞 → 內容 id」對照。問句裡出現的詞，若只屬於 ≤3 份內容、而且全站只有 ≤3 份內容提到它，就是**錨點**：這個詞很專一，問的人幾乎一定是在問那幾份內容。錨定的片段加權、句子排前面；若錨定的是沒有指名疾病的 FAQ，才可以越過疾病過濾（避免「流感停課」被「停課」拉去腸病毒）。

**為什麼比寫死問句好**：
- 寫死「哺乳 → faq.xxx」只修好被回報的那一句，換個說法（「餵母奶」「親餵」）又壞；錨點吃的是內容自己的關鍵字，承辦在後台補一個關鍵字，所有說法一起受益。
- 錨點會隨內容自動消長：某個詞被第四份內容用到，它就不夠專一、自動失效，不會留下過時的特例。
- 只用問句原文與口語改寫（PARAPHRASE）找錨點，**不用詞彙主檔的展開**——展開會把「麻疹」變成「麻疹腮腺炎德國麻疹混合疫苗」這種長名，反而造出假錨點。
- 錨點只從答案單元建，不從新聞稿、媒體素材建（「外籍勞工」曾因此把健康促進的問句拉走）。

### 13.2 近親疫苗（#95）：沒有專頁就說沒有，不拿兄弟疫苗頂替

**問題**：問帶狀疱疹疫苗，站上沒有專頁，引擎卻引用水痘疫苗（同病原）回答——對民眾是錯的資訊。

**做法**：問句指名疫苗 V，而 V 與其他疫苗共用疾病（近親）時，只留「提到 V」或「沒提到任何近親」的片段；一個都沒有就拒答，說「本站尚無 V 專頁」，時程表有這支疫苗就附上時程表連結。疫苗主檔裡沒有專頁的疫苗（`hasPage: false`）不顯示疫苗頁連結。

**疫苗主檔一致性**：Node 端評估用全部疫苗主檔，瀏覽器端原本只拿到有專頁的疫苗，所以「帶狀疱疹疫苗」在瀏覽器裡根本不被認成疫苗。這輪新增 `v1/vaccine-master.json`（次要依賴，延後載入），兩端看到同一份疫苗清單。

### 13.3 連接詞句（#96）

抽取式答案逐句挑選，曾挑出「但若已出現症狀……」這種開頭是「但是／此外／因此」的句子，卻沒挑前一句，讀起來沒頭沒尾。現在以「但、不過、另外、此外、因此、所以、此時、其中」（英文 however、but、also…）開頭的句子視為**依附句**：前一句同片段已選中就接在後面成一句；沒選中就丟掉（guard `dangling-connective-dropped`）。不採「自動補上前一句」，因為前一句可能與問題無關，會擠掉更相關的句子。

### 13.4 低相關判斷（#102）：修判斷，不調門檻

**問題**：答案明明對題，卻被標成「相關度偏低，可能沒回答到您的問題」。

**為什麼不降低 `RELEVANCE.lowBelow`（0.6）**：門檻是全域的，降低之後真正答非所問的情況（評估集裡有數十題守著）也會一起放行，等於拿正確率換掉警示。根因不是門檻太高，而是相關度是用「問句字詞被片段覆蓋多少」算的，口語問句的贅詞（「我家小孩」「請問一下」）把分數拉低。

**做法**：判為低相關之後，再做一次**主題對題**檢查——第一個被引用的片段是 FAQ（且疾病不衝突）或是同疾病的內容，而且問句與「該片段標題＋第一句」落在同一個面向（費用、照護、疫苗、症狀、預防、傳染、咬傷）——成立就標 `topicMatch`，不顯示低相關警示。判斷依據是可解釋的（guard `topic-match` 寫在除錯資訊裡），而且只影響警示，不影響挑哪些句子。評估集新增 `lowRelevance: false` 的期望值守住這幾題。

### 13.5 外語主題確認與拉丁名稱縮寫（#101）

- 印尼文、泰文、他加祿文等問句先經 CROSS_LANG 對到中文詞再檢索。這輪補了「症狀」「被咬」「狗」「貓」的多語說法。
- 外語問句只要偵測到的疾病就是第一名片段的疾病，就視為主題已確認，不因字面覆蓋率低而拒答（外語問句跟中文片段的字面重疊本來就低）。同語言但相關度低於門檻的片段直接丟掉，避免一段無關的泰文段落蓋過正確的中文內容。
- `latinStems` 新增一條通則：三個字以上的拉丁名稱，若頭或尾那個字本身就是同一疾病的另一個名稱（「Demam berdarah dengue」裡的 dengue），去掉那個字的短名（demam berdarah）也算別名。歧義檢查與第 12.3 節相同：短名是別的東西或撞名就不加。

### 13.6 待確認內容的標示（#93）

`verification: pending` 的內容，引用句尾加「（待確認）」／「(pending verification)」，來源卡片加「內容待確認」標籤。用標示而不是隱藏：內容是承辦已上架的，隱藏等於讓民眾問不到，標示則讓民眾知道要再查證。建置時另外列出「待確認卻標示已審閱」（審閱日＝建立日）的內容（`⚠ [待確認]`，目前 19 筆），交給承辦處理；這是警告不是錯誤，不擋建置。

### 13.7 拒答文案依語言拆檔與 JS 預算

加上述規則後，智慧問答頁 JS 一度到 243.8 KB，超過 240 KB 預算。沒有調高預算，而是把日、他加祿、越、印尼、泰五種語言的拒答文案從 `rules.js` 搬到 `refusal-i18n.js`，建置時拆成每語一檔（`refusal-i18n.<lang>.js`），頁面只載入自己語言那一檔（`registerRefusalText` 註冊；載入失敗退回英文）。中文、英文文案仍在主程式裡，作為保底。預算計算同時把該語言那一檔算進去，數字是誠實的。

**為什麼這樣比較好**：每位使用者只看一種語言，其他四種語言的文案對他是純負擔；而且新增語言的文案不再墊高所有頁面的預算。代價是多一次很小的請求，與引擎核心一起延後載入，不影響首屏。

### 13.8 已知限制

- 預算餘裕約 1 KB 多一點，下一條引擎規則很可能又要先找地方瘦身。
- 錨點依賴內容關鍵字的品質：關鍵字寫得太泛（「疫苗」「小孩」）不會成為錨點；寫得太窄則換個說法就對不到。
- 帶狀疱疹疫苗專頁上架後，要把疫苗主檔的 `hasPage` 改成 true，疫苗頁連結才會出現。
- 評估集新增 R48-01～R48-36；其中三題流感校園群聚需等 `faq.flu-school-cluster` 上架才會執行（`requires`）。
