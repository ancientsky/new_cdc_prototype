# 內容越來越多，Git＋CI 會不會慢到爆炸？（第五十五輪，2026-10-16）

> 給誰看：資訊室、OASIS，以及要回答廠商「用 Git 做 CI 不會越來越慢嗎」的人。
> 一句話：**會變慢的是「每次發布要重算的東西」（建置、測試、無障礙掃描），不是 Git。Git 的部分（checkout）十天來一直是 2–3 秒；原型 CI 從 1 分鐘變 3–4 分鐘，九成是這十天多寫的 60 個測試檔，內容只多了一成。以舊站規模（頁面數千）推估，照現在的做法全站建置約 10–15 分鐘，是「要管、管得住」的量級，不是爆炸。** 本文列出實測數據、推估方法、哪些步驟是線性的、何時該做哪一步，以及 Anthropic 的 Scion 文章哪些能借用、哪些不能。

目錄：0 先回答廠商・1 把問題拆成三件事・2 原型 CI 十天的實測・3 本機實驗：內容加到 4 倍與 10 倍・4 推估正式站規模・5 Anthropic 的 Scion 文章能不能用・6 對策：現在就做的、上線前做的、什麼訊號出現再做的・7 教訓

## 0. 先回答廠商

廠商的質疑可以拆成兩句：「Git 存很多內容會變慢」與「每次改一筆都要整站重建，內容多了就撐不住」。

1. **Git 不會是瓶頸。** 內容是小的 JSON 檔（目前 369 筆共 5 MB；舊站規模放大 10 倍也不過 50 MB），Git 對幾萬個小文字檔的 commit、diff、clone 都是毫秒到秒級。CI 用的是淺層 checkout（只抓最新一版，不抓歷史），所以**歷史再長，CI 的 checkout 時間都不變**。十天 334 次執行的紀錄裡，checkout 一直是 2–3 秒（第 2 節）。會把 Git 撐大的只有二進位大檔，這已由 [assets-policy.md](assets-policy.md) 擋在外面（影片、大型原始檔放物件儲存，Git 只放連結與雜湊）。
2. **整站重建的時間與內容量成正比，而且是建置機的事，不是民眾的事。** 建置期間網站照常服務，建置完成才換上新版；所以建置變慢影響的是「送出到上線要等多久」，不是「網站會不會慢」。目前的實測是**每一頁約 8 毫秒（版型）＋ 8 毫秒（全文索引）**，舊站規模推估全站 10–15 分鐘（第 4 節）。這個量級有成熟的對策（第 6 節），而且**對策都是加在建置腳本上的，不需要換掉 Git 當正本的設計**。
3. **原型 CI 最近變慢，原因是測試變多，不是內容變多。** 10/5 到 10/15 內容只從 332 筆增加到 369 筆（+11%），測試檔從 32 個增加到 93 個（+190%），測試步驟從 17 秒變成 104 秒。這是原型階段每一輪都加測試的結果；正式站的內容 PR 不需要跑全部的程式測試（第 6.1 節）。

給廠商的反問：「你們的 CMS 改一筆內容後，搜尋索引、相關連結、多語版本、AI 問答的引用，是什麼時候重算的？」傳統 CMS 不是不重算，是改成在民眾瀏覽時即時算（資料庫查詢），或是乾脆不算（所以會有壞連結與過期引用）。我們把這些工作搬到發布那一刻一次做完並檢查，代價就是發布要等幾分鐘。

## 1. 把問題拆成三件事

| 面向 | 隨什麼成長 | 原型現況 | 正式站的量級 |
| --- | --- | --- | --- |
| **Git 儲存庫**：clone、commit、diff | 檔案數、歷史長度、二進位大檔 | 205 個 commit、34 MB（最大的檔是 docs 裡的截圖 PNG，不是內容） | 內容 JSON 幾萬個檔、幾十 MB；歷史每年幾千個 commit；CI 淺層 checkout 不受歷史影響 |
| **建置**：schema、治理、答案索引、版型輸出、全文索引、連結檢查 | 內容筆數 × 語言數 | 369 筆 → 3,759 頁，本機 4 核 70 秒、GitHub runner 39 秒（不含索引驗證的 `--check` 只要 4 秒） | 線性外推見第 4 節 |
| **測試與掃描**：`npm test`、axe 無障礙、Playwright | 程式與測試的數量，**與內容幾乎無關** | 93 個測試檔，4 核並行 104 秒；axe 掃 24 頁 × 3 種視窗 162 秒 | 內容 PR 不該全跑；程式 PR 才跑 |

三件事的成長曲線不同，對策也不同。廠商把它們混在一起講成「Git 做 CI 會慢」，所以先拆開。

## 2. 原型 CI 十天的實測（GitHub Actions，2026-10-01 至 10-15，334 次執行）

資料來源：GitHub Actions API 的 workflow runs 與 jobs（每一步的開始與結束時間）。只算成功的執行；`pages.yml` 是 push 到 main 與每 2 小時排程的整站建置部署，`content-pr.yml` 是每個 PR 的檢查車道。

### 2.1 每日中位數

| 日期 | pages.yml（分鐘，中位／最大） | content-pr.yml（分鐘，中位／最大） | 當天 main 的內容筆數 | 測試檔數 |
| --- | --- | --- | --- | --- |
| 10-05 | 1.3 ／ 2.2 | 1.2 ／ 1.7 | 332 | 32 |
| 10-09 | 1.3 ／ 1.4 | 1.4 ／ 1.4 | 328 | 35 |
| 10-10 | 1.8 ／ 2.3 | 3.2 ／ 4.9 | 349 | 51 |
| 10-11 | 2.2 ／ 2.5 | 5.0 ／ 6.1 | 359 | 66 |
| 10-13 | 2.6 ／ 3.5 | 6.1 ／ 6.7 | 366 | 73 |
| 10-14 | 3.2 ／ 3.9 | 7.5 ／ 8.7 | 369 | 92 |
| 10-15 | 3.8 ／ 5.0 | 8.2 ／ 9.8 | 369 | 93 |

10-10 那天 PR 車道一口氣從 1.2 分鐘跳到 3.2 分鐘：第四十輪在 PR 車道加了 lint、格式、型別檢查與 axe 無障礙掃描（Chromium 安裝 + 另建一版 + 掃描），不是那天內容變多。

### 2.2 同一條流程，10-05 與 10-15 逐步比較

`pages.yml` build job：

| 步驟 | 10-05（run #57） | 10-15（run #257） | 差異來自 |
| --- | --- | --- | --- |
| checkout | 2 秒 | 3 秒 | — |
| setup-node + `npm ci`（有快取） | 3 秒 | 4 秒 | — |
| lint + format + typecheck | （當時沒有） | 8 秒 | 第四十輪加的 |
| `npm test` | **17 秒** | **104 秒** | 測試檔 32 → 93 |
| `npm run build` | 16 秒（當時沒有全文索引） | 39 秒 | 第二十八輪加 Pagefind 索引（約 22 秒）、內容 +11%、多語頁數 |
| 上傳與部署 | 15 秒 | 15 秒 | — |

`content-pr.yml` test job（10-15，run #77，共 5.7 分鐘）：

| 步驟 | 秒 | 說明 |
| --- | --- | --- |
| checkout（`fetch-depth: 0`，抓完整歷史） | 3 | 目前 34 MB；會隨歷史成長，但很慢（見 6.2） |
| lint、format、typecheck、PII 掃描 | 7 | 程式檢查 |
| `npm test` | 79 | 程式與治理規則測試 |
| `build --check`（schema、治理、評估集，不輸出頁面） | **4** | **真正「內容的閘門」只要 4 秒** |
| 安裝 Chromium | 16 | 每次重裝 |
| 為無障礙掃描建一版（含索引） | 28 | |
| axe 掃描 24 頁 × 3 視窗 | **162** | 單一最大項 |
| 建預覽版 | 29 | 第三次建置 |
| 上傳 artifact | 7 | |

一個 PR 車道建了三次站（check、a11y、preview），其中兩次是完整建置；axe 一項就占 47%。這些都是**程式品質**的檢查，對一筆新聞稿的 PR 來說是多餘的。

### 2.3 `npm test` 的時間花在哪

逐檔單獨計時（本機 4 核，加總 464 秒；CI 並行後 104 秒）。最慢的 10 個檔都是會啟動 HTTP 伺服器或 Chromium 的端到端測試：

| 測試檔 | 秒 | 測什麼 |
| --- | --- | --- |
| round48-ui | 36 | 後台頁面（Playwright） |
| round53-editors-gateway | 36 | 四個編輯頁走寫入閘道（起閘道、起瀏覽器） |
| round52-concurrent-edit | 25 | 版本碼 409 |
| round52-bulletin-gateway | 25 | 疫情報導編輯頁走閘道 |
| round47-nav-panels | 20 | 導覽面板（Playwright） |
| round53-holdout2 | 18 | 盲測題組（跑答案引擎） |
| round50-rereview | 17 | 重審流程 |
| round24-a11y | 17 | axe（測試內又掃一次） |
| round30-gateway | 16 | 閘道端到端 |
| round53-engine | 16 | 答案引擎 |

沒有一個是「因為內容多而慢」；它們是因為每輪加功能就加一個端到端測試。這是原型階段的健康現象，但正式站要把它們和內容 PR 分開（6.1）。

## 3. 本機實驗：內容加到 4 倍與 10 倍

方法：把 `content/news`、`faq`、`documents`、`clarifications` 四種「一筆一頁」的內容複製成 4 倍與 10 倍（id、標題加編號，拿掉附件參照，其他欄位原樣），在同一台 4 核機器上跑完整 `npm run build`，看哪些步驟隨內容線性成長、有沒有超線性的。

| 倍數 | 內容筆數 | 輸出頁數 | 版型輸出 | 全文索引 | 連結檢查 | 一致性比對的句數 | 整次建置（4 核本機） |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1× | 369 | 3,759 | 32 秒（8.6 ms／頁） | 24 秒（8.1 ms／頁） | 3.6 秒（44 萬連結） | 3,699 | **70 秒**（18.6 ms／頁） |
| 4× | 786 | 5,121 | 39 秒（7.6 ms／頁） | 27 秒（6.6 ms／頁） | 4.9 秒（62 萬連結） | 5,256 | **85 秒**（16.6 ms／頁） |
| 10× | 1,620 | 7,845 | 63 秒（8.1 ms／頁） | 43 秒（6.3 ms／頁） | 8.7 秒（99 萬連結） | 8,370 | **143 秒**（18.2 ms／頁） |

（複製的四種型別多半只有中文版，所以筆數 4.4 倍、頁數只有 2.1 倍；比例要看「每頁」那一欄。原始紀錄：GitHub Actions run #57、#77、#257 與本機 `scripts/build.mjs` 的輸出。）

讀法：
- **每頁成本不變**：版型輸出每頁約 8 ms、全文索引每頁 6–8 ms、連結檢查每頁約 1 ms，從 3,759 頁到 7,845 頁都一樣。整次建置約 18 ms／頁，**頁數加倍、時間加倍，沒有平方項**。
- **說法一致性比對**（兩兩比對句子，最可能平方成長的步驟）從 3,699 句到 8,370 句時整次建置沒有突出，因為它用倒排索引找候選、常見詞不當候選（`scripts/lib/consistency.mjs` 的 `MAX_DF`），實際接近線性。
- **第一個撐不住的不是 CI，是瀏覽器端的答案資料預算。** 第一次跑 4 倍時建置在輸出頁面之前就中止：智慧問答頁要下載的答案索引（每語言 gzip 後）從 369 KB 漲到 461 KB，超過 445 KB 的預算（[deploy.md](deploy.md) §15.3）。上表是把預算暫時放寬後量到的。這表示**內容大約到現在的 2 倍，智慧問答就必須改成按主題分片下載或改由伺服器端回答**（[deploy.md](deploy.md) §17 的設計備忘；LINE 疾管家已經是伺服器端跑同一個引擎，[line-chatbot.md](line-chatbot.md)）。這是內容量第一個會碰到的牆，而且與 Git、CI 都無關，但要排進上線前的工作。
- 評估集通過數從 449 降到 434／423，是因為複製出來的內容和原文幾乎一樣、引擎引用了複本；這是實驗的副作用，不是效能問題。

## 4. 推估正式站規模

舊站規模（[transition-faq.md](transition-faq.md) §5.1）：疾病 99 種、可索引頁面數千、附件數千。本節以 **5,000 筆中文內容**（約現在的 13 倍）、7 種語言、每筆都有外語版為上限推估；實際上大多數內容不會翻 7 種語言（外語版只做重點內容），所以頁數會比「13 倍」少。

| 步驟 | 現在（369 筆、3,759 頁） | 成長方式 | 5,000 筆推估 |
| --- | --- | --- | --- |
| 版型輸出 | 30 秒（約 8 ms／頁） | 線性（每頁獨立） | 約 6–7 分鐘 |
| Pagefind 全文索引 | 22 秒（約 8 ms／頁） | 線性 | 約 5 分鐘 |
| 連結檢查 | 4 秒（44 萬個連結，大多是導覽列） | 線性於「頁數 × 每頁連結數」；導覽列若列出全部疾病會變成兩者都長 | 約 1 分鐘；導覽改成分層後維持線性 |
| 答案索引、說法一致性、評估集 | 約 10 秒 | 一致性比對用倒排索引、常見詞不當候選（`MAX_DF`），接近線性；評估集與題數成正比 | 約 2 分鐘 |
| schema 與治理（`--check`） | 4 秒 | 線性 | 約 1 分鐘 |
| **整站建置合計（4 核）** | **70 秒（約 18 ms／頁）** | 線性於頁數 | **5 萬頁約 15 分鐘；GitHub runner 比本機快約 1.8 倍（同一版 39 秒對 70 秒），約 8 分鐘。外語版只做重點內容的話（例如平均每筆 3 頁、1.5 萬頁），約 3–5 分鐘** |

頁數的假設：現在每筆內容平均 10 頁（7 種語言加專業版），因為示範內容幾乎全部翻了；正式站 5,000 筆若全翻是 5 萬頁，只翻重點內容則 1–2 萬頁。

兩個結論：

1. **沒有超線性的步驟。** 實驗（第 3 節）與程式碼（一致性比對有倒排索引與 `MAX_DF`；連結檢查是查表；索引是逐頁）都支持「10 倍內容約 10 倍時間」。「爆炸」指的是平方成長，這裡沒有。
2. **但最壞情況的 10–15 分鐘對緊急車道太長，而且智慧問答的資料預算會更早碰到（第 3 節）。** 緊急發布的承諾是「CI 通過 10 分鐘內合併」（[publishing-lanes.md](publishing-lanes.md)），合併後還要建置部署。所以正式站不能等到那時候才處理，第 6 節的對策要在試點期就排進去，目標是**內容 PR 的閘門 1 分鐘內、整站建置部署 5 分鐘內**。

## 5. Anthropic 的 Scion 文章能不能用

文章：[Redesigning source control for the agentic era](https://www.anthropic.com/engineering/redesigning-source-control)（2026）。Anthropic 把內部 monorepo 從 Git 換成自製的 Scion。

### 5.1 他們的問題是什麼

- 每天合併從 2,500 次成長到 **30,000 次**；主分支歷史近 **100 GB**，一份壓縮後的工作副本 25 GB；每天 **2,500 萬次 CI checkout**；最多時跑了數百台 Git 鏡像。
- 客戶端幾乎都是永遠在線的 agent 與 CI job，Git「離線優先、每個副本都有完整歷史」的設計在這個場景是負擔。

### 5.2 他們做了什麼

- 伺服器端算所有東西（歷史、blame、合併、rebase），客戶端只留有限快取。
- 變更單位是「changeset」（只記改了哪些檔），不是 Git 的完整樹快照。
- **稀疏／虛擬化 checkout**：只抓要用的目錄，檔案讀到才真的下載；**很多 CI job 根本不 checkout**，改用 API 向伺服器要 diff。
- 結果：CI checkout 從分鐘級降到秒級，CI CPU 省 25%。

### 5.3 哪些能借用

| 他們的做法 | 我們對應的做法 | 狀態 |
| --- | --- | --- |
| CI 不抓完整歷史 | `actions/checkout` 預設 `fetch-depth: 1`，`pages.yml` 已是如此 | 已做；`content-pr.yml` 還是 `fetch-depth: 0`（6.2） |
| CI 不 checkout、向伺服器要 diff | 內容 PR 的車道判定（改了哪些檔、屬於哪個車道）可以只用 GitHub／GitLab API 的「PR 變更檔案清單」，不需要 clone | 可做；目前 `lane.mjs` 用 `git diff` |
| 只抓要用的目錄 | 內容 PR 只需要 `content/` 與 `schemas/`，不需要 `tests/`、`docs/`、截圖 | Git 的 sparse checkout 就能做；現在不需要 |
| 二進位不進版本控制的主要路徑 | [assets-policy.md](assets-policy.md) | 已做 |

### 5.4 哪些不能用，為什麼

- **規模差四個數量級以上。** 他們一天 3 萬次合併、100 GB 歷史；我們一天幾次到幾十次合併、幾十 MB。文章自己說：「these concepts really only make sense for truly enormous monorepos」、Scion「is not a suitable replacement for git for general use」。
- **他們換掉的是 Git 的儲存與協定，不是「建置要重算」這件事。** 我們變慢的部分（建置、測試、掃描）在 Scion 的世界一樣要做；文章完全沒有碰這一塊。
- **自製版本控制是一個七人團隊五個月的工程**，而且他們明說內部工具非常客製、很難對外提供。機關的資訊室沒有理由走這條路；文章建議的是讓 Git 平台吸收這些想法（伺服器端 RPC、sparse／shallow），而 GitHub 與 GitLab 的 shallow clone、sparse checkout、PR 檔案清單 API 早就有了。

一句話：**文章證明的是「Git 在極端規模下的協定成本可以降到秒級」，而我們的 Git 協定成本現在就是秒級。它對我們的用處是觀念上的提醒：CI 要什麼就拿什麼，不要每次都抓整個倉庫。**

## 6. 對策

分三層：現在就能做、上線前做、看到訊號再做。每一項都是改建置腳本或 CI 設定，**不改「Git 是正本、CI 是閘門」的設計**。

### 6.1 現在就能做（原型期，各約半天）

> 第五十六輪（2026-10-16）：四項都做了，見 [deploy.md](deploy.md) §28 與 README 第五十六輪；實際的加速數字請在合併後的第一個內容 PR 與程式 PR 核對。

1. **內容 PR 與程式 PR 走不同的檢查。** PR 只改 `content/`、`data/snapshots/` 時：跑 `build --check`（4 秒）、PII 掃描、變更頁的連結檢查、一次預覽建置；**不跑** `npm test` 的程式測試、lint、typecheck、axe（內容不會改版型，axe 的結果和上一次一樣）。PR 改到 `src/`、`scripts/`、`schemas/`、`tests/` 才全跑。預期內容 PR 從 6–8 分鐘降到 1 分鐘內。`lane.mjs` 已經會算「改了哪些檔」，這一步只是把結果拿來決定要跑哪些步驟。
2. **一個 PR 只建一次站。** 現在建三次（check、a11y、preview）；a11y 與 preview 可以共用同一份 `dist`（`BASE_PATH` 的差異用相對路徑或在掃描時設 base 解決）。省約 30 秒。
3. **快取 Chromium。** `playwright install` 每次 16 秒，用 `actions/cache` 快取 `~/.cache/ms-playwright`。
4. **axe 只掃改到的版型。** 內容 PR 不掃；程式 PR 掃全部 24 頁。

第六十八輪（2026-10-27）補兩項，起因是「多人同時上架，最晚的要等多久」：`pages.yml` 的 concurrency 改為排隊不取消（連續合併不再可能把建置無限取消），審核後沿用同一 commit 的檢查結果（省掉 Approve 後 2.5–6 分鐘的重跑）。計算與實測見 deploy.md §34。

### 6.2 上線前做（試點期）

1. **PR 車道改淺層 checkout。** `content-pr.yml` 的 `fetch-depth: 0` 是為了 `git diff` 找變更檔；改用平台 API 的 PR 檔案清單（GitHub `pulls/{n}/files`、GitLab `merge_requests/{iid}/changes`），就可以 `fetch-depth: 1`。歷史再長也不影響。
2. **全文索引與答案索引增量更新。** Pagefind 與答案索引目前每次全建；兩者都能以「內容檔的雜湊」做快取，只重算有變的頁。這是最大的單項（兩者合計約半分鐘，正式規模約 10 分鐘）。
3. **自架 runner。** 署內 GitLab 的 CI runner 可以是一台固定的機器，`node_modules`、Chromium、上一次的 `dist` 都留在磁碟上，不用每次重抓；核心數也可以比 GitHub 的 4 核多。建置輸出頁面是逐頁獨立的，可以用 worker 並行，8 核約再快一倍。
4. **內容與程式分倉。** 正式站建議 `content` 倉（承辦人透過寫入閘道寫入、只跑內容閘門）與 `site` 倉（工程師、跑全部測試）分開；`site` 的建置拉 `content` 的最新版。這樣承辦人的每一筆 PR 的 CI 都只有內容閘門，程式測試再多也不會拖慢上架。
5. **智慧問答的答案資料改成按主題分片或伺服器端回答。** 內容到現在的 2 倍就會超過瀏覽器端 445 KB 的預算（第 3 節）；這一項與 CI 無關，但是內容成長第一個碰到的牆，要和搬遷第一個專區一起做。
6. **緊急車道的建置預算寫進驗收。** 建議的 KPI：內容 PR 閘門 ≤ 1 分鐘、合併到上線 ≤ 5 分鐘（含建置與部署）。這兩個數字要在試點（一個專區完整搬進來之後）實測，不是上線後才量。

### 6.3 看到什麼訊號再做什麼

| 訊號 | 做法 |
| --- | --- |
| 整站建置超過 5 分鐘（做完 6.2 之後） | 把版型輸出改成增量：只重算內容有變的頁與引用它的列表頁。靜態網站產生器（Astro、Eleventy、Hugo）都有成熟做法；我們的 build.mjs 已經以「一筆內容一個檔」為單位，加雜湊快取即可 |
| 內容 JSON 超過 100 MB 或單檔超過 1 MB | 檢查是不是有人把附件 base64 塞進 JSON；附件一律走 assets-policy |
| 一天的合併次數超過 100 | 合併佇列（merge queue）避免互相等；GitHub 與 GitLab 都內建 |
| Git 倉庫超過 1 GB | 幾乎一定是二進位檔進了 Git；`git filter-repo` 清掉並補 CI 檢查（檔案大小上限） |
| 同一時間多人改同一筆 | 已由版本碼 409 處理（第五十二輪）；不是效能問題 |

### 6.4 不建議做的

- **不要因為 CI 慢就把閘門關掉或改成抽查。** 閘門慢是工程問題（上面都有解），把閘門拿掉是治理問題（第二十三輪以來擋下的錯誤都會回來）。
- **不要把內容搬回資料庫「因為資料庫快」。** 資料庫快的是讀取，而我們的讀取已經是靜態檔案（更快）；慢的是發布時的檢查與重算，那在資料庫方案裡不是消失了，是沒人做了。
- **不要自製版本控制。** 見第 5 節。

## 7. 教訓

1. **「越來越慢」要先量，再歸因。** 直覺上「CI 變慢是因為內容變多」，實測是「測試從 32 個檔變成 93 個檔」。沒有 Actions API 的每步時間，這一題只能憑感覺吵。本文的數字來自 334 次執行的每一步起訖時間，方法可以重跑（第 2 節）。
2. **把「Git」「建置」「測試」三種成長分開講。** 廠商的質疑混在一起時聽起來很有道理；拆開以後，Git 的部分是秒級且不隨歷史成長，建置是線性且有對策，測試與內容無關。
3. **內容 PR 不該為程式測試買單。** 每輪加測試是對的，但承辦人的一筆新聞稿不需要等 Chromium 跑 36 秒的後台測試。正式站的車道設計要把這兩種 PR 分開，最乾淨的做法是分倉。
4. **讀大公司的工程文章，先看規模與問題是不是同一個。** Scion 解的是「一天 3 萬次合併、100 GB 歷史」的協定成本；我們的協定成本已經是秒級。能借的是觀念（CI 要什麼拿什麼），不是做法（自製版本控制）。
5. **對策要在試點期實測，不是上線後。** 建置時間與內容量成正比，所以「一個專區完整搬進來」就能量出斜率，推估整站。KPI 寫在 6.2。
