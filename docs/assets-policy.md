# 檔案資產政策：附件、圖片與資料檔

> 給誰看：各組 Steward（承辦人）、公關室、資訊室、OASIS、法務與個資窗口、要審上架 PR 的複核者。
> 依據：[ARCHITECTURE.md](../ARCHITECTURE.md) §16；治理規則見 [governance-model.md](governance-model.md) 規則 22–24，操作步驟見 [guide-staff.md](guide-staff.md) 第 2 節；無障礙部分參照《無障礙網站建置規範》與《身心障礙者權益保障法》對政府網站的要求，授權見 governance-model 第 4 節。
> 性質：**檔案放哪裡、叫什麼、建置時檢查什麼，是原型已經實作的規則；病毒掃描、保存年限、真刪流程等是正式站的政策建議，標「待確認」者須由資訊室、法務與檔案管理單位定案。**

## 一句話

**每一個檔案都要在內容裡「宣告」過：放在 `content/assets/{內容 id}/`，在內容的 `assets` 欄位寫明種類、說明與雜湊值。沒宣告的檔不會上線，宣告了卻缺檔、雜湊不符、沒有替代文字、沒有可及性版本，建置會失敗或開待辦。**

## 1. 檔案放哪裡

| 項目 | 規則 |
| --- | --- |
| 原始檔位置（repo） | `content/assets/{內容 id}/{檔名}`，例：`content/assets/news.2026-09-18-flu-antiviral-extended/press-release.pdf` |
| 公開網址 | `/files/{內容 id}/{檔名}`（站台有 basePath 時自動加在前面），例：`/files/news.2026-09-18-flu-antiviral-extended/press-release.pdf` |
| 語言 | **不帶語言前綴，七語共用同一個檔案。** `/vi/news/…` 的頁面引用的也是同一個 `/files/…`。需要不同語言的檔案（例如越南文版海報），就是另一個檔、另一筆宣告，檔名帶語言碼（`poster-vi.pdf`） |
| 一筆內容的檔案數 | 最多 30 個 |
| 誰擁有 | 檔案屬於**一筆**內容（路徑裡的 id）。兩筆內容要用同一個檔時，各放一份並各自宣告，不要跨目錄引用，這樣任何一筆內容下架或改版都不會牽動另一筆 |

`content/assets/` 底下的資料夾名稱必須是存在的內容 id；資料夾沒有對應內容會建置失敗（內容改名或刪除時，資料夾要一起搬移或刪除）。**只有狀態為 `published` 或 `archived` 的內容，其宣告的檔案才會複製到站台**；`draft`、`review` 的檔案不公開。

## 2. 命名規則與自動正規化

- 檔名只能用**小寫英文、數字、連字號 `-`、底線 `_` 與點 `.`**，以英數字開頭並有副檔名。不可有空白、中文、全形符號、大寫（建置會擋下，並給出建議檔名）。檔案直接放在 `content/assets/{id}/` 下，**不支援子資料夾**。
- 檔名要能讓人一眼看出內容與版次：`{主題}-{版次或日期}.{副檔名}`，例：`mmr-recommendation-114-04-16.pdf`、`ili-weekly-chart-2026w39.png`、`dengue-cases-2026.csv`。
- 不要用 `final`、`最終版`、`new`、`copy`、`v2-改` 這類無法排序的詞；版次寫進檔名（見第 8 節）。
- **自動正規化**：後台附件面板收到檔案時會自動轉換（也可在該列手動改檔名，內文引用會跟著改）——大寫轉小寫、空白轉連字號、移除不合法字元，並提示改了什麼。**中文檔名無法自動轉成有意義的英文**，面板會要求你自己輸入檔名（例如「新聞稿.pdf」→ 改為 `press-release.pdf`）。直接把檔案放進 repo 的人沒有這一步，建置會擋。
- 副檔名必須與實際內容一致（`.pdf` 真的是 PDF）；建置會核對 `mime` 與副檔名。

## 3. 允許的格式與大小

| 種類 | 副檔名 | 上限 | 備註 |
| --- | --- | --- | --- |
| PDF 與文件類 | `pdf` `docx` `odt` `md` `ics` | 20 MB | PDF 必須有文字層，見第 4 節；`.md`、`.odt` 是首選的機讀與開放格式 |
| 圖片 | `png` `jpg` `jpeg` `webp` `svg` | 2 MB | 必須有替代文字（alt），見第 5 節；SVG 不得含 `<script>`、`on*=` 事件屬性、`javascript:` 連結與 `<!ENTITY>` 宣告（建置掃描） |
| 資料檔 | `csv` `json` `xlsx` | 50 MB | 資料檔要同時登錄資料目錄，見第 6 節 |

- 一筆內容最多 30 個檔。**限制值定義在 `site.config.mjs` 的 `assets`**，要調整由資訊室與 OASIS 討論後改設定，不是各單位自己放寬。
- 上限分三組：PDF 與文件類（`pdf` `docx` `odt` `md` `ics`）一組、圖片一組、資料檔一組；各組上限定義在 `site.config.mjs` 的 `assets.maxBytes`（`pdf`／`image`／`data`）。
- 建置也會**核對檔案內容與副檔名**（把 `.exe` 改名成 `.pdf` 會被擋）、`.json` 資料檔必須是可解析的 JSON。
- 超過上限的檔：圖片先縮圖與壓縮（網頁用不到 4000 像素的原圖）；PDF 先用「另存為最佳化 PDF」；真的超過的大型資料檔，改放資料目錄的外部連結（CKAN 或開放資料平臺），內容裡只放 `dataset` 的連結。
- 不允許的格式：可執行檔、壓縮檔（zip、rar）、巨集文件（doc、xls、docm）、影片與音訊檔（影音走 YouTube 與 `media` 型別，見 [guide-staff.md](guide-staff.md) 第 8 節）、含密碼保護的檔案。

## 4. PDF 的可及性

PDF 是政府網站最常見的無障礙缺口。規則是：**PDF 只能是「附件」，而不是唯一的資訊來源；資訊本身要在網頁或機讀版裡。**

| 檢查 | 要求 | 怎麼做 |
| --- | --- | --- |
| **文字層** | PDF 內的文字可選取、可複製、可被螢幕閱讀器朗讀 | 用 Word／LibreOffice 直接「匯出為 PDF」（不要列印成 PDF、不要拍照轉 PDF）。開啟 PDF，用游標拖選一段文字，能選取代表有文字層 |
| **標籤（Tagged PDF）** | 標題、段落、清單、表格有結構標籤；閱讀順序正確 | 匯出時勾選「建立標籤的 PDF／加入文件結構標籤」；標題一律用樣式（標題 1、標題 2），不要只放大字體 |
| **圖片替代文字** | PDF 內重要圖表有替代文字 | 在 Word 圖片上設定替代文字後再匯出 |
| **文件屬性** | 標題、語言已設定 | 匯出時填文件標題；語言設為繁體中文 |
| **機讀替代版** | 無法做到完整標籤的 PDF，另附 `.md` 或 `.docx`／`.odt` | 內容欄位 `accessibleAlt` 指向該檔；`.md` 為首選（也是 AI 唯一能引用的版本） |

**宣告方式**：附件的 `machineReadable` 欄位誠實填：PDF 有文字層且為標籤 PDF，填 `true`；否則填 `false`，並用 `accessibleAlt` 指向同一內容的 `.md`（或 `.docx`）。PDF 的 `machineReadable` 不是 `true`（填 `false` 或沒填）且沒有 `accessibleAlt`，系統開待辦 `attachment-no-accessible-version`（中優先，規則 24）。`machineReadable` 是承辦人的聲明。建置時只做一道**簡易偵測**：宣告 `machineReadable: true` 卻在 PDF 裡找不到文字繪製內容時，印出**警告**（不擋建置）；它看不出標籤是否正確、閱讀順序對不對，也可能漏判某些加密或特殊編碼的 PDF，所以自己要真的檢查，複核者也會抽查。

### 掃描檔怎麼辦

掃描成圖片的 PDF（沒有文字層）**不是**可及文件：

1. 優先找回原始檔（Word、公文系統的電子檔），重新匯出 PDF。
2. 找不到原始檔：用 OCR 軟體做成可搜尋 PDF，**逐頁校對**（OCR 對表格、手寫、印章與舊字體常出錯）。
3. 校對完的文字另存成 `.md` 或 `.docx`，掛為 `accessibleAlt`，並在附件 `label` 註明「掃描檔，另附文字版」。
4. 掃描檔本身可以保留當作「原件影像」，但 `machineReadable` 填 `false`。
5. 手寫、印章、簽名等無法文字化的部分，在文字版用括號說明（「〔核章〕」），不要省略。

## 5. 圖片：替代文字、來源與授權

### 替代文字（alt）

- 所有 `kind: image` 的檔案**必須有 `alt`**（≤ 150 字）。沒有 alt 建置失敗，不是警告。Markdown 內文 `![替代文字](/files/…)` 的文字與 `assets.alt` 擇一非空即可；建置時以 `assets.alt` 補進 `<img alt>`。
- alt 寫「這張圖要傳達什麼」，不是「圖片」「截圖」「image.png」。圖表寫出結論與關鍵數字：「近八週類流感門診就診比率由 1.2% 上升至 2.9%，第 38 週起明顯上升」。
- 純裝飾的圖不要放進內文；放進內文就表示它有資訊。
- 圖中有文字（海報、資訊圖表）時，文字要在 alt 或緊鄰的內文中完整出現，不要只放圖。

### 來源與授權

| 素材 | `license` | `source` |
| --- | --- | --- |
| **本署自製**（本署人員拍攝、繪製、製作的照片與圖表） | 必填，填 `OGDL-1.0` | 可省略；寫製作單位更好 |
| **外購、CC 或第三方素材**（圖庫、他機關、媒體、國際組織） | 必填，寫原授權（如 `CC-BY-4.0`、`CC0-1.0`）；無法適用許可清單者，在內容的 `licenseNote` 寫明限制 | **必填**：原作者、出處網址、取得日期，以及要求的標示文字 |

- 授權許可清單同 governance-model 第 4 節：`OGDL-1.0`、`CC0-1.0`、`CC-BY-4.0`。清單外的素材先問 OASIS，由 OASIS 確認是否可進 API。
- **沒有授權證明的圖不要放。** 從網路搜尋來的圖、媒體報導的圖、廠商提供但未簽授權的圖，一律不得上架。
- 圖片 `license` 缺漏是建置閘門（規則 23），建置失敗；`license` 不是 `OGDL-1.0` 的素材（即非本署自製）缺 `source` ⇒ 待辦 `image-license-missing`。
- 人物照片：必須有當事人書面同意；兒童與病患影像原則上不使用。拍攝到的車牌、病歷、螢幕上的個資要先遮蓋。

## 6. 資料檔（CSV、JSON、XLSX）

- 內容 `assets` 裡以 `kind: data` 宣告，`label` 必填，例：「2026 年登革熱境外移入病例數（CSV）」。
- **資料檔必須同時登錄資料目錄**：建立（或更新）對應的 `dataset` 內容（`content/datasets/{id}.json`），`canonicalUrl` 指向正本位置——本站檔案的 `/files/…` 網址，或 CKAN 上的網址（**正本只能有一個**）；填 `updateFrequency`、`lastUpdated`、`license`。這樣資料才會出現在 `/admin/catalog/`、開放資料目錄與 `/v1/` 的資料集清單，並受更新逾期與授權檢查。
- 若資料的正本在 CKAN（政府資料開放平臺），本站不必再放一份檔案，只在 `dataset` 填 `canonicalUrl` 即可，避免兩份資料不一致。
- 檔案要能被機器讀：CSV 用 UTF-8（建議帶 BOM 以利 Excel）、第一列欄位名、一列一筆、日期用 `YYYY-MM-DD`；不要合併儲存格、不要在資料列之間穿插說明文字。欄位意義另寫在 `dataset` 的說明或附上 `.md` 資料字典。
- 資料檔**不得含個人資料**（見第 10 節）；統計小於 3 例的格子，依機關去識別化規定處理（待確認）。

## 7. 引用：附件列表、內文圖片與既有欄位

- `kind: attachment`：列在頁面的附件區（news 的 `attachments[]`、document 的 PDF、publication 的 `pdfUrl`、service 的 `forms[]` 等既有欄位仍可用）。凡是網址以 `/files/{id}/` 開頭的，**必須在 `assets` 宣告**；外部網址（`https://…`）照舊走外部連結檢查，不是 assets。
- `kind: image`：只用於內文，以 Markdown `![alt](/files/{id}/檔名)` 引用。每個內文裡的 `/files/` 引用都必須有宣告，且 kind 為 image。
- 網頁渲染時，內文圖片會自動加上 `loading="lazy"` 與 basePath；有 `width`／`height` 時一併輸出，避免版面跳動。

## 8. 版本與保存

- **新版是新檔，舊版保留。** 文件的新版 PDF 放在**新版內容**的 `content/assets/{新版 id}/`；舊版內容與它的檔案原樣留在原地，由文件版本鏈（`supersedes`）處理失效標示。不要在原檔上覆蓋換內容——否則舊網址、歷史引用與雜湊都對不上。
- 檔名帶版次：`mmr-recommendation-114-04-16.pdf`；宣告時文件型附件可填 `version`（例：`114.04.16`）與 `effectiveAt`。
- 同一筆內容內只有**勘誤**（錯字、遺漏）才可以換檔：換檔後必須同步更新 `sha256`、`bytes`（用 `--fix-assets`），並在內容的更新紀錄或 `reviewedAt` 留下紀錄。實質內容改變一律走新版。
- Git 歷史就是保存：檔案隨 repo 一起備份。`/files/` 不處理 301（`redirects.json` 不處理檔案）：舊站的 `/File/Get/{id}` 一律轉到**新文件頁**，不是轉到 PDF，見 [migration-playbook.md](migration-playbook.md) 第 2.8 節。
- 檔案體積會讓 repo 變大。單檔 20 MB 的 PDF 放幾十份就是 GB 等級；長期做法（Git LFS 或物件儲存＋CDN）待資訊室評估。

## 9. 刪除與下架

**原則：不刪檔，只下架。**

| 情況 | 做法 |
| --- | --- |
| 內容過期、不再適用 | 把內容 `status` 改 `archived`。頁面保留（供查閱與引用），退出索引與白名單；**內容宣告的檔案仍可存取**，網址不變 |
| 文件被新版取代 | 照版本鏈；舊版與它的 PDF 仍可存取，頁首紅色警示指向現行版 |
| 只有某個附件不該再提供 | 從內容的 `assets` 與 `attachments[]` 拿掉該筆宣告；檔案留在 repo 但**不再複製到公開站台**（只複製有宣告的檔）。注意同時要處理孤兒檔：宣告拿掉但檔還在 `content/assets/{id}/` 會被報為孤兒（`asset-orphan`），請一併 `git rm` 或確認要保留 |
| **真的要刪**（含個資、誤上傳機密、侵權、法院或主管機關要求） | 見下 |

### 真要刪的理由與流程

只有下列理由才可以從公開站台與 repo 移除檔案：（1）含個人資料或機密資訊；（2）侵害第三方著作權或其他權利；（3）法令、法院或主管機關要求；（4）依檔案管理規定屆期銷毀（待確認）。

1. 承辦人向 OASIS 與資訊室提出，說明檔案路徑、理由、是否已被外部引用。
2. 立即處置：內容 `status` 改 `archived`，或移除該檔宣告，緊急 PR（可免複核，事後補審）合併，公開站台先不再提供。
3. 若含個資或機密：**Git 歷史裡仍有該檔**，要請資訊室依事故流程清除歷史（`git filter-repo`／重寫歷史並強制更新、通知所有複本持有者、清 CDN 快取），並依個資事故通報流程通報。這一步不是刪檔 commit 能做到的。
4. 原檔位置的網址改回 410（已移除），並在內容或移轉清單中記錄「於何日因何故移除」，不留原檔內容。
5. 事後檢討為什麼通過了複核，補強上架前檢查（第 10 節、第 12 節檢查清單）。

## 10. 病毒掃描與個資

> 以下是**正式站**的政策建議。原型的建置檢查只驗證存在、雜湊、大小、格式與 SVG 腳本，**不做病毒掃描與個資偵測**；因此兩者靠流程把關（待確認：由資訊室定案工具與日誌格式）。

- **病毒掃描**：檔案進 repo 的 PR 在合併前，CI 或資訊室的閘道必須掃描（例如機關核定的防毒引擎、ClamAV），掃描**通過才可合併**；掃描日誌（檔名、sha256、掃描時間、引擎與病毒碼版本、結果）保存於資訊室，保存期限比照資安稽核規定。承辦人電腦上的檔案上傳前也要自己先掃一次。
- **含個資的檔不得上架**：身分證字號、電話、電子郵件、地址、病歷號、出生日期搭配姓名、病患或兒童影像、疫調個案資料。PDF 要特別注意——**塗黑不等於刪除**（黑色方塊下的文字仍在文字層裡）；Word 轉 PDF 前先「檢查文件」移除作者、修訂紀錄、註解與隱藏文字；圖片的 EXIF（拍攝位置、裝置）要移除；XLSX 要檢查隱藏的工作表與欄位。
- **檔案中繼資料**：PDF 與 Office 檔會帶作者、單位、電腦名稱、路徑。匯出時選「移除個人資訊」。
- 甄選結果、招募報名等有個資風險的內容，另依 [careers-privacy.md](careers-privacy.md)：報名者的附件**絕不**進 repo。
- 資料檔（第 6 節）要有去識別化確認；小樣本交叉表可能辨識個人。
- 發現已上架的檔含個資 ⇒ 立刻走第 9 節「真要刪」流程，不要等下次審閱。

## 11. 與 `/pending/` 佔位頁的關係（過渡期）

舊站遷移時，還沒有電子檔或還沒做好可及性處理的附件，內容裡的連結不放失效網址，而是連到 `/pending/?ref=<內容 id>&doc=<文件名稱>`（見 [plan-supplement.md](plan-supplement.md) 第 3 項）。assets 管線上線後：

- 取得檔案、確認可及性後，把 `/pending/?…` 連結換成 `/files/{id}/…`，並在 `assets` 宣告；換掉一筆，`/pending/` 的引用清單就少一筆。
- 還拿不到檔案的，繼續用 `/pending/`；它是**誠實的暫時狀態**，不要為了讓連結「看起來是真的」而放一個空檔或假檔。
- `/pending/` 不是假網址的替代品，也不是長久做法：上線前它的引用清單應清零或逐筆有理由（待辦與 `migration-pending` 清單整合）。

## 12. 同事檢查清單（上架前逐項打勾）

**檔案本身**
- [ ] 檔名全是小寫英數、連字號、底線、點；沒有空白與中文；有版次或日期
- [ ] 副檔名在允許清單；單檔大小在上限內；沒有放不需要的檔
- [ ] 已用機關核定防毒軟體掃描，無異常
- [ ] 檔案內沒有個資、機密、作者與路徑等中繼資料；PDF 沒有「塗黑但文字還在」

**PDF**
- [ ] 能用游標選取文字（有文字層），不是掃描圖片
- [ ] 標題用樣式、閱讀順序正確；已設定標題與語言
- [ ] 若無法做到標籤 PDF：已附 `.md`／`.docx` 並填 `accessibleAlt`；`machineReadable` 誠實填寫

**圖片**
- [ ] 每張內文圖都有 alt，寫的是「傳達什麼」而不是「圖片」
- [ ] 每張圖都有 `license`；非本署素材有 `source`，且確有授權
- [ ] 圖中有文字時，文字已寫入 alt 或內文

**宣告與引用**
- [ ] 每個檔都在內容的 `assets` 宣告（`kind`、`label`、必要的 `alt`、`mime`、`bytes`、`sha256`）
- [ ] 內文的 `/files/…` 引用都已宣告；`content/assets/{id}/` 底下沒有多餘（孤兒）的檔
- [ ] 資料檔已同步登錄資料目錄（`dataset`）
- [ ] 用 `npm run build -- --fix-assets` 補寫 `bytes`／`sha256`／`mime`／寬高後，再 `npm run build` 全綠
- [ ] 預覽頁面：附件連結打得開、圖片顯示、alt 正確

**過渡期**
- [ ] 取代了 `/pending/` 連結的，已一併更新移轉清單
