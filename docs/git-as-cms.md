# 新官網的更新機制：Git＋CI，不是傳統後台上架系統

> 給誰看：資訊室（要維運的人）、各單位主管與承辦人（想知道「以後怎麼上架」的人）、要核定架構的主管。
> 一句話：**新官網沒有另一套「後台內容上架系統」。內容是 `content/` 底下的 JSON 檔，Git 是唯一的正本，每一次改動都是一個 Pull Request，CI 自動檢查、依車道決定要不要人審、合併就是發布。承辦人仍用網頁表單填寫，不必學 Git；開分支、開 PR、跑檢查、合併、部署都是系統的事。**
> 相關文件：為什麼這樣決定見 [architecture-decisions.md](architecture-decisions.md) 第 1 節；三條發布車道見 [publishing-lanes.md](publishing-lanes.md)；承辦人操作見 [guide-staff.md](guide-staff.md) 第 0、2 節；維運與部署見 [deploy.md](deploy.md)。

## 0. 先回答最常被問的三個問題

1. **「所以不會有一個後台讓我登入、填表、按上架？」** 會有表單（原型是 `/admin/publish/`），填法跟舊後台一樣（填欄位、貼內文、拖附件、按送出，一樣是 6 步，見 [publishing-lanes.md](publishing-lanes.md) 第 11 節）。差別在按下送出之後：舊後台直接寫進資料庫並對外顯示；新流程由系統代你開一個 PR，CI 檢查過、車道規則允許，才合併並重新建置網站。
2. **「那資訊室要維運什麼？」** 不再維運 CMS 應用程式、資料庫與其登入系統；改為維運一個 Git 代管平台（GitHub 或自建 GitLab／Gitea）、CI 執行器、靜態網站主機，以及一個很小的「代承辦人送出」服務（見第 4 節）。
3. **「為什麼要這樣做？」** 機關最怕「誰、什麼時候、改了什麼、改之前是什麼」說不清楚，以及錯誤內容上線後才被發現。Git 把前者變成免費內建；CI 把後者變成機器強制。詳細比較見第 2 節。

## 1. 兩種機制在做什麼

```
傳統後台上架系統
  承辦人登入 CMS → 填表單 → 按「上架」 → 寫進資料庫 → 網站即時從資料庫讀出顯示
  （審核若有，是 CMS 內的狀態欄位；檢查靠人眼；歷史版本看 CMS 有沒有做）

Git＋CI（本原型）
  承辦人開表單 → 填表單 → 按「送出」 → 系統開分支、寫 JSON、開 PR
    → CI 自動檢查（schema、參照、治理規則、評估集、附件、連結）
    → 依車道：快車道 CI 綠燈自動合併；一般車道再等 1 位審核人；緊急發布 10 分鐘內合併
    → 合併觸發建置 → 靜態網頁部署到主機
  （每一步都留在 Git 歷史；預覽網址讓審核人看到的就是上線後的樣子）
```

## 2. 比較表

| 面向 | 傳統後台上架系統（CMS） | Git＋CI（本原型的做法） | 對機關的意義 |
| --- | --- | --- | --- |
| **內容正本在哪** | CMS 的資料庫 | Git 儲存庫的 `content/*.json` | 正本是純文字檔，不綁廠商；任何時間點都能完整取出 |
| **誰按「上線」** | 承辦人（或代上架的資訊室）按下即生效 | 承辦人按「送出」只是開 PR；**合併**才上線，由車道規則決定是機器還是人來合併 | 把「寫好」與「對外」分開，低風險自動、高風險有人把關 |
| **審核** | CMS 內的狀態欄位（草稿／待審／已發布），有沒有、嚴不嚴看系統怎麼設 | PR 審核：一般車道 1 位核准（SLA 2 個工作天），快車道 0 位但上線後 24 小時內複核，緊急發布事後補審 | 審核依「錯了的代價」分級，不是一刀切 |
| **自動檢查** | 多半只檢查必填欄位 | CI 四道關卡：schema 與跨檔參照、治理規則（逾期、版本鏈、白名單、反向稽核）、評估集版本題、附件與連結（存在、雜湊、alt、授權、壞連結） | 「新聞稿寫舊版建議」這類錯誤在合併前就被擋下，不用靠人眼 |
| **預覽** | 常與正式環境不同，或沒有 | 每個 PR 自動部署一個預覽網址（`/preview/pr-N/`），與正式站同一套程式產生 | 審核人看到的就是上線後的樣子 |
| **改動紀錄與追溯** | 看 CMS 有沒有做版本功能；通常只有「最後修改人／時間」 | 每次改動都有作者、時間、逐欄差異、審核人、討論；永久保存 | 對外更正、稽核、媒體質疑時說得清楚 |
| **回復（rollback）** | 看 CMS；多半要資訊室進資料庫 | 任何一次合併都能一鍵 revert 再合併，數分鐘內回到前一版 | 錯誤內容的「收回」有標準動作 |
| **權限** | CMS 帳號角色（通常全站或單位層級） | Git 平台帳號＋分支保護＋`CODEOWNERS`（可到**目錄層級**：`content/governance/` 歸 OASIS、`content/situation/` 歸疫情中心） | 跨單位誤改在合併前被擋 |
| **預定發布** | 看 CMS 是否支援排程；常要人到點去按 | 內容帶 `publishAt`，建置時到點才渲染；原型每 2 小時重建，延遲最多 2 小時（正式環境可改為到點觸發） | 不用半夜守著按鈕 |
| **緊急發布** | 通常沒有明確快速通道，大家不確定能不能跳過流程 | 標 `urgent` 走緊急車道：CI 通過 10 分鐘內合併並通知複核 | 緊急時規則明確，事後有紀錄 |
| **AI 與搜尋引用** | AI 讀資料庫要另外做 API 或匯出 | 內容就是結構化 JSON，AI 問答、站內搜尋、治理儀表板都直接讀同一份檔 | 一份正本，不會有 CMS 與 AI 索引不同步的問題 |
| **多語** | 看 CMS | 翻譯是同一筆內容的語言欄位；規則 `translationsNeverBlock`：翻譯沒審完不卡中文正本 | 不會因為英文版沒好而拖住中文上線 |
| **備份與災難復原** | 資料庫備份、CMS 應用程式備份、還原演練 | `git clone` 就是一份完整備份（含全部歷史）；任何一台有 Node 的機器都能重建整站 | 備援成本極低，演練容易 |
| **資安攻擊面** | CMS 登入頁、外掛、資料庫、檔案上傳功能，都是常見攻擊目標 | 對外只有靜態檔案（沒有登入頁、沒有資料庫、沒有動態執行）；可寫入的面只在 Git 平台與「代送出」服務，可用機關 SSO 與雙因子保護 | 大幅減少需要巡檢、修補的元件 |
| **效能與可用性** | 每次瀏覽都查資料庫；流量尖峰（疫情記者會）要擔心 | 靜態檔案，CDN 直接送出；流量尖峰只是多傳檔案 | 疫情高峰時網站不會因為後端慢而掛 |
| **廠商綁定** | 內容格式、外掛、範本都綁 CMS 產品 | Git、JSON、Markdown、Node 都是開放標準；換代管平台只是換遠端網址 | 換約、換廠商不必「資料移轉」 |
| **承辦人要學什麼** | CMS 操作 | 表單操作（一樣）；**不必學 Git**。另加兩個觀念：送出 ≠ 上線（看車道），以及 PR 留言是哪裡出錯的說明 | 操作門檻相同，觀念多兩個 |
| **資訊室要學什麼** | CMS 管理、資料庫、作業系統修補 | Git 平台管理、CI 工作流程（YAML）、Node 建置腳本、靜態主機／CDN；不需要資料庫 | 技能轉向 DevOps，但維運項目變少 |
| **不適合的情境** | — | 大量影音與大型檔案（不該進 Git，走物件儲存）；每日數百筆以上互動式資料（表單回覆、留言）；需要**秒級**即時更新的看板 | 這些仍由專門服務處理，網站只連結或嵌入 |

## 3. 資訊室在意的細節

### 3.1 「合併就是發布」的安全網

- `main` 分支受保護：只能透過 PR 合併，CI 綠燈是必要條件；**核准人數由車道決定**（一般 1 位，快／緊急 0 位），不要設原生的「需 N 位核准」（見 [deploy.md](deploy.md) 第 9 節）。
- 一個 PR 混多種型別時取**最嚴格**車道；程式、設定、文件的改動一律一般車道。
- 快車道自動合併的內容會自動產生「上線後複核」待辦（24 小時內），不是上線就沒人看。
- 任何合併都可 revert；revert 本身也是 PR，同樣有紀錄。

### 3.2 現在實際在跑的工作流程（GitHub Actions）

| 工作流程 | 觸發 | 做什麼 |
| --- | --- | --- |
| `content-pr.yml` | PR 開啟／更新 | 判定車道、跑完整檢查、部署預覽網址、在 PR 留言；快車道與緊急發布綠燈後自動合併 |
| `preview-cleanup.yml` | 每日 | 清掉已關閉 PR 的預覽網址 |
| `lane-sla.yml` | 每小時 | PR 超過車道 SLA 未合併 ⇒ 留言＋ `sla:breach` 標籤 |
| `pages.yml` | 合併到 `main`、每 2 小時 | 建置整站並部署（每 2 小時一次是為了讓 `publishAt` 到點的內容自動出現） |

說明見 [publishing-lanes.md](publishing-lanes.md) 附錄 A；實測結果見附錄 B。

### 3.3 正式環境要補的一塊：代承辦人送出

原型的限制：`/admin/publish/` 的「送出」是**展示**，承辦人實際上是下載一個 ZIP 上架包，再由能用 Git 的人放進 `content/` 開 PR。正式環境要補一個很小的後端服務：

- 承辦人以機關 SSO 登入 → 表單產生 JSON 與附件 → 服務用**服務帳號**在 Git 平台開分支、提交、開 PR，提交訊息帶承辦人的姓名與單位（Git 的 author 欄位），之後的流程不變。
- 它只做「把表單變成 PR」這一件事，不存內容、不做審核、不產生網頁，所以體積小、攻擊面小；壞掉時承辦人仍可退回下載 ZIP 交給資訊室代開 PR，網站本身不受影響。
- 預覽網址若含未發布內容，應限制為機關網段或登入後才能看（GitHub Pages 原型是公開的，正式環境視主機能力加存取控制）。

### 3.4 資訊室要維運的清單（對照舊有項目）

| 不再需要 | 新增或改為 |
| --- | --- |
| CMS 應用程式與其升級、外掛 | Git 代管平台（GitHub／GitLab／Gitea，可用機關現有的） |
| 內容資料庫（備份、調校、修補） | CI 執行器（雲端代管或自建 runner） |
| 動態網站主機（應用伺服器） | 靜態網站主機或 CDN（Pages、S3＋CloudFront、機關現有 web server 放靜態檔都可） |
| CMS 帳號系統 | Git 平台帳號接 SSO；`CODEOWNERS` 維護 |
| — | 「代承辦人送出」服務（3.3），一個小型後端 |
| — | 大檔案的物件儲存（影片、原始檔不進 Git） |

### 3.5 權限模型

- **誰能寫**：所有有 Git 平台帳號的承辦人都能開 PR（透過表單間接開）；**沒有人**能直接寫 `main`。
- **誰能核准**：由 `CODEOWNERS` 依目錄指定（治理設定歸 OASIS、態勢歸疫情中心、其餘依車道的審核人名單）。
- **誰能緊急處置**：緊急暫停 AI 的 PR 可由資訊室與 OASIS 值班人直接合併，事後補審。
- 全部動作都綁個人帳號，沒有共用帳號。

## 4. 風險與對策

| 風險 | 對策 |
| --- | --- |
| 承辦人覺得「送出了怎麼還沒上線」 | 表單送出後立刻顯示車道與預計時間（快車道約 3 分鐘、一般 2 個工作天內）、PR 連結與預覽網址；上線時通知 |
| CI 誤判擋住正確內容 | PR 留言寫清楚哪一條規則擋、怎麼修；規則本身走 PR 修改並有測試；緊急時由資訊室／OASIS 以緊急車道合併 |
| 同一檔案多人同時改造成衝突 | 一筆內容一個檔，衝突只在同一筆被兩人同時改時發生；表單送出前先拉最新版；衝突由資訊室協助解決 |
| Git 平台或 CI 服務中斷 | 網站本身是靜態檔，照常服務；只是暫時不能更新。緊急內容可由資訊室手動建置部署（`npm run build`） |
| 大檔案把儲存庫撐大 | 影片與大型原始檔放物件儲存，Git 只放連結與雜湊（[assets-policy.md](assets-policy.md)） |
| 資訊室技能轉換 | 依賴極少（三個 npm 套件）；建置、檢查、部署都是一條指令；本文件與 [deploy.md](deploy.md) 為交接文件 |
| 需要秒級即時的內容 | 不適合此機制：疫情看板若要秒級更新，由資料服務直接提供，網站嵌入 |

## 5. 什麼時候該重新考慮

- 同時編輯者多到 PR 衝突頻繁（例如每天數十人改同一批檔）。
- 需要分鐘級以下的即時發布成為常態，而不是例外。
- 承辦人大量回報表單無法表達他們要的版面（代表內容模型要擴充，不一定是機制問題）。

即使如此，建議的調整是在 Git 前面加一層有權限控管的編輯器（例如接 Git 的 headless CMS），**資料仍以 Git 為正本**，而不是回到「資料庫就是正本、按下去就上線」。
