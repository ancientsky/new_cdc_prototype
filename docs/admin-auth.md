# 後台維護登入怎麼設計：三種做法比較與建議（第十八輪）

> 給資訊室、OASIS 與各單位主管看。一句話：**不要再做一套帳號密碼。後台登入用機關既有的單一簽入（SSO），角色由人事／AD 群組帶入，每個動作綁個人帳號並留稽核。** 原型（`/admin/login/`）用「選一個示範帳號」模擬 SSO 回傳的身分，其餘流程（角色規則、單位視角、拒絕存取、稽核）都照正式設計跑。

> **更新（2026-10-10 第三十輪）：登入改由「寫入閘道」接，三條路徑都已實作。** 正式環境放在機關自架 GitLab，同事在後台按「儲存草稿／送審／核准上線」，由閘道（`scripts/lib/gateway/`）確認身分與 AD 群組後，用服務帳號寫進 GitLab。**同事不需要 GitLab 帳號**，所以下面第 1 節的做法 C（直接用 Git 平台帳號）只留給資訊室與想查紀錄的人。閘道只需要知道「是誰、在哪些 AD 群組」，登入方式三選一：
>
> | 路徑 | 怎麼接 | 設定 |
> | --- | --- | --- |
> | A. Keycloak＋LDAP 聯合 AD（可加 Kerberos） | 閘道驗 Keycloak 簽的 JWT（`oidc` 轉接器） | [deploy.md §14.3 路徑 A](deploy.md) |
> | B. IIS 反向代理＋Windows 驗證 | 閘道只信設定的代理 IP 送來的 `X-Remote-User`／`X-Remote-Groups`（`header` 轉接器） | [deploy.md §14.3 路徑 B](deploy.md) |
> | C. Google Workspace | 授權碼＋PKCE；`hd`、`email_verified`、email 網域都要是機關；群組來自 Google 群組（GCDS 同步 AD）或對照檔（`google` 轉接器） | [deploy.md §14.3 路徑 C](deploy.md) |
>
> 建議試點用 C（已在用、有 2 步驟驗證），正式環境依資安政策決定 C 或 A；比較表與理由見 [architecture-decisions.md §23](architecture-decisions.md)。群組命名（第 2 節的 `CDC-WEB-<unitId>-<role>`）與角色表（第 3 節）不變，閘道把角色歸成同事看得懂的三種：編輯、審核、管理。第 4 節表格「沒做」那一列的「真的 OIDC 流程、後端 403、群組同步」，對**寫入動作**已由閘道做到（閘道 API 沒身分回 401、角色不符回 403）；後台靜態頁本身仍要由反向代理擋在登入之後（第 5 節第 3 點）。第 5 節第 4 點的「代承辦人送出」服務就是寫入閘道。

## 0. 先回答三個問題

1. **「後台要不要登入？」** 要。後台雖然不直接寫資料庫（內容走 Pull Request，見 [git-as-cms.md](git-as-cms.md)），但它會：預覽未發布內容、產生要送出的上架包、按下「暫停 AI」、發布疫情態勢。這些都不該讓任何人匿名做。
2. **「做一套帳號密碼不是最快嗎？」** 最快做、最難養。每多一套密碼就多一個被釣魚、忘記、離職沒停用的地方；資安稽核時也多一套要證明的東西。機關本來就有 AD／SSO，直接接。
3. **「登入之後誰能做什麼？」** 由兩個維度決定：**單位**（只能處理自己單位的內容，除非是跨單位角色）與**角色**（承辦人、複核者、疫情發布、內容總編輯、治理幕僚、平台管理）。對照表在第 3 節，程式裡只有一份（`src/client/admin/auth-rules.js`）。

## 1. 三種做法比較

| 面向 | A. 後台自建帳號密碼 | B. 機關 SSO（OIDC／SAML）＋ MFA ← **建議** | C. 直接用 Git 平台帳號登入（GitHub／GitLab） |
| --- | --- | --- | --- |
| 帳號從哪來 | 後台自己一張表，資訊室手動開 | 人事／AD 現有帳號；到職自動有、離職自動停 | Git 平台帳號（可再接機關 SSO） |
| 密碼與雙因子 | 要自己做密碼政策、重設、鎖定、MFA | IdP 已有，後台不碰密碼 | Git 平台已有 MFA |
| 單位與角色 | 後台自己維護，容易和人事脫節 | 由 AD 群組對照（`CDC-WEB-<單位>-<角色>`），調動時人事改群組即可 | 用 Git 團隊（teams）與 `CODEOWNERS`；對不會 Git 的承辦人太抽象 |
| 離職／調動 | 常漏停用 | 停 AD 就全停 | 停平台帳號；若未接 SSO 仍可能漏 |
| 稽核 | 自己寫 | IdP 有登入日誌；後台再補動作日誌 | 平台有審計日誌 |
| 承辦人感受 | 又一組帳密 | 跟公文系統同一組，常常不用再輸入 | 要先會用 Git 平台 |
| 攻擊面 | 登入頁、密碼庫、重設信 | 後台沒有密碼可偷；只剩 IdP 與 session | 平台本身 |
| 適合 | 沒有 SSO 的小單位 | 任何有 AD／SSO 的機關 | 技術團隊、審核者 |

**建議：B 為主，C 為輔。** 承辦人用機關 SSO 登入後台（身分與角色）；後台把表單變成 PR 時，用一個**服務帳號**在 Git 平台操作，提交訊息帶承辦人姓名與單位（[git-as-cms.md](git-as-cms.md) §3.3）。審核者與資訊室本來就要用 Git 平台，平台帳號也接同一個 SSO，兩邊是同一個人。

**為什麼不是 A：** 原型第二～九輪已經把「不要再養一套系統」當原則（不養 CMS、不養資料庫）；帳號系統正是最該丟掉的那一套。多養一套密碼不會讓網站更安全，只會多一個要巡檢的地方。

## 2. 建議的登入流程（正式環境）

```
承辦人打開 /admin/… ──→ 閘道發現沒有有效 session ──→ 302 到機關 IdP
IdP：帳號密碼 ＋ 第二因子（憑證、App 推播、OTP）
IdP 回傳 id_token（OIDC）：sub（員編）、name、groups（AD 群組）、exp
後台閘道：groups → unit ＋ roles；建立 session（8 小時，閒置 30 分鐘失效）
之後每個請求：閘道先檢查 session 與頁面規則，不允許就不回傳頁面（403），並寫稽核
```

要點：

- **後台頁由閘道保護，不是靠前端藏按鈕。** 靜態後台頁放在需要登入的路徑（反向代理或 Pages 的存取控制），沒登入就拿不到 HTML；前端的角色檢查只是把結果顯示得更友善。
- **群組命名規則**（建議）：`CDC-WEB-<unitId>-<role>`，例如 `CDC-WEB-acute-infectious-editor`、`CDC-WEB-oasis-governance`。一個人可有多個群組（科長通常同時是 editor 與 reviewer）。
- **跨單位視角**只給三種角色：內容總編輯（公關室）、治理幕僚（OASIS）、平台管理（資訊室）。其他人登入後單位是鎖死的，不能切。
- **緊急動作**（暫停 AI、疫情發布）限定角色且**每次都寫稽核含原因**；原型的 AI 開關本來就要填原因，正式環境把這條帶到後端。
- **預覽網址**（PR 預覽）同樣放在閘道後面，否則未審內容外洩（[plan-supplement.md](plan-supplement.md) 第 37 項）。
- **沒有共用帳號、沒有「admin」帳號。** 需要高權限就給該人該角色，事後查得到是誰。

## 3. 角色與頁面對照（程式裡只有一份）

| 角色 | 誰 | 能做 | 跨單位 |
| --- | --- | --- | --- |
| 承辦人 `editor` | 各單位承辦 | 上架、修改、看待辦與審閱到期（自己單位） | 否 |
| 複核者 `reviewer` | 科長／審核人 | 複核區：通過或退回同單位送出的內容 | 否 |
| 疫情發布 `situation-publisher` | 疫情中心 | 疫情發布頁 | 否 |
| 內容總編輯 `chief-editor` | 公關室 | 全部內容、複核區、評估 | 是 |
| 治理幕僚 `governance` | OASIS | 全部，含 AI 開關、評估、疫情發布 | 是 |
| 平台管理 `platform` | 資訊室 | 全部，含 AI 緊急開關與稽核調閱；不發布疫情 | 是 |

頁面規則（`PAGE_RULES`）：複核區 → reviewer／chief-editor／governance；疫情發布 → situation-publisher／governance；AI 開關 → platform／governance；評估 → governance／platform／chief-editor。**沒列的頁任何已登入角色都能進，但只看得到自己單位。** 原則是最小權限：只有會改到全站行為或牽涉治理判斷的頁才限制。

這張表要改，改 `auth-rules.js` 一處，登入頁的「誰能進哪些頁」表、前端閘門、測試（`tests/round18-ui.test.mjs`）都跟著變；正式環境的閘道也應讀同一份設定（匯出成 JSON 即可）。

## 4. 原型做了什麼、沒做什麼

| | 原型（`/admin/login/`） | 正式環境 |
| --- | --- | --- |
| 身分來源 | 八個示範帳號（姓名遮罩）或自訂身分 | 機關 IdP 回傳的 id_token |
| session | `localStorage` 的 `cdc.admin.session`，8 小時／閒置 30 分鐘失效 | 閘道的 HttpOnly cookie，同樣時限 |
| 進頁檢查 | `common.js` 開頭：無效→導到登入頁帶 `?next=`；角色不符→隱藏主內容、顯示拒絕卡、寫稽核 | 閘道回 302／403，前端只顯示結果 |
| 單位視角 | 非跨單位角色的下拉鎖死（`aria-readonly`） | 同，但由後端強制 |
| 稽核 | `cdc.admin.audit`（登入、登出、拒絕、切換視角、失效），登入頁可看，最多 200 筆 | 集中式日誌，使用者不能刪，保存一年以上 |
| 開放式轉址防護 | `?next=` 只接受站內 `/admin/` 路徑 | 同 |
| 沒做 | 真的 OIDC 流程、MFA、後端 403、群組同步 | 要做 |

示範身分的姓名一律遮罩（王○安），和 [careers-privacy.md](careers-privacy.md) 的慣例一致，避免示範資料被誤當真人。

## 5. 資訊室實作清單

1. 向機關 IdP 申請一個 OIDC client（redirect URI 指向後台閘道），要求回傳 `groups` claim。
2. 在 AD 建立 `CDC-WEB-<unit>-<role>` 群組，由人事或各單位主管維護成員；初始名單由 OASIS 依 `content/master/units.json` 與各單位 Steward 名單提供。
3. 後台與 PR 預覽目錄放到閘道後面（反向代理 + OIDC 外掛，或雲端主機的身分驗證功能）；GitHub Pages 公開版只放前台。
4. 「代承辦人送出」服務（[git-as-cms.md](git-as-cms.md) §3.3）讀閘道傳來的身分，PR 的 author 帶承辦人姓名與單位，用服務帳號推送。
5. 稽核日誌集中收（登入、登出、拒絕、暫停 AI、疫情發布、送出 PR），保存一年以上，資訊室與政風室可調閱。
6. 離職流程加一條：停 AD 即停後台，不必另外處理。

## 6. 權責單位可點：為什麼順便做

同一輪把全站每個「權責單位」欄位改成連結（`unitLink`），連到新的單位介紹頁 `/about/units/{slug}/`（簡介、主要業務、該單位在本站維護的內容清單、聯絡）。理由：讀者看到「權責單位：急性傳染病組」時，下一個問題多半是「這個組還管什麼、要找誰」；後台的角色也是以單位為維度，兩邊用同一份 `units.json`。

- 單位頁由主檔自動產生，每個單位一頁（中英文），`.md` 機讀版同時輸出；該單位負責的內容清單是建置時從 `owner`／`hiringUnit` 算出來的，不必人工維護。
- 主檔新欄位：`slug`、`intro`／`introEn`（簡介）、`duties`（主要業務）＋ `dutiesSource`（出處）、`officialUrl`（現行官網介紹頁）＋ `officialUrlNote`。簡介是原型撰寫，標 `introVerified: false`，頁面顯示「尚待該單位確認」；各單位確認後改 `true`（走 PR）。
- **現行官網連結**：Yulun 提供兩個現行官網頁面（2026-10-05）：「組織與職掌」<https://www.cdc.gov.tw/CdcOrganization/Index/cBX61rWwT5TKpS7BbMzKag> 與另一頁單位介紹 <https://www.cdc.gov.tw/Category/Page/b_NCRMZiFLmXGmwIIY334w>。**現行官網沒有各單位獨立網址，所有單位在同一頁**，所以每個單位的 `officialUrl` 都指向「組織與職掌」頁，單位頁與組織圖下方同時列出兩頁（常數 `OFFICIAL_ORG_PAGES`，`units.mjs`）。新站則一個單位一頁，可以直接連結、被搜尋、被 AI 引用；這是新站比舊站好的地方之一。
- **主要業務改用處務規程用語**：`duties` 依《衛生福利部疾病管制署處務規程》的掌理事項整理（開發環境連不到官網與全國法規資料庫，依搜尋摘錄，`dutiesSource` 註明待逐字核對）。這樣比原型自己寫的描述好：用語與法規一致，日後法規修正時有明確的比對依據。
- **順帶修正的主檔錯誤**：「整備應變組」改為官網正式名稱「新興傳染病整備組」（id `unit.preparedness` 不變，所有內容自動跟著改名；內容檔中的文字也一併替換）；預防醫學辦公室的職掌改為實際的「防疫醫師與流行病學人才培訓、旅遊醫學諮詢、特殊傳染病調查與用藥審查」；官網列出的任務編組「AI推動辦公室」就是原型的 OASIS（2026-10-06 Yulun 確認）：主檔沿用 `unit.oasis`，名稱改為「AI推動辦公室」、英文「Office of AI Strategy, Innovation, and Synergy (OASIS)」，第十八輪暫時加的 `unit.ai-office` 已刪除。本文件與後台說明裡的「OASIS」都指這個單位。**為什麼不另開新 id**：所有內容的 `owner`、AI 白名單的 `approvedBy`、測試都已用 `unit.oasis`；改名只動主檔一筆，換 id 會讓幾十個檔案的參照全部要改，又沒有帶來任何資訊。
- **教訓**：主檔的單位名稱與職掌要以官網或法規為準，不要依印象撰寫；原型第一版把一個組名寫錯，所有頁面的權責單位就跟著錯。改名只改主檔一處，因為內容用的是 `unit.*` id，這正是「名稱放主檔、內容只存 id」的好處。
- 非中英語言的頁面，權責單位連到英文版單位頁（`hreflang="en"`）。
